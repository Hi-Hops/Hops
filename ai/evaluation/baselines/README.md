# 정리 전 기준선: 개발용 시나리오 12개 × 1회

AI 서버 정리([#171](https://github.com/Hi-Hops/Hops/issues/171)) 전 구조(`decide → execute → finish`)가 개발용 시나리오 12개에서 어떻게 동작하는지 실제 모델로 한 번씩 재생한 기록이다. 정리 뒤 같은 하네스로 다시 재서 비교하려는 **출발점**이다. 팀이 합의한 품질 기준이 아니며, 소수 표본이므로 일반 성능으로 쓰지 않는다.

**두 번에 나눠 돌렸다. 조건이 완전히 같지는 않다.**

- [첫 실행](2026-11-05-dev-first-run.json): 12개 전체. 이때 하네스의 실행 한도가 Spring 설정과 달랐다(출력 8,000토큰·도구 호출 3·재시도 1, Spring은 12,000·10·2). 실행당 모델 호출 한도 8회는 같다. 9번과 11번은 이후 시나리오 문장을 고쳤으므로 이 파일의 두 항목은 **대체됐다**. 실행 조건 기록(`run`)이 없다.

## 확인된 것

1. **개발용 12개 중 2개가 실행당 호출 한도(8회)를 넘겨 실패했다**(3, 10번). 둘 다 같은 역할(Inquiry)이 반복 호출됐다. 원인은 조사하지 않았다. 정리 작업(#176, #181)에서 같은 시나리오로 비교한다.
2. **Knowledge 검색을 거친 것은 사용법 문의 1·2·10번과 검색 오류를 주입한 12번뿐이다.** 증상·권한 신청·개선 요청(4~9번)과 증상으로 바꾼 11번은 검색 없이 티켓으로 갔다(3번은 시스템 미확인으로 거기까지 가지 못했다). 목표 구조([AI 에이전트 구조](../../../docs/ai/AGENT_ARCHITECTURE.md))는 증상에도 검색과 충분성 판단을 넣는다.
3. **모호한 문장 조각이 확보로 인정된다**(2, 4, 6, 9번). 안전 성질 P6은 원문 인용의 존재만 검사하고 값의 의미는 보지 않는다. 그 결과 필요한 질문이 생략됐다.
4. **정정이 반영되지 않았다**(11번, 한 번의 관찰). 하네스의 Spring 대역이나 병합 규칙의 영향인지는 구분하지 못했다.
5. **안전 성질 위반은 0건이다.** 이는 이 12번의 실행에서 관찰되지 않았다는 뜻이다. 검색 관련 성질(P2~P5)은 1번(FOUND)과 12번(ERROR)에서만 실제로 검사됐고, 나머지는 검색이 없어 검사할 내용이 없었다.

## 이 기록의 한계

- **"안전 성질 위반 0건"은 실행 당시 검사기 기준이다.** 이후 리뷰로 검사기를 고쳤다(P6가 사용자 메시지 인용만 근거로 보고 빈 인용을 거부, 임시 참조를 턴별로 구분, P9 한도 정정). 저장된 보고서에는 원본 실행 기록(trace)이 없어 고친 검사기로 다시 판정하지 않았다. 새 검사기로 재판정하려면 기준선을 다시 돌려야 한다.
- **종료 코드.** 기준선 실행 때의 도구는 실행별 예산 초과(3·10번 `BUDGET_EXCEEDED`)를 실패로 보지 않아 종료 코드 0으로 끝났다. 지금 도구는 0이 아니게 끝낸다.
- **한 번씩만 돌렸다.** 같은 시나리오를 반복하면 결과가 달라질 수 있다. 3·10번 실패가 항상 일어나는지는 모른다.
- **검색은 고정 자료**다. 안내 문장은 우리 문서와 무관하고, 정답의 `relevantEvidence`는 채점하지 못했다. `assessment`(충분성 판정)는 현재 코드에 없어 채점하지 않았다.
- **9번 시나리오는 의도한 상황에 도달하지 못했다.** AI가 `desiredChange`를 묻지 않아 사용자가 모른다고 답할 기회가 없었다. 모름 보존은 5번과 8번에서 확인했다.
- **필수 필드 확보 여부는 사람이 읽고 판단한 것**이다. 자동 채점은 아직 없다.
- 20번(`guide-unresolved`)과 `TEST` 시나리오 8개는 돌리지 않았다. `TEST`는 동결 자료이고, `followUp`의 재생은 멀티턴 작업(#189)에서 지원한다.
- 응답 저장(`store=True`)을 요청하는 어댑터로 돌렸다. 시나리오는 합성 데이터다.

### 검색 힌트(키워드·기능 후보)를 눈으로 본 결과

기록 26건(시나리오 12개의 문제 × 호출). `searchHints`에 모델 원본과 규칙이 정리한 값이 함께 있다.

- **기능 후보**: 17개가 남았고 2개가 버려졌다. 둘 다 규칙이 의도대로 막은 경우다. 7번(`login-loop`) 2턴의 "로그인·SSO"는 문제의 시스템이 전자결재라 다른 시스템의 기능이었고, 11번(`system-correction`) 2턴의 "파일 열람"은 사용자가 시스템을 파일 공유로 정정했지만 문제의 보고 시스템이 전자결재로 남아 있어(위의 기존 미반영) 규칙이 버렸다. 후자는 모델의 추측이 맞아 보이는데도 버려진 사례라서, 정정 반영이 고쳐지면 함께 달라진다.
- **눈에 띄는 약점**(수치로 측정하지는 않음): 시스템 이름("전자결재", "공통", "로그인", "포털", "시스템")이 키워드로 자주 들어간다. 관계 조회는 증상 이름과의 부분 문자열 비교이고 시스템 범위는 따로 좁히므로, 이런 단어는 일치 비율의 분모만 키울 가능성이 있다. "화면", "확인", "개선" 같은 너무 일반적인 단어, 어미가 붙은 "열려요", 구절 "지난 문서"·"찾는 방법"도 보인다.
- **조치**: ②에서는 프롬프트를 더 고치지 않는다. 키워드는 아직 쓰이지 않아 좋고 나쁨을 검색 결과로 확인할 수 없다. 키워드를 실제로 쓰는 ③에서 관계 조회 결과와 함께 보고 프롬프트(예: 시스템 이름 제외)를 조정한다.

### 이 재측정의 한계

- **한 번씩만 돌렸다.** 차이가 모델 변동인지 ② 때문인지 구분하지 못한다. 3번 1턴의 `taskOrScreen` 추출과 10번의 검색 결과 변화가 그 예일 수 있다. 같은 코드의 v5 프롬프트로 대조 실행은 하지 않았다(종결 상태가 같고 안전 성질 위반이 없어 비용을 더 쓸 근거가 약하다고 판단했다).
- **기준선과 코드가 다르다**(위). 동작을 바꾸지 않는 정리가 대부분이지만 그 사실을 이 실행으로 검증한 것은 아니다.
- **행동 성질(B1~B6) 통과율은 판정하지 못한다.** 표의 "같음"은 질문 필드·티켓 수·안내 여부를 읽고 비교한 것이다. 자동 채점이 아니다.
- **실행당 호출 한도 초과 2건(3번·10번)의 원인은 여전히 조사하지 않았다.** ② 이전부터 있던 문제이며 #181의 ④(행동 선택)와 ⑦(호출 한도)에서 다룬다.
- 검색은 고정 자료이고 `assessment`는 아직 없어 채점하지 않았다.

## 다시 재현하려면

```bash
cd ai
OPENAI_API_KEY=... uv run python -m evaluation.pilot --split DEV --max-calls 150 --out /tmp/baseline-dev.json
```

정리 뒤 비교할 때는 모델·프롬프트 버전·지식 자료가 같은지 `run` 항목으로 먼저 확인한다. 모델 호출이 있는 실행은 호출 상한과 비용을 정한 뒤에만 한다.
