# 정리 전 기준선: 개발용 시나리오 12개 × 1회

AI 서버 정리([#171](https://github.com/Hi-Hops/Hops/issues/171)) 전 구조(`decide → execute → finish`)가 개발용 시나리오 12개에서 어떻게 동작하는지 실제 모델로 한 번씩 재생한 기록이다. 정리 뒤 같은 하네스로 다시 재서 비교하려는 **출발점**이다. 팀이 합의한 품질 기준이 아니며, 소수 표본이므로 일반 성능으로 쓰지 않는다.

**두 번에 나눠 돌렸다. 조건이 완전히 같지는 않다.**

- [첫 실행](2026-11-05-dev-first-run.json): 12개 전체. 이때 하네스의 실행 한도가 Spring 설정과 달랐다(출력 8,000토큰·도구 호출 3·재시도 1, Spring은 12,000·10·2). 실행당 모델 호출 한도 8회는 같다. 9번과 11번은 이후 시나리오 문장을 고쳤으므로 이 파일의 두 항목은 **대체됐다**. 실행 조건 기록(`run`)이 없다.

## 확인된 것

1. **개발용 12개 중 2개가 실행당 호출 한도(8회)를 넘겨 실패했다**(3, 10번). 둘 다 같은 역할(Inquiry)이 반복 호출됐다. 원인은 조사하지 않았다. 정리 작업(#176, #181)에서 같은 시나리오로 비교한다.
2. **Knowledge 검색을 거친 것은 사용법 문의 1·2·10번과 검색 오류를 주입한 12번뿐이다.** 증상·권한 신청·개선 요청(4~9번)과 증상으로 바꾼 11번은 검색 없이 티켓으로 갔다(3번은 시스템 미확인으로 거기까지 가지 못했다). 목표 구조([AI 에이전트 구조](../../../docs/ai/AGENT_ARCHITECTURE.md))는 증상에도 검색과 충분성 판단을 넣는다.
3. **모호한 문장 조각이 확보로 인정된다**(2, 4, 6, 9번). 안전 성질 P6은 원문 인용의 존재만 검사하고 값의 의미는 보지 않는다. 그 결과 필요한 질문이 생략됐다.
4. **정정이 반영되지 않았다**(11번, 한 번의 관찰). 하네스의 Spring 대역이나 병합 규칙의 영향인지는 구분하지 못했다.
5. **안전 성질 위반은 0건이다.** 이는 이 12번의 실행에서 관찰되지 않았다는 뜻이다. 검색 관련 성질(P2~P5)은 1번(FOUND)과 12번(ERROR)에서만 실제로 검사됐고, 나머지는 검색이 없어 검사할 내용이 없었다.

## 이 기록의 한계

- **"안전 성질 위반 0건"은 실행 당시 검사기 기준이다.** 이후 리뷰로 검사기를 고쳤다(P6가 사용자 메시지 인용만 근거로 보고 빈 인용을 거부, 임시 참조를 턴별로 구분, P9 한도 정정). 저장된 보고서에는 원본 실행 기록(trace)이 없어 고친 검사기로 다시 판정하지 않았다. 새 검사기로 재판정하려면 기준선을 다시 돌려야 한다.
- **종료 코드.** 기준선 실행 때의 도구는 실행별 예산 초과(3·10번 `BUDGET_EXCEEDED`)를 실패로 보지 않아 종료 코드 0으로 끝났다. 지금 도구는 0이 아니게 끝낸다.
- **한 번씩만 돌렸다.** 같은 시나리오를 반복하면 결과가 달라질 수 있다. 3·10번 실패가 항상 일어나는지는 모른다.
- **검색은 고정 자료**다. 안내 문장은 우리 문서와 무관하고, 정답의 `relevantEvidence`는 채점하지 못했다. `assessment`(충분성 판정)는 현재 코드에 없어 채점하지 않았다.
- **9번 시나리오는 의도한 상황에 도달하지 못했다.** AI가 `desiredChange`를 묻지 않아 사용자가 모른다고 답할 기회가 없었다. 모름 보존은 5번과 8번에서 확인했다.
- **필수 필드 확보 여부는 사람이 읽고 판단한 것**이다. 자동 채점은 아직 없다.
- 20번(`guide-unresolved`)과 `TEST` 시나리오 8개는 돌리지 않았다. `TEST`는 동결 자료이고, `followUp`의 재생은 멀티턴 작업(#189)에서 지원한다.
- 응답 저장(`store=True`)을 요청하는 어댑터로 돌렸다. 시나리오는 합성 데이터다.

### 검색 힌트(키워드·기능 후보)를 눈으로 본 결과

기록 26건(시나리오 12개의 문제 × 호출). `searchHints`에 모델 원본과 규칙이 정리한 값이 함께 있다.

7번은 "전자결재에서 문서가 목록에 안 보여요"라는 증상 문의다. 첫 판정은 `PARTIAL`("조회 방법은 있으나 구체적 원인이 확인되지 않음")이었고, 모델이 다시 검색(RESEARCH)한 뒤 **같은 안내 문서로 `SUFFICIENT`**를 냈다. 그 문서에는 "이 안내는 조회 방법만 다룹니다. 조회가 되지 않는 문제의 확인은 IT 문의로 접수합니다"라고 적혀 있어 증상을 풀지 못한다고 스스로 밝힌다. 결과로 사용법 안내가 증상 문의의 답으로 나갔다.

- 같은 문서에 같은 부류의 증상(6번)은 `PARTIAL`로 일관됐다. 7번만 재검색 뒤에 뒤집혔다. 한 번씩만 돌렸으므로 **모델 변동인지 판정 프롬프트의 약점인지 구분하지 못한다.**
- 안전 성질 위반은 아니다(`SUFFICIENT`의 근거는 직원 공개 문서이고 P10을 지킨다). 하지만 "증상에는 근거가 원인까지 말하지 않으면 충분하지 않다"는 행동이 지켜지지 않았다. ③에서 미뤘던 판별력 문제가 실제로 나타난 첫 사례다.
- 코드의 보호 장치는 이 경우를 막지 못한다. 코드는 판정이 `SUFFICIENT`이고 인용한 근거로 안내가 만들어지면 답변을 합법으로 본다. 판정이 틀리면 그대로 나간다.

### 그 밖의 관찰

- 갈림길에서의 모델 선택은 시나리오 전체에서 이상한 행동(근거 없는 안내, 질문 가능한데 티켓 등)을 만들지 않았다. 다만 선택 호출의 횟수와 선택 값은 보고서에 따로 기록하지 않아 정량 비교는 하지 못했다.
- 2번 p2는 같은 판정(`PARTIAL`)으로 세 번 재검색한 뒤 티켓으로 끝났다(재검색 한도 2회까지). 질의가 달라져도 결과가 같은 재검색이었다.
- 기능·개선 요청(4번)은 검색 없이 필요한 정보를 모은 뒤 티켓으로 갔다. 증상 문의가 검색 없이 종결된 경우는 없었다.

### 해석과 한계

- **통과 기준:** 안전 성질 위반 0건은 충족한다. 최종 행동은 12개 시나리오의 문제 13개 중 12개가 정답 허용 범위 안이고, 1개(7번)가 밖이다.
- N=1이라 7번이 일회성인지 반복되는지 모른다. 반복 측정 전에는 프롬프트나 규칙을 고치지 않았다.
- 정답의 관련·금지 근거(`relevantEvidence`·`forbiddenEvidence`)는 채점하지 않았다. 판정 이유 문장이 근거와 맞는지도 확인하지 않았다.
- 코퍼스 근사 검색의 결과이므로 실검색에서는 달라질 수 있다.
- 한 번의 DEV 측정이며 TEST 시나리오는 사용하지 않았다. 일반화 판단은 하지 않는다.

### ④e 반복: 7번(`ea-search-time-unknown`) 5회 (2026-11-06)

위에서 증상 문의가 `SUFFICIENT`로 뒤집힌 7번만 같은 조건(커밋 `db10969`, 판정 모드, 코퍼스, 한도 20)으로 5회 더 돌렸다. 보고서는 [2026-11-06-time-unknown-judgment-repeat5.json](2026-11-06-time-unknown-judgment-repeat5.json), 원본 기록은 [2026-11-06-time-unknown-judgment-repeat5-traces/](2026-11-06-time-unknown-judgment-repeat5-traces/)에 있다. 검색 질의의 키워드는 5회 모두 같았다(`전자결재·문서·목록`). 호출 총 48회.

| 회 | 1턴 판정 | 1턴 종결 | 2턴(사용자 답 뒤) |
|---|---|---|---|
| 1 | PARTIAL, PARTIAL | 질문 | 티켓 |
| 2 | PARTIAL, PARTIAL | 질문 | 티켓 |
| 3 | PARTIAL, PARTIAL | 질문 | **실패** `INVALID_OUTPUT` (Ticket 단계 출력 거부) |
| 4 | PARTIAL, PARTIAL | 질문 | **실패** `INVALID_OUTPUT` (Ticket 단계 출력 거부) |
| 5 | **SUFFICIENT** (재검색 없이 첫 검색에서) | **사용법 안내로 종결** | - |

첫 DEV 측정(PARTIAL → 재검색 → SUFFICIENT → 안내)을 합치면 6회 중 **2회가 증상 문의를 사용법 안내로 끝냈다.** 1턴 판정 11건 중 2건이 `SUFFICIENT`다. 안전 성질 위반은 0건이다(trace 재판정 포함).

- **판정이 불안정하다.** 같은 질의·같은 근거 문서로 `PARTIAL`과 `SUFFICIENT`가 갈린다. 5회 중 5번은 재검색 없이 첫 검색에서 `SUFFICIENT`를 냈으므로 재검색이 뒤집힌 원인이 아니다. 단순한 모델 변동이라고 넘기기에는 6회 중 2회(약 3분의 1)가 사용자에게 잘못 가는 결과다.
- **Ticket 단계가 5회 중 2회, 같은 시나리오 2턴에서 실패했다.** 둘 다 `TICKET`이 `OutputRejected`로 끝났고 실행은 재시도 불가능한 `INVALID_OUTPUT`으로 실패했다. 어느 검증이 거부했는지는 기록에 남지 않아 알 수 없다(실행 결과의 오류 메시지는 고정 문구이고 trace에는 예외 이름만 있다). 같은 2턴 ticket 입력(검색 3회 분량의 근거)에서 1·2회는 성공했다. 판정 모드에서만 생기는지, 기존 경로에도 있었는지는 확인하지 못했다. 첫 DEV 측정의 티켓 6건(2·3·4·6·8·12번)은 모두 성공했다.
- 호출 한도와 안전 성질에는 문제가 없었다. 4회는 11호출, 5회는 4호출이다.
- 아직 원인을 구분하지 못한 것: (1) 판정 프롬프트가 "근거가 증상의 원인까지 말하지 않으면 충분하지 않다"는 기준을 충분히 주지 않는지, (2) Ticket 거부가 어느 검증에서 나는지.

#### 2차 5회 (실패 사유 기록 포함)

Ticket 실패의 사유를 남기도록 하네스를 고친 뒤(커밋 `23b0115`) 같은 조건으로 5회 더 돌렸다. 보고서는 [2026-11-06-time-unknown-judgment-repeat5b.json](2026-11-06-time-unknown-judgment-repeat5b.json), 기록은 [2026-11-06-time-unknown-judgment-repeat5b-traces/](2026-11-06-time-unknown-judgment-repeat5b-traces/)에 있다. 호출 총 50회, 안전 성질 위반 0건.

| 회 | 1턴 판정 | 1턴 종결 | 2턴 |
|---|---|---|---|
| 1 | PARTIAL, PARTIAL | 질문 | **실패** (Ticket) |
| 2 | PARTIAL, **SUFFICIENT** | **사용법 안내로 종결** (재검색 뒤 뒤집힘) | - |
| 3 | PARTIAL, PARTIAL | 질문 | 티켓 |
| 4 | PARTIAL, PARTIAL | 질문 | **실패** (Ticket) |
| 5 | PARTIAL, PARTIAL | 질문 | 티켓 |

- **누적(첫 DEV 1회 + 반복 10회 = 11회): 3회가 증상 문의를 사용법 안내로 종결했다**(DEV와 2차 2회는 재검색 뒤, 1차 5회는 첫 검색에서 뒤집힘). 1턴 판정 22건 중 `SUFFICIENT`는 3건이다. 재검색 때문에 생기는 문제가 아니라 같은 입력에서의 판정 불안정이다.
- **Ticket 실패의 사유:** 2건 모두 `OutputRejected`, 사유 문구는 `OpenAI 응답을 검증할 수 없습니다`였다. 이 문구는 Ticket 에이전트의 업무 검증(인용·근거·시스템 확인 등)이 아니라 **모델 클라이언트가 응답을 읽지 못한 경우**(`services/llm/openai.py`: 응답 상태가 `completed`가 아니거나 JSON·스키마 검증 실패)에서만 나온다. 따라서 에이전트 검증이 거부한 것은 아니다.
- 두 경우 중 무엇인지는 아직 모른다. 클라이언트가 둘을 같은 문구로 던진다. 후보는 (1) 출력 한도 1,500토큰(`ticket.proposal.v2`)에서 응답이 잘린 경우, (2) 모델이 낸 값이 출력 형식을 어긴 경우(UUID가 아닌 `sourceId`·`knowledgeEvidenceIds`, 길이·문자 규칙을 넘는 `quote`·`title` 등)다. 호출은 추론을 끄고(`reasoning.effort: none`) 하므로 (1)이 특히 유력하다고 말할 근거는 없다. **확인하지 않았다.**
- 누적 티켓 시도 8회(1차 4회·2차 4회) 중 4회가 실패했다. 같은 시나리오·같은 입력 구조인데 성공과 실패가 갈린다. 다른 시나리오의 티켓 시도는 첫 DEV 측정 6건 모두 성공했다.
