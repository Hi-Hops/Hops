# F004 메시지 정정·최신 버전

상태: PRD 1.44 목표 명세 · 팀 기획 합의 / hops-system-1 구체 계약안 추가·팀 리뷰/구현/검증 별도.

## 1. 목표와 범위

문의자가 내용을 정정할 때 원문·이력을 보존하고 아직 진행 중인 문제에 최신 내용을 반영한다.

근거: [PRD](../../docs/PRD.md), [API](../../docs/API.md), [데이터](../../docs/DATA.md), [목표 공통 계약](../contracts/TARGET_CONTRACT.md).

## 2. 인수 조건

- **F004-TARGET-01:** 본인의 메시지 정정 전후와 이력을 보존한다.
- **F004-TARGET-02:** 분석 중인 문제는 최신 문의 버전으로 분석하고 이전 버전의 늦은 결과는 적용하지 않는다.
- **F004-TARGET-03:** 이미 저장된 티켓은 유지하며 정정으로 중복 티켓을 만들지 않는다.
- **F004-TARGET-04:** 배정 후 입력·정정은 관련 티켓의 보완 정보로 연결하며 자동 새 티켓이나 재배정을 하지 않는다.
- **F004-TARGET-05:** 저장 결과 미확인·버전 충돌 시 입력을 보존하고 서버 상태를 확인한다.

## 화면과 사용자 흐름

### 화면

- 본인 사용자 메시지에 정정 입력과 저장 상태, 이전 내용/정정 이력을 표시한다. AI 메시지 정정은 제공하지 않는다.

### 흐름

1. 사용자가 본인 메시지를 정정하고 제출한다.
2. Spring이 작성자·문의 버전을 확인하고 새 내용을 저장한다.
3. 분석 중 문제는 새 버전으로 분석하고 저장된 티켓은 유지한다.

## 상세 인수 조건과 예외

- **F004-DETAIL-01 정정 이력:** 정정 전 내용을 덮어 없애지 않는다. 메시지 순서와 문의 버전·메시지 revision은 서로 다른 값이다.
- **F004-DETAIL-02 대상 제한:** 타인의 문의 또는 AI 메시지는 정정하지 못하며 서버가 권한을 검사한다.
- **F004-DETAIL-03 분석 중:** 정정 이후 오래된 버전의 진행·답변을 적용하지 않고 관련 문제만 최신 내용으로 분석한다.
- **F004-DETAIL-04 배정 이후:** 이미 저장된 티켓은 유지하고 정정 내용을 관련 티켓의 보완 정보로 전달한다. 자동 재배정·새 티켓 생성은 하지 않는다.
- **F004-DETAIL-05 충돌:** 문의 버전이 충돌하면 최신 저장 상태를 다시 읽어 사용자의 초안과 비교하고 입력을 보존한다.
- **F004-DETAIL-06 응답 유실:** 저장 결과를 알 수 없으면 미확인 상태로 보존하고 기존 요청의 저장 여부를 확인한다. 새 내용으로 바꾼 제출은 별개 작업이다.

## 계약·화면 상태

신규 `hops-system-1` 팀 리뷰용 구체 계약안이다. 필드·enum은 [DATA_TYPES](../contracts/DATA_TYPES.md#신규-계약-hops-system-1), REST·오류·SSE·멱등성은 [WIRE_CONTRACT 12절](../contracts/WIRE_CONTRACT.md#12-신규-계약-hops-system-1), 업무 전이는 [TARGET_CONTRACT](../contracts/TARGET_CONTRACT.md)가 정본이다. 아래 내용은 구현·팀 승인·통합 완료 표시가 아니다.

| 조작 | 계약·검증 |
|---|---|
| 정정 저장 | MessageReviseCommand의 expectedInquiryVersion·expectedMessageRevision 모두 검사 |
| 이력 | 원 messageId·sequenceNo 유지, revision 증가·이전 내용 보존 |
| 분석 반영 | 새 문의 버전·활성 Run 적용. 이미 저장된 티켓·문제 ID는 유지 |
| 보완·충돌 | 배정 후 정정은 기존 티켓 보완. 충돌이면 최신 조회와 사용자 초안을 비교하고 자동 덮어쓰기 금지 |

| 화면 상태 | 관찰 가능한 동작 |
|---|---|
| 저장 중 | 같은 정정 제출 중복 차단·입력 유지 |
| 409 버전 충돌 | 최신 서버 내용과 미전송 수정문 보존 |
| 응답 유실 | 원 키·본문으로 확인. 수정문을 바꾸면 별도 요청으로 구분 |

## hops-system-1 검증 시나리오

- **F004-CONTRACT-01:** 같은 문의 버전에서 두 정정이 경합하면 하나만 저장하고 다른 요청은 409다.
- **F004-CONTRACT-02:** 정정 뒤 늦게 온 이전 분석은 티켓·표준 요청의 최신 상태를 덮지 않는다.
- **F004-CONTRACT-03:** 배정 후 정정은 티켓 ID·workItemId를 유지하고 관련 보완에만 연결된다.

문서/JSON 검사·Mock·실제 서버 저장/권한·실제 AI/검색·브라우저 E2E를 분리해 결과를 기록한다. 기존 테스트의 이전 AC 번호를 새 시나리오 통과로 간주하지 않는다.

## 범위·연관 기능

- 정정만으로 완료·재오픈·재배정을 하지 않는다. 메시지 삭제와 AI 메시지 수정은 범위 밖이다.

## 현재 구현과 남은 작업

기존 프론트의 정정 화면과 전송 프로필은 현재 구현으로 유지되며 새 업무 저장·관련 티켓 연동은 별도다.

기존 코드·테스트의 인수 조건 번호는 이전 기준이며 목표 조건과 구분한다. 목표 AC는 실제 구현·검증 완료를 뜻하지 않는다. 실제 구현 범위는 서비스 코드와 실행 안내에서 확인한다.

기능의 목표 인수 조건은 구현·통합 검증을 대신하지 않는다. hops-system-1 계약안의 담당자 리뷰·승인 후 코드·테스트를 전환한다. 현재 구현을 문서만으로 완료 처리하지 않는다.
