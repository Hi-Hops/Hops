# F008 새 문의 분리 동의

상태: 초안 · 범위: 이슈 #30 포함, 원본 문서상 후속(MVP 포함 여부 Q-ALL-7) · 담당: frontend(화면) · 협의: infra(이벤트 중계), backend(동의 저장·새 문의 생성), ai(별개 문의 판단)
근거: PRD 4.4 "새 문의 분리", 5.1 · API 2.1(동의 설명 문단), 2.4 `inquiry.split.respond` · DATA 3, 7 · ERD 저장 위치 없음(DATA 2)

## 1. 목표

AI가 같은 채팅 안의 내용을 별개 문의로 판단하면, 새 문의로 시작할지 사용자에게 묻는다. 사용자가 동의한 경우에만 새 문의가 한 번 생기고 새 채팅으로 이동한다. 거절하거나 응답하지 않으면 새 문의를 만들지 않고, 기존 문의·티켓은 그대로 둔다. (PRD 4.4)

이 동의는 새 문의를 나눌지에 대한 확인이다. 기존 문의 안의 티켓 생성에 승인 단계를 추가하지 않는다(F005-AC06). (PRD 4.4 · API 2.1)

## 3. 화면

채팅(`/inquiries/:inquiryId/chat`, F003) 안의 동의 요청 카드. 동의 후 새 문의의 채팅(`/inquiries/:newInquiryId/chat`)으로 이동한다.

## 4. 사용자 시나리오

1. 문의자가 VPN 문제를 이야기하다가 "그리고 프린터도 안 돼요"라고 보낸다.
2. AI가 별개 문의로 판단하면 채팅에 "새 문의로 나눠서 접수할까요?" 카드가 나온다. 가져갈 내용과 출처(어느 메시지에서 왔는지)가 함께 보인다.
3. "새 문의로 시작"을 누르면 새 채팅으로 이동하고, 원래 채팅에서는 새 문의로 가는 링크가 보인다.
4. "아니요"를 누르거나 응답하지 않으면 새 문의는 생기지 않는다.

## 5. 인수 조건

- **F008-AC01 동의 요청 표시**
  Given 서버가 별개 문의 후보를 저장함 · When 채팅에서 그 후보를 받으면 · Then 동의 요청 카드에 가져갈 문맥 요약과 출처 메시지를 보여 주고, "새 문의로 시작"과 "아니요"를 제공한다. 후보를 React에 전달하는 방법(메시지 `payload`인지 별도 이벤트인지)은 정해지지 않았다. (PRD 4.4 · API 2.1 "서버가 후보 문맥과 출처를 제시" · Q-BE-13)
- **F008-AC02 동의 전송**
  When "새 문의로 시작"을 누르면 · Then `inquiry.split.respond` `{requestId,inquiryId,expectedInquiryVersion,consentId,accepted:true}`를 보내고, 저장 ACK 전에는 "새 문의를 만드는 중"을 표시한다. 저장 ACK에서 새 문의 ID를 확인한 뒤에만 새 채팅으로 이동한다. (API 2.4 · ACK 결과 필드 Q-BE-13, Q-INF-6)
- **F008-AC03 거절**
  When "아니요"를 누르면 · Then `accepted:false`를 보내고, 저장 ACK 뒤 카드를 "기존 문의에서 계속"으로 바꾼다. 새 문의는 만들어지지 않는다. (PRD 4.4 · API 2.4)
- **F008-AC04 무응답**
  사용자가 응답하지 않으면 화면은 아무것도 보내지 않는다. 화면 타이머로 거절이나 동의를 대신 보내지 않는다. 후보가 만료되는지와 만료 시 표시는 서버 상태를 따른다. (PRD 4.4 "응답하지 않으면 새 문의를 만들지 않는다" · 만료 여부 Q-BE-13)
- **F008-AC05 중복 동의**
  ACK 시간 초과·끊김이면 F003-AC04와 같이 "결과 확인 중"으로 표시하고 같은 `requestId`로 다시 보낸다. 다시 보내거나 두 탭에서 동의해도 화면은 서버가 돌려준 같은 새 문의로 이동한다(새 문의 하나만 생성하는 것은 서버 책임). (PRD 4.4 · DATA 3, 5)
- **F008-AC06 기존 문의 유지**
  동의 뒤에도 원래 채팅의 메시지·문제·티켓 카드는 바뀌지 않는다. 원래 채팅에서 새 문의로, 새 문의에서 원래 문의로 갈 수 있는 연결을 보여 준다. (PRD 4.4 "출처 연결" · DATA 3 · 연결 필드 Q-BE-13)
- **F008-AC07 오래된 동의 요청**
  화면이 아는 문의 버전과 서버 버전이 달라 충돌하면 최신 대화와 후보 상태를 다시 불러온다. 이미 처리된 후보의 버튼은 비활성화하고 처리 결과를 보여 준다. (API 1 · API 2.4 `expectedInquiryVersion`)
- **F008-AC08 남의 동의 요청**
  다른 사용자의 문의나 `consentId`로는 동의할 수 없다. 서버가 거부하면 내용을 보여 주지 않고 권한 없음 안내를 한다. (API 2.4 "검증된 사용자" · PRD 4.11)

## 6. 계약(화면이 기대하는 값)

| 용도 | 경로·이벤트 | 판정 | 비고 |
|---|---|---|---|
| 동의 응답 | `inquiry.split.respond` `{requestId,inquiryId,expectedInquiryVersion,consentId,accepted}` | 초안 | API 2.4. ACK 결과의 새 문의 ID 필드 → Q-BE-13 |
| 동의 후보 전달 | — | 미정 | Spring → React 전달 방법, 후보 문맥·출처 형식 → Q-BE-13 |
| 동의 상태 값 | — | 미정 | 대기·동의·거절·만료 등 → Q-ALL-2, Q-BE-13 |
| 동의 저장 위치 | — | 미정 | DATA 2 "최신 ERD에 없음". `QUESTIONS.md` 6절 |
| 원본·새 문의 연결 조회 | `GET /api/inquiries/{id}` 응답 | 미정 | 응답에 연결 필드가 없음 → Q-BE-13 |
| 별개 문의 판단 | 에이전트 결과 | 미정 | PR #38 결과 예시의 `action` 값에 분리 후보 없음 → Q-AI-5 |

## 7. 화면 상태

```text
후보 표시 → 동의 전송 중(ACK 대기) → 동의 저장: 새 채팅으로 이동, 원래 채팅에 링크
                                  → 결과 확인 중: 같은 requestId로 확인·재전송
          → 거절 전송 중 → 기존 문의에서 계속
          → 무응답: 아무것도 보내지 않음(서버 만료 상태가 오면 표시)
```

## 8. 범위 밖

AI의 별개 문의 판단 기준, 여러 후보를 한 번에 나누기, 이미 만든 티켓을 새 문의로 옮기기(PRD 4.4 "기존 문의·티켓·처리 상태는 유지").

## 9. 막히는 정도

- 목으로 진행 가능: 동의 카드, 전송 상태, 이동·링크 표시.
- 결정 전 구현 보류: MVP 포함 여부(Q-ALL-7), 후보 전달과 ACK 필드(Q-BE-13), 에이전트 결과의 분리 후보 표현(Q-AI-5).
