# F005 문제별 결과·복수 티켓

상태: PRD 1.44 목표 명세 · 팀 기획 합의 / 상세 계약·구현·검증 별도.

## 1. 목표와 범위

독립된 요청의 진행과 저장된 티켓, 부분 실패 및 결과 미확인을 문제별로 보여준다.

근거: [PRD](../../docs/PRD.md), [API](../../docs/API.md), [데이터](../../docs/DATA.md), [목표 공통 계약](../contracts/TARGET_CONTRACT.md).

## 2. 인수 조건

- **F005-TARGET-01:** 독립 요청과 완료 조건은 별도 문제와 티켓으로 나누며 같은 증상의 여러 원인 후보는 하나의 문제로 유지한다.
- **F005-TARGET-02:** 문제마다 확인 중·추가 질문·범위 밖·저장 성공·생성 실패·저장 결과 미확인을 구분한다.
- **F005-TARGET-03:** 서버에서 저장·배정이 확인된 티켓만 표시하고 접수 결과를 모달로 안내한다.
- **F005-TARGET-04:** 보고 시스템과 책임 시스템을 구분하며 확정된 주담당자 정보를 보여준다.
- **F005-TARGET-05:** 일부 실패나 미확인에도 성공한 티켓은 유지하고, 재조회·재시도로 중복 티켓을 만들지 않는다.

## 화면과 사용자 흐름

### 화면

- 문의 채팅의 문제별 결과 영역과 티켓 접수·배정 결과 모달. 문의자에게 보이는 정보는 권한 범위로 제한한다.

### 흐름

1. 독립 문제마다 질문·대기·저장 결과를 갱신한다.
2. 서버가 저장과 배정을 확인한 티켓만 카드로 보여준다.
3. 일부 문제에 실패·미확인이 있으면 성공 티켓을 유지하고 각각의 상태를 표시한다.

## 상세 인수 조건과 예외

- **F005-DETAIL-01 복합 요청:** 문서 열람 실패와 기능 추가는 두 문제이며 서로 다른 완료 조건을 갖는다. 같은 증상의 여러 원인 후보는 한 문제로 유지한다.
- **F005-DETAIL-02 저장된 카드:** 티켓의 제목·보고 시스템·책임 시스템·담당자·처리 상황을 권한에 맞게 표시한다. AI 제안만으로 티켓 번호나 저장 성공을 표시하지 않는다.
- **F005-DETAIL-03 상태 분리:** 질문 중, 시스템 선택 대기, 범위 밖, 생성 성공, 실패 및 저장 결과 미확인을 구분한다. 화면 표시명과 실제 코드의 매핑은 구현 계약에서 정한다.
- **F005-DETAIL-04 부분 실패:** 한 문제의 저장 실패로 다른 문제의 저장 티켓을 제거하거나 전체 성공이라고 표시하지 않는다.
- **F005-DETAIL-05 모달과 승인:** 티켓 접수·배정 결과를 모달로 확인하고 정정 방법을 제공한다. 티켓 생성에 별도 사용자 제출 승인·담당자 수락을 요구하지 않는다.
- **F005-DETAIL-06 재조회:** 업무 변경 이벤트나 복구 뒤 저장된 문의 결과를 재조회한다. 임시 모델 결과와 저장 티켓을 중복 표시하지 않는다.
- **F005-DETAIL-07 실패 항목:** 저장 여부가 미확인이면 실패로 단정하지 않는다. 재시도 권한·조작은 F010의 구현 전 합의 사항이다.

## 계약·화면 상태

- 문제·티켓·생성 작업·실패/미확인에 필요한 논리 필드는 목표 공통 계약을 따른다. 새 카드 필드·enum과 실제 경로는 미확정이다.
- 기존 InquiryResult·TicketCard는 부서 기반 Mock 프로필로, 시스템 주담당자 필드가 이미 제공된다고 가정하지 않는다.

| 상태 | 사용자에게 보이는 동작 |
|---|---|
| 로딩·처리 중 | 현재 요청의 진행을 표시하고 저장·완료로 단정하지 않는다. |
| 정상 결과 | 서버가 확정한 값만 표시한다. |
| 빈 결과 | 정상 조회된 0건을 안내한다. |
| 실패·결과 미확인 | 실패와 저장 미확인을 구분하고 입력·이미 저장된 결과를 보존한다. |
| 권한 없음 | 서버가 접근을 거부하고 허용되지 않은 내용을 표시하지 않는다. |

## 범위·연관 기능

- 정상 티켓과 아직 저장되지 않은 항목을 분리한다. 사례 승인 또는 기능 개발 승인은 이 모달에서 확정하지 않는다.

## 현재 구현과 남은 작업

현재 Mock 결과 카드는 부서 기반이다. 새 시스템·담당자·문제별 복구 응답 및 실제 저장 연결은 별도다.

기존 코드·테스트의 인수 조건 번호는 이전 기준이며 목표 조건과 구분한다. 목표 AC는 실제 구현·검증 완료를 뜻하지 않는다. 실제 구현 범위는 서비스 코드와 실행 안내에서 확인한다.

기능의 목표 인수 조건은 구현·통합 검증을 대신하지 않는다. 새 API 경로·필드·enum·권한과 테스트 연결은 담당자 간 계약 확정 후 진행한다.
