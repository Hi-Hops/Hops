# 채팅 이미지 첨부 데이터·API 계약 초안

상태: 이슈 #231 구현을 위한 **제안 초안**. 기능 브랜치에는 기본 비활성인 임시 이미지 업로드·소유자 메타데이터 조회, DB 접수와 메시지 결합, 문의자용 이미지 조회·이력 표시 기반이 추가됐다. 미사용 객체 정리·담당자 조회·AI 연결과 S3 운영 설정은 아직 구현되지 않았다. 아래 전체 제안이 구현되거나 서비스 검증을 완료했다는 뜻이 아니다. 최종 필드·오류를 기존 [데이터 계약](../contracts/DATA_TYPES.md), [전송 계약](../contracts/WIRE_CONTRACT.md), [에이전트 계약](../../contracts/agents/README.md)의 정본에 옮기고 서비스 연결을 검증해야 한다.

구현 중인 API는 기본 비활성이다. 테스트 설정의 `hops.image-attachments.enabled=true`에서만 등록되며 `hops.image-attachments.bucket`과 AWS SDK 표준 리전·자격 증명 설정이 필요하다. 가림 확인 UI 연결, 미사용 객체 정리, 운영 버킷 보안 및 실제 S3 검증 전에는 운영에서 활성화하지 않는다.

메시지 결합은 별도 `hops.image-attachments.message-link-enabled` 설정이 기본 false다. AI 이미지 분석이 연결되지 않아 `hops.agent.dispatch-enabled`가 켜진 경우 이 설정과 무관하게 첨부 메시지를 503으로 거부한다. 두 설정을 이용한 연결 테스트는 AI 전송을 끈 격리 테스트 DB 전용이다. 과거 테스트에서 이미지가 빠진 실행 입력이 저장되었을 수 있으므로 테스트 문의·실행을 AI 전송 환경에 옮기거나 재실행하지 않는다. AI 연동과 안전한 이전 실행 처리 구현 전 실제 문의를 접수하지 않는다.

문의자 본문 조회는 현재 문의자와 결합 관계를 확인하고 객체의 크기·해시를 검증한 뒤 권한을 다시 확인한다. 메시지 목록에는 이미지 식별자·크기만 제공한다. 프론트는 인증 헤더로 이미지를 조회해 임시 URL로 표시하고 화면 이탈 시 해제한다. 이 경로는 저장소 대역·격리 DB에서 검증하며 실제 S3와 브라우저 E2E 검증은 별도다.

프론트의 이미지 선택과 전송 연결은 `VITE_CHAT_IMAGE_ATTACHMENTS=true`에서만 표시되며 기본 비활성이다. 가림 확인된 이미지는 브라우저 메모리에 두고 개별 업로드의 같은 요청 키로 결과를 확인한다. 브라우저 새로고침 후에는 미전송 이미지와 업로드 확인 상태가 복원되지 않는다. 이미지 분석·고아 객체 정리와 실제 전체 흐름을 검증하기 전 운영에서 활성화하지 않는다.

## 1. 목적과 경계

- 문의자는 첫 문의와 후속 메시지에 오류 화면 여러 장과 필수 텍스트를 함께 보낸다. 문의 이력은 **가림 처리 후 확정된 이미지**를 보존한다. 텍스트만 보내는 기존 클라이언트도 동작한다.
- 브라우저는 개인정보·비밀값을 자동으로 전부 찾아낸다고 가정하지 않는다. 사용자가 원본 미리보기에서 직접 가리고, 새로 인코딩된 결과를 각각 살펴본 뒤 확인한다. 선택하지 않은 원본 바이트·원본 URL·원본 파일명은 HTTP 요청, 서버 저장소, AI, 로그 또는 추적에 보내지 않는다. 사용자 기기의 휘발성 메모리에서 원본을 읽는 과정은 필요하다.
- 서버는 제출된 이미지가 실제로 완전히 가려졌는지 보증할 수 없다. 직접 API를 호출하는 클라이언트도 사전 가림·확인이 필요하며, 미탐지 개인정보의 유출 방지를 보장하지 않는다. 실제 개인정보 사용 전 운영 정책과 별도 검증이 필요하다.
- Spring은 업로드 소유권, 메시지·문제 관계, 현재 담당자와 AI 실행 접근을 검증한다. 모델의 문구·ID·텍스트 메시지의 연결만으로 이미지 열람 권한을 부여하지 않는다.

## 2. 제한과 데이터

| 항목 | 제안값·의미 |
|---|---|
| 문의 이미지 수 | 문의 전체에서 0~5장(첫 문의와 후속 메시지 합계). 같은 ID 중복은 거부하며 메시지 안의 순서를 유지 |
| 실행 이미지 수·크기 | 상담 실행 입력에는 문의의 모든 메시지가 들어가므로 문의 한도와 같은 최대 5장·재인코딩 객체 합계 40 MiB. 이미지를 자동 누락하지 않는다 |
| 브라우저 입력 | PNG/JPEG, 각 5 MiB 이하. 직접 가림 후 메타데이터를 제거한 PNG 생성 |
| 전송 이미지 | 가림 확인된 PNG, 각 5 MiB 이하. 한 메시지의 전송 원본 합계 최대 25 MiB. 여러 장은 순차적으로 개별 요청 |
| 서버 재인코딩 | 실제 형식·디코딩·가로/세로 최대 8,192·최대 1,600만 픽셀 검사, 메타데이터 제거 PNG. 최종 객체 각 8 MiB 이하 |
| 요청 크기 | Base64 JSON은 개별 HTTP 본문 최대 7 MiB. 프록시·서버에서 같은 상한을 적용하고 제한 외 파일이나 요청은 거부 |
| 메시지 내용 | 기존 1~4,000 Unicode 코드 포인트 필수. 이미지 단독 메시지는 이번 범위 밖 |
| 객체 식별 | 서버 발급 UUID와 불변 바이트 digest. S3 key·버킷명·공개 URL은 외부 응답과 AI 스냅샷에 넣지 않음 |
| 보존 | 메시지에 결합된 이미지는 문의 이력에 보존. 미결합 `READY` 이미지는 준비 완료 시각부터 24시간 동안 결합할 수 있고 그 뒤 정리 대상으로 전환 |

5장·5 MiB는 현재 브라우저 기반 코드, 8 MiB·픽셀 한도는 서버 재인코딩 기반 코드에 맞춘 제안값이다. 총량·HTTP 제한·보존 기간은 이 초안의 신규 설계값이며 환경에 적용되거나 검증되지 않았다. 업로드 총량·동시성·토큰/비용 제한은 파일별 제한과 별개다. 24시간은 기존 명령 상세 결과의 최소 보존 시간에 맞춘 초안이며 운영 비용·사용성 검증 후 바꿀 수 있다.

이미지 `Attachment`는 서버 발급 `id`, 소유자, 변경 요청 ID, 정규화된 PNG의 digest·바이트 수, 상태, 생성/만료 시각, 결합된 messageId를 갖는다. 소유자·digest·S3 key는 저장/내부 검증용이며 직원 외부 DTO에 불필요하게 공개하지 않는다. 바이트는 메시지 JSON·`agent_run.input_snapshot`·로그·이벤트·명령 영수증에 복제하지 않는다. 물리 테이블·인덱스·마이그레이션은 이 논리 계약을 충족하도록 별도 설계한다.

## 3. 업로드 상태와 요청

새 문의는 아직 inquiryId가 없으므로 **문의자 소유의 임시 업로드 → 메시지 저장 시 결합**의 두 단계를 제안한다. 인증·명령·receipt의 기본은 WIRE 12.1을 따른다. 아래 엔드포인트·필드·상태·오류는 현재 구현이 아닌 이 기능의 제안값이다.

| 메서드·경로 | 요청 및 권한 | 응답 |
|---|---|---|
| `POST /api/v2/image-attachments` | 로그인. `Idempotency-Key`와 JSON `requestId` 동일. `mediaType`은 `image/png`, `dataBase64`는 사용자가 확인한 PNG 바이트의 Base64 | 확정 시 기존 `CommandReceipt` 200 `SUCCEEDED`, resource type `IMAGE_ATTACHMENT`와 id. 미확인/진행은 202 `PENDING` 또는 `UNKNOWN` |
| `GET /api/v2/image-attachments/{attachmentId}` | 현재 업로드 소유자. 미결합이거나 자신의 문의에 결합된 항목만 | 소유자용 메타데이터: id·상태·생성/만료 시각·메시지 연결 여부. S3 위치·바이트·다른 사용자의 존재는 제외 |
| `GET /api/v2/inquiries/{inquiryId}/image-attachments/{attachmentId}/content` | 현재 문의 소유자이고 이미지가 그 문의의 저장된 메시지에 연결 | `image/png` 바이트. 비공개·`Cache-Control: no-store`, `X-Content-Type-Options: nosniff` |
| `GET /api/v2/tickets/{ticketId}/image-attachments/{attachmentId}/content` | 현재 해당 티켓에 접근 가능한 담당자이고 이미지–해당 문제 연결이 유효 | 위와 같은 가림 PNG. 실패 시 대상 존재를 누출하지 않는 오류 |

`ResourceType.IMAGE_ATTACHMENT`은 신규 가산값으로 제안한다. 기존 명령별 반환값과 `operations/by-request/{requestId}`를 유지하며 프론트 wire 판독기도 추가 값을 처리해야 한다. 바이너리 업로드의 다른 전송 방식은 이번 제안에 포함하지 않는다. JSON과 Base64는 임시 입력일 뿐 로그·결과 journal에 본문을 저장하지 않는다. 프록시 버퍼링/임시 파일·서버 요청 로그와 제한도 구현 및 배포 시 확인한다.

요청과 성공 영수증의 형식 예시다. 꺾쇠는 실제 값이 아닌 자리표시자다.

```json
{
  "requestId": "<uuid>",
  "mediaType": "image/png",
  "dataBase64": "<가림 확인된 PNG의 Base64>"
}
```

```json
{
  "requestId": "<동일 uuid>",
  "operationId": "<서버 발급 uuid>",
  "state": "SUCCEEDED",
  "resource": {"type": "IMAGE_ATTACHMENT", "id": "<서버 발급 uuid>"},
  "error": null
}
```

소유자 메타데이터는 `id:Uuid`, `state:PENDING|READY|BOUND|EXPIRED`, `mediaType:"image/png"`, `byteSize:int`, `createdAt:time`, `expiresAt:time?`, `messageId:Uuid?`, `linkRevision:int`, `problemIds:Uuid[]`를 반환한다. `messageId`는 `BOUND`에서만 값이 있다. 미결합 상태의 `linkRevision`은 0이고 `problemIds`는 빈 배열이다. 이 응답은 현재 소유권 검사 뒤에만 제공한다. 가림 후 전송된 PNG와 서버 재인코딩 바이트의 digest는 각각 재요청 식별과 객체 무결성 확인에만 사용하며 외부 응답에서 제외한다. 브라우저의 가리기 전 원본 digest는 서버에 보내지 않는다.

업로드의 논리 상태는 `PENDING`(S3 저장 전/진행/결과 미확인), `READY`(정규화 PNG의 저장과 digest 확인), `BOUND`(하나의 메시지에 결합), `EXPIRED`(미결합 유효기간 종료 및 정리 대상)로 제안한다. `GET`은 소유자에게 이 네 값을 반환하고 `expiresAt`은 `READY`에만 결합 만료 시각을 준다. `PENDING`·`BOUND`·`EXPIRED`는 null이다. `EXPIRED`는 바이트 삭제 성공을 뜻하지 않는다. 저장 실패·권한 부재를 `READY`로 바꾸지 않는다. 정리 중이거나 삭제 확인이 안 되는 객체는 결합하지 않고 공개하지 않는다.

1. 같은 사용자·같은 requestId·같은 정규화 전송 바이트는 같은 업로드 의도다. 바이트나 경로가 다르면 409 `IDEMPOTENCY_KEY_REUSED`. 요청에는 이미지 원본이 아니라 확인된 PNG만 포함한다.
2. 업로드 접수의 중복 방지 기록과 서버 발급 attachmentId·입력 digest는 DB에 확정한다. S3 호출을 DB 트랜잭션 안에 두어 원자적으로 완료된 것처럼 취급하지 않는다.
3. 같은 객체 ID에는 조건부 생성하고, S3 성공 응답 유실 또는 이미 존재하는 객체는 서버가 정규화 바이트 digest를 확인한다. 동일성이 검증될 때만 `READY`. 다른 digest, 조회 실패 또는 저장 결과 미확인은 성공으로 응답하거나 다른 키로 자동 재생성하지 않는다.
4. 클라이언트는 응답 유실 시 원 requestId로 operation을 확인한다. 404는 미저장 증거가 아니다. 같은 입력과 키로만 확인/재시도한다. 만료된 결과의 410 처리와 요청 키 보존은 기존 공통 계약을 따른다.
5. 한 사용자·같은 키의 동시 업로드는 하나의 attachmentId를 사용하며, 상태 전이와 객체 조건부 생성으로 중복 결합·덮어쓰기를 막는다. 객체 조회·해시 실패가 반복되면 미확인으로 남기고 안전하게 재조정한다.
6. 미결합 객체 정리는 활성 업로드·결합과 경합하지 않게 DB에서 대상을 잠그고 정리 대상으로 확정한 뒤 S3 작업을 수행한다. 저장 지연·삭제 응답 유실·정리 중 재시도까지 고려해 재조정하며, **결합된 객체는 정리하지 않는다**. S3에 늦게 도착한 객체도 최종 정리될 수 있도록 상태·객체 수명 정책을 구현 전에 검증한다.

입력 형식·용량·실제 디코딩 오류는 400 `INVALID_INPUT`(프록시 크기 초과는 413), 타 사용자/범위 밖은 존재를 감춘 404, 준비되지 않음·이미 결합됨·만료 상태는 409 `INVALID_STATE`로 제안한다. 요청 접수 전에 저장소 준비 여부를 확인하지 못했다면 503이고, 접수 기록 이후 저장이 진행 중이면 202 `PENDING`, 저장 여부를 확인할 수 없으면 202 `UNKNOWN`이다. 후자는 같은 키로만 확인하며 503으로 미저장이라고 단정하지 않는다. 413은 프록시에서도 공통 ApiError 형식으로 반환하도록 구성한다. 429 제한은 `Retry-After`를 따른다. 오류·로그에는 Base64, 파일명, 이미지 바이트나 내부 저장소 경로를 넣지 않는다.

## 4. 메시지 결합·정정·조회

- 기존 `InquiryCreateCommand`와 `MessageSendCommand`에 생략 가능한 `attachmentIds: Uuid[]`를 **가산**한다. 생략은 빈 배열과 같고, 명시한 null·중복 ID와 문의에 이미 연결된 이미지를 합쳐 5장을 넘는 목록은 `400 INVALID_INPUT`으로 거부한다. 서버는 문의 행을 잠근 같은 거래에서 합계를 검사하며, 화면은 불러온 이력 기준으로 남은 장수만 고르게 한다. 기존 content·requestId·expectedInquiryVersion·problemIds 의미는 유지한다.
- 문의 생성 또는 후속 메시지의 서버 저장 거래에서 이미지가 모두 같은 사용자의 `READY`이며 만료 전·미결합인지 확인한다. 문의/메시지·연결·입력 버전·AI 실행 스냅샷·명령 receipt를 함께 commit한다. 하나라도 검증에 실패하면 해당 메시지와 모든 연결을 저장하지 않는다. 이미 준비된 이미지는 유효기간 동안 보존한다.
- 같은 메시지 명령을 같은 키·본문으로 다시 보내면 최초 결과를 반환한다. 다른 키로 이미 결합된 이미지를 재사용하면 거부한다. 이 검사는 소유권·문의 버전·중복 실행과 함께 적용한다.
- `ChatMessage`에 생략 가능한 `attachments` 목록을 가산한다. 항목은 불변 `id`, `mediaType=image/png`, `byteSize`와 순서이며 원본 파일명·S3 URL은 포함하지 않는다. 화면은 권한 검사된 content 경로로 바이트를 조회한다. 추가 필드 수용 여부와 신·구 배포 순서를 실제 wire 판독기로 확인한다.
- 메시지 정정은 텍스트만 새 revision으로 바꾸고 이미지·결합 시점의 이미지 바이트를 유지한다. 이미지 교체는 정정이 아니라 새 메시지다. 과거 텍스트 revision과 이미지 연결의 조회는 섞어 추측하지 않는다. 이미 저장된 이미지와 티켓은 정정 때문에 삭제·재배정하지 않는다.
- 사용자가 미완성 입력을 취소하거나 로그아웃하면 브라우저의 원본 File·객체 URL·가림 전 미리보기를 폐기한다. 저장 여부 미확인인 명령은 임의의 새 키로 재전송하지 않는다.

## 5. 문제별 공개와 최신 develop

`develop`의 #232는 직전 AI 질문·안내에 대한 첫 사용자 답변을 해당 **텍스트 문제**에 연결할 수 있다. 이 연결이나 `problemIds`를 그대로 이미지 전체 공개 권한으로 바꾸지 않는다. 이미지 1장은 텍스트의 한 구간처럼 분리할 수 없고, 하나의 화면에 여러 문제나 타인 정보가 있을 수 있다.

- 이미지와 문제 관계는 별도 서버 관리 기록으로 둔다. **문제 하나가 확정되고 이미지가 그 문제에만 해당함이 사용자 확인으로 명확할 때** 단일 문제에 연결한다. 관계가 미확정이거나 이미지가 복합 문의를 함께 담는 경우 담당자에게 자동 공개하지 않는다.
- 문의자는 이미지마다 연결할 기존 문제를 명시적으로 확인하거나 정정할 수 있다. 제안 명령은 `POST /api/v2/inquiries/{inquiryId}/image-attachments/{attachmentId}/problem-links`, JSON `{requestId, expectedInquiryVersion, expectedLinkRevision, problemIds}`이며 헤더 `Idempotency-Key=requestId`다. 초기 링크 차수는 0이고 성공마다 1 증가한다. `problemIds`는 전체 교체할 중복 없는 같은 문의의 문제 목록이며 `[]`는 현재 공개 관계 전체 해제다. 여러 문제를 선택하면 **이미지 전체가 각 문제의 담당자에게 보여도 되는지** 문의자가 확인한다.
- Spring은 본인·현재 문의 버전·링크 차수·해당 이미지와 문제의 같은 문의 관계를 한 거래에서 검사한다. 응답은 기존 `CommandReceipt`의 `INQUIRY`다. 버전 충돌은 기존 `INQUIRY_VERSION_CONFLICT` 또는 신규 제안 `ATTACHMENT_LINK_VERSION_CONFLICT`로 409이며 최신 상태 조회 후 다시 확인한다. 성공·재전달은 한 번만 반영하고 권한 변경 이력을 보존한다. 이미지 관계의 변경은 원문 `problem-links`를 임의 재작성하지 않는다.
- 이미지 관계를 변경하면 문의 버전을 올려 이전 분석 결과를 적용하지 않는다. 현재 진행 중인 분석이 있었다면 기존 대상과 상태를 확인해 이어가며, 단순 공개 범위 변경만으로 이미 배정된 문제의 새 티켓·재배정·해결을 만들지 않는다. 종료된 문제의 재오픈도 하지 않는다. 텍스트 메시지를 정정하면 이미지 바이트는 보존하되 이전 이미지–문제 공개 관계는 보류하고 문의자에게 재확인받는다.
- 담당자 화면은 현재 `requireStaffTicket`의 책임 시스템 권한과 현재 이미지–티켓 문제 관계를 매 조회 시 함께 검사한다. 텍스트 메시지의 일부를 볼 수 있다는 사실이나 이미지 ID를 알고 있다는 사실만으로 원본 전체를 반환하지 않는다. 정책·담당자 변경 시 기존 URL·캐시만으로 계속 제공하지 않는다.
- `develop`의 #236은 AI 안내에서 허용되지 않는 근거 표시를 숨긴다. 이미지 추가는 이 가이드 공개 검사와 기존 직원·담당자 근거 분리를 우회하지 않는다. #235는 작성 중 `origin/develop`에 병합됐다. 병합된 `CurationInputFactory`는 해당 문제의 허용된 사용자 메시지와 AI 질문·답변, 처리 기록 및 상담 근거를 사례 초안 입력에 포함한다. 따라서 미확인 이미지 관찰과 이미지 바이트는 사례 초안 입력에서 제외하고, 사용자 확인 후 텍스트로 전달되는 이미지 유래 정보도 담당자 권한·해당 문제 관계와 공개 범위를 다시 검증해야 한다. 기존 코드가 이 신규 이미지 정책을 구현했다는 뜻은 아니다.

## 6. Spring–AI 입력과 이미지 관찰

- `InputMessage`에 생략 가능한 `imageAttachments: [{attachmentId, digest}]`를 제안한다. Spring은 message·inquiryVersion·runId·정책을 고정한 실행 스냅샷에 참조만 둔다. 실제 바이트는 `GET /internal/v2/runs/{runId}/image-attachments/{attachmentId}?inquiryVersion={version}`에서 서비스 인증 후 반환한다. 참조 저장·내부 조회와 미확인 이미지 관찰의 모델 호출 기반은 구현되었지만 실행 파이프라인·관찰 저장과 확인 UI에는 연결되지 않았으며, AI는 이미지 참조가 있는 실행을 안전하게 거부한다.
- Spring은 조회 시 실행의 현재 상태·기한·문의/정책 revision, 저장된 입력 스냅샷에 정확히 포함된 첨부 ID·digest, 메시지 소유·허용 범위 및 객체 바이트 digest를 검사한다. 확인할 수 없거나 불일치하면 이미지를 반환하지 않고 해당 분석을 실패 처리한다. `CASE_DRAFT`와 그 밖의 실행에는 별도 계약 없이 이미지 조회를 허용하지 않는다.
- AI는 이미지와 텍스트를 함께 분석하되 이미지의 명령은 신뢰할 수 없는 입력이다. 이미지에서 관찰한 텍스트는 사용자 메시지의 **원문 인용으로 위장하지 않는다**. 현재 `InquiryExtraction.ground`는 실제 텍스트에 존재하는 인용만 확인된 정보로 인정하므로, 이미지 관찰은 별도 출처·미확인 제안으로 다루고 사용자 확인을 받은 뒤 사실에 반영하는 출력 및 후속 응답 계약이 필요하다. 이 구분이 구현되기 전 이미지에서 유래한 값을 확인 사실·권한·원인·해결로 확정하지 않는다.
- `AiResult`에 선택적인 `imageObservations`를 제안한다. 각 항목은 실행 안에서 유일한 `observationRef`(1~64자의 영문·숫자·하이픈), 입력에 포함된 `attachmentId`·`messageId`·`messageRevision`, 기존 문제 ID 또는 현재 결과의 신규 문제 참조인 `problemRef`, 짧은 관찰 문구, 확인 질문 묶음의 `questionRef`(없으면 null)다. 이미지당 최대 3개, 실행당 최대 15개이며 문구는 공백만이 아닌 1~400 Unicode 코드 포인트다. 숫자는 이 기능의 제한 제안이며 기존 모델의 이미지 판독 정확도를 뜻하지 않는다. 이미지가 없는 요청이나 이전 생산자의 결과에서 필드 생략은 `[]`로 받는다. AI 측 자료형·참조 검증은 구현했으나 관찰 생성기와 실제 실행·Spring 저장은 아직 연결하지 않았다. 빈 목록은 기존 결과 직렬화에서 생략하며, Spring은 비어 있지 않은 관찰을 아직 거부한다.
- Spring은 결과의 run·문의 버전·정책·이미지 digest·메시지 revision·문제 참조를 검증하고, 성공 결과 적용 거래에서 서버 발급 `observationId`와 관찰 내용을 `UNCONFIRMED`로 저장한다. 없는 이미지/문제, 다른 run의 참조, 중복 ref·한도 초과·오래된 입력은 결과 전체를 거부한다. 관찰 문구는 저장·공개 전에 기존 입력과 같은 제한적 민감정보 검사와 안전한 텍스트 표시를 거친다. 자동 검사만으로 모든 개인정보를 차단할 수는 없다. 관찰과 응답 이력을 분리한 DB 마이그레이션과 저장 구성요소는 추가했으나 실제 AI 결과 반영에는 아직 연결하지 않았다. 저장 구성요소는 실행 이력에 원문이 남는 점을 고려해 이미지 실행 결과의 텍스트 전체에 기존 가림 규칙이 탐지한 값이 있으면 거부한다. 이 검사는 모든 개인정보의 부재를 보장하지 않는다. 문제 저장 결과·안내 결과·같은 실행의 티켓 기록과 입력의 기존 문제에서 관찰 대상 ID를 해석하는 구성요소와 저장의 거래 검증은 추가했다. 문의 행 잠금과 실행·정책 검증은 호출자가 수행해야 하며, 사례 생성·확인 경계도 실제 결과 경로 연결 전에 검증해야 한다.
- 문의자에게 확인이 필요한 관찰의 `questionRef`는 같은 `problemRef`의 기존 `questions[].bundleRef`를 가리키며, 실제 질문 본문과 하나의 저장 AI 답변에도 확인 문구가 포함돼야 한다. 참조가 null이면 확인을 요구하지 않는다. 기존의 **문제당 최대 5회**에 포함하며 확인 화면으로 질문 한도를 우회하지 않는다. 남은 질문이 없거나 관찰이 불명확하면 `UNCONFIRMED`로 남기고 누락 정보로 전달한다. 담당자에게는 해당 이미지–문제 공개 관계가 있을 때만 관찰과 확인 상태를 표시한다.
- 문의자의 저장 AI 메시지 조회에는 선택적 `imageObservationQuestions` 목록을 가산한다. 항목은 서버의 `observationId`, `observationRevision`(초기 1), `attachmentId`, `problemId`, 안전하게 처리한 관찰 문구와 `state`(`UNCONFIRMED|CONFIRMED|INCORRECT|UNKNOWN`)다. 서버는 해당 저장 메시지의 현재 접근 가능한 확인 요청만 반환하고 응답 후 상태를 재조회할 수 있게 한다. 목록 생략은 `[]`다. 담당자 조회는 이 문의자용 DTO를 그대로 재사용하지 않는다. 이 조회는 이미지 기능 설정이 켜진 경우 구현됐으며 실제 관찰을 만드는 분석 경로는 아직 차단돼 있다.
- 사용자 응답 `POST /api/v2/inquiries/{inquiryId}/image-observation-responses`를 이미지 기능 설정이 켜진 경우 제공한다. 본문은 `{requestId, expectedInquiryVersion, responses:[{observationId, expectedObservationRevision, decision}]}`이며 `decision`은 `CONFIRMED`, `INCORRECT`, `UNKNOWN` 중 하나다. 1~15개, 같은 observationId 중복은 거부한다. 문의자·해당 문의·현재 공개된 확인 요청·각 관찰 차수를 한 거래에서 확인하고 모두 적용하거나 모두 거부한다. 응답은 `CommandReceipt`의 `INQUIRY`다. 문의 버전 또는 관찰 차수 불일치는 409(후자는 `OBSERVATION_VERSION_CONFLICT`), 다른 사람의 관찰은 존재를 감춘 404다. 응답 수신과 이력 조회는 격리 DB에서 검증했으며 화면과 실제 AI 연결은 별도 작업이다.
- `CONFIRMED`도 시스템 상태의 진실을 증명하지 않으며 **문의자가 해당 이미지 관찰을 확인했다는 사실**만 기록한다. `INCORRECT`·`UNKNOWN`은 확인 사실로 승격하지 않는다. 서버는 사용자 응답과 출처를 보존하고 문의 버전을 올려 오래된 결과를 대체한다. 배정된 문제의 자동 새 티켓·재배정·해결은 발생시키지 않는다. 다른 내용을 정정하려면 기존 텍스트 메시지로 보낸다.
- 누락 이미지·digest 불일치·권한 실패를 이미지 없는 정상 실행으로 대체하지 않는다. 이미지 토큰은 기존 누적 입력 예산에 포함하고 한 실행의 이미지 수·크기·기한·재시도를 제한한다. 가림 이미지도 모델 제공자에게 전달되므로 `store=false`만으로 모든 외부 보존이 없다고 가정하지 않는다.
- AI의 `WireModel`은 미정의 필드를 거부한다. 배포는 (1) 새 결과 필드를 수용하고 내부 조회를 제공하되 이미지 전송은 꺼 둔 Spring, (2) 기존 입력과 새 이미지 입력을 모두 수용하고 이미지가 있을 때만 새 결과를 내는 AI, (3) Spring의 이미지 입력 전송 활성화, (4) 이미지 화면 노출 순서로 제안한다. 구형 Spring 요청과 이미지 없는 입력은 새 AI에서 그대로 수용한다. 롤백할 때는 먼저 이미지 전송을 끄고 진행 중 run을 안전하게 정리해야 하며, 새 결과를 처리하지 못하는 Spring으로 되돌리기 전에 AI 결과 호환도 확인한다. 기능 스위치의 실제 설정 이름은 구현 때 정한다. 이미지 입력·출력의 추적과 사례 생성 경계를 따로 검증한다.

## 7. 완료를 관찰할 시나리오

1. 첫 문의와 후속 메시지에서 여러 이미지의 가림 PNG만 전송하고, 새로고침과 서버 재시작 뒤 문의자가 같은 이미지를 조회한다.
2. 같은 업로드/메시지 요청의 동시 전송, HTTP 응답 유실, S3 성공 후 DB 오류와 정리 경합에서 중복 이미지·메시지·객체 삭제가 발생하지 않는다.
3. 타 사용자, 다른 문제의 담당자, 권한 회수된 담당자와 다른 run은 이미지 존재·바이트를 얻지 못한다. 복합 이미지 대상 미확정은 비공개다.
4. 손상·위장·픽셀/용량 초과와 저장소 장애는 안전하게 실패하고, 입력 및 이미 저장된 업무를 유지한다.
5. AI는 가림 이미지와 텍스트를 실제로 함께 입력받되 이미지 유래 내용을 텍스트 원문 근거로 위장하지 않는다. 이미지 속 권한 변경·지시에도 서버 권한과 업무 상태가 바뀌지 않는다.
6. 형식이 다른 개인정보·이름·기존 이력은 자동 가림이 보장되지 않음을 사용자와 검증 결과에 명시한다. 합성 데이터 기반 단위·통합·실제 모델·실제 S3·브라우저 E2E를 구분해 기록한다.

## 8. 구현 단계에서 검증할 상세

- 여러 문제에 같은 이미지 전체를 공개할 때의 확인 UX와 링크 차수·정정 이력의 데이터 배치.
- 응답 유실 후 operation 조회, 413의 실제 프록시 매핑과 삭제·늦은 S3 쓰기 경합을 안전하게 복구하는 구체 알고리즘.
- 관찰과 사용자 응답의 물리 저장 구조, 텍스트 질문 묶음과 관찰 확인 UI를 한 번으로 집계하는 구현 및 기존 티켓·사례 투영 범위.
- 운영 버킷·리전·IAM·암호화·백업/수명·비용, 프록시/서버 크기 제한과 S3 실제 연결·복구 검증.

위는 안전 조건을 만족할 구현 상세이며 이미 채택된 코드 또는 외부 환경 설정이 아니다.
