# F010 티켓 생성 부분 실패·재시도

상태: PRD 1.44 목표 명세 · 팀 기획 합의 / 상세 계약·구현·검증 별도.

## 1. 목표와 범위

복합 문의의 실패한 생성 작업을 기존 성공 결과와 분리하고 중복 없이 복구한다.

근거: [PRD](../../docs/PRD.md), [API](../../docs/API.md), [데이터](../../docs/DATA.md), [목표 공통 계약](../contracts/TARGET_CONTRACT.md).

## 2. 인수 조건

- **F010-TARGET-01:** 성공 티켓과 실패·저장 결과 미확인 문제를 분리하고 성공한 티켓을 유지한다.
- **F010-TARGET-02:** 재시도 전 Spring은 해당 문제의 기존 저장 결과와 현재 문의 버전을 확인한다.
- **F010-TARGET-03:** 이미 저장된 티켓이 있으면 기존 결과를 반환한다. 저장 여부를 확인할 수 없으면 미확인으로 유지하고 새 티켓을 만들지 않는다.
- **F010-TARGET-04:** 실제 미생성으로 확인된 작업에 한해 보존된 제안을 사용하거나 Ticket이 제안을 다시 만들어 같은 업무 작업으로 재시도한다. Spring이 저장을 확정한다.
- **F010-TARGET-05:** 재시도 접수를 복구 완료로 표시하지 않는다. 전용 운영 복구 화면과 자동 재시도는 필수가 아니다.
- **F010-TARGET-06:** 재시도 권한·조작·작업 식별자와 결과 조회는 구현 계약에서 정한다.

## 화면과 사용자 흐름

### 화면

- 문의별 문제 결과 영역에서 성공·실패·결과 미확인을 구분한다. 전용 운영 복구 화면은 필수가 아니다.

### 흐름

1. 복합 문의의 일부 티켓만 저장됐거나 결과를 확인하지 못한다.
2. Spring이 각 작업의 저장 결과와 최신 문의 버전을 확인한다.
3. 실제 미생성인 작업만 같은 업무 작업으로 복구하고 확정된 결과를 조회한다.

## 상세 인수 조건과 예외

- **F010-DETAIL-01 성공 유지:** 문제 A가 성공하고 B가 실패해도 A의 티켓·배정은 보존한다.
- **F010-DETAIL-02 저장 성공 후 응답 유실:** 티켓이 저장됐지만 응답이 유실됐으면 재시도 확인 시 기존 티켓을 반환하고 새 티켓을 만들지 않는다.
- **F010-DETAIL-03 확인 불가:** DB 또는 저장 결과 조회가 실패해 기존 여부를 모르면 미확인으로 유지한다. 미생성으로 단정해 재생성하지 않는다.
- **F010-DETAIL-04 미생성 확인:** 실제 미생성으로 확인된 작업은 현재 문의 버전과 권한을 검사한 뒤 보존된 제안을 사용하거나 Ticket이 제안을 다시 만든다.
- **F010-DETAIL-05 동시 재시도:** 같은 문제의 동일 업무 작업이 동시에 재시도돼도 중복 티켓을 만들지 않는다. 식별자·동시성·DB 제약은 구현 전 정한다.
- **F010-DETAIL-06 접수와 완료:** 재시도 요청을 접수했다고 복구 완료로 표시하지 않는다. 저장된 티켓을 확인한 뒤 결과를 갱신한다.
- **F010-DETAIL-07 오래된 입력:** 원 문의 버전이 바뀌었으면 오래된 제안을 무조건 저장하지 않고 현재 상태에 맞는 처리 계약을 따른다.

## 계약·화면 상태

- 분석 실행 재시도와 티켓 저장 작업 복구는 별개다. 작업 식별자·결과 조회·권한·에러 코드 및 재시도 조작을 팀이 정한다.

| 상태 | 사용자에게 보이는 동작 |
|---|---|
| 로딩·처리 중 | 현재 요청의 진행을 표시하고 저장·완료로 단정하지 않는다. |
| 정상 결과 | 서버가 확정한 값만 표시한다. |
| 빈 결과 | 정상 조회된 0건을 안내한다. |
| 실패·결과 미확인 | 실패와 저장 미확인을 구분하고 입력·이미 저장된 결과를 보존한다. |
| 권한 없음 | 서버가 접근을 거부하고 허용되지 않은 내용을 표시하지 않는다. |

## 범위·연관 기능

- 전용 복구 화면·자동 재시도는 제외한다. 실제 실패 원인과 내부 오류를 문의자에게 그대로 노출하지 않는다.

## 현재 구현과 남은 작업

기존 Mock의 일부 실패 표시는 실제 저장 확인이나 복구 구현을 뜻하지 않는다.

기존 코드·테스트의 인수 조건 번호는 이전 기준이며 목표 조건과 구분한다. 목표 AC는 실제 구현·검증 완료를 뜻하지 않는다. 실제 구현 범위는 서비스 코드와 실행 안내에서 확인한다.

기능의 목표 인수 조건은 구현·통합 검증을 대신하지 않는다. 새 API 경로·필드·enum·권한과 테스트 연결은 담당자 간 계약 확정 후 진행한다.
