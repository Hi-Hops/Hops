# F010 티켓 생성 부분 실패·재시도

상태: PRD 1.44 목표 명세 · 팀 기획 합의 / hops-system-1 구체 계약안 추가·팀 리뷰/구현/검증 별도.

## 1. 목표와 범위

복합 문의의 실패한 생성 작업을 기존 성공 결과와 분리하고 중복 없이 복구한다.

근거: [PRD](../../docs/PRD.md), [API](../../docs/API.md), [데이터](../../docs/DATA.md), [목표 공통 계약](../contracts/TARGET_CONTRACT.md).

## 2. 인수 조건

- **F010-TARGET-01:** 성공 티켓과 실패·저장 결과 미확인 문제를 분리하고 성공한 티켓을 유지한다.
- **F010-TARGET-02:** 재시도 전 Spring은 해당 문제의 기존 저장 결과와 현재 문의 버전을 확인한다.
- **F010-TARGET-03:** 이미 저장된 티켓이 있으면 기존 결과를 반환한다. 저장 여부를 확인할 수 없으면 미확인으로 유지하고 새 티켓을 만들지 않는다.
- **F010-TARGET-04:** 실제 미생성으로 확인된 작업에 한해 보존된 제안을 사용하거나 Ticket이 제안을 다시 만들어 같은 업무 작업으로 재시도한다. Spring이 저장을 확정한다.
- **F010-TARGET-05:** 재시도 접수를 복구 완료로 표시하지 않는다. 전용 운영 복구 화면과 자동 재시도는 필수가 아니다.
- **F010-TARGET-06:** 재시도 권한·조작·workItemId와 결과 조회는 아래 hops-system-1 계약안에서 구체화한다.

## 화면과 사용자 흐름

### 화면

- 문의별 문제 결과 영역에서 성공·실패·결과 미확인을 구분한다. 전용 운영 복구 화면은 필수가 아니다.

### 흐름

1. 복합 문의의 일부 티켓만 저장됐거나 결과를 확인하지 못한다.
2. Spring이 각 작업의 저장 결과와 최신 문의 버전을 확인한다.
3. 실제 미생성인 작업만 같은 업무 작업으로 복구하고 확정된 결과를 조회한다.

## 상세 인수 조건과 예외

- **F010-DETAIL-01 성공 유지:** 문제 A가 성공하고 B가 실패해도 A의 티켓·배정은 보존한다.
- **F010-DETAIL-02 저장 성공 후 응답 유실:** 티켓이 저장됐지만 응답이 유실됐으면 재시도 확인 시 기존 티켓을 반환하고 새 티켓을 만들지 않는다.
- **F010-DETAIL-03 확인 불가:** DB 또는 저장 결과 조회가 실패해 기존 여부를 모르면 미확인으로 유지한다. 미생성으로 단정해 재생성하지 않는다.
- **F010-DETAIL-04 미생성 확인:** 실제 미생성으로 확인된 작업은 현재 문의 버전과 권한을 검사한 뒤 보존된 제안을 사용하거나 Ticket이 제안을 다시 만든다.
- **F010-DETAIL-05 동시 재시도:** 같은 문제의 동일 업무 작업이 동시에 재시도돼도 중복 티켓을 만들지 않는다. workItem 잠금·문제/작업별 티켓 유일 제약은 DATA의 저장 제약안을 따른다.
- **F010-DETAIL-06 접수와 완료:** 재시도 요청을 접수했다고 복구 완료로 표시하지 않는다. 저장된 티켓을 확인한 뒤 결과를 갱신한다.
- **F010-DETAIL-07 오래된 입력:** 원 문의 버전이 바뀌었으면 오래된 제안을 무조건 저장하지 않고 현재 상태에 맞는 처리 계약을 따른다.

## 계약·화면 상태

신규 `hops-system-1` 팀 리뷰용 구체 계약안이다. 필드·enum은 [DATA_TYPES](../contracts/DATA_TYPES.md#신규-계약-hops-system-1), REST·오류·SSE·멱등성은 [WIRE_CONTRACT 12절](../contracts/WIRE_CONTRACT.md#12-신규-계약-hops-system-1), 업무 전이는 [TARGET_CONTRACT](../contracts/TARGET_CONTRACT.md)가 정본이다. 아래 내용은 구현·팀 승인·통합 완료 표시가 아니다.

| 조작 | 계약·검증 |
|---|---|
| 결과 확인 | GET work-items/{workItemId}; NOT_CREATED는 서버의 롤백/미저장 확인이며 404/timeout에서 추정하지 않음 |
| 생성 재시도 | CreationRetryCommand는 소유자만, 동일 workItemId·현재 inquiryVersion 검사 |
| 성공 보존 | STORED면 기존 티켓 반환. 티켓/배정의 문제별 거래·유일 제약으로 경합 방어 |
| 분석 재시도와 구분 | run retry는 새 runId, work-item retry는 같은 생성 업무. UI 버튼과 오류를 구별 |

| 화면 상태 | 관찰 가능한 동작 |
|---|---|
| PENDING/UNKNOWN | 결과 확인만 제공, 생성 재시도 없음 |
| NOT_CREATED | 현재 버전 재조회 후 실패 항목 재시도 |
| STORED | 원 티켓 표시·복구 완료. 다른 성공 문제 유지 |
| 접수 202·충돌 | 요청 접수와 성공 구분·최신 상태 확인 |

## hops-system-1 검증 시나리오

- **F010-CONTRACT-01:** 저장 후 응답 유실은 결과 확인에서 기존 티켓 하나를 반환한다.
- **F010-CONTRACT-02:** 동일 작업에 동시에 다른 HTTP 재시도 키를 보내도 티켓·초기 배정은 하나다.
- **F010-CONTRACT-03:** DB 조회 실패는 UNKNOWN이며 재시도 호출도 새 티켓을 만들지 않는다.
- **F010-CONTRACT-04:** 실패 작업을 재시도할 때 문의 버전이 바뀌면 오래된 제안을 저장하지 않는다.

문서/JSON 검사·Mock·실제 서버 저장/권한·실제 AI/검색·브라우저 E2E를 분리해 결과를 기록한다. 기존 테스트의 이전 AC 번호를 새 시나리오 통과로 간주하지 않는다.

## 범위·연관 기능

- 전용 복구 화면·자동 재시도는 제외한다. 실제 실패 원인과 내부 오류를 문의자에게 그대로 노출하지 않는다.

## 현재 구현과 남은 작업

기존 Mock의 일부 실패 표시는 실제 저장 확인이나 복구 구현을 뜻하지 않는다.

기존 코드·테스트의 인수 조건 번호는 이전 기준이며 목표 조건과 구분한다. 목표 AC는 실제 구현·검증 완료를 뜻하지 않는다. 실제 구현 범위는 서비스 코드와 실행 안내에서 확인한다.

기능의 목표 인수 조건은 구현·통합 검증을 대신하지 않는다. hops-system-1 계약안의 담당자 리뷰·승인 후 코드·테스트를 전환한다. 현재 구현을 문서만으로 완료 처리하지 않는다.
