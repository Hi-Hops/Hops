# F010 생성 실패 목록·재시도와 역할별 권한

상태: 개발 기준 확정 / 구현·검증 별도 · 범위: 후속 · 독립 실패 목록·운영 기술 복구 UI는 MVP 제외 · 담당: frontend(화면) · 협의: backend(조회·재시도·권한)
근거: PRD 2, 4.7, 4.8, 8.3 · API 2.1 `GET /api/creation-failures`, 2.2 `/api/operator/recovery-cases` · DATA 4, 5 · ERD `recovery_case`, `member_role`

## 확정 범위와 남은 작업 (2026-10-25)

전체 독립 목록·운영 기술 복구 UI는 후속이다. 현재 문의 결과의 부분 실패 카드는 F005에서 표시하고, 문의자 분석 재시도는 F003의 run 재시도 계약을 따른다. RecoveryStatus만 DATA_TYPES에 정의했으며 역할별 필드·복구 API·예산은 Q-BE-15에서 설계한다.

정확한 타입·enum은 [DATA_TYPES](../contracts/DATA_TYPES.md), 정책은 [WIRE_CONTRACT 10절](../contracts/WIRE_CONTRACT.md#10-인증재접속최신-대화분석-재시도-추가-프로필), 담당 구현·미검증은 [11절](../contracts/WIRE_CONTRACT.md#11-담당별-구현과-검증-상태)을 따른다. 확정은 개발 기준 선택이며 팀 리뷰/병합·서비스 구현 완료가 아니다.

## 1. 목표

티켓을 만들지 못한 작업을 허용된 관리자가 티켓 목록과 따로 확인한다. 업무 관리자와 운영 관리자에게는 각 역할에 맞는 정보만 보이고, 기술 재시도는 운영 관리자만 할 수 있다. 재시도를 접수한 것과 복구가 끝난 것을 다른 상태로 보여 준다. (PRD 4.7, 4.8 · API 2.1)

## 2. 범위 판단

| 항목 | 원본 문서 | 이슈 #31 |
|---|---|---|
| 생성 실패 목록 | API 2.1(MVP) "업무 관리자·운영 관리자에게 각 역할에 맞는 정보만 제공. 기술 재시도 권한은 운영 관리자" | "허용된 관리자 생성 실패 목록" |
| 재시도 접수와 복구 완료 | API 2.2(후속) `POST /api/operator/recovery-cases/{id}/retries` "재시도 접수는 복구 완료가 아님", PRD 8.3 "기술 복구 화면" 후속 | "재시도 접수와 복구 완료 구분" |
| 표시·재시도 권한 구분 | API 2.1, DATA 5 "운영 관리자는 실행·기술 복구 정보만 조회/재시도하고, 업무 관리자는 배정·정정·재결합을 확정" | "업무 관리자·운영 관리자의 표시/재시도 권한을 구분" |

MVP 2.1 표에는 생성 실패를 재시도하는 경로가 없다. `POST /api/runs/{id}/retries`는 실행 재시도이고 작업별 티켓 생성 재시도와 같은지 정해지지 않았다(Q-BE-8, Q-BE-15). 따라서 F010-AC01~AC04는 MVP, F010-AC05~AC08은 Q-ALL-7 확인 대상이다.

## 3. 화면

| 화면 | 경로(제안) | 접근 |
|---|---|---|
| 생성 실패 목록(업무 관리자) | `/admin/tickets`의 생성 실패 영역(F007-AC04) | 업무 관리자 |
| 생성 실패 목록·재시도(운영 관리자) | `/operator/recovery-cases` | 운영 관리자 |

운영 관리자 화면 전체(실행 이력·상세)는 PRD 8.3 후속이며 이 스펙은 생성 실패 항목과 재시도만 다룬다.

## 4. 사용자 시나리오

1. 업무 관리자가 관리자 화면에서 "티켓을 만들지 못한 작업" 목록을 보고, 어떤 문의의 어떤 문제가 남아 있는지 확인한다. 재시도 버튼은 보이지 않는다.
2. 운영 관리자가 복구 화면에서 같은 항목의 오류 코드와 재시도 이력을 보고 "다시 시도"를 누른다.
3. 항목이 "재시도 접수됨"으로 바뀐다. 서버가 티켓을 만들면 "복구 완료"와 생성된 티켓이 연결되어 보인다.
4. 문의자의 결과 카드(F005)에서도 그 문제가 실패에서 티켓 카드로 바뀐다.

## 5. 인수 조건

**목록과 역할별 표시 (MVP · API 2.1)**
- **F010-AC01 허용된 관리자만**
  `GET /api/creation-failures`는 업무 관리자(`BIZ_ADMIN`)와 운영 관리자(`AGENT_OPS_ADMIN`)만 화면에서 연다. 다른 사용자는 권한 없음 화면으로 보내고, 서버가 403을 돌려줘도 같은 화면을 쓴다. 문의자는 F005-AC04의 자기 문의 안 실패 표시만 본다. (API 2.1 · ERD `member_role.role` · F001-AC04)
- **F010-AC02 역할별 정보**
  화면은 서버가 돌려준 필드만 표시하고, 역할에 따라 필드를 숨기는 판단을 화면에서 하지 않는다. 업무 관리자에게 기술 오류 상세가 오지 않으면 그 칸 자체를 두지 않는다. (API 2.1 "각 역할에 맞는 정보만 제공" · 역할별 필드 Q-BE-15)
- **F010-AC03 티켓과 구분**
  생성 실패 항목은 티켓 목록과 다른 영역에 두고, 티켓 상세로 연결하지 않는다. 원본 문의·문제·작업 식별자를 보여 준다. (PRD 4.7 "생성 실패 항목은 티켓이 아직 없을 수 있으므로 기존 티켓 상세와 구분" · API 2.1 `workItemId, problemId, status, errorCode`)
- **F010-AC04 업무 관리자에게 재시도 없음**
  업무 관리자 화면에는 재시도 버튼을 두지 않는다. 업무 판단(부서·유형) 수정은 이 화면에서 하지 않고, 후속 재검토 화면으로 둔다. (API 2.1 "기술 재시도 권한은 운영 관리자" · PRD 4.7 "기술 복구는 … 업무 관리자의 재검토와 혼동하지 않는다")

**재시도와 복구 완료 (이슈 #31 · API 2.2 후속, Q-ALL-7)**
- **F010-AC05 운영 관리자 재시도**
  Given 운영 관리자 · When 미처리 항목에서 "다시 시도"를 누르면 · Then 재시도 요청을 보내고, 응답 전에는 버튼을 막아 두 번 보내지 않는다. 경로는 정해지지 않았다. (PRD 4.8 · API 2.2 `POST /api/operator/recovery-cases/{id}/retries` · 생성 실패 항목과 복구 항목의 관계 Q-BE-15)
- **F010-AC06 접수와 완료 구분**
  재시도 응답을 받으면 "재시도 접수됨"으로 표시하고 "복구 완료"로 표시하지 않는다. 서버가 복구 완료를 저장한 뒤 재조회했을 때만 "복구 완료"와 생성된 티켓 링크를 보여 준다. 계속 실패하면 원인과 현재 상태를 보여 준다. (PRD 4.8 "재시도 요청 접수를 복구 완료로 표시하지 않는다" · DATA 5 · ERD `recovery_case.recovery_status`)
- **F010-AC07 중복 재시도**
  네트워크 오류 뒤 다시 보낼 때는 같은 요청 키를 쓴다. 이미 성공한 작업이면 서버가 알려 준 결과(기존 티켓)를 보여 준다(중복 생성 방지는 서버 책임). 멱등 키 전달 방식은 정해지지 않았다. (PRD 4.8 · DATA 5 "성공한 작업은 재생성하지 않는다" · Q-BE-15)
- **F010-AC08 복구 결과 반영**
  복구가 끝나 `state.changed`를 받거나 재접속하면 생성 실패 목록과 관련 문의 결과를 REST로 다시 조회한다. 문의자 화면(F005)의 해당 문제도 실패에서 티켓 카드로 바뀐다. (API 2.4 · PRD 4.11 · 이슈 #31 "실시간 연결 유실 후 저장 상태 복구")

## 6. 계약(화면이 기대하는 값)

| 용도 | 경로·이벤트 | 판정 | 비고 |
|---|---|---|---|
| 생성 실패 목록 | `GET /api/creation-failures` | 초안 | API 2.1. 역할별 응답 필드 → Q-BE-15, 페이지 → Q-BE-5 |
| 실패 항목 | `workItemId, problemId, status, errorCode` | 초안 | API 2.1 제안. 생성 작업 저장소 후보·실제 DDL 구현 필요(Q-BE-4) |
| 기술 재시도 | `POST /api/operator/recovery-cases/{id}/retries` | 초안(후속) | API 2.2. 생성 실패 ID와 recoveryCaseId 관계·복구 경로는 후속 상세(Q-BE-15) |
| 실행 재시도(참조) | `POST /api/runs/{id}/retries` | 개발 기준 확정 | 문의자 분석 재시도는 F003/Q-BE-8, 운영 작업 복구와 별개 |
| 복구 상태 값 | RecoveryStatus(DATA_TYPES) | 개발 기준 확정 | 후속 복구 API/전이 구현은 Q-BE-15 |
| 역할 값 | `BIZ_ADMIN`, `AGENT_OPS_ADMIN` | 초안 | ERD `member_role.role` → Q-ALL-5 |

## 7. 화면 상태

```text
미처리 → (운영 관리자) 재시도 요청 중 → 재시도 접수됨 → [서버 저장 후 재조회] → 복구 완료(티켓 연결)
                                                                         → 계속 실패(원인·현재 상태)
       → (업무 관리자) 조회만
```

## 8. 범위 밖

운영 관리자의 실행 이력·실행 상세, 배정 저장 실패·재이관 기술 실패 복구(PRD 4.8, 8.3 후속), 자동 재시도 정책, 문의자의 생성 실패 재시도(F005-AC05, Q-BE-8).

## 9. 막히는 정도

- 목으로 진행 가능: 목록, 역할별 화면 분기, 접수·완료 상태 표시.
- 구현·검증 상태: 위 확정 범위와 공통 계약 11절을 따른다. 후속 상세 설계는 QUESTIONS의 해당 ID로 추적한다.
