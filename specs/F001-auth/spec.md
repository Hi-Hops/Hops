# F001 JWT 로그인·인증 만료·권한 이동

상태: 초안 · 범위: MVP · 담당: frontend(화면) · 협의: backend(인증), infra(소켓 인증)
근거: PRD 2, 4.2, 4.11, 8.5 · API 1, 2.1, 2.5 · DATA 5 · ERD `member`, `member_role`

## 1. 목표

자체 계정으로 로그인하고, 역할에 맞는 화면에만 들어간다. 토큰이 만료돼도 입력과 저장된 문의를 잃지 않는다. (PRD 4.2)

## 2. 화면

| 화면 | 경로(제안) | 접근 |
|---|---|---|
| 로그인 | `/login` | 비로그인 |
| 공통 헤더(사용자 이름·부서·로그아웃) | 모든 로그인 화면 | 로그인 사용자 |
| 권한 없음 / 찾을 수 없음 | `/403`, `/404` | 전체 |

## 3. 사용자 시나리오

1. 문의자가 로그인 ID와 비밀번호로 로그인하면 메인으로 이동한다.
2. 업무 관리자는 로그인 후 관리자 화면에 들어갈 수 있고, 문의자는 들어갈 수 없다.
3. 채팅 입력 중 토큰이 만료되면, 입력을 지키면서 다시 로그인하라는 안내를 본다. 다시 로그인하면 같은 문의를 이어간다.
4. 로그아웃하면 인증 정보가 지워지고 채팅 연결이 끊긴다.

## 4. 인수 조건

- **F001-AC01 로그인 성공**
  Given 유효한 계정 · When 로그인 ID·비밀번호로 로그인하면 · Then 액세스 JWT를 받고, `GET /api/auth/me`로 받은 이름·부서를 헤더에 표시하며, 역할별 첫 화면으로 이동한다. (API 2.1 · 첫 화면은 Q-FE-1)
- **F001-AC02 로그인 실패**
  Given 틀린 비밀번호 · When 로그인하면 · Then 401을 받고 로그인 화면에서 원인을 안내한다. 입력한 로그인 ID는 지우지 않는다. (PRD 4.2 · ID 유지는 프론트 제안)
- **F001-AC03 권한 판단의 원본**
  화면의 메뉴 노출과 이동 가능 여부는 `/api/auth/me`의 역할·부서로 정한다. 토큰을 브라우저에서 풀어 읽은 값으로 권한을 정하지 않는다. 부서명은 표시용으로만 쓴다. (API 2.5)
- **F001-AC04 역할 밖 화면**
  Given 문의자 · When 관리자 화면 주소로 들어가면 · Then 내용을 보여 주지 않고 권한 없음 화면으로 이동해 접근 가능한 화면을 안내한다. 서버가 403을 돌려줘도 같은 화면을 쓴다. (PRD 4.11)
- **F001-AC05 토큰 만료**
  Given 로그인 상태에서 토큰 만료 · When REST가 401을 받거나 소켓이 인증 실패로 끊기면 · Then 합의된 갱신 정책을 적용하고(Q-BE-2), 갱신할 수 없으면 입력을 보존한 채 재로그인을 안내한다. 재로그인 뒤 원래 화면으로 돌아가 다시 연결·구독한다(F002). (PRD 4.2)
  개발 프로필은 Access Token 만료 시 단일 refresh 요청을 공유한다. Refresh Token 만료·폐기 또는 서버가 AUTH_CONTEXT_CHANGED로 확인한 부서/역할 변경은 재로그인한다. 단순 권한 부족 403은 권한 안내, 갱신 통신 장애는 입력을 유지한 재연결 안내다. WIRE_CONTRACT 10절을 따른다.
- **F001-AC06 미전송 입력 재전송**
  같은 사용자로 재로그인한 뒤 동일한 미확인 요청을 다시 보낼 때는 사용자 확인 후 같은 `requestId`를 쓴다. 내용·대상 버전을 고친 새 요청은 새 키를 쓴다. 다른 계정 로그인·로그아웃 시 이전 사용자 캐시·초안·대기 명령·구독을 정리한다. (PRD 4.2 · API 1)
- **F001-AC07 만료가 작업 취소로 보이지 않음**
  인증 만료나 소켓 종료 때 이미 접수된 문의·분석을 "취소됨"이나 "실패"로 표시하지 않는다. 재로그인 후 REST로 실제 상태를 확인한다. (PRD 4.2)
- **F001-AC08 로그아웃**
  When 로그아웃하면 · Then `POST /api/auth/logout`을 호출하고, 브라우저의 인증 정보를 지우고, Socket.IO 연결을 끊고, 로그인 화면으로 이동한다. 호출이 실패해도 브라우저 정리는 한다. (API 2.1 · 실패 시 정리는 프론트 제안)
- **F001-AC09 인증 정보 노출 방지**
  액세스 토큰과 비밀번호를 주소(URL)·화면·콘솔 로그·오류 보고에 남기지 않는다. 로그인 실패 뒤에도 비밀번호 입력값은 지운다. 토큰 보관 위치는 Q-BE-2 결정을 따른다. (API 2.5 "불필요한 개인정보를 추가하지 않는다" · DATA 5 "JWT 원문·서명키는 업무 JSON·로그·이벤트 이력에 저장하지 않는다" · 화면 규칙은 프론트 제안)

## 5. 계약(화면이 기대하는 값)

공통 필드·필수/nullable·wire 표현의 원본은 [데이터 타입·필드 문서](../contracts/DATA_TYPES.md)다. 아래는 이번 Mock 프로필의 연결표이며 팀 승인·운영 미정 질문의 확정을 뜻하지 않는다. 기존 API의 최소 의미를 구체화한 제안이다.

| 용도 | 경로 | 공통 Mock 타입 | 미정 추적 |
|---|---|---|---|
| 로그인 | POST /api/auth/login | LoginRequest → LoginResponse | Q-BE-1/2 |
| 현재 사용자 | GET /api/auth/me | CurrentUser | Q-BE-1, Q-ALL-5 |
| 로그아웃 | POST /api/auth/logout | 204, 본문 없음 | 서버 폐기/CSRF Q-BE-2 |
| 부서 | GET /api/departments | Department[] | isRoutable 추가 제안 Q-ALL-5 |
| 오류 | REST 오류 | ApiErrorBody | Q-ALL-4 |

Mock은 메모리 가짜 Access/Refresh 세션으로 갱신·만료를 재현한다. 실제 HttpOnly 쿠키·JWT·회전/폐기·CSRF 검증은 Spring 구현 및 통합 검증이 필요하다. 임시 live는 POST /api/auth/refresh를 호출하며 반환 타입은 LoginResponse다. 사용자 이름은 CurrentUser이며 기존 Me와 같은 의미다.

## 6. 화면 상태

```text
입력 대기 → 로그인 중 → 성공: /api/auth/me 조회 → 역할별 첫 화면
                     → 401: 안내, 로그인 ID 유지
                     → 503·네트워크: 재시도 안내
로그인됨 → 토큰 만료 → [갱신 정책 Q-BE-2] → 실패 시 재로그인 안내(입력 보존) → 재로그인 → 원래 화면·재연결
```

## 7. 범위 밖

회원가입, 비밀번호 찾기·변경, 부서·역할 변경 중 실시간 권한 회수의 서버 정책(화면의 최소 처리는 F002-AC11).

## 8. 막히는 정도

- 목으로 진행 가능: 로그인 화면, 헤더, 권한 없음·찾을 수 없음, 라우트 이동 규칙.
- 결정 전 구현 보류: 토큰 저장 위치와 갱신 흐름(Q-BE-2), 로그인 응답 처리(Q-BE-1).

## 공통 Mock 계약 (2026-10-23)

이 기능의 Mock 전송 데이터는 [공통 데이터 타입 문서](../contracts/DATA_TYPES.md)와 [요청·응답 연결표](../contracts/WIRE_CONTRACT.md#8-작업별-데이터-타입-연결)을 따른다. 공용 입력·응답·이벤트 예시는 [Mock 시나리오](../mocks/README.md)를 사용한다. 이 절은 Mock 개발용 제안이며 기존 계약 표의 미정 항목이나 팀 승인 상태를 확정으로 바꾸지 않는다. 서버 저장·권한·AI 품질 완료를 뜻하지 않는다.
