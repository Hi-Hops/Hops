# 프론트엔드 기능 스펙

상태: **개발 기준 확정 · 팀 리뷰/구현 검증 별도** · 작성 2026-10-21 · 범위: React 화면의 MVP 기능

이 폴더는 React 화면을 기능별로 "무엇을 만들고 언제 완료로 보는가"를 정리한다. 제품 정책은 [PRD](../docs/PRD.md), 통신 계약안은 [API](../docs/API.md), 저장 규칙은 [DATA](../docs/DATA.md)·[ERD 설명](../docs/ERD_설명.md)이 원본이다. 스펙은 원본 문장을 복제하지 않고 절 번호로 가리킨다. 원본과 스펙이 다르면 원본을 따르고 스펙을 고친다.

스펙을 코드로 옮길 때의 구조·문법·통신 타입·공통 컴포넌트·작업 순서는 [프론트엔드 개발 기준](../docs/frontend/README.md)을 따른다.

2026-10-25 추천 정책을 개발 기준으로 확정했다. [QUESTIONS](QUESTIONS.md)는 결정 상태·담당 설계·후속 상세 설계를 구분하며 팀 리뷰/병합·실제 구현은 별도다.

## 공통 Mock 계약 진입점

로그인·채팅·부서 티켓 조회의 네 영역 공통 JSON 구조는 [공통 계약](contracts/README.md), Mock 자료 안내는 [Mock 안내](mocks/README.md)를 참조한다. 필드·데이터 타입·입출력은 문서로 명시하며 각 서비스가 필요한 타입을 구현한다. 확정한 정책과 담당 구현/검증은 WIRE_CONTRACT 10·11절로 구분한다.

## 범위

- 이 스펙은 **프론트엔드(React) 화면의 완료 기준**이다. 인수 조건은 화면에서 관찰할 수 있는 동작만 쓴다.
- Spring·Node.js Socket.IO 서버·Python 에이전트의 완료 기준(저장·중복 방지·권한 검사·분석 품질)은 포함하지 않는다. 각 담당이 정하며, 이 스펙이 대신 정하지 않는다.
- 각 스펙의 "계약" 표는 화면이 기대하는 REST 응답과 Socket.IO 이벤트다. 현재 확정값은 공통 계약 10절을 따른다. 추가 변경은 [API](../docs/API.md)·영향 담당자의 리뷰를 거친다. 이슈 #22의 실제 완료 상태와 구분한다.
- 각 스펙 머리의 "협의"는 계약을 함께 맞출 담당이다. 그 담당의 작업 범위를 뜻하지 않는다.

MVP 밖으로 둔 것: 해결 신고·해결 확인, 숨기기·복원, 담당자 처리(가져오기·처리 완료)·재이관, 장애 그룹, 알림, 통계, 운영 관리자의 실행 이력·상세(PRD 8.2 "재이관·최종 처리·알림 전체를 MVP 완료 조건에 포함하지 않는다", 8.3).

이슈 작업 목록과 스펙·인수 조건의 대응은 [이슈 대응표](ISSUE_MAP.md)에 정리한다. 공통 계약 질문과 이슈 #22·PR #38의 관계는 [합의 질문](QUESTIONS.md) 0절에 있다.

## 스펙 작성 규칙

- 한 기능 = 한 폴더(`Fnnn-이름/spec.md`). 이슈 하나·PR 하나와 맞춘다.
- 번호는 [Git 컨벤션](../GIT_CONVENTION.md) 3절의 커밋 예시 형식을 따른다. 기능은 세 자리 `F001`, 인수 조건은 두 자리 `F001-AC04`다. 커밋 본문의 `명세:` 줄에 이 번호를 쓴다.
- Git 컨벤션 예시의 요구사항 번호(`F001-R07`)는 아직 쓰지 않는다. 요구사항은 각 스펙의 "목표"와 인수 조건으로 표현한다.
- 이 폴더의 `F001`~`F010`은 프론트 스펙 번호다. 다른 담당이 같은 형식의 스펙을 만들면 번호가 겹치지 않도록 팀에서 범위를 나눈다.
- 인수 조건은 `Fnnn-ACnn`으로 번호를 붙이고 Given/When/Then으로 화면에서 확인할 수 있게 쓴다. 테스트 이름과 하나씩 대응시킨다.
- 계약 표의 판정은 세 가지로 쓴다.
  - **확정**: 원본 문서가 값까지 정했다.
  - **초안**: 원본에 경로·이름·최소 필드는 있으나 "초안·후보·제안·구현 전 확정"으로 표시돼 있다.
  - **미정**: 원본에 없거나 문서끼리 다르다. 해당 질문 ID를 단다.
- 현재 화면 경로는 docs/frontend/ROUTES.md를 따른다. 후속 화면 경로는 해당 기능 착수 전에 설계한다.
- 미정 항목은 구현을 막는 정도를 함께 적는다. 미정이어도 목(mock) 데이터로 화면을 먼저 만들 수 있는 항목은 "목으로 진행 가능"으로 표시한다.

## 공통 화면 규칙 (모든 기능에 적용)

| 규칙 | 근거 |
|---|---|
| 401의 Access 만료는 refresh 후 복원, 갱신 불가/권한 문맥 변경은 재로그인 안내, 403은 권한 없음 화면(내용 비노출), 404는 찾을 수 없음 화면 | PRD 4.11 · API 1 |
| 409(버전 충돌·중복)는 "최신 내용을 다시 불러와 주세요" 성격의 안내와 재조회 | API 1 |
| 503·일시 오류는 입력과 저장된 결과를 보존하고 재시도. 재시도는 같은 요청 키로 보냄(중복 생성 방지는 서버 책임) | PRD 4.11 · API 1 |
| 처리 중·빈 결과·실패·일부 성공을 구분해 표시. 일부 영역 실패가 정상 영역을 막지 않음 | PRD 4.11 |
| 상태는 문구와 색을 함께 쓰고, 저장 확인 전에는 성공·해결로 보이지 않게 함 | PRD 4.11, 7.1 |
| 상세 모달을 닫으면 목록의 검색·필터·페이지 유지 | PRD 4.11 |
| 응답 필드 camelCase, 식별자 UUID 문자열, 시각 UTC RFC 3339(화면은 현지 시각으로 표시) | API 1 |
| 사용자 입력은 공백 포함 1~4,000 코드 포인트, 공백만 있는 입력 거부, 초과 시 원문 유지 | API 1 · PRD 4.4 |
