# F011 해결 사례 초안·승인·검색 공개

상태: PRD 1.44 목표 · hops-system-1 계약·화면 기준 / 구현·통합 검증 별도. 관련 문서: [PRD](../../docs/PRD.md), [API](../../docs/API.md), [데이터](../../docs/DATA.md), [데이터 구축 계획](../../docs/knowledge/DATASETS.md#저장검색과-사례-공개). [UNKNOWN 복구·수동 공개 중단 변경안](RECOVERY_PROPOSAL.md)을 참고한다.

## 목표와 사용자

시스템 주담당자는 실제 처리 기록으로 생성된 사례 초안을 확인·수정하고, 문의자의 해결 확인 후 승인한다. 기능 요청은 구현·검증 기록도 필요하다. 문의자 확인 및 담당자 승인이 없으면 검색에 공개하지 않는다.

## 인수 조건

- **F011-AC01** 담당자 해결 기록 저장 직후 Curator 실행을 요청하고, 초안 실패가 저장된 업무 기록이나 완료를 취소하지 않는다.
- **F011-AC02** 시스템 담당자가 원문·실제 조치·검증·적용 조건·공개 범위·민감정보를 확인·수정한다. 별도 검토자 없이 자기 승인을 허용한다.
- **F011-AC03** 문의자 해결 확인과 담당자 승인 및 같은 승인 버전의 Vector·Neo4j 반영이 모두 성공한 사례만 검색 공개한다.
- **F011-AC04** 반영 하나가 실패하거나 상태 미확인이면 어느 검색 경로에서도 공개하지 않는다. 승인 및 업무 기록은 보존한다.
- **F011-AC05** 원인 수정 뒤 실패 반영을 재실행할 수 있다. 중복 방지·재실행 권한·조작은 아래 index-checks/index-retries 계약안을 따르며 전용 화면·자동 재시도는 요구하지 않는다.
- **F011-AC06** 결과에 시스템 적용 버전과 조건을 제공하며 버전을 모르면 미확인으로 표시한다. 오래된 사례를 자동 삭제·차단하지 않는다.
- **F011-AC07** 합성 사례의 가상 문의자 확인과 실제 HOPS에서 수행한 확인을 출처와 함께 구분한다.

## 화면과 사용자 흐름

### 화면

- 시스템 담당자의 사례 초안 조회·수정·승인과 검색 반영 상태 표시. 별도 복구 화면은 요구하지 않으며 목표 경로는 아래 신규 계약안에서 제안한다.
- 담당자 사례 검색 결과는 적용 시스템·버전·조건을 함께 표시한다.

### 흐름

1. 담당자 해결 기록이 저장되면 Curator가 사례 초안과 기존 관계 연결 후보를 제안한다.
2. 문의자가 해결을 확인한 뒤 해당 시스템 담당자가 초안을 수정·승인한다.
3. 같은 승인 버전의 Vector·Neo4j 반영을 확인하고 양쪽 성공 후 권한별 검색에 공개한다.

## 상세 인수 조건과 예외

- **F011-DETAIL-01 초안 실패:** Curator 실행이 실패해도 저장된 담당자 기록과 업무 완료를 취소하지 않으며 검색 공개로 표시하지 않는다.
- **F011-DETAIL-02 검토·수정:** 담당자는 원문·실제 조치·검증 결과·적용 조건·공개 범위·민감정보를 확인한다. 별도 지식 검토자 없이 자기 승인을 허용한다.
- **F011-DETAIL-03 문의자 확인:** 문의자의 해결 확인 전이나 담당자의 승인 전에는 공개하지 않는다. 기능 요청은 실제 구현·검증 완료 기록도 확인한다.
- **F011-DETAIL-04 부분 반영:** Vector만 또는 Neo4j만 성공하면 양쪽 검색에서 해당 승인 버전을 반환하지 않는다. 성공한 반영과 승인·업무 기록은 보존한다.
- **F011-DETAIL-05 미확인·버전 불일치:** 한쪽 결과가 미확인이거나 승인 사례와 색인 버전이 다르면 공개 가능으로 취급하지 않는다.
- **F011-DETAIL-06 재반영:** 원인을 수정하고 FAILED 반영을 수동 재실행한다. PENDING/RUNNING/UNKNOWN은 기존 반영 확인 조작을 사용하며, 유효한 원격 NOT_FOUND에서만 보존한 같은 요청의 멱등 재접수를 허용한다. 새 attempt 생성과 구분하고 자동 재시도·전용 복구 화면은 제외한다.
- **F011-DETAIL-07 버전·적용:** 사례 문서 버전과 적용 시스템 버전을 구분하고 알 수 없는 적용 버전은 미확인으로 표시한다. 오래된 사례를 무조건 삭제·차단하지 않는다.
- **F011-DETAIL-08 출처:** 합성 사례의 가상 문의자 확인 설정과 실제 HOPS 확인을 구분한다. 실제 운영 이력으로 오인하지 않는다.
- **F011-DETAIL-09 검색 권한:** 직원용 공개 지식과 담당자 내부 자료를 분리하고 서버가 승인·공개 상태 및 현재 접근 권한을 검색 양쪽 경로에서 검증한다.
- **F011-DETAIL-10 무티켓·실패:** 담당자 처리 기록이 없는 무티켓 안내 대화만으로 초안을 만들지 않는다. 실패 시도는 업무 이력에 남기되 해결 사례로 게시하지 않는다.

## 계약·화면 상태

신규 `hops-system-1`의 계약이다. 필드·enum은 [DATA_TYPES](../contracts/DATA_TYPES.md#신규-계약-hops-system-1), REST·오류·SSE·멱등성은 [WIRE_CONTRACT 12절](../contracts/WIRE_CONTRACT.md#12-신규-계약-hops-system-1), 업무 전이는 [TARGET_CONTRACT](../contracts/TARGET_CONTRACT.md)가 정본이다. 아래 내용은 구현·통합 완료 표시가 아니다.

| 반영·확인 | PENDING/RUNNING/UNKNOWN은 index-checks로 확인. 유효한 원격 NOT_FOUND이면 승인 시 보존한 같은 요청을 멱등 재접수. 새 jobId/attempt 생성 없음 |

## hops-system-1 검증 시나리오

- **F011-CONTRACT-01:** 같은 WorkRecord 이벤트 중복은 Curator 작업·초안을 중복 생성하지 않는다.
- **F011-CONTRACT-02:** 해당 원 기록의 문의자 응답이 미해결이면 초안을 승인하지 못한다.
- **F011-CONTRACT-03:** 한쪽 실패/UNKNOWN/다른 버전 성공에서는 Vector와 Neo4j 양쪽 검색 모두 해당 승인 버전을 반환하지 않는다.
- **F011-CONTRACT-04:** 현재 DRAFT 편집은 version_no를 증가시키고, 승인된 사례 편집은409 INVALID_STATE로 거부한다. 기존 승인 내용과 반영 성공 상태는 바꾸지 않는다.
- **F011-CONTRACT-05:** 권한 없는 관리자는 사례를 승인하지 못하고 현재 시스템 담당자의 자기 승인은 가능하다.

문서/JSON 검사·Mock·실제 서버 저장/권한·실제 AI/검색·브라우저 E2E를 분리해 결과를 기록한다. 기존 테스트의 이전 AC 번호를 새 시나리오 통과로 간주하지 않는다.

## 범위·연관 기능

- 완료 후 재오픈, 사례 자동 재검토·비활성화·폐기 전파와 시스템 직접 변경은 제외한다.

## 현재 구현과 남은 작업

현재 프론트는 사례 목록·현재 초안 편집·승인, 원 기록의 해결 확인과 구현 검증, 같은 승인 버전의 Vector/Neo4j 반영·공개 상태·수동 확인/실패 재시도를 구현했다. 생성 실패·재사용 사례 없음·부분 반영과 버전 충돌을 Mock·UI로 검사한다. 실제 Curator·Spring 승인 저장·두 검색 저장소의 반영/ACL 및 다음 문의 재검색은 통합 검증이 남아 있다.

실행법과 현재 화면·호출 범위는 [프론트 안내](../../frontend/README.md), 서비스별 실제 구현은 [공통 계약 11절](../contracts/WIRE_CONTRACT.md#11-담당별-구현과-검증-상태)을 따른다. 신규 계약의 프론트 검사를 실제 Spring 저장·권한, AI·검색 및 전체 E2E 검증으로 대신하지 않는다.

## 서비스 간 계약 추적

| 경계 | 이 기능에 적용할 계약 |
|---|---|
| Frontend↔Spring | 초안/버전/승인/index-checks/index-retries/공개. 필드·응답·오류·멱등성은 [DATA_TYPES](../contracts/DATA_TYPES.md#신규-계약-hops-system-1)·[WIRE12절](../contracts/WIRE_CONTRACT.md#12-신규-계약-hops-system-1) |
| Spring↔AI | CASE_DRAFT·IndexApplyRequest/Snapshot·KnowledgeAuthorization, 승인/attempt/digest 검증. 실제 wire 필드는 [에이전트 계약](../../contracts/agents/README.md#반영검색-권한-서비스-계약) |
| 기본값 | [결정 대장](../QUESTIONS.md#실행검색-기본값)의 저장·서비스 인증·검증 게이트를 참조. 비밀값은 배포 환경 주입 |

- **F011-CONTRACT-06:** IndexApplySnapshot의 caseVersion/store/attempt/digest 중 하나라도 현재 승인 작업과 다르면 성공 반영·검색 공개에 적용하지 않는다.
- **F011-CONTRACT-07:** Vector/Neo4j 후보를 읽었어도 Spring의 knowledge authorization이 거부·실패하면 CASE 원문을 모델에 전달하지 않는다.


## 병합 ERD 적용 조건

[DATA11절](../../docs/DATA.md#11-완성-erd-대조-결과와-병합-기준)의 E01~E10 대조와 [ERD6절](../../docs/ERD.md#6-hops-system-1-공통-계약-보완)의 저장 보완을 이 기능에 적용한다. 외부 필드/상태는 DATA_TYPES·WIRE12절을 정본으로 유지하며 DB 코드를 UI에 직접 노출하지 않는다.

- **F011-CONTRACT-08:** 기존 resolved_case의 현재 승인 버전과 vector_status/graph_status 두 성공을 확인한 경우에만 공개한다. 추가 버전·반영 이력 테이블 없이 다른 버전의 응답은 적용하지 않는다.

- **F011-CONTRACT-09:** 승인 commit 뒤 색인 POST 전 종료되고 원격이 유효한 NOT_FOUND를 반환하면, 승인과 같은 거래에 보존한 source_metadata.indexRequests의 동일 jobId/attempt/digest/본문을 담당자 확인으로 재접수하며 두 성공 전 검색 비공개를 유지한다. 승인 또는 요청 보존이 실패하면 해당 승인 거래 전체가 롤백된다.
- **F011-CONTRACT-10:** 원격이 접수했으나 응답이 유실된 경우 기존 RUNNING/UNKNOWN snapshot은 조회만 반영한다. 최초 전달과 수동 재전달이 경합해도 AI의 같은 (jobId,attempt) 실행은 하나이며 내용이 다르면409다.
- **F011-CONTRACT-11:** timeout·5xx·인증/권한 오류·형식이 잘못된404·메타데이터 누락·승인 버전 불일치는 새 POST나 attempt 증가를 만들지 않는다. 현재 권한 없는 사용자의 확인 요청과 브라우저 GET·폴링도 색인을 시작하지 않는다.
- **F011-CONTRACT-12:** FAILED의 다음 attempt를 저장한 뒤 전달 전 종료되면 그 현재 요청을 같은 키로 재접수한다. 이전 attempt의 늦은 성공은 무시하고 다른 저장소의 성공은 유지한다. 원격 상세 보존 기간이 지나 기존 키만 남으면 UNKNOWN을 반환하고 새 작업으로 실행하지 않는다. 이 경우 현재 계약에는 자동 또는 수동 새 시도 복구 경로가 없다.
