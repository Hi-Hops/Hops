# 사례 색인 복구와 수동 공개 중단 변경안

사례 색인 복구와 수동 공개 중단의 권한·API·저장 제약을 정리한다. 실제 코드·DB 마이그레이션·검색 연동은 아직 없다. 기존 계약은 [F011](spec.md), [공통 계약](../contracts/TARGET_CONTRACT.md#7-사례-버전승인검색-공개), [에이전트 색인 계약](../../contracts/agents/README.md#i1-승인-case-반영)을 따른다.

## 1. 목표와 범위

원격에 접수된 색인 작업이 복원 불가능한 `UNKNOWN`으로 남았을 때 담당자가 안전하게 복구하고, 잘못 공개된 사례는 승인·처리 기록을 보존한 채 검색에서 수동으로 제외한다. 자동 재시도·자동 비활성화·승인 취소·전용 복구 화면은 추가하지 않는다. 기존 `NOT_FOUND`의 동일 요청 재전달과 `FAILED`의 수동 재시도는 유지한다. 대상은 CASE이며 가이드·정책·런북의 생명주기를 이 변경으로 확정하지 않는다.

## 2. 시도별 격리와 UNKNOWN 복구

### 저장·검색 불변 조건

- 반영 단위는 `(caseId, caseVersion, store, jobId, attempt)`다. 같은 저장소의 같은 작업은 attempt가 증가하며 각 attempt의 색인 산출물을 분리한다. 동일 attempt의 같은 입력 재전달은 멱등이고 다른 입력은 충돌이다. 승인 본문과 digest는 바꾸지 않는다.
- Vector 조각은 attempt를 포함한 별도 키·격리 영역에 저장한다. Neo4j도 CASE별 노드와 관계를 attempt별로 분리한다. 기존 공통 System/Feature 등 노드는 재사용하되 이전 작업이 현재 시도의 관계나 공통 노드 속성을 덮어쓰거나 삭제하지 못한다. 저장 중 부분 결과와 오래된 시도는 검색 후보가 아니다.
- Spring은 저장소별 **현재 성공 attempt**를 정본으로 유지한다. 양쪽 현재 attempt가 동일 승인 버전과 각 저장소 요청의 digest로 성공하고 공개 중단 상태가 아닌 경우에만 검색을 허용한다. 검색은 현재 성공 attempt만 후보로 삼는다. 반환할 조각·관계와 모든 이웃/경로도 동일한 CASE 버전·시도의 소속을 검사하고, 권한 검사 후 본문을 읽는다. 이전 시도 결과를 현재 시도의 일부로 조합하지 않는다.
- 현재 attempt로의 전환과 공개 조건 검사는 Spring DB에서 CASE 행 잠금 또는 동등한 원자적 조건부 갱신으로 처리한다. 결과에는 caseId·caseVersion·store·jobId·attempt·digest를 대조한다. 지연된 이전 작업은 자기 격리 영역에만 기록할 수 있고 현재 성공 attempt를 변경하지 못한다. 물리 삭제나 취소 성공을 안전성 전제로 삼지 않는다.
- 각 검색 경로는 현재 성공 attempt와 공개 상태를 Spring에 확인한다. 변경 중 또는 확인 실패 시 해당 사례를 반환하지 않는다. 결과를 모델 입력으로 전달하기 직전과 외부 응답 적용 직전에 현재 공개·권한을 다시 확인한다. 이미 외부 모델에 전송된 정보까지 회수할 수 있다고 보장하지 않는다.
- 시도별 격리를 위해 Vector의 기존 `(knowledge_document_version_id, chunk_no)` 유일 제약과 Neo4j의 노드·관계 식별 및 조회를 변경해야 한다. 저장 구조·FK·인덱스·기존 데이터 이관과 격리된 이전 산출물의 보존·정리는 구현 설계에서 확정한다. 기존 22개 테이블만으로 변경 없이 구현된다고 가정하지 않는다. 저장소별 격리나 현재 attempt 검증이 입증되지 않으면 UNKNOWN 재실행은 비활성화한다.

### 수동 복구 명령안

`POST /api/v2/cases/{caseId}/index-recoveries`를 제안한다. 본문은 기존 공통 `requestId`와 `expectedCaseVersion`, `store`, `expectedJobId`, `expectedAttempt`다. 일반 명령과 같은 멱등 키·권한·오류 계약을 적용한다. 같은 키/본문의 재전달은 기존 receipt를 반환하고 다른 본문은 충돌 처리한다.

1. 현재 사례 시스템의 PRIMARY만 명령할 수 있다. Spring은 현재 승인 버전·저장소·작업·attempt·권한과 공개 중단 여부를 검증한다. 저장소별 현재 요청과 동일하지 않으면 충돌로 거부한다.
2. 저장된 동일 작업을 원격에서 확인한다. **정상 형식의 원격 snapshot이 `UNKNOWN`이고 식별자와 digest가 모두 일치하는 경우에만** 복구를 시작한다. `PENDING`/`RUNNING`은 기다리고, `SUCCEEDED`/`FAILED`는 현재 결과를 반영해 각 기존 경로를 따른다. 원격 `NOT_FOUND`는 기존 index-checks의 동일 요청 재전달 경로다. timeout·5xx·인증 실패·응답 불일치·메타데이터 누락은 복구 허용 근거가 아니다.
3. Spring은 잠금 아래 권한·버전·현재 요청을 재검사하고 같은 jobId의 다음 attempt와 원 승인 본문·digest를 저장하며 해당 저장소를 비공개 대기 상태로 전환한다. 작업 상태 확인과 저장 사이에 결과가 바뀌면 현재 저장 상태와 비교해 충돌 처리한다. 외부 호출은 commit 뒤 수행한다. 경합하는 다른 복구 명령은 이전 attempt를 기준으로 했으므로 거부한다.
4. commit 뒤 저장한 새 요청을 전달한다. 전달 전 종료되면 기존 index-checks로 같은 새 요청을 확인·재접수한다. 기존 attempt는 실행 중일 수 있으므로 취소만으로 격리를 대체하지 않는다. 새 시도 결과가 확인되지 않으면 다시 `UNKNOWN`으로 남긴다. 성공한 다른 저장소와 승인·업무 기록은 유지한다.

`UNKNOWN`은 실패 확정이 아니다. 이 명령은 동일 승인 내용을 격리된 새 시도로 다시 적용하기 위한 명시적 조작이며 자동 실행하지 않는다. 공개 중단된 사례는 색인 복구로 다시 공개되지 않는다.

## 3. 수동 검색 공개 중단

`POST /api/v2/cases/{caseId}/publication-suspensions`를 제안한다. 본문은 `requestId`, `expectedCaseVersion`, 공백만이 아닌 `reason`이다. 구체 길이 제한은 다른 입력 제한과 함께 구현 전에 정한다. 현재 사례 시스템의 PRIMARY만 허용하며 관리자 긴급 권한은 이번 제안에서 부여하지 않는다. 승인된 현재 버전만 대상이다. 중복 명령에는 일반 멱등 규칙을 적용하고, 다른 키로 이미 중단된 버전을 요청하면 현재 상태를 반환하며 이력을 중복 생성하지 않는다.

- Spring은 CASE 행을 잠그고 현재 권한·승인 버전·상태를 검증한다. 같은 거래에서 공개 중단 상태와 대상 버전·행위자·시각·사유를 보존한다. 조회 DTO에는 담당자 권한 범위에서 상태와 이력을 표시한다. 사유에는 비밀값이나 민감한 원문을 넣지 않는다.
- 트랜잭션 commit 이후 신규 검색의 양쪽 경로는 승인·양쪽 성공 외에 공개 중단 여부도 검사한다. 기존 색인 데이터가 남아 있어도 중단된 버전은 본문·경로·모델 근거로 제공하지 않는다. 처리 중 요청도 모델 입력 직전과 외부 응답 적용 직전에 재검사한다. 캐시 사용 시 중단 이후 허용 결과를 재사용하지 않으며 현재 상태를 확인할 수 없으면 비공개다.
- 중단은 승인 취소·사례 편집·색인 삭제·업무 완료 취소가 아니다. 승인 본문, 색인 상태와 감사 이력을 보존한다. 색인 작업이 늦게 성공해도 중단 상태를 해제하지 않는다. 이미 외부로 전달된 내용의 회수는 보장하지 않는다.
- **재공개 조작은 이 변경에서 정의하지 않는다.** 수정·재승인·새 사례 생성과 중단 해제 권한은 별도 팀 결정 전까지 허용하지 않는다. 새 해결 기록에서 생성된 별도 사례는 기존 정책에 따라 검토할 수 있다.

기존 `Publication` 투영에는 중단 여부와 담당자가 조회 가능한 사유·행위자·시각이 필요하다. 중단 정본과 감사 이력을 영속화할 구체 컬럼·테이블, 동시성 및 기존 데이터 이관은 ERD와 migration 리뷰에서 정한다. 본 제안은 기존 상태 컬럼만으로 충분하다고 주장하지 않는다.

## 4. 검증 및 인수 조건

다음은 구현 후 수행할 시나리오이며 현재 통과 결과가 아니다.

| 상황 | 기대 결과 |
|---|---|
| 승인 commit 뒤 최초 전송 전 종료 | 기존 index-checks가 유효한 원격 NOT_FOUND에서 같은 요청을 재전달한다. 두 성공 전 비공개다. |
| 접수 응답 유실·원격 RUNNING | 조회만 하고 새 시도나 중복 실행을 만들지 않는다. |
| 원격이 유효한 UNKNOWN 반환 | 현재 PRIMARY가 명령하면 동일 승인 본문의 다음 attempt를 원자적으로 저장한다. 서로 경합한 복구 요청은 하나만 전진한다. |
| timeout·5xx·인증 오류·잘못된 snapshot | 새 attempt를 만들지 않고 미확인으로 둔다. |
| UNKNOWN인 이전 시도가 새 시도 완료 후 늦게 쓰기·삭제·성공 응답 | 새 시도의 Vector 조각, Neo4j 관계, 성공 포인터 및 검색 결과가 바뀌지 않는다. 반대 순서와 동시 실행도 검증한다. |
| 한 저장소만 FAILED 또는 UNKNOWN | 두 경로 모두 비공개이며 다른 저장소의 성공은 유지한다. |
| 중단과 검색·색인 성공이 경합 | 중단 commit 이후 새 조회는 제외한다. 진행 중 조회는 본문 전송과 응답 적용 전 재검사하고, 늦은 색인 성공은 중단을 해제하지 않는다. |
| 무권한자·오래된 버전·중복 명령 | 중단/복구를 수행하지 않으며 기존 상태·이력을 보존한다. 동일 키 재전달은 중복 실행하지 않는다. |
| 공개 상태 확인 불가·캐시 지연 | 두 경로 모두 사례를 반환하지 않는다. 이전 attempt의 조각·그래프 경로도 결과에 포함하지 않는다. |

Spring 실제 DB 거래와 동시성, 서비스 재시작·응답 유실, Vector와 Neo4j의 격리 및 검색 경로, 현재 권한과 모델 입력 경계를 통합 검증한다. 문서·Mock 검사만으로 이를 대체하지 않는다.
