# F006 내 문의·해결 확인

상태: PRD 1.44 목표 명세 · PRD 정책 유지 / hops-system-1 계약 기준·구현/검증 별도.

## 1. 목표와 범위

문의자가 본인의 대화와 문제별 처리 상태를 확인하고 해결 여부를 응답한다.

근거: [PRD](../../docs/PRD.md), [API](../../docs/API.md), [데이터](../../docs/DATA.md), [목표 공통 계약](../contracts/TARGET_CONTRACT.md).

## 2. 인수 조건

- **F006-TARGET-01:** 본인 문의 목록과 대화·연결 티켓의 진행 상태를 조회한다.
- **F006-TARGET-02:** 담당자가 처리 및 검증을 기록하면 해당 문제에 대한 해결 확인 요청을 표시한다.
- **F006-TARGET-03:** 기능 요청은 실제 구현·검증 완료와 문의자의 최종 해결 확인을 구분해 표시한다.
- **F006-TARGET-04:** 해결 응답 시 해당 문제의 최종 완료를 저장하고 미해결 응답 시 같은 티켓의 처리를 이어간다.
- **F006-TARGET-05:** 무응답은 확인 대기를 유지한다. 자동 종료·예약 재알림·완료 후 재오픈을 제공하지 않는다.
- **F006-TARGET-06:** 타인의 문의와 담당자 전용 자료는 노출하지 않는다.

## 화면과 사용자 흐름

### 화면

- 내 문의 목록과 본인 채팅 재진입. 현재 프론트의 `/inquiries` 및 채팅 경로는 구현 안내를 따른다.
- 처리 결과와 문제별 해결/미해결 확인은 본인 채팅 안 확인 영역에서 제공한다.

### 흐름

1. 문의자가 목록에서 자신의 문의를 선택해 문제와 티켓 진행을 확인한다.
2. 담당자가 처리·검증한 문제의 결과를 확인한다.
3. 해결 또는 미해결을 응답하고 서버가 해당 문제의 상태를 확정한다.

## 상세 인수 조건과 예외

- **F006-DETAIL-01 목록·권한:** 본인 문의만 조회하고 다른 사용자의 ID로 상세를 열어도 서버가 거부한다.
- **F006-DETAIL-02 페이지·빈 결과:** 목록 로딩, 빈 목록, 오류를 구분한다. 추가 페이지 조회가 실패해도 이미 읽은 목록을 보존하고 해당 조회만 다시 시도할 수 있다.
- **F006-DETAIL-03 결과 확인 요청:** 담당자의 처리·검증 이후에만 해당 문제의 확인 요청을 표시한다. 알림 읽음은 해결 응답이 아니다.
- **F006-DETAIL-04 기능 요청:** 담당자의 구현 완료를 표시하되 문의자 확인 전 최종 해결 완료로 표시하지 않는다.
- **F006-DETAIL-05 해결:** 문의자 해결 응답은 관련 문제·티켓에만 적용한다. 다른 문제가 자동 완료되지 않는다.
- **F006-DETAIL-06 미해결·무응답:** 미해결은 같은 티켓의 처리로 돌아가며, 무응답은 확인 대기다. 예약 재알림·자동 종료·완료 후 재오픈은 제공하지 않는다.
- **F006-DETAIL-07 저장 오류:** 확인 요청의 응답이 유실되면 성공으로 단정하지 않고 입력과 대상 문제를 보존해 서버 상태를 확인한다.

## 계약·화면 상태

신규 `hops-system-1`의 계약이다. 필드·enum은 [DATA_TYPES](../contracts/DATA_TYPES.md#신규-계약-hops-system-1), REST·오류·SSE·멱등성은 [WIRE_CONTRACT 12절](../contracts/WIRE_CONTRACT.md#12-신규-계약-hops-system-1), 업무 전이는 [TARGET_CONTRACT](../contracts/TARGET_CONTRACT.md)가 정본이다. 아래 내용은 구현·통합 완료 표시가 아니다.

| 조작 | 계약·검증 |
|---|---|
| 목록 | /inquiries 상단 메뉴 제공. InquirySummary의 문제·티켓·대기 수와 updatedAt 표시 |
| 처리 결과 | 채팅 안에 activeResolutionRequest의 resultSummary와 대상 문제 표시. 내부 담당 자료는 제외 |
| 해결 응답 | ResolutionResponse.expectedRequestRevision과 대상 요청 ID로 한 처리 주기에 응답 |
| 무티켓 확인 | GUIDE source도 동일 해결 확인 API 사용. WORK_RECORD 확인의 전제와 구분 |

| 화면 상태 | 관찰 가능한 동작 |
|---|---|
| PENDING | 해결/미해결 버튼; 무응답은 대기 유지 |
| RESOLVED | 해당 문제 최종 완료. 다른 독립 문제는 그대로 |
| UNRESOLVED | 같은 티켓 처리 계속; 가이드이면 담당자 연결 검토 |
| 문의 CLOSED | 모든 문제가 OUT_OF_SCOPE인 경우 '지원 범위 밖 안내 종료' 표시. 해결 완료와 구분하며 범위 밖 문제에 티켓·해결 확인을 만들지 않음 |
| 오래된/중복 응답 | 원 키 같은 응답은 기존 결과. 다른 응답·오래된 revision은 충돌 후 조회 |

## hops-system-1 검증 시나리오

- **F006-CONTRACT-01:** 두 문제 중 하나의 확인 응답이 다른 문제·티켓을 완료하지 않는다.
- **F006-CONTRACT-02:** 미해결 뒤 같은 티켓에서 새 검증 기록·새 확인 요청이 생성되며 이전 요청은 이력으로 유지된다.
- **F006-CONTRACT-03:** 무응답으로 시간이 지나도 대기 상태이고 알림 읽음은 해결 응답이 아니다.
- **F006-CONTRACT-04:** 응답 저장 후 HTTP 유실을 재확인하면 원 응답 하나만 남는다.
- **F006-CONTRACT-07:** 모든 문제의 범위 밖 안내가 저장되면 문의는 CLOSED, 문제는 OUT_OF_SCOPE로 조회된다. 목록·채팅은 '지원 범위 밖 안내 종료'로 표시하고 해결 성공·티켓·해결 확인 요청을 만들지 않는다.
- **F006-CONTRACT-08:** 해결 확인된 문제와 OUT_OF_SCOPE 문제만 남으면 문의는 RESOLVED이며 범위 밖 문제는 OUT_OF_SCOPE를 유지한다.
- **F006-CONTRACT-09:** 범위 밖 문제 외의 미완료 문제가 모두 WAITING_USER/WAITING_SYSTEM/WAITING_CONFIRMATION이면 문의는 WAITING_USER다. 하나라도 ANALYZING/TICKET_PENDING/IN_SERVICE이면 IN_PROGRESS이며 무응답·화면 종료로 CLOSED가 되지 않는다.

문서/JSON 검사·Mock·실제 서버 저장/권한·실제 AI/검색·브라우저 E2E를 분리해 결과를 기록한다. 기존 테스트의 이전 AC 번호를 새 시나리오 통과로 간주하지 않는다.

## 범위·연관 기능

- 문제별 확인을 제공하되 독립 상세 모달의 정확한 경로나 검색·숨김/복원 기능을 신규 필수로 가정하지 않는다.

## 현재 구현과 남은 작업

현재 프론트는 본인 문의 목록·페이지 이동·채팅 재진입과 채팅 안 문제별 해결/미해결 응답을 구현했다. GUIDE/WORK_RECORD 출처, 확인 대기, 미해결 후 같은 티켓의 다음 처리 주기를 Mock으로 검사한다. Spring의 확인 요청 조회·문의자 단일 응답·동시 경합·문제별 상태 전이를 실제 DB에서 검사했다. GUIDE 미해결의 같은 입력 버전·질문 횟수·기존 분류와 재분석 접수도 검증하며, 문의 Problem/GUIDE 결과 투영과 실제 서비스·브라우저 통합 검증은 남아 있다.

실행법과 현재 화면·호출 범위는 [프론트 안내](../../frontend/README.md), 서비스별 실제 구현은 [공통 계약 11절](../contracts/WIRE_CONTRACT.md#11-담당별-구현과-검증-상태)을 따른다. 신규 계약의 프론트 검사를 실제 Spring 저장·권한, AI·검색 및 전체 E2E 검증으로 대신하지 않는다.

## 서비스 간 계약 추적

| 경계 | 이 기능에 적용할 계약 |
|---|---|
| Frontend↔Spring | ResolutionRequest/Response·문제별 처리 주기. 필드·응답·오류·멱등성은 [DATA_TYPES](../contracts/DATA_TYPES.md#신규-계약-hops-system-1)·[WIRE12절](../contracts/WIRE_CONTRACT.md#12-신규-계약-hops-system-1) |
| Spring↔AI | AI 저장 명령 없음. Spring 응답 결과를 CASE 승인 전제와 다음 입력에서 사용. 실제 wire 필드는 [에이전트 계약](../../contracts/agents/README.md#반영검색-권한-서비스-계약) |
| 기본값 | [결정 대장](../QUESTIONS.md#실행검색-기본값)의 저장·서비스 인증·검증 게이트를 참조. 비밀값은 배포 환경 주입 |


## 병합 ERD 적용 조건

[DATA11절](../../docs/DATA.md#11-완성-erd-대조-결과와-병합-기준)의 E01~E10 대조와 [ERD6절](../../docs/ERD.md#6-hops-system-1-공통-계약-보완)의 저장 보완을 이 기능에 적용한다. 외부 필드/상태는 DATA_TYPES·WIRE12절을 정본으로 유지하며 DB 코드를 UI에 직접 노출하지 않는다.

- **F006-CONTRACT-05:** 같은 문제의 검증 기록A에 미해결 응답 후 기록B의 새 확인 요청이 생겨도 A의 요청/응답을 보존한다. 다른 원 기록의 해결 응답으로 CASE를 승인하지 않는다.

- **F006-CONTRACT-06:** GUIDE의 미해결 응답 후 같은 문제의 원 안내/확인 요청은 보존하고 새 run에 resolutionContext=UNRESOLVED를 전달한다. 질문 수와 기존 입력 버전을 초기화하지 않고 activeRunId로 이전 결과를 차단한다.
