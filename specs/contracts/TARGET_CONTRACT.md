# PRD 1.44 목표 공통 계약 — 리뷰 초안

상태: 팀이 합의한 제품 방향의 **논리 입출력·상태 설계 초안**. 실제 API 경로·필드 식별자·enum·타입·nullable·HTTP 상태·물리 제약은 아직 팀의 구현 계약으로 확정되지 않았다. 표의 명칭은 의미를 설명하며 전송 필드나 구현 완료를 뜻하지 않는다. 기존 구현은 [전환 전 데이터 프로필](DATA_TYPES.md), [전송 프로필](WIRE_CONTRACT.md)을 따른다. 충돌 시 현재 구현과 목표를 혼동하지 말고 서비스별 전환을 계획한다.

## 1. 공통 책임

React는 Spring REST로 사용자 명령·조회를 보내고 권한이 확인된 Spring SSE로 진행과 업무 변화 알림을 받는다. Spring은 인증·현재 권한·문의 버전, 업무 데이터 저장·배정·완료·사례 승인과 검색 공개를 확정한다. AI 서비스는 서버가 허용한 정보·도구로 질문·검색·티켓·사례를 제안하며 업무 DB에 직접 쓰지 않는다. 모델 응답·진행 이벤트·요청 접수는 업무 성공이 아니다.

## 2. 공통 논리 데이터

| 개념 | 전달·저장할 의미 | 검증·표시 |
|---|---|---|
| 사용자 문맥 | 인증된 사용자, 역할, 소속, 접근이 허용된 시스템 | 현재 서버 권한을 확인하며 클라이언트·모델의 역할 주장은 신뢰하지 않는다. |
| 시스템 | 지원 시스템과 기능, 시스템별 유효한 주담당 관계 | 한 사람은 여러 시스템을 맡고 시스템별 주담당자는 1명. 부서는 소속 정보. |
| 문의·대화 | 작성자, 원문·정정 이력, 문의 버전, 메시지와 문제 연관 | 문의자는 본인 범위만 조회한다. 늦은 이전 입력의 분석 결과는 적용하지 않는다. |
| 문제 | 의도·처리 유형, 보고 시스템·기능, 질문 수, 확인 사실·추정·미확인 | 질문 묶음은 문제당 최대 5회. 미확인 시스템은 선택 요청·대기. |
| 표준 요청 | 문제 참조와 버전, 요약·유형별 정보, 책임 시스템 후보·근거, 관련 지식·조건 | 원문을 대체하지 않는다. AI가 제안한 수용 조건은 미확인 시 제안으로 표시한다. |
| 티켓·배정 | 문제와 작업 참조, 저장 결과, 보고/책임 시스템, 담당자·배정 근거 | 서버가 지원 시스템과 주담당자를 확인한다. 그래프 관계만으로 원인을 확정하지 않는다. |
| 처리·확인 | 실제 조치·검증, 기능 구현 완료, 문의자 해결·미해결 응답 | 구현 완료와 최종 완료를 구별하고 문제별로 확인한다. |
| 사례 | 초안·문서 버전·원문/티켓/처리 기록 출처, 실제 조치·검증, 적용 시스템 버전·조건·공개 범위 | 합성·데모 검증·실제 운영 출처와 가상 확인·실제 확인을 구분한다. |
| 승인·검색 반영 | 승인자·승인 버전, Vector·Neo4j 각각의 반영 결과, 공개 가능 여부 | 문의자 확인·담당자 승인 뒤 동일 버전 두 반영 모두 성공해야 양쪽 검색에 공개한다. |
| 실행·근거 | 실행·문의 버전, 자료 출처·권한·검색 결과·안전한 오류 | 검색 없음·오류를 구분하고 내부 사고 과정이나 민감정보를 노출하지 않는다. |

기획에 정한 문의 의도와 내부 처리 유형의 의미는 [PRD 3.1](../../docs/PRD.md#31-대화-기반-문의-분석과-복수-티켓-생성)을 따른다. 다른 저장·표시 상태의 코드와 세부 필드는 아래 의미를 기준으로 구현 전 합의한다.

## 3. 문의·배정·부분 실패의 상태 의미

| 상황 | 서버가 확인할 사실 | 화면·후속 동작 |
|---|---|---|
| 시스템 미확인 | 보고 시스템을 아직 확인하지 못함 | 선택을 요청하고 확인 대기를 저장. 화면을 닫아도 유지. |
| 질문 중 | 현재 문제의 확인 항목과 문제별 질문 수 | 최대 5회 질문 묶음. 이미 확인된 내용을 반복하지 않음. |
| 배정 가능 | 확인된 보고 시스템, 책임 시스템 후보·근거, 유효한 주담당자 | 서버 검증 후 저장된 티켓·배정 결과만 표시. 책임 시스템 근거가 부족하면 보고 시스템 담당자에게 조사 요청. |
| 생성 성공 | 해당 문제의 기존 티켓이 실제 저장됨 | 저장된 기존 결과를 표시하고 다시 생성하지 않음. |
| 생성 실패 | 해당 업무 작업의 미생성이 확인됨 | 성공한 다른 문제는 유지. 제안 재생성 또는 재사용 후 같은 작업을 재시도. |
| 저장 결과 미확인 | 저장 여부를 아직 확인할 수 없음 | 성공·실패를 단정하지 않고 확인. 결과 확인 전 신규 생성 금지. |
| 배정 이후 보완 | 기존 티켓이 있고 사용자가 메시지·정정을 보냄 | 기존 티켓에 관련 보완 정보를 연결. 자동 새 티켓·재배정 없음. |

재시도 전 Spring은 기존 티켓 저장 결과와 현재 문의 버전을 확인한다. 같은 작업·입력의 식별, 결과 보존, 경합 처리 및 사용자 조작/권한은 상세 계약에서 정한다. 네트워크 오류 자체를 DB 미저장으로 판단하지 않는다. 이미 생성한 티켓과 성공한 다른 문제는 유지한다.

## 4. 처리·확인·사례 공개의 상태 의미

```text
담당자 처리·검증 / 기능 요청의 구현·검증 완료 기록
    → 문의자 확인 대기
       → 미해결: 같은 티켓에서 처리 계속
       → 무응답: 확인 대기 유지
       → 해결 확인: 업무 최종 완료

담당자 해결 기록 저장 → Curator 초안 생성(업무 저장과 분리)
    → 문의자 해결 확인 → 해당 시스템 담당자 확인·수정·승인
    → 같은 승인 버전의 Vector 반영 + Neo4j 반영
    → 양쪽 성공 확인 → 서버의 접근·공개 검사 → 검색 공개
```

처리 기록 저장 시 초안 생성을 시작할 수 있으나 초안 실패가 처리 기록·업무 완료를 취소하지 않는다. 사용자 확인과 사례 승인은 별개다. 무티켓 안내 대화만으로 사례 초안을 만들지 않는다. 승인·양쪽 반영 결과는 같은 버전 기준으로 구분한다. 하나라도 실패하거나 확인할 수 없으면 두 검색 경로에서 모두 공개하지 않고 승인·업무 기록을 유지한다. 실패 반영은 원인 수정 후 다시 실행한다. 자동 재시도·전용 복구 화면은 제외하며 멱등성·권한·조작·원자적 공개의 세부 방식은 별도 협의한다.

## 5. 화면 ↔ Spring의 기능별 최소 입출력

| 기능 | 요청에서 필요한 의미 | 응답 또는 조회에서 필요한 의미 | 핵심 검증 |
|---|---|---|---|
| 문의 시작·답변·정정 | 인증된 사용자, 내용·대상 문의, 필요한 경우 입력 버전과 동일 요청 식별 | 저장 확정 또는 결과 미확인, 문의·대화와 현재 실행 상태 | 소유권·입력·최신 버전·중복 요청 |
| 시스템 선택 | 문제·선택한 지원 시스템 | 보고 시스템 확인 또는 대기 | 문의 소유·지원 목록·문제 상태 |
| 결과 조회 | 본인 문의 또는 허용된 담당 업무 대상 | 문제별 질문·대기·범위 밖·티켓 성공·실패·미확인 | 현재 접근 범위 및 저장된 결과 |
| 담당 업무 조회·처리 | 담당 시스템과 티켓, 실제 처리·검증 또는 변경 내용 | 담당 업무, 관련 대화·근거, 저장된 처리 결과 | 현재 주담당 관계·공개 범위·대상 버전 |
| 수동 정정 | 티켓, 새 책임 시스템, 근거·사유 | 서버가 확정한 담당자 및 변경 이력 | 담당자/업무 관리자 권한·지원 시스템·주담당자 |
| 해결 확인 | 문의자의 대상 문제·해결/미해결 응답 | 확인 결과와 업무 상태 | 문의 소유·대상 문제·처리 완료 전제 |
| 사례 검토·승인 | 대상 사례·버전과 담당자의 수정·승인 | 초안·승인·각 반영 상태 및 검색 공개 가능 여부 | 해당 시스템 담당자·문의자 확인·기능 구현 검증·승인 버전 |
| 반영 재실행 | 승인 사례 버전 및 실패 반영 대상 | 요청 접수·반영 상태·최종 공개 가능 여부 | 권한·동일 버전·기존 성공과 중복 |

표는 사용자 기능의 최소 의미이며 실제 경로, 전달 형식이나 저장 성공 응답을 정하지 않는다. 결과 미확인은 확인된 실패와 구분한다. 오류 응답은 안전한 범위에서 상태를 전달하고 내부 오류·비밀값을 노출하지 않는다.

## 6. Spring ↔ AI의 역할별 최소 의미

| 역할 | 입력 | 출력 제안 | 서버 또는 실행기의 검증 |
|---|---|---|---|
| Supervisor | 허용된 실행 상태·전문 결과·서버 결과 | 다음 행동과 응답 조율 | 허용 경로와 전체 시간·모델 호출·토큰·재시도 한도 |
| Inquiry | 최신 대화·문제·시스템 목록 | 의도·확인/미확인·시스템 후보·문제 분리·질문 | 현재 문의 버전과 문제별 질문 횟수 |
| Knowledge | 현재 표준 요청·검색 목적·권한 범위 | 문서·사례·관계 근거, 적용 조건, 가능한 원인·다음 확인 항목 | 허용 자료·승인·공개 상태, Mock 여부 및 근거 출처 |
| Ticket | 표준 요청·허용 근거·시스템 목록 | 문제별 제목·내용·처리 유형·책임 시스템 후보와 이유 | 현재 버전, 지원 시스템·주담당자, 중복 및 실제 저장 결과 |
| Curator | 담당자 해결 기록·원문·기존 지식·관계 스키마 | 사례 초안, 중복 및 기존 엔티티 연결 후보 | 기록 출처, 권한·승인·기존 관계 유형, 이후 양쪽 반영 상태 |

독립 Diagnosis 역할은 없으며 Knowledge가 필요 시 조건부 분석한다. 각 역할에 대한 필수/선택 필드·형식·실패·타임아웃·재시도 예산과 서비스 간 인증은 구현 전 합의한다. AI 서비스는 인증·업무 저장·배정을 확정하지 않는다.

## 7. 합의·검증이 남은 사항

- 시스템/담당 관계, 문의·문제·작업·티켓 관계와 상태 코드, 식별자·버전·필드 선택성.
- API 경로·호출 방법·오류, 기존 부서 기반 클라이언트와의 호환·전환.
- 재시도 키·저장 결과 확인·동시성·트랜잭션, 권한 변경 및 SSE 연결 회수.
- Curator 실행 중복 방지, 사례 버전·승인, 저장소별 반영·공개·복구 구현.
- 그래프 스키마·질의·접근 범위, 모델·임베딩·시간·호출·비용 상한과 평가 데이터.

이 문서는 목표 계약에 대한 검토 자료다. 이 문서의 작성은 서버 DTO·DB 제약·AI 역할·실제 통합이 구현되거나 테스트됐다는 뜻이 아니다.

## 8. 상세 필드 제안 — 공통 규칙

이 절부터의 필드명과 자료형은 **팀 리뷰용 제안**이다. 기존 `hops-mock-1` 또는 `agent-1`의 확정 wire 형식이 아니며 새 API·DB·DTO가 이미 구현되었다는 뜻도 아니다. 제안한 필드와 값은 팀이 합의하기 전에는 서비스 간 강제 규격으로 사용하지 않는다. 실제 경로, HTTP 상태 코드, 필드 선택성, 버전 관리 및 호환 방식은 구현 계약에서 확정한다.

- 표현 후보는 기존 계약과 같이 `camelCase`, JSON 객체·배열, ID 문자열, UTC 시각 문자열을 사용한다. 실제 ID 발급 방식과 문자열 제약은 별도 확정한다.
- **필수**는 해당 논리 객체를 반환할 때 반드시 있어야 하는 후보, **조건부**는 명시한 상황에서만 필요한 후보, **미확인 허용**은 필드는 존재하되 값을 모르면 `null`로 표시하는 후보를 뜻한다. 생략 허용 여부와 null 규칙은 최종 스키마에서 정한다.
- `[]`는 확인 가능한 항목이 없음을 표현한다. 조회 실패·권한 거부를 빈 목록이나 `null`로 바꿔 성공처럼 표현하지 않는다. 권한상 비공개 자료는 요청자가 존재 여부를 유추할 수 있는 방식으로 반환하지 않는다.
- 서버가 확인한 사실, 모델의 제안과 사람이 확인하지 않은 추정은 서로 다른 항목에 둔다. 입력받은 사용자 ID·시스템 ID를 권한의 증거로 사용하지 않는다.

시스템 목록 조회와 실제 주담당자 조회의 권한·필드는 별도다. 문의자에게 불필요한 개인 정보나 내부 소유권 정보를 자동으로 공개하지 않는다. 한 사용자가 여러 시스템을 맡아도 각 시스템에 유효한 주담당자는 하나여야 한다는 제품 전제는 유지한다. 담당 관계가 없거나 둘 이상이거나 조회에 실패하면 배정 성공을 확정하지 않는다. 정상 가상 데이터의 예외 업무 UI는 만들지 않는다.

## 9. 상태 전이와 경계 사례 — 제안

아래는 UI·서버·AI가 구분해야 할 **상태의 의미**다. enum 이름이나 모든 구현 중간 상태를 확정한 표가 아니다.

### 9.1 문의·티켓

| 현재 상황 | 이벤트·검증 | 다음에 보이는 사실 |
|---|---|---|
| 시스템 미확인 | 문의자가 지원 시스템을 선택하고 서버가 확인 | 보고 시스템이 확인됨. 필요한 경우 남은 문제 정보 분석. |
| 시스템 미확인 | 화면을 닫거나 응답하지 않음 | 문의와 확인 대기 보존. 임의 담당자 배정 없음. |
| 추가 질문 중 | 질문 묶음 발송 확정 | 해당 문제의 질문 횟수를 기록. 5회를 넘기지 않음. |
| 질문 한도에 도달하고 시스템 확인됨 | 필요한 항목이 일부 미확인 | 확인된 사실·미확인 정보를 보존해 담당자에게 전달. |
| 티켓 생성 요청 | 서버가 이미 저장된 해당 작업의 티켓을 확인 | 기존 티켓 반환. 중복 생성 없음. |
| 티켓 생성 요청 | 실제 미생성 확인과 현재 문의 버전 검증 | 보존된 제안을 사용하거나 Ticket 제안을 재생성해 동일 작업 재시도. |
| 티켓 생성 요청 | 기존 저장 여부 확인 불가 | 결과 미확인 유지. 신규 생성·성공/실패 확정 금지. |
| 담당자 처리·검증 완료 | 결과 통보와 확인 요청 저장 | 문의자 확인 대기. 기능 요청은 실제 구현·검증 완료 기록 필요. |
| 확인 대기 | 문의자 미해결 응답 | 같은 티켓 처리 계속. |
| 확인 대기 | 문의자 무응답 | 확인 대기 유지. 예약 재알림·자동 종료 없음. |
| 확인 대기 | 문의자 해결 응답 및 서버 검증 | 해당 문제/티켓 최종 완료. 완료 후 재오픈은 범위 밖. |

동일 복합 문의의 다른 문제는 각자 진행한다. 하나의 문제 실패·미응답이 이미 성공한 다른 티켓이나 완료 결과를 삭제하지 않는다. 상태 코드를 제안할 때도 문의·문제·작업·티켓의 상태를 하나의 enum으로 합치지 않는다.

### 9.2 사례·검색 반영

| 확인 상태 | 검색 공개 | 처리 |
|---|---|---|
| 초안 생성 실패 또는 초안 생성 중 | 비공개 | 이미 저장된 담당자 처리 기록과 업무 완료 유지. |
| 초안만 있음 | 비공개 | 담당자가 내용을 확인·수정할 수 있음. |
| 문의자 확인 전 또는 담당자 승인 전 | 비공개 | 승인 순서와 확인 대기를 유지. |
| 승인됨, 두 저장소 반영 전 | 비공개 | 승인 버전을 기준으로 각 반영을 진행. |
| Vector만 성공 또는 Neo4j만 성공 | 양쪽 모두 비공개 | 성공한 결과를 보존하고 실패 원인을 수정해 실패 반영 재실행. |
| 어느 한쪽 결과 미확인 | 양쪽 모두 비공개 | 결과 확인 후 재반영 여부를 결정. 성공으로 추정하지 않음. |
| 다른 사례 버전의 반영만 성공 | 해당 승인 버전 비공개 | 승인 버전과 저장소별 반영 버전을 일치시킨 뒤 재검증. |
| 같은 승인 버전의 양쪽 반영 성공 | 접근 권한 검증 후 공개 가능 | 서버가 반환 시점의 승인·공개 가능 상태와 요청자 권한을 검사. |

담당자가 수정한 뒤 승인하는 사례 버전, 승인 후 내용을 다시 수정할 경우 새 버전·재승인을 적용하는 방법은 구현 전 팀이 정한다. 본 표는 이전 승인 사례 전체를 삭제하거나 일괄 비활성화하라는 뜻이 아니다.

## 10. 요청·응답과 오류의 의미 — 제안

HTTP URL·메서드·응답 코드·이벤트명은 여기서 임의로 확정하지 않는다. 기존 경로를 유지·확장할지 새 경로를 만들지는 현재 클라이언트·Spring 구현의 호환성 검토 후 정한다. 다음은 모든 전송 방식에서 구분할 의미다.

| 상황 | 소비자에게 전달할 의미 | 재시도·표시 원칙 |
|---|---|---|
| 입력 검증 실패 | 어떤 입력 조건을 충족하지 않았는지 | 입력 보존. 같은 잘못된 요청 자동 반복 금지. |
| 인증 실패 / 권한 없음 | 인증 필요 또는 현재 대상 접근 불가 | 인증과 권한 오류 구분. 비공개 내용을 반환하지 않음. |
| 최신 문의 버전 충돌 | 현재 입력을 그대로 적용할 수 없음 | 서버 최신 상태를 조회하고 변경한 새 요청은 기존 미확인 요청과 구분. |
| 저장 결과 미확인 | 응답 유실 또는 기존 저장 결과 조회 불가 | 같은 업무 작업의 결과를 우선 확인. 새 티켓 생성 금지. |
| 실제 미생성 확인 | 해당 작업이 저장되지 않았음을 서버가 확인 | 권한·현재 버전·동일 작업을 확인한 뒤 재시도. |
| 시스템/담당 관계 확인 실패 | 유효한 배정을 확정하지 못함 | 로그에 안전한 오류 기록, 저장·배정 성공으로 표시하지 않음. |
| 검색 결과 없음 | 검색은 성공했으나 허용된 결과가 없음 | 근거 부족으로 안내·담당자 연결을 검토. |
| 검색 시스템 오류 | 검색을 수행하거나 결과를 검증하지 못함 | 결과 없음과 구분. 근거를 만들어내지 않음. |
| 모델·시간·예산 오류 | 분석 실행이 끝나지 못함 | 기존 저장 결과 유지. 실행 실패와 업무 저장 실패를 혼동하지 않음. |
| 색인 반영 실패·미확인 | 승인 버전의 한쪽 또는 양쪽 반영을 확인하지 못함 | 양쪽 검색 비공개. 승인·처리 기록 유지, 실패 반영 복구. |

오류 코드 목록, 재시도 가능 여부·주체, 저장 결과 조회 방법과 유지 시간은 실제 API 계약에서 정한다. 안전한 오류 메시지는 내부 예외·비밀값·다른 사용자의 정보를 포함하지 않는다.

## 11. 가상 예시 — 역할과 버전 구분

다음은 계약의 의미를 설명하는 **가상 예시**이며 실제 API 응답·DB 데이터·승인된 fixture가 아니다. 식별자와 필드명은 예시다.

```json
{
  "inquiryId": "예시-문의",
  "inquiryVersion": 2,
  "problem": {
    "problemId": "예시-문제",
    "intent": "OBSERVED_SYMPTOM",
    "processingType": "INVESTIGATION",
    "reportedSystemId": "예시-전자결재",
    "questionCount": 2
  },
  "standardRequest": {
    "summary": "전자결재 이용 중 로그인이 반복됨",
    "confirmedFacts": ["전자결재에서 로그인 화면이 반복됨"],
    "assumptions": ["공통 로그인과 관련될 가능성"],
    "unknowns": ["현재 인증 상태의 구체 원인"],
    "responsibleSystemCandidateId": "예시-공통로그인",
    "responsibilityEvidenceIds": ["예시-대화-근거"]
  }
}
```

이 예시는 **보고 시스템은 전자결재로 유지**하면서 대화와 근거가 충분하다고 판단된 경우에만 공통 로그인을 책임 시스템 후보로 제안한다. Spring은 실제 지원 목록·근거·주담당 관계를 검증해 배정을 확정한다. 근거가 부족하면 보고 시스템 담당자가 최초 조사한다. 예시의 문자열은 식별자 형식이나 실제 시나리오 정답을 확정하지 않는다.

```json
{
  "caseId": "예시-사례",
  "caseVersion": 3,
  "appliesToSystemVersion": null,
  "origin": "합성",
  "confirmationKind": "가상 문의자 확인 설정",
  "approval": {"caseVersion": 3, "status": "승인됨"},
  "indexResults": [
    {"store": "Vector", "caseVersion": 3, "state": "성공"},
    {"store": "Neo4j", "caseVersion": 3, "state": "미확인"}
  ],
  "publication": {"canSearch": false}
}
```

Neo4j 반영 결과가 미확인이므로 동일 사례는 Vector를 포함한 **어느 검색 경로에서도 비공개**다. `caseVersion`은 사례 문서 버전이며, `appliesToSystemVersion: null`은 적용할 시스템 버전이 미확인이라는 의미다. 위 한글 상태 문자열은 enum 제안이 아니다.

## 12. 기존 구현과 전환 점검

| 기존 자료·구현에서 확인한 항목 | 새 목표에서 필요한 변경 | 영향과 검증 대상 |

현재 `develop` 기준 Spring의 문의·티켓 패키지는 자리표시자가 있으며 이 문서는 그 업무 API나 사례 저장이 이미 구현되었다고 가정하지 않는다. 개발 중인 별도 브랜치의 작업과 이 문서의 목표 계약은 별도로 비교해야 한다. 구현 범위와 검증 여부는 해당 서비스 README 및 실제 코드로 확인한다.

## 13. 리뷰와 관찰 가능한 검증 항목

- [ ] 전자결재에서 경험했지만 공통 로그인 담당으로 배정되는 경우와 근거 부족으로 보고 시스템 담당자가 조사하는 경우를 구분한다.
- [ ] 각 문제의 질문 묶음이 최대 5회이며 시스템 미확인·선택하지 않고 닫기·범위 밖 상태가 정확히 표현된다.
- [ ] 복합 문의에서 성공·실패·결과 미확인을 나누고, 중복 재시도 및 저장 확인 실패 시 중복 티켓이 생기지 않는다.
- [ ] 기능 구현·검증 완료, 문의자 미해결/무응답/해결과 최종 완료를 구분한다.
- [ ] 문의자 확인·담당자 승인·같은 승인 버전의 Vector/Neo4j 성공이 모두 충족되어야 권한이 허용된 검색에서만 사례가 노출된다.
- [ ] 두 저장소 중 하나의 실패·미확인·버전 불일치 시 양쪽 검색 경로가 해당 사례를 반환하지 않고 성공한 반영과 업무 기록을 보존한다.
- [ ] 합성 사례의 가상 확인, 실제 HOPS 확인과 시스템 적용 버전 미확인을 구분한다.
- [ ] 필드 선택성·상태 코드·요청/응답·권한·오류·동시성·기존 wire 호환을 담당자별로 리뷰하고 합의한다.

위 항목은 계약 리뷰와 구현 후 검사에 사용할 **목표 조건**이다. 체크하지 않은 상태가 실제 서버 테스트를 통과했거나 실패했다는 의미는 아니다.
