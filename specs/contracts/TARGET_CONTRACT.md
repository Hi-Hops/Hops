# PRD 1.44 구현 계약안 — hops-system-1

상태: 2026-10-31 팀 리뷰용 구현 계약안. [PRD 1.44](../../docs/PRD.md)의 제품 정책을 구체화한 제안이며 팀 승인·API 배포·DB 변경·서비스 통합 완료를 뜻하지 않는다. 작성자 외 팀원 리뷰와 병합 후 적용한다. 현재 코드·Mock의 `hops-mock-1`은 별도 보존한다.

## 2. 서비스 책임과 권한

- React는 Spring REST로 명령·조회를 보내고 Spring SSE를 수신한다. Python에 직접 연결하거나 토큰을 전달하지 않는다.
- Spring이 로그인 사용자·현재 시스템 주담당 관계·문의 소유권·버전·업무 저장·배정·해결 확인·승인·공개를 검증한다. 모델 문구와 진행 이벤트는 저장 증거가 아니다.
- Python은 허용된 문맥으로 질문·지식·티켓·사례를 제안한다. 업무 DB에 직접 쓰지 않으며 사용자나 책임 시스템을 임의 확정하지 않는다.
- 모든 로그인 사용자는 본인 문의를 이용한다. 시스템 담당 능력은 현재 유효한 PRIMARY 관계에서, 관리자 능력은 `BIZ_ADMIN`에서 얻는다. 한 사용자는 문의자·담당자·관리자 능력을 함께 가질 수 있다.
- 문의자는 본인 대화와 외부 공개 가능한 결과만 읽는다. 담당자는 현재 맡은 시스템 티켓과 해당 문제에 관련된 메시지·근거만 읽는다. 다른 독립 문제의 원문은 제공하지 않는다.
- 업무 관리자는 업무 메타데이터와 정정을 이용한다. 관리자 역할만으로 타인의 전체 대화·담당자 내부 지식·사례 승인 권한을 얻지 않는다.
- 조회·변경마다 현재 권한을 검사한다. 담당 관계 변경 트랜잭션에서 권한 변경 이벤트를 발행하고 기존 관련 SSE 전달을 차단한다. 다음 요청까지 이전 캐시 권한을 신뢰하지 않는다.

## 3. 식별·버전·관계

1. `Inquiry` 1:N `Problem`; 각 Problem은 논리 생성 작업 `WorkItem` 0:1, 그 작업은 `Ticket` 0:1이다. 별도 WorkItem 테이블을 강제하지 않으며 외부 키와 물리 모델 매핑은 DATA 10절·이슈 #66에서 맞춘다. 동일 문제에 두 번째 자동 티켓을 만들지 않는다.
2. 원문 메시지 ID는 고정한다. 내용 정정은 메시지 `revision`을 증가시키고 이전 내용을 보존한다. 표시 순서 `sequenceNo`와 구분한다.
3. `inquiryVersion`은 최초 사용자 메시지 1에서 시작한다. 사용자 메시지·정정·확정 시스템 선택 저장 시 1 증가한다. AI 메시지·질문·업무 처리·해결 응답은 이 분석 입력 버전을 올리지 않는다.
4. 티켓 변경에는 `ticketRevision`, 확인 응답에는 `requestRevision`, 사례 편집·승인에는 `caseVersion`을 사용한다. 서로 대체하지 않는다.
5. 분석 결과 적용은 현재 입력 버전·활성 runId를 잠금 안에서 대조한다. 오래된 미반영 제안은 저장하지 않는다. 이전에 확정된 메시지·티켓·배정은 유지한다.
6. 신규 문제는 AI의 임시 참조를 Spring UUID에 매핑해 저장한다. 재분석에서 기존 문제 ID를 재사용한다. 임시 참조·요약·배열 순서를 DB 유일 키로 사용하지 않는다.

## 4. 문의·문제·질문

| 현재 문제 상태 | 조건·조작 | 저장되는 다음 상태 |
|---|---|---|
| ANALYZING | 질문 묶음과 AI 메시지를 같은 트랜잭션으로 저장 | WAITING_USER; 질문 수 1 증가 |
| WAITING_USER | 해당 문제에 답변·정정 저장 | ANALYZING; 질문 수 유지 |
| ANALYZING | 질문 5회·보고 시스템 확인 | 누락 정보를 보존하고 티켓 제안 진행 |
| ANALYZING | 질문 5회·보고 시스템 미확인 | WAITING_SYSTEM; 추가 자유 질문 금지 |
| WAITING_SYSTEM | 소유자가 지원 시스템 선택 | ANALYZING; 새 입력 버전, 질문 수 유지 |
| ANALYZING | 승인 직원 가이드 안내 저장 | WAITING_CONFIRMATION; GUIDE 확인 요청 생성 |
| ANALYZING | 지원 범위 밖 | OUT_OF_SCOPE; 티켓 없음 |
| ANALYZING | 생성 작업이 존재 | TICKET_PENDING; 작업 결과는 별도 표시 |
| TICKET_PENDING | 티켓·배정 저장 확인 | IN_SERVICE |
| IN_SERVICE | 담당자 검증 완료 기록 | WAITING_CONFIRMATION |
| WAITING_CONFIRMATION | 문의자 RESOLVED | RESOLVED |
| WAITING_CONFIRMATION | 문의자 UNRESOLVED | 티켓 있으면 IN_SERVICE, GUIDE이면 ANALYZING 후 담당자 연결 검토 |

재분석·SSE 재전달은 같은 `questionBundleId`를 다시 세지 않는다. 복합 문제에 보낸 같은 메시지가 서로 다른 문제의 질문을 포함하면 각 문제에 번들 하나씩 연결한다. 5회 도달 후 시스템 선택은 질문 횟수에 포함하지 않으며 저장된 대기를 화면 종료 후에도 복원한다.

문의 표시 상태는 문제들의 집계다. 최초 분석 전 문제 목록이 비어 있으면 IN_PROGRESS다. 하나라도 ANALYZING/TICKET_PENDING/IN_SERVICE이면 IN_PROGRESS, 그 외 미완료 문제는 WAITING_USER, 모두 RESOLVED/OUT_OF_SCOPE이고 하나 이상 RESOLVED면 RESOLVED, 모두 OUT_OF_SCOPE면 CLOSED다. 집계는 문제별 상태·작업 결과를 숨기지 않는다. 무응답 종료 상태는 새 프로필에 두지 않는다.

배정된 문제의 메시지·정정은 관련 기존 티켓의 보완 정보다. 기존 티켓 생성 작업은 다시 만들지 않는다. 완료 티켓의 이후 같은 현상은 새 문의 진입을 안내하고 재오픈하지 않는다. 여러 문제 중 대상이 불명확한 보완 정보는 어느 티켓에도 자동 배포하지 않고 대상 선택을 요청한다. 이는 추가 질문 한도를 늘리는 자유 질문으로 사용하지 않는다.

## 5. 티켓 생성·배정·복구

| 작업 결과 | 판단 근거 | 허용 조작 |
|---|---|---|
| PENDING | 생성·저장 확인 진행 중 | 결과 조회 |
| STORED | 같은 workItemId의 티켓·배정 DB commit 확인 | 기존 티켓 조회; 생성 재시도 없음 |
| NOT_CREATED | 진행 중 저장이 없고 트랜잭션 롤백·미저장을 서버가 확인 | 소유자가 같은 작업 재시도 |
| UNKNOWN | DB/저장 여부를 확인할 수 없음 | 저장 결과 확인; 재생성 금지 |

자동 생성은 사용자 승인·담당자 수락 없이 실행한다. Spring은 최신 입력 버전·지원 시스템·근거·유효 PRIMARY를 확인하고 티켓·초기 배정을 문제별 하나의 트랜잭션으로 저장한다. 다른 책임 시스템 근거가 부족하면 확인된 보고 시스템 담당자가 조사한다. 담당 관계 오류는 배정 성공으로 반환하지 않는다.

업무 작업 ID는 입력 정정·재분석·재시도에도 유지한다. 성공 티켓은 유일 제약으로 보호한다. 미생성이 확인된 작업만 최신 버전에 맞는 제안을 재사용/재생성해 재시도한다. HTTP 멱등 키와 workItemId는 서로 다른 목적이다. 네트워크 오류·GET 404만으로 미생성을 확정하지 않는다.

결과 모달은 저장된 생성 결과 revision이 새로 관찰됐을 때 연다. 소유자·문의·결과 revision별 확인 상태는 로컬 UI에만 보관한다. 새 탭/기기에서 다시 나타날 수 있지만 닫기·확인 버튼은 생성·해결·승인을 변경하지 않는다. 성공·실패·미확인은 같은 모달 안에서 문제별로 보존한다.

## 6. 처리·해결 확인·수동 정정

- 티켓은 WAITING → IN_PROGRESS → WAITING_CONFIRMATION → RESOLVED다. PROGRESS 기록은 WAITING을 IN_PROGRESS로, 검증 완료 기록은 WAITING/IN_PROGRESS를 WAITING_CONFIRMATION으로 바꾼다.
- 일반 요청은 VERIFIED_RESOLUTION, 기능 추가·개선은 IMPLEMENTED_VERIFIED 기록만 해결 확인을 요청한다. 실제 조치·검증 내용이 필요하다. PROGRESS/실패 시도만으로 사례를 생성하지 않는다.
- 검증 완료 기록·확인 요청·Curator 실행 예약은 같은 업무 저장 경계에서 연결한다. 실제 AI 실행과 성공 여부는 분리한다. 초안 실패가 업무 기록을 취소하지 않는다.
- 확인 요청은 GUIDE 메시지 또는 특정 WorkRecord 하나를 참조한다. WAITING_CONFIRMATION 중 새 검증 기록으로 요청을 교체하지 않고, 문의자의 미해결 응답 후 다음 처리 주기를 시작한다.
- 소유자는 PENDING 요청에 한 번 RESOLVED/UNRESOLVED 응답한다. 같은 키·본문은 기존 결과를 반환하고 다른 응답·오래된 requestRevision은 409다. 같은 문의의 다른 문제는 바뀌지 않는다.
- 미해결이면 같은 티켓을 IN_PROGRESS로 돌린다. 무응답은 계속 대기한다. 기존 실패/미해결 기록을 CASE로 게시하지 않는다. GUIDE 해결은 티켓 없이 종료하고 Curator를 실행하지 않는다.
- 수동 정정은 현재 시스템 담당자 또는 업무 관리자만 수행한다. 새 책임 시스템을 선택하면 서버가 유효 주담당자를 결정한다. 변경 전후·사유·근거·행위자·시각을 보존하고 ticketRevision으로 경합을 차단한다.
- 정정은 RESOLVED 이외 상태에 허용한다. 같은 시스템의 잘못된 담당자도 현재 유효 PRIMARY로 정정할 수 있다. 진행 중 확인 요청은 원 처리 기록에 연결해 유지한다. 최종 완료 티켓은 수정하지 않는다.
- 시스템 PRIMARY 변경은 과거 티켓 assignee를 자동 수정하지 않는다. 업무 권한은 현재 PRIMARY로 검사하며 상세는 저장 배정 assignee와 currentPrimary를 구분한다. 필요 시 현재 담당자가 이력을 남겨 수동 정정한다.

## 7. 사례 버전·승인·검색 공개

| 사실 | 상태·조건 | 공개 여부 |
|---|---|---|
| Curator 실행 | 처리 기록당 한 작업; PENDING/RUNNING/SUCCEEDED/FAILED | 비공개 |
| 사례 초안 | 재사용할 내용 없으면 NO_REUSABLE_CASE로 종료; 있으면 DRAFT | 비공개 |
| 문의자 확인 | 해당 원 처리 기록의 확인 요청이 RESOLVED | 아직 비공개 |
| 사례 승인 | 현재 시스템 담당자가 원문·조치·검증·조건·공개 범위를 확인; 자기 승인 허용 | 아직 비공개 |
| 반영 | 승인 버전별 VECTOR·NEO4J 각각 PENDING/RUNNING/SUCCEEDED/FAILED/UNKNOWN | 두 성공 전 양쪽 비공개 |
| 공개 | 같은 승인 버전의 두 성공을 Spring DB에서 확인하고 현재 ACL 검증 | 권한 있는 검색만 허용 |

초안 편집은 낙관적 버전 검증 후 새 caseVersion을 만든다. 승인된 내용을 바꾸려면 기존 승인을 수정하지 않고 새 초안 버전을 만든다. 새 버전은 재승인·재반영하며 이전 공개 버전은 자동 삭제·차단하지 않는다. 최초 신규 초안과 승인된 버전 편집을 같은 저장으로 취급하지 않는다.

CASE 버전은 원 WorkRecord·확인 요청·원문 출처에 고정한다. 미해결 응답을 받은 처리 기록의 초안은 승인하지 않는다. 이후 검증 완료 기록은 별도 Curator 작업과 새 사례 후보를 만든다. 초안이 재사용할 내용이 없으면 승인 대상을 만들지 않는다.

승인 commit 뒤 저장소별 반영 작업을 outbox로 전달한다. 외부 저장소와 분산 트랜잭션을 가정하지 않는다. `(caseId, caseVersion, store)`별 작업·중복 키를 사용한다. 승인 버전의 공개 가능 상태 갱신은 Spring DB의 잠금/버전 검사로 원자화한다. Vector/Neo4j 결과는 Spring을 통한 현재 승인·공개·ACL 검증을 통과한 항목만 반환한다.

실패 반영은 담당자가 원인을 수정한 뒤 수동 재실행한다. UNKNOWN은 먼저 상태 확인으로 성공/실패를 판정하며 그대로 재실행하지 않는다. 성공한 저장소는 유지한다. 사용자에게 원시 예외·비밀값을 보여 주지 않는다. 자동 재시도·전용 복구 화면·새 지식 검토자 역할은 추가하지 않는다.

## 8. 화면 구성과 계약 연결

| 화면 | 목표 경로 | 명세 |
|---|---|---|
| 로그인·새 문의·채팅 | /login, /, /inquiries/:inquiryId/chat | F001·F003·F004·F005·F008·F010 |
| 내 문의·문제별 확인 | /inquiries, 기존 채팅 안 확인 영역 | F006 |
| 담당 시스템 보드·목록 | /tickets?view=board 또는 list | F009 |
| 티켓 상세·처리·사례 탭 | /tickets/:ticketId?tab=request 또는 work 또는 case | F009·F011 |
| 업무 관리·정정 | /admin/tickets, /admin/tickets/:ticketId | F007·F009 |
| 사례 검토 목록·상세 | /cases, /cases/:caseId | F011 |

담당자 상세는 독립 페이지, 관리자 상세는 같은 상세 화면을 관리자 권한의 제한된 데이터로 표시하는 안이다. 정정·접수 안내는 모달이다. 기존 버튼·입력·배지·토큰·모달의 공통 UI를 재사용한다. 이는 실제 router 등록 상태가 아니며 [ROUTES](../../docs/frontend/ROUTES.md)의 현재 경로와 구분한다.

## 9. 전환·리뷰·완료 조건

1. 생산자·소비자가 신규 타입·상태·경로·오류·권한·동시성·예시를 함께 리뷰한다. 미선정한 모델·예산·인프라는 [QUESTIONS](../QUESTIONS.md)에서 담당·적용 전 조건을 추적한다.
2. 새 `/api/v2`·AI wire·DB 마이그레이션을 구현하고 신규 프로필용 DTO/어댑터를 연결한다. legacy 프로필을 필드명 일괄 치환해 변환하지 않는다.
3. 신규 프로필은 배포 설정으로 한 번에 선택한다. 기능별로 구/신규 프로필의 저장 결과를 섞거나 통신 실패 시 Mock으로 대체하지 않는다.
4. 기존 가상 데이터는 고정 보존한다. 전환 리허설은 별도 신규 가상 데이터로 진행한다. 실제 데이터 이관·롤백은 별도 마이그레이션 검토를 통과한다.
5. 권한 회수, 질문 5회, 시스템 대기 재진입, 복합 일부 성공, 응답 유실·동시 재시도, 오래된 결과, 처리·미해결·무응답, 사례 부분 반영·버전 불일치·양쪽 비공개를 검증한다.
6. 문서·예시 검사, Mock, 서비스 저장·권한, 실제 모델·검색, 브라우저 E2E 결과를 따로 기록한다. 문서 작성만으로 어떤 구현도 완료 처리하지 않는다.
