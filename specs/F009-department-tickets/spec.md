# F009 담당 시스템 업무·티켓 처리

상태: PRD 1.44 목표 명세 · PRD 정책 유지 / hops-system-1 계약 기준·구현/검증 별도.

## 1. 목표와 범위

시스템 주담당자가 맡은 업무를 조회하고 처리·검증 결과를 기록한다.

근거: [PRD](../../docs/PRD.md), [API](../../docs/API.md), [데이터](../../docs/DATA.md), [목표 공통 계약](../contracts/TARGET_CONTRACT.md).

## 2. 인수 조건

- **F009-TARGET-01:** 유효한 주담당자는 자신이 맡은 시스템의 티켓과 허용된 관련 대화·보완 정보·처리 이력을 조회한다.
- **F009-TARGET-02:** 티켓에서 표준 요청·보고/책임 시스템·확인 사실·추정·미확인 항목·권한에 맞는 검색 근거를 확인한다.
- **F009-TARGET-03:** 해결 사례에는 적용 시스템·버전·조건을 보여주고 버전을 모르면 미확인으로 표시한다.
- **F009-TARGET-04:** 담당자는 실제 처리·검증을 기록하고 문의자에게 해결 확인을 요청한다. 기능 요청은 구현·검증을 마친 경우에만 구현 완료로 기록한다.
- **F009-TARGET-05:** 책임 시스템이 잘못되면 담당자 또는 업무 관리자가 근거·사유를 남겨 수동 정정한다.
- **F009-TARGET-06:** 담당자 선점·수락, 업무량 기반 자동 배정과 자동 재이관은 제공하지 않는다.

## 화면과 사용자 흐름

### 화면

- `/tickets`는 담당 시스템 업무 보드/목록, `/tickets/:ticketId`는 목록 위 상세 모달이다. 요청 내역, 문의 처리 기록(`tab=work`), 해결 사례 탭을 같은 상세 모달에서 제공한다.
- 상세는 표준 요청, 보고/책임 시스템, 사실·추정·미확인, 허용 근거, 처리 이력, 해결 사례 적용 조건을 제공한다.

### 흐름

1. 주담당자가 자신이 담당하는 시스템의 업무 목록을 연다.
2. 티켓 상세에서 관련 대화와 확인 사실·사례를 검토한다.
3. 담당자가 처리·검증을 기록하고 문의자 확인을 요청하거나 잘못된 책임 시스템을 수동 정정한다.

## 상세 인수 조건과 예외

- **F009-DETAIL-01 담당 시스템 범위:** 현재 주담당 관계가 있는 시스템만 허용한다. 한 사람이 여러 시스템을 맡으면 허용된 각 시스템을 조회할 수 있다.
- **F009-DETAIL-02 목록 상태:** 로딩·빈 목록·조회 실패를 구분한다. 목록 필터·페이지와 상세 복귀 시 사용자 문맥을 유지하며 필터가 서버 권한을 넓히지 않는다.
- **F009-DETAIL-03 관련 대화:** 해당 티켓과 관련된 대화·배정 후 보완·정정 이력만 권한 범위에서 보여준다. 한 메시지에 여러 문제가 있으면 허용된 원문 구간만 투영하고 안전하게 분리할 수 없으면 표준 요청을 사용한다. 무관한 문제의 대화나 내부 운영 로그는 노출하지 않는다.
- **F009-DETAIL-04 사례 적용:** 검색된 사례의 적용 시스템·버전·조건을 표시한다. 버전이 없으면 미확인으로 표시하고 현재 시스템에 적용 가능하다고 단정하지 않는다.
- **F009-DETAIL-05 처리·기능 요청:** 실제 조치와 검증을 기록한다. 기능 요청은 구현·검증을 마친 경우에만 구현 완료로 표시한다.
- **F009-DETAIL-06 해결 확인:** 처리 결과를 통보하고 문의자 확인 요청으로 연결한다. 담당자 조치나 모달 닫기만으로 최종 완료하지 않는다.
- **F009-DETAIL-07 수동 정정:** 담당자 또는 업무 관리자는 변경 대상과 근거·사유를 기록한다. 새 시스템과 주담당자를 확인하지 못하면 정정 성공으로 표시하지 않는다.
- **F009-DETAIL-08 동시 변경:** 티켓 상태나 소유권이 다른 요청으로 바뀌었을 때 이전 화면의 변경을 무조건 덮어쓰지 않는다. ticketRevision 충돌은 409 후 최신 조회·초안 보존으로 처리한다.
- **F009-DETAIL-09 접근 회수:** 담당 관계가 사라진 뒤 재조회·재접속에서 서버가 현재 권한을 검사하고 내용을 노출하지 않는다.

- **F009-DETAIL-10 상세 모달 탐색:** 문의 처리 기록 탭은 선택·직접 URL 진입 모두 업무 목록 위 상세 모달에 표시한다. 탭 전환은 현재 이력을 교체하고 미전송 처리 입력을 유지한다. 목록/사례에서 진입했으면 뒤로 가기·닫기·Escape는 진입 전 화면으로 복귀하며 앞으로 가기는 마지막 탭을 다시 연다. 사례 복귀 시 원 사례의 조회 조건을 유지한다. 모달 안에서 처리 기록을 저장하고 이력을 확인하며, 목록에서 연 모달 또는 직접 URL 진입의 닫기·Escape는 `tab`을 제외한 목록 조건과 티켓 포커스를 복원한다. 관리자 상세는 제한된 메타데이터만 표시한다.

## 계약·화면 상태

신규 `hops-system-1`의 계약이다. 필드·enum은 [DATA_TYPES](../contracts/DATA_TYPES.md#신규-계약-hops-system-1), REST·오류·SSE·멱등성은 [WIRE_CONTRACT 12절](../contracts/WIRE_CONTRACT.md#12-신규-계약-hops-system-1), 업무 전이는 [TARGET_CONTRACT](../contracts/TARGET_CONTRACT.md)가 정본이다. 아래 내용은 구현·통합 완료 표시가 아니다.

| 조작 | 계약·검증 |
|---|---|
| 목록·보드 | GET tickets?scope=ASSIGNED_SYSTEMS&systemId&state&page&size. 보드/목록은 같은 조회·URL 조건 유지 |
| 상세 경로 | /tickets/:ticketId 상세 모달. tab=request/work/case는 같은 모달의 탭이며 직접 진입도 모달로 표시. 목록 쿼리를 보존해 복귀 |

| 사례 이동 | 원 WorkRecord의 CaseGeneration 상태와 /cases/:caseId 연결 |

| 화면 상태 | 관찰 가능한 동작 |
|---|---|
| 조회·빈 결과 | 서버 허용 시스템만 표시. 보드 숫자는 현재 페이지 건수 |
| 검증 기록 저장 | 성공 전 상태 변경 금지. 성공 후 확인 대기와 생성 작업을 별도 표시 |
| 동시 변경·권한 회수 | 최신 상세 재조회·초안 격리·보호 영역 마스킹 |
| 최종 완료 | 기록·정정·재오픈 버튼 없음. 이후 같은 현상은 새 문의 |

## hops-system-1 검증 시나리오

- **F009-CONTRACT-01:** 한 사람이 두 시스템을 맡으면 둘 다 조회하고 미담당 시스템 필터는 거부된다.
- **F009-CONTRACT-02:** CHANGE_REQUEST에 검증되지 않은 PROGRESS 기록만 있으면 구현 완료·해결 확인 요청을 만들지 않는다.
- **F009-CONTRACT-03:** 검증 완료 저장 뒤 Curator 실패해도 처리 기록·확인 요청·티켓 상태가 유지된다.
- **F009-CONTRACT-04:** 문의자 미해결 후 같은 티켓에서 다음 검증 주기를 진행하고 실패 시도는 검색 사례로 게시하지 않는다.

문서/JSON 검사·Mock·실제 서버 저장/권한·실제 AI/검색·브라우저 E2E를 분리해 결과를 기록한다. 기존 테스트의 이전 AC 번호를 새 시나리오 통과로 간주하지 않는다.

## 범위·연관 기능

- 주담당자 자동 배정 후 선점·수락은 없다. 동일 장애 그룹·일괄 처리·우선순위는 범위 밖이다.

## 현재 구현과 남은 작업

현재 프론트는 PRIMARY 기준 시스템 업무 보드/목록·상세 모달, 표준 요청·허용 관련 대화, 모달 안의 문의 처리 기록 탭과 책임 시스템/조사·장애 정정을 구현했다. PROGRESS·FAILED_ATTEMPT·VERIFIED_RESOLUTION·IMPLEMENTED_VERIFIED를 구분하고 입력 보존·버전 충돌을 Mock·UI로 검사한다. Spring의 티켓 목록·상세·관련 대화와 저장된 처리/확인/사례 생성 상태 조회, 현재 PRIMARY·공개 범위 검사를 구현하고 PostgreSQL/MockMvc로 검증한다. Spring의 처리·정정·해결 확인 응답과 CASE_DRAFT 접수·결과 처리기를 공통 Dispatcher에 연결했다. 실제 DB에서 권한·멱등성·동시 버전·상태 전이·commit 후 변경 신호를 검사하며 외부 AI는 가상 응답으로 검증한다. Python Curator와 사례 조회/승인/색인, 실제 서비스·브라우저 통합 검증은 남아 있다.

실행법과 현재 화면·호출 범위는 [프론트 안내](../../frontend/README.md), 서비스별 실제 구현은 [공통 계약 11절](../contracts/WIRE_CONTRACT.md#11-담당별-구현과-검증-상태)을 따른다. 신규 계약의 프론트 검사를 실제 Spring 저장·권한, AI·검색 및 전체 E2E 검증으로 대신하지 않는다.

## 병합 ERD 적용 조건

[DATA11절](../../docs/DATA.md#11-완성-erd-대조-결과와-병합-기준)의 E01~E10 대조와 [ERD6절](../../docs/ERD.md#6-hops-system-1-공통-계약-보완)의 저장 보완을 이 기능에 적용한다. 외부 필드/상태는 DATA_TYPES·WIRE12절을 정본으로 유지하며 DB 코드를 UI에 직접 노출하지 않는다.

- **F009-CONTRACT-05:** FAILED_ATTEMPT는 실제 실패 이력으로 저장하고 해결 확인/Curator를 만들지 않는다. confirmedCause·appliesToSystemVersion은 사람 입력 또는 null이며 검증 완료 두 종류는 verification이 필수다.

- **F009-CONTRACT-06:** 현재 담당자가 근거·사유와 ticketRevision을 보내 INVESTIGATION↔INCIDENT를 정정한다. WORK_TYPE_CHANGED 이력과 티켓 변경은 같은 거래로 저장하고 관리자 역할만 있는 사용자·AI 제안·완료 티켓의 변경은 거부한다.

- **F009-CONTRACT-07 추천 근거:** 추천 카드는 실제 키워드·의미 검색 순위에서 만든 추천 이유와 결합 점수를 보여준다. 해결 확률로 표현하지 않는다. 펼치면 검색에 사용한 티켓 제목·경로별 점수·승인 사례 버전과 조건 비교를 제공한다. 조건 비교는 권한이 검증된 확인 사실만 사용하며 추정은 제외한다. 책임 시스템 ID와 명시된 단일 조회 상태는 일치·불일치, 부정·미확인·여러 값·자유서술 조건·현재 시스템 버전은 추가 확인으로 표시한다. 불일치는 적용 전 확인을 안내한다. 구 서버가 설명을 보내지 않으면 점수·이유를 만들어 채우지 않고 근거 미제공을 안내한다. 검색 오류·정상 빈 결과·권한 거부는 기존대로 구분한다. 순위·배정·사례 승인 정책은 변경하지 않는다.

- **F009-CONTRACT-08 담당자 해결 근거:** 요청 내역에서 문의 요약·확인 사실·미확인 조건과 자료 워크스페이스를 함께 표시한다. 사례·매뉴얼·런북·정책을 전환하고 대표 사례의 업무 이유·조건 일치 현황·현재 문의와 근거 원문의 강조 구간·다음 확인·조치와 검증을 확인한다. 주요 검색 점수는 카드를 선택한 직후 보여준다. 사례 본문에 여러 문단이 있어도 조치와 검증을 혼동하지 않는다. 합성 자료를 운영 실적으로 표시하지 않는다. 유형별 빈 결과·검색 실패·접근 거부를 구분하며 인용 범위·문서 버전이 검증되지 않으면 내용을 신뢰해 표시하지 않는다. 요청 내역은 다른 상세 탭과 같은 모달 크기와 오른쪽 티켓 정보 블록을 유지한다. 본문은 문의 요약 다음에 추천순 카드의 제목·순위·조건 일치 수를 나열한다. 카드를 선택하면 해당 자료의 시각화가 즉시 화면에 들어온다. 상단에는 RAG 의미 유사도 원점수와 -1~1 척도, 키워드·의미 검색 순위와 RRF, 이름·현재 값·판정이 있는 조건별 현황을 항상 표시한다. 의미 유사도를 해결 확률이나 조건 일치율로 환산하지 않고, 점수가 없으면 미제공으로 표시한다. 조치·검증 / 비교 근거 / 원문·검색 점수는 아래에서 전환해 확인한다. 기본은 모노톤이며 선택한 카드와 인용문의 핵심 단어를 강조하고, 불일치 경고에만 별도의 주의 색을 쓴다. 카드를 바꾸면 이전 자료의 본문이나 비교 선택이 섞이지 않아야 한다. 적용 조건은 이름이 붙은 항목별 일치·미확인·불일치로 표현하며 검색 유사도나 해결 확률로 바꾸지 않는다. 추천 자료는 모든 카드의 조건별 현황을 보고 선택할 수 있다. 모달 크기·자료 유형 탭·키보드·반응형을 함께 검사한다.

- **F009-CONTRACT-08 서술형 조건 표시:** 미확인 판정은 물음표 아이콘 없이 표시한다. 자동 대조하지 않은 자유서술 묶음은 요약 카드에서 문의 전체를 나열하거나 단일 조건의 일치율처럼 표현하지 않고 직접 대조가 필요함을 알린다. 비교 근거에서 확인 사실과 사례의 적용 조건을 분리하며, 표시상 동일한 확인 사실은 한 번만 보이고 다른 값과 문장 내용은 보존한다.

- **F009-CONTRACT-08 자연어 조회 기간:** 해당 문제에서 허용된 문의자 원문에 기안일이 조회 기간 안에 포함된다고 확인한 표현은 조건 비교와 정확한 원문 인용에 반영한다. 기간 밖·미포함은 구분하고 질문·가정·조치 제안·미확인·서로 충돌하는 값은 일치로 확정하지 않는다. 문의 요약에서는 조회 상태 필터를 실제 문서의 결재 상태로 바꾸지 않는다.

- **F009-CONTRACT-09 묶인 사례 확인:** 대표 카드를 선택하면 묶인 사례 수와 펼치기를 제공한다. 대표를 포함한 승인 사례의 번호·버전·원 티켓 번호·승인 시각을 보고 멤버를 선택하면, 현재 티켓 모달 안에서 그 멤버의 조치·검증·적용 조건·원문·검색 점수를 확인한다. 멤버를 개별 1위라고 표시하지 않고 대표 그룹의 순위와 구분한다. 승인 사례 페이지를 새 탭으로 열어 원 티켓을 추적할 수 있다. 카드·자료 유형을 바꾸면 이전 멤버 선택이 섞이지 않는다. 모든 멤버는 현재 공개 가능한 동일 시스템의 승인 후보이며, 멤버의 인용 구간·판정도 검증한다. 단일 사례나 구 서버의 그룹 필드 누락에는 펼치기를 표시하지 않는다.

- **F009-CONTRACT-10 완료 티켓 목록 보관:** `archived_at`이 있는 완료 티켓은 담당자·관리자 업무 목록과 총건수에서 제외한다. 삭제하지 않으며 원 티켓 상세와 문의·처리 기록·승인 사례·검색 공개 조건은 현재 권한으로 계속 검증한다. 완료 전 티켓은 목록 보관할 수 없다. 공개 보관 명령 UI/API는 추가하지 않는다.
