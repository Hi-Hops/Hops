# F009 부서 티켓 목록·상세와 관련 대화

상태: 개발 기준 확정 / 구현·검증 별도 · 범위: MVP 부서 티켓 읽기 전용 목록·상세 / 관련 대화·담당 업무는 후속 · 담당: frontend(화면) · 협의: backend(조회·권한·SSE)
근거: PRD 4.6, 4.11, 8.3 · API 2.1 `GET /api/tickets`, 2.2 `GET /api/tickets/{id}/messages`, 2.4 · DATA 3, 4 · ERD `ticket`, `ticket_assignment`, `member`

## 확정 범위와 남은 작업 (2026-10-27)

MVP는 현재 처리 부서 또는 BIZ_ADMIN 범위의 읽기 전용 목록·상세다. AC07~AC09의 관련 대화는 후속이다. 목록 기본 20·최대 100, processingStatus 필터만 사용한다. routingStatus/개인 담당자 필터·가져오기/처리는 후속이다.

정확한 타입·enum은 [DATA_TYPES](../contracts/DATA_TYPES.md), 정책은 [WIRE_CONTRACT 10절](../contracts/WIRE_CONTRACT.md#10-인증재접속최신-대화분석-재시도-추가-프로필), 담당 구현·미검증은 [11절](../contracts/WIRE_CONTRACT.md#11-담당별-구현과-검증-상태)을 따른다. 확정은 개발 기준 선택이며 팀 리뷰/병합·서비스 구현 완료가 아니다.

## 1. 목표

부서 구성원이 현재 자기 부서에 배정된 티켓을 목록과 상세로 확인하고, 그 티켓과 관련된 사용자·AI 대화만 읽는다. 다른 부서 티켓, 다른 문제의 대화, 운영 로그는 보이지 않는다. MVP 범위는 조회까지다. 가져오기·처리 완료·재이관은 후속이다. (PRD 4.6, 8.2 "재이관·최종 처리·알림 전체를 MVP 완료 조건에 포함하지 않는다")

## 2. 범위 판단

| 항목 | 원본 문서 | 이슈 #31 |
|---|---|---|
| 티켓 목록·상세 | API 2.1(MVP) "현재 배정 부서·개인 및 업무 관리자 범위의 목록과 티켓 상세" | "부서/관리자 티켓 목록·상세" |
| 부서·본인 티켓 목록 화면 | PRD 8.3 후속 필수 | 같은 항목 |
| 관련 대화 | API 2.2(후속) `GET /api/tickets/{id}/messages`, DATA 7 "메시지↔문제/티켓 연결"은 후속 합의 항목 | "관련 대화 접근" |

API 2.1이 목록·상세를 MVP에 두므로 F009-AC01~AC06은 MVP로 쓴다. 관련 대화(F009-AC07~AC09)는 경로가 2.2에 있어 Q-ALL-7로 범위를 확인한다.

## 3. 화면

| 화면 | 경로(제안) | 접근 |
|---|---|---|
| 부서 티켓 목록 | `/tickets` | 현재 처리 부서 구성원 |
| 티켓 상세 | `/tickets/:ticketId` | 현재 처리 부서 구성원, 업무 관리자(관련 대화 권한은 Q-BE-14) |

업무 관리자 화면(F007)은 같은 상세 컴포넌트를 읽기 전용으로 재사용한다. 현재 /tickets/:ticketId와 /admin/tickets/:ticketId 경로를 유지한다(Q-FE-1).

## 4. 사용자 시나리오

1. 네트워크 부서 구성원이 로그인 후 부서 티켓 목록에서 VPN 티켓을 본다.
2. 티켓을 누르면 상세에서 문의 요약, AI 진단, 처리 상태·배정 상태, 배정 이력을 본다.
3. 상세의 "관련 대화"에서 VPN 문제와 관련된 메시지와 이관 뒤 보완 정보, 정정 이력을 시간순으로 본다. 같은 문의의 프린터 문제 대화는 보이지 않는다.
4. 다른 부서 티켓 주소로 들어가면 권한 없음 화면이 나온다.

## 5. 인수 조건

**목록 (MVP · API 2.1)**
- **F009-AC01 부서 범위 목록**
  `GET /api/tickets`로 서버가 허용한 범위의 티켓만 보여 준다. 행마다 제목, 처리 부서, 처리 상태, 배정 상태, 생성 시각을 표시한다. 범위는 화면이 계산하지 않고 서버 응답을 그대로 쓴다. (API 2.1 · 범위 구분 방식 Q-BE-6)
- **F009-AC02 상태 분리**
  `processingStatus`와 `routingStatus`를 따로 표시한다. (API 2.1 · 상태값 Q-ALL-2)
- **F009-AC03 필터·페이지 유지**
  필터와 페이지는 주소에 남기고, 상세를 닫으면 목록의 필터·페이지를 그대로 유지한다. 필터 값을 바꿔도 서버가 허용한 범위만 보인다. (PRD 4.11 · API 2.1 "목록 필터가 권한을 넓히지 않음" · 파라미터 Q-BE-5)
- **F009-AC04 빈 결과·실패 구분**
  배정된 티켓이 없으면 "배정된 티켓이 없어요", 조회 실패면 실패 안내와 다시 시도를 보여 준다. (PRD 4.11)

**상세 (MVP · API 2.1)**
- **F009-AC05 티켓 상세 읽기**
  `GET /api/tickets/{id}`로 문의 요약, AI 진단, 현재 처리 부서, 처리 상태·배정 상태, 배정 이력을 보여 준다. MVP에서는 가져오기·처리 완료·재이관·AI 내용 정정 버튼을 두지 않는다. (PRD 4.6 · API 2.1 · 응답 필드 Q-BE-6)
- **F009-AC06 다른 부서 티켓**
  Given 현재 처리 부서 구성원도 업무 관리자도 아닌 사용자 · When 티켓 주소로 들어가면 · Then 내용을 보여 주지 않고 권한 없음 화면에서 부서 티켓 목록으로 돌아가도록 안내한다. 재이관으로 부서가 바뀐 뒤 다시 열어도 같다. (PRD 4.11 · DATA 4 "현재 처리 부서 구성원만 티켓과 관련 대화를 조회")
  프론트가 현재 사용자에게 티켓 화면 접근 자격이 없음을 아는 경우 상세 모달·상세 조회·TICKET SSE를 시작하지 않는다. 상세 훅에서도 같은 조건을 적용한다. 처리 부서 구성원 등 화면 접근 자격은 있으나 특정 티켓에 접근 가능한지는 서버가 최종 검사한다.

**관련 대화 (이슈 #31 · API 2.2 후속, Q-ALL-7)**
- **F009-AC07 관련 대화 조회**
  상세에서 `GET /api/tickets/{id}/messages`로 해당 티켓과 관련된 사용자·AI 대화를 시간순으로 보여 준다. 가져오기 전에도 현재 처리 부서 구성원이면 볼 수 있다. (PRD 4.6 · API 2.2 · 관련 범위 기준 Q-BE-14)
- **F009-AC08 이관 뒤 보완 정보와 정정 이력**
  이관 뒤 문의자가 보낸 보완 메시지와 정정을 구분해 표시하고, 정정된 메시지는 이전 내용을 볼 수 있게 한다. 표시 형식은 F004-AC02와 같다. (PRD 4.4 "관련 티켓 상세에서 담당자가 확인", 4.6 · DATA 3)
- **F009-AC09 범위 밖 대화 비노출**
  같은 문의의 다른 문제 대화와 내부 운영 로그는 표시하지 않는다. 화면은 문의 전체 대화(`GET /api/inquiries/{id}/messages`)를 대신 불러와 거르지 않는다. (PRD 4.6 · API 2.2 · API 2.4 "문의자용 전체 대화·담당자용 관련 티켓 대화 … 구독 범위를 분리")

**실시간 (MVP · API 2.4)**
- **F009-AC10 재조회 신호**
  목록·상세에 있는 동안 `state.changed`를 받으면 해당 목록이나 티켓을 REST로 다시 조회한다. 이벤트만으로 상태를 확정 표시하지 않고, 재접속 뒤에도 REST로 다시 맞춘다. (API 2.4 · PRD 4.11 · 이슈 #31 "상태 변경 이벤트는 재조회 신호" · 구독 대상 Q-INF-3)

## 6. 계약(화면이 기대하는 값)

공통 필드·필수/nullable·wire 표현의 원본은 [데이터 타입·필드 문서](../contracts/DATA_TYPES.md)다. 아래 MVP 연결표는 확정 개발 기준이다. 후속 기능 후보와 실제 담당 구현·검증은 구분한다.

| 용도 | 경로·이벤트 | 공통 계약 타입 | 구현·검증 추적 |
|---|---|---|---|
| 부서/관리자 목록 | GET /api/tickets | TicketListQuery → TicketPage(TicketCard[]) | Q-BE-5/6 |
| 읽기 전용 상세 | GET /api/tickets/{id} | TicketDetail, AssignmentHistory[] | Q-BE-6/12 |
| 부서 메뉴 판단 | GET /api/auth/me | CurrentUser.department.isRoutable | Q-ALL-5 |
| 목록/상세 실시간 연결 | GET /api/realtime/events?targetType={type}&targetId={id} | DepartmentTicketsTarget / TicketTarget | Q-INF-3 |
| 변경 재조회 | state.changed | StateChangedEvent | Q-INF-6 |
| 관련 대화 | GET /api/tickets/{id}/messages | 이번 공통 Mock 제외 | Q-BE-14, Q-ALL-7 |

목록은 서버가 현재 사용자 부서 또는 BIZ_ADMIN 권한으로 범위를 정한다. 필터는 page/size/processingStatus만 제공하며 부서 선택으로 권한을 넓히지 않는다. 처리 부서 구성원이 아닌 업무 관리자도 허용되지만 운영 관리자 역할만으로는 허용되지 않는다. 읽기 전용 목록·상세는 MVP, 관련 대화는 후속으로 확정했다(Q-ALL-7). 실제 서버 구현·통합 검증은 별도다.

## 7. 범위 밖

가져오기·반환, 처리 완료, 재이관, AI 내용 정정, 장애 그룹 상세, 부서 통계(모두 API 2.2·PRD 8.3 후속), 본인 담당 티켓만 보기(이번 Mock 제외이며 개인 담당자 자동 선정 기능과는 별개).

## 8. 막히는 정도

- 목으로 진행 가능: 목록·상세·권한 없음·빈/실패 상태, 관련 대화 표시 틀.
- 구현·검증 상태: 위 확정 범위와 공통 계약 11절을 따른다. 후속 상세 설계는 QUESTIONS의 해당 ID로 추적한다.

## 공통 Mock 계약 (2026-10-23)

이 기능의 Mock 전송 데이터는 [공통 데이터 타입 문서](../contracts/DATA_TYPES.md)와 [요청·응답 연결표](../contracts/WIRE_CONTRACT.md#8-작업별-데이터-타입-연결)을 따른다. 공용 입력·응답·이벤트 예시는 [Mock 시나리오](../mocks/README.md)를 사용한다. Mock은 계약 예시의 일부이며 모든 확정 정책을 구현한 서버가 아니다. 팀 리뷰·서버 저장/권한·AI 품질 검증 완료를 뜻하지 않는다.
