# ERD 설명 — PRD 1.44 논리 모델

상태: 팀 합의 제품 기획을 바탕으로 한 논리 설계 제안 · 물리 테이블·컬럼·DDL·마이그레이션·구현은 미확정. 실제 구현된 구조는 현재 코드와 마이그레이션에서 확인한다. 목표 정책은 [PRD](PRD.md), 데이터 정본은 [DATA](DATA.md), 서비스 간 정보는 [목표 공통 계약](../specs/contracts/TARGET_CONTRACT.md)을 따른다.

## 1. 관계 한눈에 보기

```text
부서 ── 사용자 ──< 시스템 담당 관계 >── 업무 시스템 ──< 기능
                 (한 사람이 여러 시스템, 시스템별 유효 주담당자 1명)

문의자 ──< 문의 ──< 메시지·정정 이력
             └──< 문제 ── 표준 요청 ── [티켓 생성 작업] ── [티켓]
                       └── 보고 시스템 / 책임 시스템 / 판단 근거
                                    티켓 ──< 배정·수동 정정 이력
                                        ──< 처리·구현·검증 기록
                                        ──< 문의자 해결 확인

처리 기록 ──< 사례 초안 ──< 사례 문서 버전 ── 담당자 승인
                                             ├── Vector 반영 상태
                                             └── Neo4j 반영 상태
시스템·기능·증상·가능 원인·확인 항목·사례·시스템 의존 ── Neo4j 관계
```

그림의 이름과 연결은 논리 개념이다. 실제 테이블 수, 메시지와 문제의 참조 방식, 중간 작업 엔터티와 물리 cardinality는 합의 전이다. 한 문의에 여러 문제가 있고 독립 요청은 개별 티켓을 가질 수 있으나, 구체 작업 모델과 문제당 티켓 제약은 구현 계약에서 정한다.

## 2. 논리 객체와 책임

| 객체 | 보존할 의미 | 관계·유효성 |
|---|---|---|
| 사용자·부서·역할 | 임직원 계정, 소속과 접근 권한 | 부서는 소속이며 티켓 배정 대상이 아니다. |
| 시스템·기능·담당 관계 | 지원 시스템·기능, 유효 기간과 주담당 관계 | 한 사람은 여러 시스템을 맡고 각 시스템은 유효한 주담당자 1명을 갖는다. 이력 관리와 동시성 제약은 물리 설계 시 정한다. |
| 문의·메시지·정정 | 작성자, 원문, 메시지·정정, 최신 문의 버전 | 문의자는 본인 문의를 조회하고 이전 내용은 보존한다. |
| 문제·표준 요청 | 문의 의도·처리 유형, 질문 수, 확인 사실·추정·미확인, 유형별 정보, 보고/책임 시스템·후보·근거 | 문의별 독립 문제를 관리하고 한 문제의 여러 원인 후보를 분리 티켓으로 오인하지 않는다. 보고 시스템은 보존한다. |
| 티켓 생성 작업·결과 | 문제별 티켓 제안, 작업 식별·입력 버전, 성공·실패·저장 결과 미확인 | 동일 업무 작업을 재시도하기 전 기존 저장 여부를 확인하고 미확인 상태에서는 재생성하지 않는다. |
| 티켓·배정 이력 | 처리 대상·주담당자, 배정 근거, 변경 전후와 수동 정정 사유 | 지원 시스템과 주담당자를 Spring이 확인해 저장한다. 자동 재이관과 선점은 범위 밖이다. |
| 처리 기록·해결 확인 | 실제 조치·검증·기능 구현 완료·문의자의 해결/미해결 | 구현 완료와 최종 완료는 별개다. 미해결은 같은 티켓, 무응답은 확인 대기다. |
| 사례 초안·사례 버전·승인 | 원 처리 기록, 내용·버전·출처·공개 범위·작성자·담당자 승인 | 초안은 검색에서 제외한다. 문의자 확인과 해당 시스템 담당자 승인, 기능 요청의 구현·검증을 확인한다. |
| 검색 반영·공개 상태 | 같은 승인 버전별 Vector·Neo4j 반영 결과 및 공개 가능 여부 | 각 저장소를 별도로 추적한다. 둘 다 성공하기 전 양쪽 검색에서 비공개한다. |
| 실행·근거·알림 | 실행·입력 버전, 출처와 권한, 공개 가능한 상태, 확인 요청 | 모델 제안과 서버 확정 결과를 구분한다. 이벤트만으로 저장·해결을 확정하지 않는다. |

## 3. 저장과 상태 불변식

1. **시스템 배정:** 보고 시스템과 책임 시스템을 구분하고 후보·근거를 보존한다. 서버가 지원 시스템과 주담당자를 확인하지 못하면 배정 성공으로 확정하지 않는다.
2. **복합 문의:** 문제별 성공 티켓을 보존한다. 동일 작업 재시도 전 저장 결과와 현재 문의 버전을 확인한다. 저장 미확인은 실패로 단정하거나 새 티켓을 만들지 않는다.
3. **정정과 보완:** 원문·정정 이력을 보존하고 최신 문의 버전에만 새 분석 결과를 적용한다. 배정 후 메시지는 관련 티켓 보완으로 연결한다.
4. **완료:** 담당자 처리·검증 후 문의자 해결 확인으로 최종 완료한다. 기능 요청은 구현 완료 기록이 선행한다. 무응답은 대기하며 완료 후 재오픈은 제외한다.
5. **지식 공개:** 담당자 기록 저장 후 Curator 초안 → 문의자 확인 → 담당자 승인 → 동일 승인 버전의 두 저장소 반영 → 양쪽 성공 시 공개. 실패·미확인은 양쪽 모두 비공개하고 승인·업무 기록은 보존한다.
6. **버전과 출처:** 사례의 문서 버전과 시스템 적용 버전·조건을 구분하고 미확인은 추정하지 않는다. 합성·데모 검증·실제 운영 출처를 구분한다. 구버전 사례를 무조건 삭제하거나 차단하지 않는다.
7. **권한:** 직원 공개 지식과 담당자 내부 자료를 구분하며 시스템 소유권·승인·공개 상태는 서버가 확인한다. 그래프 관계나 모델 출력으로 권한·원인을 확정하지 않는다.

## 4. 물리 설계·마이그레이션 전 확인

- 시스템 주담당자 유효성의 저장 방식, 유일성·동시성, 담당 변경 이력과 권한 회수.
- 문제·티켓 생성 작업·티켓의 물리 관계, 재시도 식별·멱등성, 저장 결과 미확인 확인 방법.
- 표준 요청·메시지·티켓별 관련 대화의 보존·참조 범위와 문의 버전 충돌.
- 처리·확인·승인·각 색인 상태의 저장 위치·전이, 동일 버전의 공개 제어와 실패한 반영의 재실행.
- 기존 부서 기반 API·seed·테이블과 호환성, 실제 이관·롤백과 migration. 기획의 논리 모델을 현재 DB에 적용된 구조로 표현하지 않는다.

## 5. 논리 객체별 필드 검토표

아래는 엔터티별 **보존 정보와 관계를 리뷰하기 위한 후보**다. 표의 명칭은 실제 컬럼명·자료형·nullable·FK·새 마이그레이션을 확정하지 않는다. 요청/응답 필드 후보는 [목표 공통 계약](../specs/contracts/TARGET_CONTRACT.md#8-상세-필드-제안--공통-규칙)을 따른다.

### 5.1 계정·시스템

| 논리 객체 | 필수적으로 추적할 의미 | 관계·제약 검토 |
|---|---|---|
| 사용자 | 내부 사용자 식별·로그인·사번·소속·현재 활성 여부 | 기존 회원과 사번·로그인 ID를 구분하고 비밀번호 원문을 보존하지 않는다. |
| 소속·역할 | 부서 소속, 업무 관리자 등 서버가 확인한 역할 | 소속과 시스템의 책임 관계는 별개다. |
| 업무 시스템·기능 | 시스템 식별·표시 이름·기능과 지원 범위 | 전자결재·공통 로그인·파일 공유의 기능 경계와 ID는 데이터 설계에서 정한다. |
| 시스템 담당 관계 | 시스템·주담당자·유효 기간과 변경 사유/이력 | 현재 유효 주담당자 1명, 한 사람이 여러 시스템을 담당할 수 있다. 동시 변경과 과거 이력의 저장 방식 검토. |

현재 [V1 마이그레이션](../backend/spring/hops/src/main/resources/db/migration/V1__create_department_member_role.sql)에서 확인되는 테이블은 `department`, `member`, `member_role`이다. 기존 `department.is_routable`은 이전 부서 배정의 데이터이며 새 시스템 담당 관계를 뜻하지 않는다. 기존 마이그레이션을 수정했다고 가정하지 않는다.

### 5.2 문의·메시지·문제

| 논리 객체 | 보존 의미 | 관계·제약 검토 |
|---|---|---|
| 문의 | 문의자·생성 시점·분석 입력 버전·전체 표시 상태 | 본인 문의 접근과 여러 문제의 독립 진행. |
| 메시지·정정 | 내용·작성 주체·순서·revision·시각과 이전 내용 | 문의 원문을 보존하고 AI 결과와 사용자 입력을 구분. |
| 문제 | 원 문의, 요약·의도·처리 유형·문제별 질문 수·확인/미확인 | 문제당 질문 묶음 최대 5회. 보고 시스템 미확인일 수 있다. |
| 표준 요청 | 문제·문의 버전·보고/책임 시스템 후보·근거·유형별 정보 | 원문과 출처를 대체하지 않으며 제안과 확인 사실을 분리. |
| 관련 메시지 | 문제·티켓과 관련 있는 대화·보완 정보의 연결 | 연결 모델·인덱스와 허용 조회 범위는 확정 전. |

복합 문의의 각 문제는 별도의 완료 조건을 가진다. 같은 증상의 여러 원인 후보는 문제 자체를 늘리는 기준이 아니다. 업무 작업·티켓과의 세부 물리 cardinality는 [DATA](DATA.md#62-문제생성-작업티켓)의 불변식을 충족하도록 합의한다.

### 5.3 티켓·담당자 처리

| 논리 객체 | 보존 의미 | 관계·제약 검토 |
|---|---|---|
| 생성 작업 | 문제·입력 버전·제안·저장 결과와 재시도 식별 | 실제 미생성, 성공, 저장 결과 미확인을 구분한다. 같은 작업의 중복 생성을 방지한다. |
| 티켓 | 원 문제·제목·내용·보고/책임 시스템·처리 상태 | 서버가 검증한 결과만 저장·표시. |
| 배정·정정 | 주담당자, 판단 근거, 변경 전후·사유·주체·시각 | 담당 관계 확인 실패 시 성공 확정 금지. 선점·자동 재이관 제외. |
| 처리 기록 | 실제 조치·변경·검증과 작성자·시각 | 기능 요청의 구현 완료와 최종 문의자 확인을 구분. 실패한 시도도 업무 이력으로 보존. |
| 해결 확인 | 문제·티켓·문의자·응답·시각 | 해결·미해결을 구분하고 무응답은 확인 대기. 타 문제를 일괄 완료하지 않는다. |

### 5.4 사례·검색·실행

| 논리 객체 | 보존 의미 | 관계·제약 검토 |
|---|---|---|
| 사례 초안·버전 | 처리 기록·문의/티켓 출처, 사례 문서 버전·대상 시스템·적용 시스템 버전·조건 | 생성만으로 검색 공개하지 않는다. 적용 버전 미확인을 추정하지 않는다. |
| 사례 검토·승인 | 문의자 확인, 해당 시스템 담당자, 승인 사례 버전·시각 | 기능 요청은 구현·검증 기록 필요. 제품 내 자기 승인과 팀 데이터 PR 리뷰는 별개. |
| 저장소 반영 상태 | 사례 ID·승인 버전·Vector/Neo4j 각각의 성공·실패·미확인 | 같은 승인 버전의 양쪽 성공 전 검색 비공개. 반영 재실행의 멱등성 검토. |
| 실행·근거 | 문의 버전·역할·소요 시간·공개 가능한 근거·오류 | 실행 완료는 업무 저장·배정 성공이 아니다. 비밀값·내부 사고 과정 제외. |
| 관계 데이터 | 시스템·기능·증상·가능 원인·확인 항목·사례 및 의존 관계 | Neo4j 관계의 노드/속성/제약은 미정. 그래프를 담당자 정본으로 쓰지 않는다. |

## 6. 현재 구현과 제안 모델의 연결

현재 코드에서 확인된 V1의 계정·부서·역할 구조와 새 논리 객체는 같은 완성도를 갖지 않는다. 문의·티켓·사례의 새 물리 스키마는 확정하지 않았으며, 서버의 관련 패키지 존재만으로 업무 저장이 구현됐다고 판단하지 않는다. 기존 데이터·API를 전환할 때는 다음을 검토한다.

1. 기존 회원·소속을 재사용할 수 있는지와 시스템 담당 관계를 새로 연결하는 방법.
2. 문제·생성 작업·티켓의 동시 요청과 성공 결과 유일성, 오류 후 저장 확인.
3. 현재 사용자 권한과 관련 대화 범위, 담당자 변경 시 과거·현재 접근.
4. 사례 승인 버전과 두 저장소 반영의 추적·재실행·공개 검증.
5. 새 DB 마이그레이션과 기존 데이터 호환성, 배포·롤백 및 테스트. 운영 데이터는 문서 변경만으로 삭제·이관하지 않는다.
