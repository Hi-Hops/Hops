# API 설계 — PRD 1.44 전환 기준

상태: 팀 합의 제품 방향을 반영한 설계 · 상세 입출력과 새 경로는 구현 전 협의 · 실제 구현 별도. [PRD](PRD.md), [데이터](DATA.md), [공통 계약](../specs/contracts/README.md)을 함께 본다. 이전 부서 기반 구현과 Mock wire 형식은 [기존 전송 계약](../specs/contracts/WIRE_CONTRACT.md)에 보존하며 새로운 시스템 배정 계약으로 오인하지 않는다.

## 1. 책임과 공통 원칙

React는 Spring에 REST 요청을 보내고 허용된 SSE를 수신한다. Spring은 인증·현재 권한, 문의 버전, 시스템과 주담당자, 업무 저장·배정·완료·승인·검색 공개를 확정한다. Python은 Supervisor 및 전문 에이전트의 분석·검색과 제안을 수행하며 업무 DB에 직접 쓰지 않는다. 진행 이벤트, 모델 출력, 요청 접수는 저장·배정·완료의 증거가 아니다.

입력 검증과 인증을 수행하고 민감정보·내부 사고 과정을 응답하지 않는다. 문의·티켓·지식은 현재 권한으로 서버에서 필터링한다. 조회 실패와 결과 없음, 시스템 오류와 범위 밖, 업무 저장 미확인과 확인된 실패를 구분한다. 이미 저장된 결과를 재시도로 중복 생성하지 않는다.

## 2. 사용자와 업무 흐름

| 기능 | 요청과 결과의 의미 | 검증과 남은 계약 |
|---|---|---|
| 인증·지원 시스템 | 자체 로그인·현재 사용자·지원 시스템 조회 | 토큰과 현재 접근 범위 검증; 시스템 목록·담당자 표현 및 전환 방식 설계 |
| 문의 생성·채팅·정정 | 문의·메시지 저장, 질문 답변, 정정과 최신 버전 분석 | 본인 권한·버전·중복 요청 검증; 저장 전 성공 표시 금지 |
| 시스템 확인 | 보고 시스템이 불명확한 문제에 지원 시스템 선택 | 미선택 시 저장된 확인 대기 유지; 5회 질문 제한 우회 금지 |
| 문의·문제별 결과 | 확인 사실·미확인·문제별 진행·저장 티켓·실패/미확인 조회 | 본인 범위; 성공한 티켓과 실패한 문제를 분리 |
| 티켓 생성·배정 | Ticket의 표준 요청·책임 시스템 후보·근거를 서버에 제안 | 시스템/주담당자 검증 후 저장; 불확실하면 보고 시스템 담당자가 조사 |
| 부분 실패 복구 | 확인된 미생성 작업을 재시도 | 저장 결과·문의 버전 선확인, 기존 티켓 재사용, 결과 미확인 시 신규 생성 금지 |
| 담당자 처리·정정 | 담당 시스템 업무와 관련 대화·근거 조회, 처리·검증 및 수동 정정 기록 | 현재 담당 관계·권한, 변경 주체·사유 확인; 자동 재이관 없음 |
| 사용자 확인 | 처리 결과 확인 및 해결/미해결 응답 | 문제별 처리, 미해결은 같은 티켓 계속, 무응답은 대기 |
| 사례 승인·검색 반영 | 초안 조회·수정·승인 및 반영 상태 조회·실패 반영 재실행 | 문의자 확인, 기능 요청의 구현·검증, 담당자 권한 및 같은 승인 버전 확인 |

경로·HTTP 메서드·필드·상태 enum·성공/오류 코드·재시도 조작·권한은 구현 전 협의한다. 위 기능 표는 신규 API의 구현이나 URL 확정을 의미하지 않는다. 기존 로그인 및 SSE 구현 상태는 [Spring 실행 안내](../backend/spring/hops/README.md)를 따른다.

## 3. REST·SSE와 버전

- 저장 성공은 Spring의 확정 응답이나 저장 결과 조회로 확인한다. 전송 결과가 불명확하면 입력과 같은 업무 요청 식별을 보존해 재확인한다.
- 최신 문의 버전으로 정정·분석하며 이미 저장한 티켓을 유지한다. 늦은 이전 버전의 분석 결과는 현재 상태에 적용하지 않는다.
- 공개 가능한 진행과 업무 변경 이벤트를 전달하고, 재연결 뒤 인증·현재 대상 권한을 다시 검사하며 REST로 저장 상태를 조회한다.
- 구독 대상, 저장 명령의 멱등 범위, 이벤트 중복·복구와 토큰 정책은 기존 프로필 및 실제 구현을 대조해 전환한다. 현재 부서 SSE가 시스템 대상도 지원한다고 가정하지 않는다.

## 4. Spring ↔ AI와 지식 반영

Spring은 허용된 대화·문제·입력 버전·지원 시스템과 권한 문맥을 제공한다. AI는 질문·근거·표준 요청·책임 시스템 등 제안을 반환하고 Spring은 현재 버전, 접근 범위, 지원 시스템 및 주담당자를 검증한다. 구체 payload·식별자와 인증은 [에이전트 계약](../contracts/agents/README.md)에서 기능 구현 전 협의한다.

해결 기록 저장은 Curator 실행과 분리한다. 문의자 해결 확인과 담당자 승인 뒤 같은 승인 버전의 Vector와 Neo4j 반영 상태를 각각 확인한다. 양쪽 성공 전 어느 검색 경로에서도 사례를 공개하지 않는다. 실패나 결과 미확인 시 승인·처리 기록은 유지하고 실패 반영을 다시 실행할 수 있어야 한다. 원자적 공개, 재반영 식별·권한·호출 방식은 아직 정하지 않았다.

## 5. 구현 전 협의·검증

1. 시스템·주담당자 조회, 권한과 책임 시스템 수동 정정 및 접근 회수.
2. 문제·작업·티켓 식별, 멱등·버전 충돌·부분 실패와 저장 결과 미확인 복구.
3. 처리·구현 완료·문의자 확인·사례 승인·두 저장소 반영 및 공개 상태.
4. AI 호출·서비스 인증·진행 이벤트, 실제 모델 예산과 재시도 제한.
5. React–Spring SSE 대상과 REST 재조회, 오류·권한·통합 검증.

## 6. 인증·조회·업무 변경의 상세 경계

### 6.1 현재 구현과 목표

| 영역 | 현재 확인 가능한 기준 | 새 기획에서 필요한 내용 |
|---|---|---|
| 인증 | Spring에 자체 로그인·JWT 발급·내 정보 조회가 있다. 구체 실행과 설정은 [Spring 안내](../backend/spring/hops/README.md)를 따른다. | 현재 시스템 담당 관계와 관리자 권한을 서버에서 확인한다. Refresh·로그아웃·접근 회수의 실제 구현은 별도 검증한다. |
| 문의·메시지 | 기존 프론트는 문의 생성·메시지·정정에 REST 프로필을 사용한다. | 실제 Spring 저장·버전·소유권 및 새 시스템 확인을 연결한다. |
| 티켓 | 기존 프론트 Mock은 부서 중심 티켓 결과를 제공한다. | 책임 시스템·주담당자·배정 근거와 처리 기록을 서버가 확정해 제공한다. |
| 실시간 | Spring SSE의 현재 대상은 부서 기반이다. | 문의·티켓·담당 시스템에 대한 접근 범위·구독·재조회 계약을 확정한다. |
| 사례·검색 | 새 사례 승인 및 두 저장소 공개는 목표 기능이다. | 해결 확인·담당자 승인·동일 버전별 양쪽 반영과 검색 접근을 연결한다. |

현재 코드의 엔드포인트를 목표 기능의 완성으로 간주하지 않는다. 기존 프론트 호출·응답과 현재 구현 차이는 [전송 계약](../specs/contracts/WIRE_CONTRACT.md) 9~11절을 참고한다. 새 경로·필드·응답 코드는 [목표 공통 계약](../specs/contracts/TARGET_CONTRACT.md)의 제안을 기준으로 소비자와 리뷰한다.

### 6.2 문의·문제별 변경

1. **문의 생성:** 서버는 인증한 문의자를 사용해 원문을 저장한다. 사용자 전달 ID로 소유자를 확정하지 않는다. 저장 확인이 불가능하면 화면은 입력을 보존하고 결과 미확인으로 표시한다.
2. **대화·정정:** 메시지와 정정 이력을 보존하고 분석 대상 문의 버전을 추적한다. 실행 결과가 늦게 도착하면 서버가 현재 버전과 대조한다. 배정된 문제에 관한 추가 메시지는 관련 티켓의 보완 정보로 연결한다.
3. **보고 시스템 확인:** 문의·문제의 소유자가 지원 시스템 목록에서 선택한 값을 서버가 검사한다. 미선택 상태와 시스템 확인 대기를 저장하며 별도 CS 검토 티켓을 만들지 않는다.
4. **질문·결과:** 서버는 같은 문제의 질문 묶음 수를 최대 5회로 관리한다. 문제별 추가 질문·범위 밖·생성 성공·실패·결과 미확인을 각각 표현한다. AI는 질문 수나 티켓 저장 성공을 임의 확정하지 않는다.
5. **무티켓 안내:** 허용된 직원 가이드에 근거해 답변하고 문의자의 해결 확인을 받는다. 검색 결과 없음과 검색 시스템 오류를 구분한다. 처리 기록이 없는 대화만으로 사례 초안을 만들지 않는다.

### 6.3 티켓·담당자 업무

- **생성:** Ticket 제안에는 원 문제·입력 버전·표준 요청과 책임 시스템 후보·근거가 필요하다. Spring은 문의/문제 소속, 최신 버전, 지원 시스템과 유효 주담당자를 검증한다. 보고 시스템은 별도로 보존한다.
- **저장 확인:** 성공 응답은 해당 작업의 티켓과 배정 저장이 확인된 뒤 반환한다. 각 티켓의 트랜잭션 경계와 부분 실패 저장 방법은 물리 설계에서 정한다. 성공한 다른 문제를 실패로 되돌리지 않는다.
- **재확인과 재시도:** 기존 성공 티켓은 재사용한다. 결과가 미확인이면 저장 여부를 확인하기 전 새 티켓을 만들지 않는다. 실제 미생성으로 확인된 작업은 동일 업무 작업으로 재시도한다. 재시도 주체·권한·요청 키와 동시성 처리는 미정이다.
- **담당자 조회:** 현재 담당 시스템의 티켓과 관련 문제의 대화·보완 정보·근거만 제공한다. 전체 문의의 다른 문제, 내부 운영 로그와 제한된 지식을 자동으로 포함하지 않는다.
- **수동 정정:** 담당자 또는 업무 관리자의 권한, 대상 티켓의 현재 상태, 새 시스템·주담당자, 변경 사유와 근거를 확인한다. 변경 전후·주체·시각을 이력으로 남긴다. 자동 재이관은 구현하지 않는다.
- **처리·확인:** 담당자가 실제 조치·검증과 필요한 경우 기능 구현 완료를 기록한다. 문의자의 해결/미해결 응답은 해당 문제에만 적용하고 미해결은 같은 티켓을 계속 처리한다. 무응답은 확인 대기다.

### 6.4 사례의 승인·반영·검색

| 행위 | 서버가 확인할 정보 | 사용자에게 표시할 사실 |
|---|---|---|
| 처리 기록 저장 | 티켓·작성자·실제 조치/검증·권한 | 처리 기록 저장. Curator 실행 성공과 구분 |
| Curator 초안 생성 | 원 처리 기록·문의 버전·접근 범위 | 초안 또는 실패. 업무 기록·완료는 유지 |
| 해결 확인 | 대상 문제·티켓·문의자 응답 | 확인 대기, 해결 또는 미해결. 한 문의의 다른 문제를 일괄 완료하지 않음 |
| 사례 검토·승인 | 문의자 확인, 해당 시스템 담당자, 사례 버전; 기능 요청이면 구현·검증 기록 | 승인과 검색 반영은 별개 |
| 검색 반영 | 같은 승인 버전의 Vector와 Neo4j 각각의 결과 | 두 결과가 모두 확인되기 전 공개 완료가 아님 |
| 반영 재실행 | 실패/미확인 결과, 승인 버전과 재실행 권한 | 재실행 접수와 성공을 구분. 성공한 반영·업무 기록은 보존 |
| 검색 | 승인 버전의 두 반영 성공, 사용자 접근 범위, 적용 버전·조건 | 직원용·담당자용 결과를 구분하고 적용 버전 미확인은 추정하지 않음 |

한 저장소의 성공·다른 저장소의 실패/미확인/다른 버전만으로 어느 경로에서도 해당 승인 사례를 공개하지 않는다. 반영 실패의 재실행 API·자동 실행 여부·잠금·원자적 공개 방식은 아직 결정하지 않았다. 자동 재시도와 전용 복구 화면은 제품 범위에서 제외한다.

## 7. 통신 실패·동시 요청 검토

| 상황 | 소비자가 구분할 결과 | 책임과 복구 |
|---|---|---|
| 입력 검증 실패 | 요청을 저장하지 못한 검증 오류 | 입력 보존. 잘못된 값을 자동 반복하지 않는다. |
| 인증 실패·권한 없음 | 인증 문제와 대상 접근 거부 | 서버가 현재 사용자의 소유권·시스템 담당 관계를 검사한다. |
| 조회 0건·검색 없음 | 정상 수행했지만 허용된 결과가 없음 | 시스템 오류와 구분한다. 근거가 없으면 원인을 지어내지 않는다. |
| 요청 응답 유실 | 업무 저장 결과 미확인 | 저장 여부를 확인한다. 단순 timeout을 미저장으로 단정하지 않는다. |
| 버전 충돌·늦은 실행 | 현재 입력과 다른 버전에 대한 결과 | 저장된 결과를 보존하고 최신 상태를 다시 조회한다. |
| 동일 작업 동시 요청 | 하나의 업무 결과가 여러 번 요청됨 | 동일 작업 식별·DB 유일성·거래 경계의 구체 방법을 설계하고 테스트한다. |
| 검색 반영 부분 실패 | 저장소별 성공·실패·미확인 | 해당 사례 버전은 양쪽에서 비공개하고 실패 반영만 복구한다. |

기존 전송 프로필의 `Idempotency-Key`, `MutationResult`, 오류 코드·시간값은 **기존 클라이언트가 기대하는 형식**이다. 새 계약에 그대로 채택할지 별도로 정한다. 기존 키로 저장 결과 확인이 가능한지 및 보존 기간은 실제 서버 구현으로 검증해야 한다.

## 8. 실시간 통신과 서비스 간 연결

React→Spring 업무 명령·조회와 Spring→React SSE는 별개다. Spring은 허용된 진행·상태 변경만 보내고, 화면은 연결 재개 뒤 REST로 영속 상태를 다시 조회한다. 답변 조각과 이벤트 도착만으로 업무 저장을 확정하지 않는다. 권한이 변경된 사용자에게 과거 구독 권한을 계속 부여하지 않도록 새 요청·재연결 시 현재 관계를 검사한다.

Spring→Python 실행 요청과 AI 진행/결과의 경로·서비스 인증·이벤트 스키마는 통합 전에 합의한다. 기존 Python `hops-mock-1`과 내부 `agent-1`은 부서 중심이며 새 시스템 계약이 아니다. 사용자 JWT를 AI에 그대로 전달하기보다 서버가 검증한 최소 권한 문맥을 전달하도록 계약을 검토한다. 모델 출력의 시스템 ID·근거·버전은 Spring이 다시 검증한다.

## 9. 검증 사례와 연결 문서

- 본인의 문의·권한 없는 문의/티켓·시스템 담당 변경 후 접근을 각각 검증한다.
- 전자결재에서 발생한 로그인 문의가 공통 로그인 담당으로 배정되는 경우와 근거 부족으로 보고 시스템 담당이 조사하는 경우를 구분한다.
- 복합 문의 일부 성공, 저장 후 응답 유실, 저장 여부 조회 실패, 동일 요청 경합과 오래된 분석 결과를 검증한다.
- 구현 완료와 문의자 확인, 무응답·미해결·최종 완료를 구분한다.
- 사례의 한쪽 반영 실패·미확인·버전 불일치에서 Vector와 Neo4j 양쪽 검색이 공개하지 않는지, 재반영 이후 권한별 검색이 가능한지 검증한다.

이는 구현 후 관찰할 조건이다. 실제 경로·DTO와 상태 전이는 [목표 공통 계약](../specs/contracts/TARGET_CONTRACT.md), 업무 관계는 [DATA](DATA.md), 화면별 동작은 [기능 명세](../specs/README.md)와 함께 리뷰한다.
