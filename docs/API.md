# API 설계 — PRD 1.44 공통 계약

상태: hops-system-1 목표 계약 · 코드 적용/통합 검증은 별도. 사용자 명령·조회는 React↔Spring REST, 공개 진행·변화는 Spring→React SSE, AI 실행/색인/검색 권한은 서비스 전용 HTTP를 사용한다. [공통 진입점](../specs/contracts/README.md), [결정 대장](../specs/QUESTIONS.md)을 따른다. [사례 복구·공개 중단 API 변경안](../specs/F011-case-lifecycle/RECOVERY_PROPOSAL.md)을 참고한다.

## 1. 정본과 책임

AI→Spring 내부 티켓 생성·조회·제한 재시도는 [Ticket 도구 REST 계약](../contracts/agents/TICKET_TOOLS.md)을 따른다. 공개 work-item API와 인증·호출 주체를 구분한다.

AI→Spring 내부 지식 검색·관계 조회는 [지식 검색 REST 계약](../contracts/agents/KNOWLEDGE_TOOLS.md)을 따른다. 같은 서비스 토큰 인증을 쓰며 접근 범위는 요청이 아니라 실행에서 Spring이 확정한다.

| 내용 | 정본 |
|---|---|
| 필드·자료형·필수/null·enum·요청 본문 | [DATA_TYPES 신규 절](../specs/contracts/DATA_TYPES.md#신규-계약-hops-system-1) |
| /api/v2 REST·오류·SSE·멱등/저장 확인 | [WIRE_CONTRACT12절](../specs/contracts/WIRE_CONTRACT.md#12-신규-계약-hops-system-1) |
| /internal/v2 실행·반영·권한 검증·State | [에이전트 계약](../contracts/agents/README.md#hops-system-1-실행-계약안) |

Spring이 현재 인증·권한·문의 버전·업무 저장·배정·해결 확인·승인·검색 공개를 확정한다. Python은 허용된 자료로 제안하고 업무 DB에 직접 쓰지 않는다. AI State와 Entity와 외부 DTO는 별도 객체다. 모델 응답·202 접수·진행 이벤트만으로 업무 성공을 표시하지 않는다.

인증·권한 문맥·모델 출력·검색·도구의 공통 요구사항은 [보안 개발 명세](SECURITY.md)를 따른다. 해당 SEC 요구사항의 구체 입출력·상태는 아래 연결 계약으로 정의하며 실제 구현·검증과 구분한다.

공통 receipt·작업/키 결과 조회·페이지·SSE 재동기화도 WIRE12절에 정의한다. 관리자는 메타데이터/정정만, 문의자는 본인 결과만, 현재 담당자는 관련 업무와 허용 원문 구간만 받는다. 조회 실패를 빈 결과로, timeout을 DB 미저장으로 바꾸지 않는다.

채팅은 [WIRE12.8절](../specs/contracts/WIRE_CONTRACT.md#128-채팅-송수신-완료-규칙)의 입력 저장→실행 접수→임시 SSE→최종 저장→REST 병합 순서를 사용한다. 상담 run당 Spring이 예약한 answerMessageId의 AI 메시지 하나를 저장하며 공개 Run 성공은 답변·질문/가이드 상태 commit 뒤 반환한다. SSE 유실이나 조각 없는 성공도 같은 REST 조회로 완료한다.

## 3. Spring↔AI

상담/Curator는 `/internal/v2/runs`, 사례 저장소 반영은 `/internal/v2/index-jobs`, AI 검색 후보의 최신 권한 검증은 Spring의 `/internal/v2/knowledge/authorizations`로 구분한다. 모든 내부 호출은 서비스 Bearer·고정 origin과 정해진 타입을 사용하고 사용자 JWT/쿠키를 전달하지 않는다.

Spring은 기존 저장 결과·원문·현재 입력/정책 버전·실행 기한과 누적 한도를 제공한다. AI는 구조화된 제안을 반환하며 Spring이 현재 버전·실제 출처·지원 시스템·현재 PRIMARY를 검증해 적용한다. 같은 runId·다른 결과는 거부한다. 문서/CASE 후보는 승인·공개·ACL 검증 전에 모델 입력으로 넣지 않는다.

승인 후 반영은 같은 caseId/caseVersion/store/jobId/attempt/digest를 대조한다. 다른 버전·오래된 attempt·결과 미확인으로 공개 gate를 열지 않는다. 두 저장소 성공을 DB에서 확인한 뒤 검색 반환 시에도 현재 권한을 다시 검사한다.

## 4. 값과 완료 상태

Vector 저장·RunLedger·개발 origin·평가 게이트는 [결정 대장](../specs/QUESTIONS.md#실행검색-기본값)을 따른다. 모델 선정·단가·예상 비용·금액 예산과 구체 실행 설정값은 이 계약에서 제외한다. 공용 도메인·키·비밀번호는 배포 환경 입력이며 계약을 비워 둔 항목이 아니다. 새 공급자·유료 관리형 인프라로 자동 대체하지 않는다.

현재 프론트는 `/api/v2`·`hops-system-1` DTO·Mock을 사용한다. Spring도 인증·부서 SSE의 공개 경로는 `/api/v2`이며, 시스템 권한 DTO·업무 API·시스템/사례 SSE는 구현·통합 검증이 남아 있다. Python은 실행 wire 검증·서비스 인증·저장된 실행 조회와 파이프라인 주입 시 접수·백그라운드 실행을 제공한다. 실제 역할·모델·검색 파이프라인과 실행 SSE는 미연결이며 옛 agent-1 실행 API는 제거됐다. 문서/JSON 검사·Mock·실제 저장/권한·실제 모델/검색·브라우저 E2E를 분리해 기록한다.


## 5. 병합 ERD 반영

[PR #69](https://github.com/Hi-Hops/Hops/pull/69)의 물리 ERD를 기준으로 [DATA11절](DATA.md#11-완성-erd-대조-결과와-병합-기준)에 상태/버전·원문/표준 요청·CASE/색인·실행/명령 매핑을 확정했다. 현재 PRIMARY DTO는 관계 ID 없이 반환하고 처리 기록의 FAILED_ATTEMPT·확인된 원인/적용 버전·CASE 문제 설명을 포함한다. 저장 보완은 ERD6절의 공통 계약 설계다. 프론트는 신규 계약으로 전환됐으며 서버의 업무 DTO·저장·권한 연결은 별도다. 전환 전 계약은 기록으로 보존한다.

담당자의 실제 장애 확정은 POST /api/v2/tickets/{ticketId}/processing-type-corrections로 INVESTIGATION↔INCIDENT만 변경한다. 자동 AI 확정과 관리자 역할만으로의 변경은 허용하지 않으며 상태·확인 요청과 분리한다.

### 완료 티켓 목록 보관

완료 티켓의 `archived_at`은 업무 목록 보관 시각이다. `RESOLVED`만 보관할 수 있으며 담당자·관리자 티켓 목록과 총건수에서 제외한다. 삭제와 달리 기존 권한의 원 티켓 상세·문의 연결·승인 사례·검색 공개 조건은 유지한다. 현재 공개 보관 명령 API는 없으며 별도 로컬 데이터 정리에 사용한다.

### 담당자 티켓 추천 사례

`GET /api/v2/tickets/{ticketId}/recommended-cases`는 현재 책임 시스템의 주담당자에게 티켓 제목과 유사한 승인 사례를 최대 5건 반환한다. 해당 시스템의 공개 범위와 현재 승인 버전을 확인하며 Vector와 Neo4j가 모두 성공한 사례만 포함한다. 기존 지식 근거 필드에 추천 전용 `recommendation`을 추가한 배열이다([DATA_TYPES](../specs/contracts/DATA_TYPES.md)). 검색을 수행할 수 없으면 빈 결과 대신 검색 불가 오류를 반환한다. 검색을 위해 티켓 제목을 기존 임베딩 서비스로 전달하며, 설명을 위한 추가 모델 호출이나 저장·배정 변경은 없다.

`recommendation`은 실제 키워드·벡터 검색의 순위·원점수·일치 검색어·결합 점수와 검색어를 제공한다. 결합 점수는 `0.8/(10+키워드 순위) + 1.0/(10+의미 순위)`이며 후보에 없는 경로의 기여는 0이다. 해결 확률·조건 일치율로 변환하지 않는다. 조건 비교는 검색 순위를 바꾸지 않으며, 권한 검사를 거친 표준 요청의 확인 사실만 사용한다. 책임 시스템은 ID로 비교하고 명시적인 조회 상태 필터는 단일 값만 일치·불일치로 판단한다. 부정·변경 이력·모름·복수 값은 추가 확인으로 남긴다. 그 밖의 자유서술 적용 조건은 확인 사실과 승인 조건을 나란히 제공하고 추가 확인으로 표시한다. 현재 시스템 버전 정보가 없으므로 사례의 적용 버전이 있어도 버전 일치를 단정하지 않는다. 프론트는 구 서버의 `recommendation` 누락·null을 허용하며 근거 미제공을 안내한다.

### 담당자 해결 근거 워크스페이스

`GET /api/v2/tickets/{ticketId}/assistance`는 현재 주담당자에게 티켓 문맥과 CASE·GUIDE·RUNBOOK·POLICY를 제공한다. 기존 `recommended-cases`는 유지한다. 신규 응답은 `ticketId`, `ticketRevision`, `standardRequestId`, `query`, 허용된 USER 원문 `sources`, `materials`다. 자료는 기존 근거와 `assessment`를 묶는다.

검색 입력은 제목·요약·사용 화면·실제 동작·확인 사실과 문제별 공개가 허용된 최근 USER 원문이며 추정·미래 조치·검증 기록은 넣지 않는다. 같은 입력의 임베딩을 한 번 계산해 유형별 후보를 확보한다. 정렬은 명시적 불일치가 없는 자료 우선 → 일치 조건 수 내림차순 → 미확인 핵심 조건 수 오름차순 → 전체 미확인 조건 수 오름차순 → 기존 통합 검색 점수 내림차순이다. 핵심 미확인 조건은 `conditions`의 UNKNOWN 중 분류 항목인 `기능`과 `SYSTEM`을 제외한 적용 전 확인 항목이다. 승인 시각·특정 사례 ID는 가점으로 쓰지 않는다. 검색 경로별 원점수·순위는 재정렬 후에도 그대로 보존한다.

사례 중복은 제목이나 `사례 유형` 라벨만으로 판단하지 않는다. 같은 시스템·적용 버전·공개 범위에서 승인 스냅샷의 실제 조치가 같고, 구조화된 적용 조건이 충돌하지 않으며 공통 조건이 2개 이상(기능 제외)이거나 적용 조건 원문이 같을 때 대표 하나를 선택한다. 조회 상태를 전체로 바꾼 실제 조치는 제한된 표현 규칙으로 묶되, 부정·가정·미실행 또는 별도 권한·기간·제목 변경이 포함되면 동일 조치로 단정하지 않는다. 그 밖의 조치는 공백을 정리한 조치 원문이 같을 때만 묶는다. 그룹 내 모든 사례를 서로 대조해 조건 누락을 경유한 충돌 조건 병합을 막는다. 현재 문의에 대한 불일치 유무가 다른 사례도 별도로 남긴다. 대표는 위 정렬 기준으로 선택하고 `assessment.reasons`에 실제 검색 범위·정렬 기준·묶인 사례 수를 제공한다. 최종 상한은 사례 3건, 매뉴얼·런북·정책 각 2건이다. 승인·권한·현재 버전·동일 버전 양쪽 CASE 색인 조건을 그대로 적용한다.

`assessment`는 `relevance`(HIGH/MEDIUM/REFERENCE/CONFLICT), `family`, 업무 관련 `reasons`, `conditions`, `quotePairs`, 원문 `sections`, `nextChecks`, `matched/unknown/mismatched`를 포함한다. HIGH는 알려진 조건 2개 이상 일치하고 미확인·불일치가 없을 때만 표시한다. 이는 내용 유사도나 해결 확률이 아닌 **적용 조건 대조 등급**이다. 기록된 기능 분류는 해당 보고 시스템과 책임 시스템이 같을 때만 보완한다. 원인·현재 문서 상태를 최근 상신했다는 이유만으로 확정하지 않는다.

기능 ID가 없는 기존 요청은 같은 문제로 공개된 USER 원문과 출처가 있는 `하려던 업무·화면`/`기능` 확인 사실을 대조해 현재 시스템 카탈로그의 단일 기능명을 보완한다. 새 티켓 저장도 같은 규칙을 적용하며 현재 활성 기능 ID를 재검증한다. 화면·기능명이 없는 단순 증상, 출처가 다른 사실, 부정·질문·추정·복수 기능은 확정하지 않는다. AI의 검색용 `featureCandidates`는 기능 확정 근거가 아니다. 보완한 기능의 원문 인용도 조건 비교에 제공한다.

각 자료의 `sourceCase`는 사례일 때 사례 번호·원 티켓 ID/번호·승인 시각을 제공한다(`caseNumber`, `ticketId`, `ticketNumber`, `approvedAt`). `groupedCases`는 중복으로 묶인 승인 사례 전체(대표 포함)를 같은 조건 정렬 순서로 제공하며, 단일 자료는 빈 배열이다. 멤버는 `evidence`, `assessment`, `sourceCase`를 보존하고 그룹을 재귀 중첩하지 않는다. 모든 멤버는 대표와 동일한 현재 권한·승인 버전·양쪽 색인 공개 검증을 통과한 검색 후보다. 번호·승인 시각은 정본에서 읽고 제목이나 모델 문구에서 추정하지 않는다. 그룹을 펼쳐 멤버를 선택하면 해당 멤버의 조치·검증·조건·원문·실제 검색 점수를 표시하며, 대표 카드의 순위를 멤버의 개별 순위로 표시하지 않는다. 승인 사례 페이지는 별도 탭으로 열 수 있다. 구 서버의 필드 누락은 펼치기 없이 기존 자료 표시를 유지한다.

`quotePairs`는 라벨·판정, 현재 USER 메시지 ID, 현재 인용구와 UTF-16 시작/끝, 자료 인용구와 시작/끝을 제공한다(end exclusive). 현재 원문은 문제별 권한 투영 후 사용한다. 자료 인용은 현재 승인 문서 원문의 정확한 구간이며 사례 조치·검증은 해시가 검증된 승인 스냅샷 필드에서 분리한다. 클라이언트는 구간과 실제 문자열·판정을 다시 확인한다. 미검증 HTML을 삽입하지 않는다. 주요 검색 점수와 항목별 조건 현황은 자료 선택 직후에 표시하며 생성형 설명 모델 호출은 추가하지 않는다.
