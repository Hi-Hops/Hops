# 가상 기업·시스템 정본

HOPS의 가상 기업(조직·직원·시스템·기능·담당)과 그 위에서 만드는 지식 문서·시드 해결 사례·상담 시나리오의 **정본**이다. DB seed, 지식 문서, 평가 시나리오는 모두 이 문서에서 파생하며, 다른 위치와 값이 다르면 이 문서를 따른다. 프론트도 이 문서에서 만든 DB 데이터를 받아 쓴다. 제품 정책은 [PRD](../PRD.md)가 우선한다. 이 문서의 모든 값은 **합성**이다. 실제 회사·제품·개인을 설명하지 않으며 구현된 대상 시스템이나 확정된 API를 뜻하지 않는다.

이 문서는 PR 리뷰를 거쳐 병합된 뒤에 팀 기준이 된다. 병합 전의 값은 제안이다. 판단이 갈리는 값과 열린 문제는 [10절](#10-미정과-후속-반영)에 모아 둔다.

## 1. 쓰는 법

- 값의 우선순위: PRD → 이 문서 → [데이터](../DATA.md)·seed·프론트·AI 고정 자료.
- 기능의 정상 동작, 화면 경로, 버튼명, 기본값, 상태 코드를 바꾸려면 이 문서를 먼저 바꾸고, 같은 PR(또는 후속 이슈로 명시한 PR)에서 파생 위치를 맞춘다.
- 지식 문서·사례·시나리오를 쓸 때 이 문서에 없는 사실을 절차나 원인으로 만들어 넣지 않는다. 필요한 사실이 없으면 먼저 이 문서에 추가한다.
- 시스템·기능의 ID와 코드는 이미 쓰이고 있으므로 바꾸지 않는다.
- 대상 시스템 전체를 구현하지 않는다. 대표 문의를 재현하는 최소 기능만 설계하며, 계정·권한 변경, 문서 수정, 자동 복구를 에이전트가 실행하는 도구로 만들지 않는다.

## 2. 이전 정의와의 관계

가상 회사 정의가 여러 곳에 따로 있었다. 이 문서가 정본이 되면서 다음과 같이 정리한다.

| 이전 위치 | 상태 | 조치 |
|---|---|---|
| 이 문서의 이전 판 | 설계 제안, 기능 8행 | 이 문서로 대체(기능은 10개로 풀어 씀) |
| [데이터](../DATA.md) 2절 카탈로그 | 시스템 3·기능 10·ID는 **그대로 유효**. 부서 1개·사용자 4명(DEMO-001~004)·담당 구성은 구 프론트 Mock 시연용 | 시스템·기능 ID는 유지, 사용자·부서·담당은 이 문서를 따름(2절 주석 추가) |
| DB seed (`R__seed_dev_*.sql`) | 부서 11·직원 20명, 한 사람이 두 시스템 담당 | **새 구성으로 대체**(#191). 이미 적재된 DB는 초기화 후 재적재 |
| 프론트 Mock (`systemMockData.ts`) 등 | 구 DEMO 사용자와 가상 카탈로그 | 정본이 아니다. 프론트가 DB 데이터를 받게 바꾸는 작업은 프론트 담당 후속(#171 범위 밖) |
| 계약 예시 (`specs/mocks/fixtures.json`) | 별도 DEMO 사용자와 부서 9개 | 참고용 계약 예시. 이 문서와 대응하지 않음 |
| AI 고정 자료 (`fixture_documents.py`) | 문서 4건 | #191·#194에서 DB 지식 문서로 대체 |

시스템 3개와 기능 10개의 ID·코드는 [데이터](../DATA.md)·seed·프론트에서 이미 같은 값이다. 이 문서에서 바뀌는 것은 조직·직원·담당과 지식·사례·시나리오다.

## 3. 데이터 계층과 구축 범위

"문의 데이터"는 서로 다른 세 가지를 가리킨다. 아래처럼 계층을 나누고, DB에 들어가는 것과 파일로 두는 것을 구분한다.

| 계층 | 내용 | 위치 | 해결 사례인가 |
|---|---|---|---|
| L0 회사 설정 | 부서, 직원, 시스템, 기능, 담당 | DB seed | 아니다 |
| L1 지식 문서 | 직원 가이드·업무 정책·담당자 런북(회사의 매뉴얼). 문의와 무관하게 먼저 존재 | DB seed (`knowledge_document*`) | 아니다 |
| L2 시드 해결 사례 | 과거에 해결됐다고 가정한 처리 이력과 승인된 사례 | DB seed (이력 체인 포함) | **그렇다** (합성, 승인 상태) |
| L3 평가 시나리오 | 상담 첫 문장, 사용자 모사 규칙, 평가 정답 | 파일 (`ai/evaluation/`), DB 아님 | 아니다 |
| L4 외부 헬프데스크 자료 | 공개 티켓 데이터 등 | 개인 작업 공간, 참고 전용 | 아니다 |

### 3.1 문의는 해결 사례가 아니다

해결 사례는 다음을 모두 갖춘 기록이다: 확인된 원인, 실제로 한 조치, 검증 결과, 적용 조건, 시스템 주담당자의 승인. 이는 사용자가 한 말이 아니라 **담당자가 처리하고 검증한 기록**에서 나온다. 따라서:

- 사용자가 문의했다는 사실만으로 사례가 생기지 않는다. 모든 대화를 자동으로 사례로 만들지 않는다.
- **사용법·절차 문의는 사례로 만들지 않는다.** 직원 가이드로 해결한다. 사례는 티켓을 거친 증상·처리 건에서만 나온다.
- 외부 헬프데스크 자료(L4)는 사례가 될 수 없다. 이 가상 시스템에 대한 검증된 원인·조치가 아니기 때문이다. 시나리오의 첫 문장과 표현 변형을 현실적으로 쓰는 참고로만 쓴다(출처·라이선스 확인이 먼저다).
- 평가 시나리오(L3)는 DB에 넣지 않는다. 평가용 입력과 정답이 운영 데이터와 섞이고 정답이 새어 나가기 때문이다. 시험할 때 실제 API로 문의를 만들어 보낸다.

### 3.2 사례와 문서의 연결 규칙

1. 사용법 문의의 해결법은 직원 가이드에 있다. 사례를 따로 만들지 않는다.
2. 증상 사례의 **원인은 이 문서(5절)에 정의된 동작 안에서** 고른다. 담당자 런북이 가능한 원인 후보를 나열하고, 사례는 그중 실제로 확인된 한 건이다.
3. 직원 가이드·정책에는 원인과 조치를 쓰지 않는다. 사례는 담당자 전용(`SYSTEM_STAFF`)이다.
4. 선순환 검증 묶음(문의 A → 사례 A → 후속 B → 방해 C)의 **사례 A는 시드에 넣지 않고** 시험 중 실제 흐름으로 만든다. A의 원인은 시드 사례에 없는 것으로 #201에서 정한다. 방해 문의 C의 원인은 시드 사례와 겹쳐도 된다.
5. 평가 정답과 미래 처리 기록은 시드 사례·지식 문서·검색 자료에 들어가지 않는다.

## 4. 조직·직원·담당

### 4.1 부서

부서는 직원의 소속 정보다. 문의 배정은 **책임 시스템의 현재 주담당자 한 명**이 기준이며 부서와 무관하다. 부서는 부서별 티켓 실시간 구독 권한에만 쓰인다(자기 부서이면서 `is_routable = true`인 부서, 또는 업무 관리자).

| 구분 | 부서 (코드) | `is_routable` | 소속 직원 |
|---|---|---|---|
| 일반 업무 | 마케팅팀 (`MARKETING`) | false | 문의자 2 |
| 일반 업무 | 영업팀 (`SALES`) | false | 문의자 1 |
| 일반 업무 | 인사팀 (`HR`) | false | 문의자 1 |
| IT | IT운영팀 (`IT_OPS`) | true | 담당자 3 |
| 시스템 관리 | 시스템관리팀 (`SYS_ADMIN`) | false | 관리자 1 |

### 4.2 직원 (8명)

| 역할 | 직원 | 로그인 ID | 사번 | 소속 | 담당·역할 |
|---|---|---|---|---|---|
| 문의자 | 정다은 | `requester1` | 20260101 | 마케팅팀 | - |
| 문의자 | 오세준 | `requester2` | 20260102 | 마케팅팀 | - |
| 문의자 | 한지우 | `requester3` | 20260103 | 영업팀 | - |
| 문의자 | 윤서아 | `requester4` | 20260104 | 인사팀 | - |
| 담당자 | 한도윤 | `ea_owner` | 20260011 | IT운영팀 | 전자결재 주담당 |
| 담당자 | 장하린 | `login_owner` | 20260012 | IT운영팀 | 공통 로그인 주담당 |
| 담당자 | 구태현 | `file_owner` | 20260013 | IT운영팀 | 파일 공유 주담당 |
| 관리자 | 문관리 | `admin` | 20260001 | 시스템관리팀 | `BIZ_ADMIN` + `AGENT_OPS_ADMIN` |

- **한 사람이 한 시스템**을 맡는다. 시스템마다 현재 주담당자는 한 명이다.
- 문의자가 4명인 이유: 선순환 검증에서 문의자 A와 후속 문의자 B가 서로 다른 사람이어야 하고, 남의 문의를 볼 수 없는지 확인하려면 한 명이 더 필요하다.
- 담당자도 다른 시스템에 대해서는 문의자가 될 수 있다(PRD). 이때 그 시스템의 담당자 전용 지식은 보이지 않는다.
- 이름·로그인 ID·사번은 이 문서에서 정한 값이며, 모두 가상이다. 모든 계정의 로그인 비밀값은 seed 파일 상단 주석에 있고 문서에 옮기지 않는다. 실제 개인정보·조직도를 사용하지 않는다.
- 이전 seed(부서 11·직원 20명)가 적재된 DB와 코드·ID가 겹치므로 **DB를 초기화한 뒤 재적재**해야 한다(10절).

### 4.3 역할별 접근 범위

| 역할 | 확인할 범위 |
|---|---|
| 문의자 | 자신의 문의·대화·해결 확인, 직원 공개 지식 |
| 시스템 주담당자 | 담당 시스템의 티켓·처리 기록·담당자 전용 지식, 해당 시스템 해결 사례 승인 |
| 업무 관리자 (`BIZ_ADMIN`) | 권한이 허용된 업무 조회, 책임 시스템·담당자 수동 정정, 모든 부서의 티켓 구독 |
| AI 운영 관리자 (`AGENT_OPS_ADMIN`) | AI 실행 상태 조회·재시도 등 운영 업무 |

역할 이름만으로 모든 대화나 파일에 접근할 수 있다고 가정하지 않는다.

## 5. 시스템·기능 명세

**표기 규칙.** 화면 경로는 `메뉴 > 하위 메뉴`, 버튼은 [버튼명]으로 쓴다. 상태·코드 값은 대문자 식별자, 화면 문구는 큰따옴표로 쓴다. 모든 값은 합성 정의이며 "정상 동작"은 지식 문서가 안내할 기준이다.

**오류 구분.** 모든 기능에서 아래 네 가지를 서로 다른 상황으로 취급한다: 결과 없음(조건에 맞는 것이 없음), 권한 거부(볼 수 없음), 조회 오류(시스템 일시 장애), 조건 불일치(입력 규칙 위반). 한 가지를 다른 것으로 바꿔 설명하지 않는다.

### 5.1 전자결재 (`ELECTRONIC_APPROVAL`)

주담당자는 전자결재 담당자(`ea_owner`). 로그인은 공통 로그인(SSO)을 쓴다. 최상위 메뉴: `전자결재 > 새 기안`, `기안함`, `결재함`, `문서함`.

**문서 작성 (`DOCUMENT_CREATE`)**
- 경로: `전자결재 > 새 기안`. 입력: 제목(필수, 100자 이내), 결재선(상신 시 1명 이상), 본문(필수), 첨부(선택).
- 버튼: [임시 저장]은 필수값 없이도 저장되고 `기안함 > 임시 저장`에 나타난다. [상신]은 필수값을 검사한다. 상신한 문서는 수정할 수 없고, 첫 결재자가 처리하기 전까지만 [회수]할 수 있다.
- 오류: 필수값 누락 "필수 항목을 입력해 주세요", 결재선 없음 "결재선을 1명 이상 지정해 주세요"(조건 불일치), 저장 실패 "저장하지 못했습니다. 잠시 후 다시 시도해 주세요"(조회 오류).

**문서 조회 (`DOCUMENT_VIEW`)**
- 경로: `전자결재 > 문서함 > 전체 문서`. 조건: 기간, 상태(기본 전체), 제목 키워드. 버튼: [조회].
- **기간은 문서의 기안일 기준**이며 기본값은 최근 3개월, 최대 12개월이다. 임시 저장한 지 오래된 문서를 최근에 상신해도 기안일이 기간 밖이면 목록에 나오지 않는다.
- 볼 수 있는 문서: 본인이 기안했거나 결재선·참조에 포함된 문서.
- 기안자는 상신한 뒤에도 문서 상세의 [참조 추가]로 열람자(참조)를 추가할 수 있다. 상신한 문서의 본문과 결재선은 수정할 수 없다.
- 임시 저장(`DRAFT`) 문서는 `문서함 > 전체 문서`에 나타나지 않고 `기안함 > 임시 저장`에서만 볼 수 있다. 상태·제목 키워드 조건을 넣으면 그 조건에 맞는 문서만 나타난다.
- 오류: 결과 없음 "조건에 맞는 문서가 없습니다", 권한 거부(직접 링크 접근) "열람 권한이 없는 문서입니다", 조회 오류 "문서를 불러오지 못했습니다. 잠시 후 다시 시도해 주세요", 조건 불일치 "조회 기간은 최대 12개월입니다".

**결재 상태 (`APPROVAL_STATUS`)**
- 경로: 문서 상세 > `결재선` 탭.
- 문서 상태 코드: `DRAFT`(임시 저장), `SUBMITTED`(상신, 아직 아무도 처리하지 않음), `IN_PROGRESS`(결재 중, 한 단계 이상 처리됨), `APPROVED`(승인, 마지막 결재자 승인), `REJECTED`(반려, 사유 표시), `WITHDRAWN`(회수).
- 결재선 단계 상태: `WAITING`(대기), `APPROVED`, `REJECTED`. 전이: `DRAFT → SUBMITTED → IN_PROGRESS → APPROVED | REJECTED`, `SUBMITTED`·`IN_PROGRESS`(첫 결재자 처리 전)에서 `WITHDRAWN`.
- 볼 수 있는 사용자: 문서 열람 권한자.

**첨부 열람 (`ATTACHMENT_VIEW`)**
- 경로: 문서 상세 > `첨부 파일`. 버튼: [열기] (미리보기), [내려받기]. 한 번에 한 파일씩만 내려받을 수 있고 **일괄 내려받기는 지원하지 않는다**.
- 제한: 파일당 20MB, 문서당 10개. 허용 형식 pdf, docx, xlsx, pptx, hwp, txt, png, jpg, zip. 미리보기 형식은 pdf, png, jpg, txt이며 그 외는 [열기]가 비활성이고 [내려받기]만 된다. 업로드 직후 보안 검사를 최대 10분 하며 "검사 중"에는 열기·내려받기가 안 된다.
- 오류: 첨부 없음(목록이 비어 있음), 권한 거부 "첨부 파일 열람 권한이 없습니다"(문서 열람 권한이 있어야 첨부를 볼 수 있다), 조회 오류 "첨부 파일을 열 수 없습니다"(저장소 일시 오류 등), 조건 불일치 "파일 크기는 20MB 이하여야 합니다"·"허용하지 않는 파일 형식입니다".

**담당 경계.** 문서·결재선·첨부 열람의 문제는 전자결재 담당이다. 로그인이 반복되거나 세션이 끊기는 문제는 공통 로그인 담당이다. 첨부 저장소는 전자결재 자체이며 파일 공유와 자동으로 연결되지 않는다.

### 5.2 공통 로그인 (`COMMON_LOGIN`)

주담당자는 공통 로그인 담당자(`login_owner`). 인증과 시스템 이용 권한을 담당한다.

**로그인·SSO (`LOGIN_SSO`)**
- 경로: 사내 포털 로그인 화면. 입력: 사번, 비밀번호.
- 성공하면 SSO 세션이 8시간 유지되고, 그동안 전자결재·파일 공유에 다시 로그인하지 않는다. 비활동 30분이 지나면 세션이 만료된다.
- 정상 흐름: 로그인 성공 → 대상 시스템 화면. **로그인 후 다시 로그인 화면으로 돌아오는 것은 정상이 아니다.**
- SSO 세션은 브라우저의 포털 도메인 쿠키에 저장되고, 전자결재·파일 공유는 이 세션을 검증해 이용을 허용한다. 따라서 다음 세 경우에 로그인에 성공해도 로그인 화면으로 돌아온다: (1) 브라우저가 쿠키를 차단해 세션이 저장되지 않음, (2) 단말 시각이 서버와 5분 넘게 어긋나 발급된 세션이 곧바로 만료로 판정됨, (3) 포털 로그인은 정상인데 연동 시스템의 세션 검증이 실패함(포털에서 직접 로그인하면 되고 특정 시스템에서만 반복됨).
- 오류: 인증 실패 "사번 또는 비밀번호가 올바르지 않습니다", 계정 잠금(아래), 세션 만료 "세션이 만료되었습니다. 다시 로그인해 주세요", 시스템 이용 권한 없음 "이 시스템을 사용할 권한이 없습니다"(권한 거부 — 인증 실패와 구분).

**계정 접근 (`ACCOUNT_ACCESS`)**
- 비밀번호를 5회 연속 틀리면 계정이 잠기고 30분 뒤 자동 해제된다. 즉시 해제는 [잠금 해제 요청]으로 접수하며 공통 로그인 담당자가 처리한다.
- 비밀번호 재설정: 로그인 화면 > [비밀번호 찾기] → 사번과 등록 이메일 확인 → 재설정 링크(유효 30분). 새 비밀번호는 10자 이상, 영문·숫자·특수문자 조합, 직전 3개 재사용 불가.

**권한 신청 (`PERMISSION_REQUEST`)**
- 경로: `내 정보 > 접근 권한 신청`. 입력: 대상 시스템, 필요한 기능·권한(읽기 / 쓰기 / 관리), 업무 목적(필수), 필요 기간(선택, 없으면 상시).
- 승인: 읽기 권한은 대상 시스템 주담당자가 승인한다. 쓰기·관리 권한은 소속 팀장 확인이 추가된다. 처리 목표는 2영업일이다.
- 신청 접수와 진행 관리는 공통 로그인 담당자가 맡고, 승인은 위처럼 대상 시스템 주담당자(쓰기·관리는 팀장 확인 추가)가 한다. 팀장 확인은 직원 데이터에 팀장을 두지 않고 외부 확인 단계로 다루며, 신청자가 소속 팀장에게 확인을 요청한다. 쓰기·관리 신청은 팀장 확인이 끝나기 전까지 `REQUESTED`에 머문다.
- 신청 상태: `REQUESTED`(접수), `APPROVED`(승인), `REJECTED`(반려), `APPLIED`(적용).
- 오류: 이미 보유 "이미 보유한 권한입니다"(조건 불일치), 업무 목적 누락 "업무 목적을 입력해 주세요".

**담당 경계.** 인증 문제(로그인 실패·잠금·세션)와 시스템 이용 권한 신청은 구분한다. 폴더·파일 단위 접근 권한은 공통 로그인이 아니라 파일 공유 담당이다. 정상 로그인에 성공했다는 사실만으로 모든 문서·파일의 열람 권한이 있다고 판단하지 않는다.

### 5.3 파일 공유 (`FILE_SHARING`)

주담당자는 파일 공유 담당자(`file_owner`). 로그인은 공통 로그인(SSO)을 쓴다.

**파일 열람 (`FILE_VIEW`)**
- 경로: `파일 공유 > 공유 폴더`. 접근 권한이 있는 폴더만 목록에 나타난다. 버튼: [열기] (미리보기, pdf·png·jpg·txt), [내려받기].
- 업로드 한도는 파일당 1GB이고, 삭제한 파일은 휴지통에 30일 보관된다.
- 오류: 폴더 접근 권한 없음 "이 폴더에 접근할 권한이 없습니다"(링크로 접근한 경우. 목록에서는 폴더가 보이지 않음), 파일 없음 "파일을 찾을 수 없습니다"(삭제·이동), 링크 만료 "공유 링크가 만료되었습니다", 조회 오류 "파일을 열 수 없습니다. 잠시 후 다시 시도해 주세요". **권한 없음과 파일 없음은 다른 상황이다.**

**파일 공유 (`FILE_SHARE`)**
- 경로: 파일 선택 > [공유]. 방식: 임직원·부서 지정 공유, 링크 공유(링크를 가진 로그인한 임직원). 권한: 보기 / 내려받기. 만료일 기본 7일, 최대 30일. **사외 공유는 지원하지 않는다.** 공유는 언제든 취소할 수 있다.
- 오류: 사외 대상 지정 "사내 임직원에게만 공유할 수 있습니다"(조건 불일치), 만료 30일 초과 "만료일은 최대 30일입니다".

**접근 권한 (`ACCESS_PERMISSION`)**
- 폴더 권한은 `읽기`, `읽기·쓰기`. 신청: 폴더 > [접근 권한 요청](업무 목적 필수) → 폴더 소유 부서 팀장 확인 → 파일 공유 담당자 반영. 처리 목표 2영업일. 권한은 회수할 수 있다.

**담당 경계.** 폴더·파일 단위 접근 권한은 파일 공유 담당이다. 로그인·SSO 문제는 공통 로그인 담당이다.

### 5.4 시스템 간 관계와 책임 경계

- 전자결재와 파일 공유는 로그인에 공통 로그인(SSO)을 쓴다. 이 의존 관계만 정의돼 있다. **전자결재 첨부 저장소와 파일 공유의 저장소 연결은 정의하지 않으며 자동 연결하지 않는다.**
- 문의자가 현상을 경험한 **보고 시스템**과 실제 처리를 맡을 **책임 시스템**은 구분한다. 전자결재에서 로그인 반복을 보고하면 원 맥락은 전자결재로 보존하고, 대화와 허용된 근거가 공통 로그인의 처리를 뒷받침할 때만 책임 시스템 변경을 제안한다. 의존 관계만 있거나 근거가 부족하면 보고 시스템 담당자가 최초 조사한다. 시스템 자체가 확인되지 않으면 PRD의 시스템 확인 대기를 따른다.
- 특정 상용 SSO·파일 프로토콜·클라우드 제품을 전제로 두지 않는다.

## 6. 지식 문서 카탈로그

- 규모: 문서 16건은 파이프라인·권한·방해 사례 검증용 1단계 규모다. 검색 성능 비교(Vector 대 관계 보강)에는 부족하며, 그 시점에 정본 기반으로 확장한다(10절).

### 6.1 관계 카탈로그 (증상·원인·확인 항목)

상담이 "증상 → 가능한 원인 → 원인을 가르는 확인 항목 → 직원에게 묻는 질문"으로 이어지게 하는 관계 데이터의 **범위와 ID**를 정한다(#191 ⑤). 원인·확인 항목은 5절의 동작에서만 고르고, 새 사실이 필요하면 5절에 먼저 쓴다.

- **ID 규칙**: 증상 `sym-{시스템}-{주제}`, 원인 `cause-{시스템}-{주제}`, 확인 항목 `check-{시스템}-{주제}`. 질문 문구의 ID는 `q-{확인 항목 키}-{두 자리 번호}`이며 한 확인 항목에 질문 여러 개를 허용한다.
- **원본의 위치**: 증상·원인·확인 항목과 그 연결은 해당 **런북의 front matter**가 단일 원본이다. 질문 문구와 공개 여부, 사례 연결은 관계 카드(YAML)에 쓴다. 이 절의 표는 범위를 정하는 것이며, 문구는 카드에만 쓴다.
- **공개 범위**: 증상은 직원이 말하는 현상이라 `EMPLOYEE`, 원인과 확인 항목은 `SYSTEM_STAFF`다. 질문 문구는 해당 확인 항목이 직원 공개(`employeeDisclosable = true`)일 때만 `EMPLOYEE`로 쓴다. 직원 공개는 **직원이 화면에서 직접 보거나 설정으로 알 수 있는 사실**을 묻는 항목에만 준다. 담당자가 시스템 기록으로만 확인할 수 있는 항목(`N`)에는 질문을 두지 않는다. 직원에게는 원인의 이름을 말하지 않는다.
- 연결은 후보다. 연결만으로 원인을 확정하지 않는다.

| 증상 (기능) | 가능 원인 | 확인 항목 (직원 공개) | 근거 문서 |

## 7. 시드 해결 사례

기존 사례가 하나도 없으면 사례 재사용을 시험할 수 없으므로, **과거에 해결됐다고 가정한 합성 사례 6건**을 시드로 둔다. 3.1절의 원칙대로 사용법 문의가 아니라 티켓을 거친 증상·처리 건이다.

### 7.1 사례 카드

각 사례는 카드 한 장으로 먼저 쓰고(#191), 스크립트가 아래 이력 체인과 사례 행으로 풀어 SQL을 만든다. 카드에 들어갈 항목: 사례 키, 시스템·기능, 문의 첫 문장과 이후 문답, 확인된 사실, 원인, 조치, 검증 결과, 적용 조건과 한계, 근거 위치(런북·정책 키), 처리한 담당자. 원인과 조치는 5절의 동작을 벗어나지 않는다.

### 7.2 사례 6건

| 사례 키 | 시스템·기능 | 증상 | 확인된 원인 | 조치 | 근거 위치 |
|---|---|---|---|---|---|
| `case-ea-doc-no-permission` | 전자결재·문서 조회 | 특정 문서가 문서함에 없음 | 결재선·참조에 문의자가 없어 열람 권한 없음 | 기안자 확인 후 참조 지정 | `runbook-ea-document-not-listed` |
| `case-ea-attach-scanning` | 전자결재·첨부 열람 | 방금 올린 첨부가 안 열림 | 업로드 직후 보안 검사 중(최대 10분) | 검사 완료 후 다시 열기 안내 | `runbook-ea-attachment-open-failure` |

- 모든 사례는 `origin_type = SYNTHETIC`, `case_status = APPROVED`, `case_type = RESOLUTION`, 공개 범위는 담당자 전용(`STAFF`)이다. 승인자는 해당 시스템 주담당자이고, 문의자 해결 확인은 가상 설정이며 확인 요청과 응답의 `confirmationOrigin`을 `SYNTHETIC_PRESET`으로 표시한다.
- 해당 시스템의 주담당자가 처리한 것으로 쓴다(전자결재 2건은 `ea_owner`, 로그인 2건은 `login_owner`, 파일 공유 2건은 `file_owner`). 문의자는 문의자 4명 중에서 정한다.
- 사례 내용은 #191의 사례 카드 검수에서 확정한다. 6건은 시작 규모이며 시간이 부족하면 4건(시스템당 최소 1건)으로 줄일 수 있다.

### 7.3 사례를 DB에 넣는 데 필요한 이력 체인

`resolved_case.source_work_log_id`가 필수이고, 이미 병합된 사례 조회 API가 큐레이터 실행과 해결 확인 이벤트를 읽으므로(`GET /cases`, `GET /cases/{id}`), 사례 한 건마다 아래 행이 같이 필요하다(합성 과거 이력). 약 19행이며 6건이면 약 114행이다.

`문의`(해결 완료) → `메시지 4개`(문의자 첫 문장, AI 확인 질문, 문의자 답, AI 접수 안내) → `상담 AI 실행 2`(`model_version`에 seed 표시) → `문제` → `표준 요청` → `티켓`(해결 완료) → `배정`(주담당자) → `처리 기록 2`(진행 1, 검증 결과가 있는 해결 1) → `티켓 이벤트 2`(해결 확인 요청, 문의자 응답) → `큐레이터 AI 실행 1`(해결 기록이 시작, 성공) → `사례`(승인) → `지식 문서(CASE)와 버전`

- **번호**: 문의 `SEED-Q-00N`, 티켓 `SEED-T-00N`, 사례 `SEED-C-00N`. 실제 번호(`Q-00000001`, `T-0000000000000001`)와 시퀀스가 겹쳐 나중에 만들 번호와 충돌하지 않게 접두사로 구분한다.
- **ID**: 사례 ID는 `uuid5(NAMESPACE_URL, "hops-seed-case.example/" + 사례 키)`, 나머지는 사례 키와 역할을 이어 같은 방식으로 정한다. 사례의 지식 문서 ID는 `resolved_case.id`와 같다(DATA.md 11.3).
- **공개 상태**: 승인(`APPROVED`)이고 `vector_status`·`graph_status`는 `PENDING`이다. 지식 문서(CASE) 스냅샷은 실제 승인 거래와 같은 형식으로 본문, 승인 스냅샷 digest, 저장소별 반영 요청(`indexRequests`)을 보존하되 AI에 전달하지 않은 승인 직후 상태다. 이 PR은 Vector·Neo4j에 색인하지 않으므로 `SUCCEEDED`로 적는 것은 사실이 아니다. 현재 공개 판정은 둘 다 `SUCCEEDED`를 요구하므로 시드 사례는 1차 SQL 검색에 아직 나오지 않으며, 규칙 변경은 열린 문제 1에서 정한다.
- 이 이력은 문의자의 "내 문의" 목록에 과거 해결된 문의로 보일 수 있다.

**질문 한도는 시나리오로 다루지 않는다.** 처음에는 9번을 "질문 5회 한도에 도달"로 구상했으나, 현재 규칙에서는 한 문제의 필수 필드가 시스템을 포함해 최대 5개이고 이미 물은 필드를 다시 묻지 않으므로 질문 묶음이 5개가 되기 전에 필드가 소진돼 도달할 수 없다. 한도(P8)는 검사기 단위 테스트로만 확인하고, 재질문을 허용하는 규칙이 생기면 한도 시나리오를 추가한다. 필수 상황 목록([데이터 형식](DATA_FORMAT.md))의 "질문 한도"는 이 때문에 시나리오로 충족하지 못한다.

**분포의 한계.** 테스트 8개에는 모름·정정·시스템 미확인 상황이 없다. 테스트 결과는 이 상황들에 대한 일반화로 쓰지 않는다. 테스트 시나리오는 동결하며, 병합 뒤 조정하려면 해당 사건 계열을 개발로 옮기고 새 테스트 계열을 만든다.

## 9. 새 시스템을 추가하는 절차

4번째 시스템(예: 사내 메신저)을 코드 변경 없이 데이터만으로 추가하는 것이 목표다. 아래는 만들어야 할 것의 목록이다. 현재는 AI 코드의 시스템 코드 제한 때문에 3번 항목이 완전히 데이터만으로는 되지 않으며, #181에서 해소한다.

1. **이 문서**: 시스템·기능·주담당·화면 경로·상태 코드·오류 구분·담당 경계를 5절 형식으로 추가한다.
2. **seed**: `it_system`·`system_feature` 행과 해당 시스템의 주담당자(IT운영팀 직원 한 명)를 추가한다. ID는 [데이터](../DATA.md) 2절의 `uuid5` 규칙을 따르고 기존 ID는 바꾸지 않는다.
3. **AI 입력**: 시스템 코드가 `SupportedSystem` 목록으로 전달되는지 확인한다.
4. **지식 문서**: 직원 가이드(기능마다), 필요한 정책, 증상 계열마다 런북을 6절 규칙으로 쓰고 카탈로그에 추가한다.
5. **시드 사례**: 증상·처리 건 1~2건을 7절 카드로 추가한다.
6. **시나리오**: 사용법·권한 신청·현상 각 1개 이상을 8절 형식으로 추가하고 분할을 정한다.
7. **검증**: seed를 두 번 적재해도 같은 결과인지, 새 시스템의 가이드 시나리오가 실제로 안내를 만드는지 확인한다.

## 10. 미정과 후속 반영

**이 문서가 의도적으로 정하지 않은 것**
- 시스템·기능의 실제 버전 체계(모든 문서의 `appliesToSystemVersion`은 `null`).
- 알림·감사 로그·통계 같은 기능 밖의 부가 기능.
- 후속 확장 시스템(인사·경비 정산·구매 등)의 명세. PRD는 이를 후속 목표로 구분한다.
- 선순환 묶음(문의 A·B·C)의 구체적 내용과 사례 A의 원인(#201).

**합성 값이라 리뷰에서 바꿀 수 있는 것**: 기본 조회 기간(3개월), 첨부 한도(20MB·10개), 세션 시간(8시간·비활동 30분), 계정 잠금(5회·30분), 권한 처리 목표(2영업일), 공유 만료(7일·최대 30일), 단말 시각 허용 오차(5분), 직원 수(8명)와 이름·로그인 ID. 값을 바꾸면 이 문서와 해당 지식 문서·사례·시나리오를 함께 바꾼다.

**열린 문제 (PR 리뷰에서 확인)**
1. **시드 사례의 검색 공개 조건.** 계약은 승인 사례가 벡터와 그래프 양쪽에 반영돼야 검색에 쓴다고 한다. 1차 검색은 SQL이라 실제 벡터·그래프 반영이 없다. 시드의 `vector_status`·`graph_status`를 `SUCCEEDED`로 적는 것은 사실이 아니므로, 이 PR의 시드는 두 열을 `PENDING`으로 둔다(7.3절). 1차 SQL 검색에서 승인된 CASE를 공개하는 규칙은 별도로 정해야 하고, 현재 공개 판정(`isCurrentlyVisible`)과 사례 API의 `searchable`은 둘 다 `SUCCEEDED`를 요구한다. 계약과 다른 규칙이라 Spring 담당자의 확인이 필요하다(#194, #201).
2. **시드 이력의 노출.** 시드 사례의 과거 문의가 문의자의 "내 문의" 목록에 보인다. 권고는 허용이다. 시연 화면이 어수선해 보이면 조정한다.
3. **기존 DB.** 이전 seed가 적재된 DB는 부서 코드·ID가 겹쳐 새 seed가 적용되지 않는다. 초기화 후 재적재가 필요하다. 영향받는 테스트(`DemoSeedIntegrationTest`)는 #191에서 고친다.
4. **프론트.** 프론트가 Mock 대신 DB 데이터를 받게 바꾸고 로그인 화면의 빠른 계정을 정리하는 작업은 프론트 담당이며 #171 범위 밖이다.
5. **확장.** 지식 문서 16건·사례 6건은 1단계 규모다. 검색 성능 비교를 시작할 때 정본 기반으로 문서 약 40~60건·사례 약 15~20건으로 늘린다(수치는 추정). 늘릴 때는 정본에서 출발해 초안을 만들고 사람이 검수하며, 생성 방법을 기록하고 평가 정답이 섞이지 않게 한다.
6. **권한 신청 지연의 근거.** `case-login-write-permission-delay`는 런북이 아니라 공개 정책이 근거다(6.1절). 원인 노드의 공개 범위는 `SYSTEM_STAFF`로 두어 직원에게 원인 이름이 나가지 않게 한다. 별도 런북을 두는 편이 낫다고 보면 문서가 17건이 되며, 이슈의 16건 수치와 6절을 함께 바꿔야 한다. 권고는 현행 유지다.
7. **`QuestionTemplate`의 그래프 노드 여부.** 1차는 SQL 테이블이라 별도 개체로 둔다. 에이전트 계약의 그래프 허용 노드(`Check`까지)에는 이 개체가 없으므로, 2차에 Neo4j로 옮길 때 별도 노드로 둘지 `Check`의 속성으로 투영할지를 정하고 계약을 갱신한다.

**이 PR 밖의 후속 반영**
- seed를 이 문서의 조직·직원·담당과 사례로 바꾸고 지식 문서를 DB에 적재한다(#191).
- AI 고정 자료를 DB 지식 문서로 대체한다(#191, #194).
- 프론트의 Mock 정리(위 4번).
