# Hops 지식 수명주기

기준: [PRD 1.44](../PRD.md) · 팀 합의 기획 반영 / 데이터와 검색 구현은 별도. 공통 데이터의 PR 리뷰와 제품 내 시스템 담당자의 사례 승인은 서로 다른 절차다.

## 1. 지식 종류와 출처

직원 가이드·정책·담당자 런북·승인 해결 사례·관계 데이터를 관리한다. 사례 초안은 검색에서 제외한다. 공개 문서에서 파생한 자료는 실제 처리 CASE가 아니다. 합성·데모 검증·실제 운영 출처와 문서 버전, 적용 시스템 버전, 권한 및 근거를 구분한다. 초기 합성 사례의 가상 문의자 확인은 실제 사람의 확인이 아니다.

## 2. 처리에서 사례 공개까지

```text
담당자 해결 기록 저장 → Curator 자동 초안 → 문의자 해결 확인
→ 해당 시스템 주담당자 검토·수정·승인 → 동일 승인 버전 Vector + Neo4j 반영
→ 양쪽 성공 확인 → 권한에 맞게 검색 공개 → 다음 문의에 활용
```

기능 요청은 실제 구현·검증 완료 기록도 필요하다. 별도 지식 검토자는 없으며 담당자의 자기 승인을 허용한다. 초안 생성·업무 완료·승인·각 반영·공개는 독립 사실이다. 무티켓 안내 대화만으로 사례를 자동 생성하지 않는다. 실패 시도는 업무 이력에 남기고 해결 사례로 승격하지 않는다.

## 3. 두 검색 저장소와 복구

승인 버전별로 Vector와 Neo4j의 반영을 각각 추적한다. 한쪽 실패나 상태 미확인은 전체 미완료이며 양쪽 검색 경로 모두 비공개다. 서버는 승인·공개 가능 상태와 접근 권한을 재검증한다. 반영 실패가 승인이나 처리 기록을 취소하지 않는다. 원인 수정 후 실패 반영을 재실행한다. 자동 재시도·전용 복구 화면은 제외하며 상세 순서·동시성·멱등성과 조작 권한은 구현 전 정한다.

## 4. 검색·버전·권한

Vector는 의미 유사성을, Neo4j는 시스템·기능·증상·가능 원인·확인 항목·사례의 관계 탐색을 제공한다. 관계나 유사도는 현재 원인 확정이 아니다. 기존 시스템·기능·증상에 새 사례를 연결할 후보는 Curator가 제안하며 새로운 개념·관계 유형을 임의 게시하지 않는다.

직원 공개 가이드와 담당자 내부 자료를 분리하고 서버 권한을 적용한다. 결과에는 사례 적용 시스템·버전·조건을 표시하고 알 수 없으면 미확인으로 표시한다. 담당자가 현재 환경과 비교하며 구버전만을 이유로 사례를 무조건 삭제·차단하지 않는다. 다른 해결이 필요하면 새 사례와 적용 버전을 기록한다. 잘못되었거나 권한을 잃은 자료의 취급은 별도 검토다.

## 5. 데이터 검수와 평가

출처·사용 조건·공개 범위를 확인하고 파생 문서와 청크의 버전·해시를 관리한다. 공통 데이터는 팀 리뷰를 거치며 검수 전 `ingest_status=PENDING`을 유지한다. 기존 v0는 이전 가상 기업과 정책의 검토 자료다. 새 시스템·정책과의 대조·갱신 전 검색 정본으로 사용하지 않는다.

평가 사건의 정답 매핑·숨겨진 요구사항·미래 해결 내용을 검색 자료나 프롬프트 예시에 넣지 않는다. 기존 승인된 관련 사례 자체는 검색할 수 있다. 같은 승인 문서·사례 버전·접근 범위·모델 조건으로 Vector/관계 보강과 원문/표준화를 비교한다.

## 6. 데이터 계층과 상태를 구분하는 이유

| 계층 | 내용 | 저장·검색 시 주의 |
|---|---|---|
| 공개 근거 | 원문 위치·출처·라이선스·버전·해시·해당 부분 | 공개 원문 자체를 해결 사례로 취급하지 않는다. |
| 파생 지식 | 가상 기업의 직원 가이드·정책·담당자 런북·용어 | 파생 과정과 적용 대상, 공개 범위를 기록한다. |
| 업무 기록 | 문의·대화·티켓·담당자의 실제 조치·검증 | 서버 업무 정본. 실패한 시도와 미확인 사실을 포함할 수 있다. |
| 사례 초안·승인 사례 | 처리 기록의 재사용 가능한 해결 내용 | 초안과 승인, 문의자 확인·출처를 구분한다. |
| 검색 파생물 | 문서 청크·Vector 색인·Neo4j 관계 | 문서/승인 버전·권한·반영 상태를 참조한다. 원본 승인과 반영은 별개다. |
| 평가 자료 | 가상 문의·사용자 응답·정답 매핑·기대 행동 | 평가 사건의 숨겨진 내용과 미래 해결 결과는 검색에 노출하지 않는다. |

내용 작성·담당자 검수, 공통 데이터의 팀 리뷰, 제품 내 사례 승인, Vector 반영, Neo4j 반영, 검색 공개, Mock 연결과 시나리오 검증은 서로 다른 사실이다. 기존 v0의 `PENDING` 등은 해당 v0 데이터의 상태이며 새 v1 계약의 enum을 확정하지 않는다. 하나를 통과했다고 나머지가 모두 완료되는 것은 아니다.

## 7. 자료 작성·검수 절차

1. 자료의 출처·사용 조건·버전과 근거 위치를 기록하고 가상 기업의 설정인지 공개 문서에서 파생한 기술 사실인지 구분한다.
2. 해당 시스템·기능과 직원용/담당자용 범위를 검토한다. 실제 화면이나 기술 스택을 확인하지 못했다면 가정 또는 미확인으로 남긴다.
3. 직원 가이드에는 직원에게 안전하고 허용된 안내만 담는다. 관리자용 절차·비밀정보·실제 개인정보는 공개 안내와 분리한다.
4. 담당자 런북은 확인 조건과 원인 후보, 실제 관측 또는 Mock 여부, 조치 전제와 한계를 구분한다. 사례·그래프 관계만으로 현재 원인을 확정하지 않는다.
5. 공통으로 채택할 데이터는 작성자 외 팀원의 PR 리뷰를 거친다. 제품 내에서 시스템 담당자가 자신의 해결 사례를 승인하는 절차와 혼동하지 않는다.
6. 자료의 출처·시스템 적용 조건·공개 범위가 바뀌면 관련 문서·JSON·청크·해시·시나리오에 미치는 영향을 확인한다. 검수 이전 자료를 검색에 넣지 않는다.

## 8. 청킹·검색·권한

- 직원 가이드·정책·런북을 검색 단위로 구성할 때 의미가 연결되는 제목·절차·전제조건과 한계를 잃지 않도록 검토한다. 실제 청킹 규칙과 임베딩 모델은 아직 확정하지 않았다.
- 파생 청크에는 원 문서와 문서 버전·출처·접근 범위·검수 상태 등을 추적할 수 있어야 한다. 실제 메타데이터 필드와 해시 생성 방식은 데이터 계약에서 정한다.
- 서버가 조회 목적과 현재 사용자에 맞는 접근 범위를 제공하고, 반환 근거의 출처·승인·공개 가능 상태를 재검증한다. 검색 0건과 검색 실패·권한 거부를 구분한다.
- 직원 답변에 내부 담당자 런북 원문이나 다른 사용자의 비공개 대화를 포함하지 않는다. 읽기 전용 Mock을 실제 운영 관측으로 표시하지 않는다.
- 새 승인 사례는 동일 승인 버전의 Vector와 Neo4j가 모두 성공한 경우에만 양쪽 경로에서 검색 공개한다. 권한·승인 상태와 캐시·색인 일치 확인의 세부 구현은 별도로 검증한다.

## 9. 사례 검토와 검색 재사용

사례 초안 검토자는 해당 시스템 담당자다. 문의자 확인과 담당자 승인을 받기 전에 다음을 살펴본다.

- 원 문의·티켓·처리 기록의 출처와 해당 내용이 서로 일치하는가.
- 확인된 사실과 추정·원인 미확인이 구분되는가. 기능 요청이라면 실제 변경과 구현·검증 결과가 기록됐는가.
- 증상 또는 변경 목적, 실제 조치·검증, 시스템 적용 버전·조건·한계가 설명되는가. 모르는 값은 미확인으로 남겼는가.
- 개인정보·비밀값·권한 밖 문서가 불필요하게 포함되지 않았는가. 직원과 담당자의 공개 범위가 맞는가.
- 출처가 합성·데모 검증·실제 운영 중 무엇인가. 합성 사례의 가상 문의자 확인 설정과 HOPS에서 실제 수행한 문의자 확인을 구별했는가.

원인이 확인되지 않았더라도 해결된 실제 조치와 검증 결과가 있고 나머지 공개 조건을 충족하면, 원인을 미확인으로 명시해 재사용할 수 있다. 실패한 조치만으로 해결 사례를 만들지 않는다. 해결이 확인된 모든 업무를 강제로 사례로 만드는 것도 아니다.

검색 결과에서 담당자는 사례의 적용 시스템·버전·조건을 현재 환경과 비교한다. 오래된 사례만을 이유로 일괄 삭제·차단하지 않으며, 새 해결을 찾으면 적용 버전과 함께 새로 기록한다. 잘못된 자료·권한을 잃은 자료의 처리와 승인 후 수정/재승인 정책은 별도 설계가 필요하다.

## 10. 평가·변경 영향 검토

- 사건의 변형 표현을 원 사건과 같은 분할에 두고 정답 매핑·숨겨진 요구사항·미래 해결 내용이 검색 자료·프롬프트 예시에 포함되지 않는지 확인한다.
- 기존 승인 사례는 실제 검색 대상일 수 있다. 다만 현재 평가 사건에서 나중에만 알 수 있는 해결 내용을 선행 지식으로 주지 않는다.
- Vector 단독과 관계 보강, 원문과 표준화 비교 시 동일 질문·승인 문서/사례 버전·권한·모델 조건을 유지한다. 검색 결과 적합성과 그 근거를 사용한 최종 답변 품질은 구분한다.
- 문서·적용 조건·공개 범위·관계 또는 임베딩이 바뀌면 영향받는 청크·관계·평가 결과를 재검토한다. 이전 사례의 자동 비활성화·폐기 전파는 이번 제품 범위에 추가하지 않는다.
- 비교에 사용한 지식·관계·데이터·모델·프롬프트 버전과 검토자·분할·실행 결과를 기록한다. 수량·목표가 정해지지 않았다면 임의로 성과 기준을 만들지 않는다.
