# Hops 지식 데이터 수명주기

상태: 구축·검수·적재·개선 규칙 확정안 · 팀 리뷰 전

## 1. 전체 흐름

```text
공개 근거 수집
→ 출처·라이선스·버전 고정
→ 문서·섹션 사람 검수
→ 한국어 가이드·런북·정책 작성
→ 내용 검수와 팀 승인
→ 의미 단위 청킹
→ 임베딩·검색 인덱스 적재
→ 사용자 안내·읽기 진단·이관
→ 담당자 해결과 재시험
→ 검증된 CASE 생성
→ 가이드·런북·평가셋 개선
→ 버전 증가·재검수·재인덱싱
```

런북을 전부 완성한 뒤 CASE를 꾸미지 않는다. MVP 시나리오를 재현하고 해결하면서 런북과 CASE를 반복적으로 함께 개선한다.

## 2. 데이터 계층

| 계층 | 정본 | 용도 |
|---|---|---|
| Source | 공개 원문의 URL·commit·hash·locator | 기술적 사실과 라이선스 추적 |
| Derived knowledge | 직원 가이드·런북·정책·용어 | RAG와 담당자 참고 |
| Diagnostic contract | 신호 레지스트리·Evidence Bundle Schema | 런북·Tool·Diagnosis 비교 규격, RAG 적재 금지 |
| Retrieval | section·chunk·embedding·검색 설정 | 권한 필터가 적용된 검색 |
| Operational evidence | 읽기 Tool 결과·로그·메트릭 스냅샷 | 현재 장애 관측 |
| Resolved case | 재현·복구·재시험이 끝난 해결 기록 | 과거 유사 사례 검색 |
| Evaluation | 질의·숨겨진 정답·기대 근거·부서 | 회귀 평가, KB와 분리 |

공개 문서의 증상·원인·해결을 변환한 자료는 실제 해결 CASE가 아니다. `origin=derived`인 지식 근거로만 취급한다.

## 3. 독립 상태

다음 상태는 서로 대신할 수 없다.

| 상태 | 예시 값 | 의미 |
|---|---|---|
| 내용 검수 | `AI_DRAFT`, `OWNER_CONFIRMED`, `REJECTED` | 문서 내용의 담당자 판단 |
| 팀 리뷰 | `PENDING`, `APPROVED`, `CHANGES_REQUESTED` | 공통 데이터 채택 여부 |
| RAG 적재 | `PENDING`, `APPROVED`, `BLOCKED` | 검색 인덱스 포함 여부 |
| Tool 연결 | `PENDING`, `READY`, `NOT_REQUIRED` | 등록된 읽기 Tool과 연결 여부 |
| 시나리오 재현 | `NOT_RUN`, `PASSED`, `FAILED` | Demo 환경에서 실제 재현 여부 |
| CASE 검증 | `DRAFT`, `VERIFIED`, `REJECTED` | 해결 기록 승격 여부 |

내용 검수만 통과한 문서를 자동으로 임베딩하지 않는다. Tool이 없어도 문서를 검토할 수 있지만, Tool 관측 없이 현재 원인을 확정해서는 안 된다.

## 4. 원문에서 파생 지식까지

1. 원문 URL, 라이선스, commit SHA, 파일 hash를 고정한다.
2. 제목·본문·적용 버전·관리자 절차·레거시 여부를 사람 검수한다.
3. include된 문서에서 필요한 절만 locator로 선택한다.
4. 한국어 파생 문서에 `source_evidence_ids`를 기록한다.
5. 기술적 사실과 가상 회사 정책을 구분한다.
6. 직원용 단계와 관리자용 단계를 분리한다.
7. 보안 약화 절차는 `NEVER_EXPOSE`, 관리자 절차는 `INTERNAL_ONLY + risk_flags`로 둔다.
8. 다른 팀원 한 명이 검토하기 전에는 팀 승인으로 바꾸지 않는다.

## 5. 청킹과 RAG 적재

- 문서 제목·단계·표·원인 묶음을 토큰 길이만으로 자르지 않는다.
- 모든 청크에 문서·버전·section·권한·노출·근거·hash를 복제한다.
- `ANSWER`는 `EMPLOYEE/QUOTABLE`만 검색한다.
- `SUPPORT_DIAGNOSIS`는 권한 검사 후 `EMPLOYEE + STAFF`를 검색하지만 사용자에게 STAFF 원문을 인용하지 않는다.
- Spring이 검색 전에 접근 범위를 만들고 반환 근거를 다시 검증한다.
- 평가 질의와 정답 문구는 검색 인덱스에 넣지 않는다.
- 진단 신호 레지스트리는 독립 청크로 만들거나 임베딩하지 않는다. 런북 청크를 만들 때 참조 신호 정의만 파생 포함한다.
- 정본이 바뀌면 영향 청크를 재생성하고 이전 버전을 비활성화한 뒤 재임베딩한다.

생성 청크와 임베딩은 파생물이다. 정본 JSON과 생성 규칙으로 재생성할 수 있어야 한다.

## 6. 문의에서 해결까지

1. Knowledge가 승인된 가이드·런북·CASE를 검색하고 관련 신호 정의를 Evidence Bundle로 조립한다.
2. Spring이 접근 범위와 근거 ID를 검증해 Evidence Bundle을 State에 저장한다.
3. Diagnosis가 등록된 읽기 Tool로 현재 상태를 관측하고 Evidence Bundle과 비교한다.
4. 현재 근거에 없는 관측이 나오면 Diagnosis는 `NEED_MORE_KNOWLEDGE`를 반환하고 Supervisor가 Knowledge를 재호출한다.
5. 과거 CASE는 원인 정답이 아니라 후보 우선순위를 조정하는 근거다.
6. CASE와 현재 관측이 충돌하면 현재 관측을 우선한다.
7. 재조회 후에도 근거가 없거나 안내 후 미해결이면 원인을 꾸미지 않고 이관한다.
8. Agent는 코드·설정·배포·재시작·DB 쓰기를 수행하지 않는다.
9. 담당자가 조치하고 동일 조건으로 재시험한다.
10. 사용자 또는 백엔드 상태로 해결 완료를 확인한다.

Agent별 상세 책임과 입출력은 [Knowledge–Diagnosis 계약](KNOWLEDGE_DIAGNOSIS_CONTRACT.md)을 따른다.

## 7. CASE 승격 조건

다음을 모두 만족해야 `VERIFIED CASE`로 저장한다.

- 정의된 시나리오를 실제로 재현했다.
- 발생 시각·요청 ID·마스킹된 로그·관측값을 보존했다.
- 원인과 반대 신호를 함께 확인했다.
- 담당자가 수행한 조치와 승인 여부를 기록했다.
- 동일 조건 재시험으로 장애가 사라졌음을 확인했다.
- 사용자 또는 백엔드 상태가 해결을 확인했다.
- 개인정보·비밀값·원시 SQL·내부 IP를 제거했다.
- 연결 런북·근거·Tool 스냅샷 버전을 기록했다.

다음은 CASE로 만들지 않는다.

- `pg_sleep` 같은 트리거 동작 확인
- 원인을 추정만 한 티켓
- 해결 조치나 재시험이 없는 기록
- 사용자가 해결됐다고 확인하지 않았고 백엔드 상태 근거도 없는 기록
- 공개 문서를 티켓 형식으로 변환했을 뿐인 자료

## 8. CASE를 다시 지식으로 사용하는 규칙

- RAG는 CASE의 증상·관측·원인·해결 요약을 검색할 수 있다.
- 사용자·서버·SQL 식별값은 일반화하거나 마스킹한다.
- 단일 CASE로 원인을 확정하지 않는다.
- 같은 증상에 다른 원인의 CASE를 함께 보존한다.
- 현재 Tool 결과와 필요 신호가 일치할 때만 유사 사례로 제시한다.
- 재오픈되거나 해결 검증이 취소된 CASE는 검색에서 비활성화한다.

## 9. 평가와 데이터 누수 방지

- Eval은 `dev`와 고정 `test`로 나눈다.
- test 질의·정답·정답 CASE는 프롬프트 예시와 KB에 넣지 않는다.
- 같은 원문, 같은 정답 문서, 정규화된 동일 질문은 양쪽 split에 걸치지 않는다.
- 문서·프롬프트·모델·임베딩·검색 설정 버전을 평가 결과와 함께 기록한다.
- Tool fixture가 숨겨진 원인명을 직접 반환하지 않게 한다.
- 정확도뿐 아니라 근거 적합성, 부서, 권한 누출, 불필요한 단정, 안전한 이관을 평가한다.

## 10. 변경·폐기·재인덱싱

| 변경 | 필요한 처리 |
|---|---|
| 오탈자·표현 수정 | 문서 버전 증가, 영향 청크 재생성 |
| 기술 사실·절차 수정 | 근거 재검수, 팀 리뷰, 회귀 평가 |
| 권한·노출 변경 | Spring 카탈로그와 인덱스 ACL 동시 갱신 |
| 서비스·부서 경계 변경 | 시나리오 정답·라우팅 fixture·Eval 재검토 |
| 원문 버전 변경 | hash 비교 후 영향 절만 재검수 |
| CASE 재오픈·오판 확인 | 검색 비활성화, 수정 이력 보존 |
| 임베딩 모델 변경 | 전체 재임베딩 후 동일 Eval 비교 |

이전 버전은 감사와 재현을 위해 식별 가능하게 보존하되 검색 기본 대상에서는 제외한다.

## 11. 역할과 승인

| 역할 | 책임 |
|---|---|
| 데이터 담당 | 근거 수집, 파생 문서 작성, 검증 실행, 변경 영향 기록 |
| 서비스·부서 담당 | 기술 내용·담당 경계·복구 절차 검토 |
| 팀 리뷰어 | 공통 데이터 채택, 권한·안전성 교차 검수 |
| Tool 담당 | 읽기 계약·마스킹·스냅샷 버전 구현 |
| Spring 담당 | 권한 원본, 업무 저장, 부서·상태 최종 검증 |
| AI 담당 | 검색·근거 조립·불확실성·평가 구현 |

작성자 본인 확인은 팀 승인과 다르다. 공통 데이터는 Draft PR과 작성자 외 최소 한 명의 리뷰를 거친다.

## 12. Git과 실행 데이터

Git에는 검수된 정본·Schema·manifest·검증 코드만 둔다. 원문 전체, 생성 청크, 임베딩, Vector DB, 실행 로그와 실제 티켓은 두지 않는다. Demo에서 생성한 CASE 중 회귀 테스트에 필요한 비식별 고정 fixture만 별도 리뷰 후 공유한다.
