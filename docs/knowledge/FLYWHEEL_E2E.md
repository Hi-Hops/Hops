# 지식 선순환 E2E 실행 절차

문의 A가 담당자 처리와 해결 확인을 거쳐 사례 A로 승인되고, 표현이 다른 후속 문의 B에서 그 사례가 근거로 쓰이는 흐름을 **로컬에서 한 번 끝까지** 재현하는 방법이다. 문의 A·B·C와 정답은 [정본 8.1절](VIRTUAL_COMPANY.md#81-선순환-검증-묶음-문의-abc)과 [데이터 형식](DATA_FORMAT.md#지식-선순환-검증-묶음)에 있다.

이 시험의 통과는 **한 시나리오가 한 번 이어졌다는 뜻**이다. 일반 성능, 서비스 통합 검증 완료, 운영 동작의 근거가 아니다. 기록에는 실제 모델과 Fake를 구분해 쓰고 섞어 보고하지 않는다.

## 확인하는 것

| 단계 | 내용 | 확인 방법 |
|---|---|---|
| A1 | 문의 A 접수·대화가 티켓 생성으로 끝남 | 공개 API, 질문은 사용자 모사 규칙(`ASKED_FIELD_ONLY`)이 답함 |
| A2 | 관찰자 계정이 남의 문의를 볼 수 없음 | 공개 API 응답 코드 |
| A3~A5 | 담당자가 티켓을 보고 진행·검증된 해결 기록을 저장 | 공개 API (카드의 처리 기록) |
| A6~A7 | Curator가 사례 초안을 만들고, 원인·공개 범위·관계 연결이 정답과 맞음 | DB 읽기 |
| A8 | 문의자가 해결됨으로 확인 | 공개 API |
| B0·C0 | **승인 전** 후속 문의에서 초안이 근거에 나오지 않음 | DB 읽기 |
| A9~A12 | 담당자가 사례를 승인하고 검색 문서로 공개됨, 색인 확인 요청 | 공개 API, DB 읽기 |
| A13 | 승인 사례의 관계가 관계 조회 테이블에 반영됨 | DB 읽기 |
| B1·C1 | **승인 후** 후속 문의: B는 프로필별 기대대로 사례 A를 근거로 인용, C는 사례 A를 원인으로 확정하지 않음, 직원에게 보이는 메시지에 사례 A 문장이 없음 | DB 읽기, 공개 API |

승인 전후 비교는 같은 입력·같은 지식·같은 모델 설정에서 사례 승인만 다르다. 이 비교는 **지식 추가의 효과만** 보여 주며 Neo4j나 검색 방식의 효과가 아니다.

**사례 A 유무의 판정은 상담 근거가 1건 이상 저장됐을 때만 한다.** 근거가 0건이면 "사례 A가 없음"은 사례가 걸러진 것이 아니라 상담이 지식을 찾지 않았거나 결과가 없었다는 뜻일 수 있어서, 통과가 아니라 `BLOCKED`(판정 불가)로 기록한다. 증상 문의(B·C)가 지식을 검색하는 것은 충분성 판정을 켠 문제별 행동 경로(`HOPS_AI_KNOWLEDGE_ASSESSMENT=true`)뿐이다.

상태 의미: `PASS` 기대와 같음, `FAIL` 기대와 다름, `BLOCKED` 알려진 공백이라 확인하지 못함(실패로 세지 않고 별도로 보고), `INFO` 판정하지 않고 기록만 함. 위 표에서 대화록의 의미 판단(원인 확정 여부 등)은 자동 검사가 문장 일치로 대신할 뿐이므로 사람이 대화록을 읽어 확인한다.

## 준비

1. **스택**: PostgreSQL(pgvector), Redis, Spring, AI. 이 저장소의 Compose(`docker compose up --build -d`, 루트 [README](../../README.md))를 쓰거나, 각 서비스를 직접 실행한다. 새 시드(직원 8명, 부서 5개, 문서 16건, 시드 사례 6건, 관계 데이터)가 들어간 DB여야 한다. 이전 시드가 적재된 DB는 **초기화한 뒤** 다시 적재한다([정본 10절](VIRTUAL_COMPANY.md#10-미정과-후속-반영)).
2. **AI 설정**: `HOPS_AI_MODE=real`, `HOPS_AI_KNOWLEDGE_SOURCE=spring`, `HOPS_AI_INTERNAL_API_ENABLED=true`, `OPENAI_API_KEY`. AI→Spring 내부 API용 `SPRING_SERVICE_TOKEN`은 Spring과 AI에 같은 값을 둔다([AI 실행 안내](../../ai/README.md)). 충분성 판정은 `HOPS_AI_KNOWLEDGE_ASSESSMENT`(기본 꺼짐)로 켜고 끈다.
3. **Compose 전달 범위**: 현재 `compose.services.yaml`은 `HOPS_AI_KNOWLEDGE_ASSESSMENT`, `HOPS_AI_GUIDE_EXCERPT`와 Spring의 내부 판단 옵션을 컨테이너에 전달하지 않는다. 이 값을 바꿔 시험하려면 서비스를 직접 실행하거나 Compose 설정을 따로 보완한다(이 문서의 범위 밖, [#240](https://github.com/Hi-Hops/Hops/issues/240)). 서비스 하나만 다시 빌드할 때는 `docker compose up --build -d --no-deps <서비스>`처럼 `--no-deps`를 붙인다. 붙이지 않으면 `depends_on` 때문에 `backend`가 함께 시작되어 직접 띄운 서버와 8080 포트가 겹칠 수 있다.
4. **드라이버 환경변수**(비밀값은 문서와 기록에 남기지 않는다):

```bash
export HOPS_E2E_BASE_URL=http://127.0.0.1:8080        # 기본값
export HOPS_E2E_DB_DSN='postgresql://<읽기 전용 계정>@localhost:5432/hops'
export HOPS_E2E_PASSWORD='<시드 계정 로그인 비밀값, seed 파일 상단 주석>'
```

`HOPS_E2E_DB_DSN`은 질문이 요청한 필드와 상담 근거처럼 공개 API가 주지 않는 값을 읽는 데만 쓴다. 드라이버는 이 연결을 읽기 전용 세션으로 열며 업무 데이터를 바꾸지 않는다.

## 점검 (모델을 부르지 않음)

```bash
cd ai
uv run python -m evaluation.flywheel.validate          # 묶음 형식·누수 검사
uv run python -m evaluation.flywheel.e2e --preflight   # 로그인, 시드 확인
```

## 실행 (모델을 호출함)

**실제 모델을 호출하며 비용이 든다.** 모델, 호출 상한, 예상 비용을 정해 승인한 뒤 직접 실행한다. 한 번의 전체 실행은 문의 5건(A, 승인 전 B·C, 승인 후 B·C)이며 문의마다 AI 실행이 질문 횟수만큼 만들어지고 사례 초안 실행이 1건 더 만들어진다. `--max-runs`는 시작할 AI 실행 수의 상한이며 닿으면 다음 문의나 답변을 보내기 전에 멈춘다.

```bash
cd ai
uv run python -m evaluation.flywheel.e2e --run \
    --model-label real:<모델 이름> --assessment off --max-runs 24 --note '<조건 메모>'
```

`--model-label`과 `--assessment`는 실행하는 사람이 밝힌다. 서버가 모델 종류나 판정 설정을 알려 주지 않기 때문이다. 결과는 기본으로 `.local/flywheel-e2e/`에 JSON으로 남는다(공유 문서의 근거로 링크하지 않는다). 종료 코드는 `FAIL`이 있으면 1이다.

## 공개 프로필

사례는 담당자 전용(`STAFF`)이고 직원 상담은 직원 공개 자료만 읽는다. 그래서 **기본 설정에서는 B가 사례 A를 근거로 쓰지 못하는 것이 맞다**(`DEFAULT`). B에서 인용되는지는 Spring의 내부 판단 경계 옵션(`hops.agent.run.internal-judgement.enabled`, 기본 꺼짐)을 켠 `INTERNAL_JUDGEMENT`에서만 볼 수 있다. 이 옵션은 SECURITY.md 개정과 보안 리뷰 전에는 켜지 않으며, 켜려면 보안 리뷰 기록을 `review-reference`에 적어야 서버가 시작한다. 켠 결과는 로컬 시험의 관찰이고 운영 동작의 근거가 아니다. 드라이버는 상담 실행 입력에 `retrievalScopes`가 있는지로 프로필을 읽어 기록하고, 프로필에 맞는 기대를 적용한다.

## 알려진 공백

- **A13 관계 반영**: 승인된 사례의 연결(`ADDRESSES`·`USES_CHECK`)은 사례의 `relation_candidates`와 색인 요청에만 남고, 관계 조회 테이블(`relation_case_symptom`·`relation_case_check`)에 쓰는 코드는 시드 밖에 없다. 그래서 이 단계는 `BLOCKED`로 기록되는 것이 현재 기대다. 구현은 이 시험의 범위 밖이며 [#239](https://github.com/Hi-Hops/Hops/issues/239)로 분리했다.
- **확인 항목 질문**: 판정을 켠 실제 실행에서도 AI가 확인 항목을 묻지 않고 양식 필드만 물었다. 하네스 측정과 다른 관찰이며 원인은 조사하지 않았다([#241](https://github.com/Hi-Hops/Hops/issues/241)).
- **검색 방식**: 1차 검색은 토큰 일치 SQL이라 동의어와 어미 변화를 찾지 못한다. B가 사례 A를 찾지 못하면 결함이라기보다 이 한계일 수 있다. 결과를 본 뒤 B의 문장이나 검색 규칙을 맞춰 바꾸지 않는다.
- **사례 공개 규칙**: 승인 직후 검색 공개는 `hops.knowledge.case-visibility=APPROVED_SNAPSHOT`(1차 SQL 검색 제안)에 따른다. Spring·사례 담당자 리뷰 전까지는 제안이다. 색인 상태는 `PENDING`으로 남는 것이 정상이다.

## 실행하지 않은 것

- 내부 판단 프로필(`INTERNAL_JUDGEMENT`)의 실행은 하지 않았다. 따라서 **승인 후 B가 사례 A를 근거로 인용하는지는 아직 확인하지 못했다.** 기본 프로필에서는 사례 A가 담당자 전용이라 B에 나오지 않는 것이 맞고, 인용은 내부 판단 옵션을 켠 프로필에서만 볼 수 있다.
- 같은 조건의 반복 실행(통과율)은 하지 않았다. 아래 기록은 조건마다 1회다.
- 실제 브라우저·프론트 화면, 운영 배포, 실제 임베딩·Neo4j 색인은 이 시험의 범위가 아니다.

## 실행 기록

### 실행 1: 판정 끔, 기본 프로필

| 항목 | 값 |
|---|---|
| 모델 | 실제 모델 `gpt-6-luna` (Fake 아님) |
| 충분성 판정 | 끔 (`HOPS_AI_KNOWLEDGE_ASSESSMENT` 기본값) |
| 프로필 | `DEFAULT` (실행 입력에 `retrievalScopes` 없음을 읽어 확인) |
| 환경 | 로컬, Spring·AI를 Docker 밖에서 직접 실행, PostgreSQL·Redis는 컨테이너. 새 시드 DB |
| 코드 | 커밋 `f5c441e` + 이 드라이버(커밋 전 작업 트리). 같은 코드를 내려받아 재현할 수 없고, 이후 근거 검사와 BLOCKED 처리가 고쳐졌다 |
| 규모 | 문의 5건, 시작한 AI 실행 11개(상한 24), 사례 초안 실행 포함 |

**실제로 이어진 것 (공개 API와 DB 확인):** 문의 A가 질문 1회 뒤 티켓이 만들어지고 담당자에게 보임, 담당자가 진행·검증된 해결 기록을 저장, Curator가 사례 초안을 만들고 원인·공개 범위(`STAFF`)·관계 연결이 정답과 맞음, 문의자가 해결됨으로 확인, 담당자가 사례를 승인하고 검색 문서로 저장되어 `visibleToSearch`가 참이 됨(색인 상태는 `PENDING`), 관찰자 계정은 남의 문의를 볼 수 없음. 이 구간(A1~A12)은 실제 모델·Spring·PostgreSQL 위에서 한 번 재현됐다. 사례 초안의 문구 품질은 사람이 검수하지 않았다.

**확인하지 못한 것:** 이 실행의 B·C 문의 5건은 모두 저장된 상담 근거가 **0건**이다(안내도 없음). 판정을 끈 기본 경로에서는 증상 문의가 지식을 검색하지 않았다. 그래서 B·C에서 "사례 A가 근거에 없음"으로 나온 결과는 사례가 걸러진 증거가 아니며 판정 불가다. 기록 당시의 드라이버는 이를 통과로 적었고, 이후 드라이버가 근거 0건을 `BLOCKED`로 기록하도록 고쳤다. 선순환의 마지막 고리(승인 후 B가 사례 A를 근거로 쓰는가)는 이 실행으로 확인하지 못했다.

**BLOCKED:** A13 — 승인된 사례의 관계가 관계 조회 테이블에 반영되지 않는다(행 0건). 반영하는 코드가 없다는 알려진 공백이다.

**그 밖의 관찰:** 판정이 꺼져 있어 AI가 확인 항목(예: 입력한 상태·키워드)을 묻지 않았다. 질문은 양식 필드 1~2개뿐이었고 티켓 근거에 지식이 붙지 않았다.

### 실행 2: 판정 켬, 기본 프로필

| 항목 | 값 |
|---|---|
| 모델 | 실제 모델 `gpt-6-luna` (Fake 아님) |
| 충분성 판정 | 켬 (`HOPS_AI_KNOWLEDGE_ASSESSMENT=true`) |
| 프로필 | `DEFAULT` (실행 입력에 `retrievalScopes` 없음) |
| 실행당 모델 호출 상한 | 12 (Spring·AI 양쪽, 기본 8에서 올림). 모든 실행이 한도 오류 없이 `SUCCEEDED` |
| 환경 | 실행 1과 같다. 단 DB를 시드 상태로 다시 만든 뒤 시작해 실행 1의 사례가 남아 있지 않다 |
| 규모 | 문의 5건, 시작한 AI 실행 11개(상한 24), 사례 초안 실행 포함 |

**이어진 것:** A→처리→해결 확인→Curator 초안→승인 구간(A1~A12)이 실행 1과 같은 결과로 다시 재현됐다.

**실행 1과 달라진 것 (지식 검색이 돌았다):** 문의 5건 모두 상담 근거가 저장됐다. B·C는 직원 공개 가이드 `전자결재에서 지난 문서 찾기`를 근거로 받았고, 담당자 전용 런북과 사례는 받지 않았다. 따라서 B·C의 아래 결과는 검색이 수행된 뒤의 결과이며 실행 1과 달리 판정 불가가 아니다.

- 승인 전 B·C: 사례 A의 초안이 근거에 나오지 않음 (미승인 자료가 상담에 쓰이지 않음). **아래 정정 참조.**
- 승인 후 B·C: 사례 A가 직원이 보는 AI 메시지에 나오지 않음(작성자가 대화록을 읽음). 근거에 나오지 않는지는 **아래 정정 참조.**
- C: 사례 A의 원인·제목이 표준 요청·티켓에 옮겨지지 않음(문장 일치 검사. 모델이 말을 바꾸면 잡지 못하는 대리 검사다).
- 모든 B·C 문의는 질문 1회 뒤 티켓 제안으로 끝났다.

**정정 (근거 검사의 결함):** 이 실행의 드라이버는 사례 A를 사례 번호(`resolved_case.id`)로 근거에서 찾았다. 그런데 상담 근거(`KnowledgeEvidence`)는 사례 번호를 담지 않고 승인 시 새로 만들어진 지식 문서의 id(`documentId`)·제목·발췌를 담는다. 그래서 이 검사는 사례가 근거에 있어도 "없음"으로 나왔을 것이다. 즉 위의 "근거에 나오지 않음"과 "직원 상담 경로에 나가지 않는다는 안전 성질이 지켜졌다"는 이 실행의 **드라이버 검사로는 입증되지 않는다.** 직원이 보는 메시지에 사례 문장이 없다는 것(작성자가 읽은 대화록)만 남는다. 드라이버는 이후 문서 id·제목·확인된 원인 문장으로 찾도록 고쳤고, 고친 드라이버로 실제 모델을 다시 돌린 결과가 아래 실행 3이다.

**확인하지 못한 것:** 승인 후 B가 사례 A를 근거로 쓰는지(내부 판단 프로필 필요), 사례 A가 있을 때 C가 방해를 받는지(같은 이유), 관계 조회에 사례 A가 반영되는지(A13 `BLOCKED`, 반영 코드 없음). 판정을 켰는데도 AI는 확인 항목(입력한 상태·키워드)을 묻지 않았고 양식 필드 1~2개만 물었다. 이 경로가 확인 항목 질문까지 가지 않은 이유는 조사하지 않았다.

**해석의 한계:** 조건마다 1회이고 모델 출력은 매번 달라질 수 있다. 위 결과를 일반적인 안전성이나 성능으로 보고하지 않는다. 대화록 중 B(승인 전·후)와 C(승인 후)만 작성자가 읽었고 사람의 검수는 받지 않았다. 원문은 `.local/flywheel-e2e/`에만 있다.

### 실행 3: 판정 켬, 기본 프로필, 근거 검사를 고친 드라이버

| 항목 | 값 |
|---|---|
| 모델 | 실제 모델 `gpt-6-luna` (Fake 아님) |
| 충분성 판정 | 켬 (`HOPS_AI_KNOWLEDGE_ASSESSMENT=true`) |
| 프로필 | `DEFAULT` (실행 입력에 `retrievalScopes` 없음) |
| 실행당 모델 호출 상한 | 12 (Spring·AI 양쪽) |
| 환경 | 로컬, Spring(Gradle `bootRun`)·AI(uvicorn)를 Docker 밖에서 직접 실행, PostgreSQL·Redis는 컨테이너. `hops` DB를 새로 만들어 시드를 다시 적재한 뒤 시작 |
| 코드 | 실행 2 이후 고친 드라이버(근거를 문서 id·제목·원인 문장으로 찾음, 승인 직전 사례 버전 재조회, 오류에도 보고서 저장) |
| 규모 | 문의 5건, 시작한 AI 실행 11개(상한 24). 이 밖에 AI 서버가 꺼져 있어 `SERVICE_UNAVAILABLE`로 끝난 첫 시도의 문의 1건이 DB에 남아 있다(모델 호출 없음, 사례와 무관) |

**이어진 것:** A1~A12가 다시 이어졌다. 문의 A가 질문 1회 뒤 티켓으로 끝나고, 담당자가 진행·검증된 해결 기록을 저장하고, Curator 초안이 원인·공개 범위(`STAFF`)·관계 연결에서 정답과 맞고, 문의자가 해결됨으로 확인하고, 담당자가 승인해 검색 문서로 저장되고 `visibleToSearch`가 참이 되었다. A13은 이전과 같이 `BLOCKED`(관계 반영 코드 없음, [#239](https://github.com/Hi-Hops/Hops/issues/239))다. 색인은 `PENDING`이다.

**실패한 것:** `C0.1` — 승인 전 C 문의의 두 번째 AI 실행이 `INVALID_OUTPUT`(모델 출력이 형식을 어김)으로 끝나 티켓 제안에 이르지 못했다. 같은 조건의 다른 C 문의(승인 후)는 티켓 제안으로 끝났다. 모델 출력 한 번의 실패이며 반복 실행으로 빈도를 보지 않았다. 원인은 조사하지 않았다.

**근거 검사의 결과 (고친 검사):** 승인 전 B·C와 승인 후 B·C 모두 사례 A가 상담 근거에도 직원이 보는 AI 메시지에도 나오지 않았고, 모든 문의에 저장된 근거가 1건 이상이라 판정 불가로 처리되지 않았다. 실행 2의 같은 결과와 달리 이번에는 검사가 실제로 근거에 담긴 값(문서 id·제목)을 본다. 이를 읽기 전용 쿼리로 확인했다. 승인 후 B가 받은 근거에서 그 근거의 공개 가이드 문서 id는 찾아지고, 승인된 사례 A의 문서 id는 찾아지지 않았다.

**확인하지 못한 것:** 승인 후 B가 사례 A를 근거로 인용하는지(내부 판단 프로필 필요, 켜지 않음), 사례 A가 있을 때 C가 방해를 받는지(같은 이유), 관계 조회 반영(#239), 반복 실행의 통과율. 이번 실행의 대화록은 사람이 읽지 않았다.

**해석의 한계:** 조건마다 1회다. 위 결과는 기본 프로필에서 담당자 전용 사례가 직원 상담 근거로 나가지 않았다는 이 한 번의 관찰이며 일반적인 안전성이나 성능이 아니다. `C0.4`·직원 메시지 검사는 문장 일치 대리 검사라 말을 바꾼 노출은 잡지 못한다.
