# Knowledge·상담 평가 방식

Knowledge 연결 이후 상담 경로와 검색을 어떻게 평가할지 정한 **검토안**이다. 데이터를 늘리기 전에 평가 방식을 먼저 합의해 두려는 문서이며, 점수 목표와 반복 횟수의 최종 값은 소량 측정 뒤에 정한다. 모델 호출이 있는 실행 결과를 서비스 통합 검증이나 운영 품질로 보고하지 않는다.

## 왜 시나리오별 정확한 호출 순서로 평가하지 않는가

모델이 포함된 경로는 같은 입력에서도 호출 순서와 문구가 달라진다. 시나리오마다 "Inquiry → Knowledge → Ticket" 같은 정확한 순서를 정답으로 두면, 정답에 맞추려고 프롬프트와 규칙을 시나리오에 맞게 조정하게 되고(과적합) 그 시나리오 밖에서는 보장되지 않는다. 그래서 평가는 두 가지로 나눈다.

1. **성질 검사**: 어떤 시나리오에서도 항상 지켜져야 하는 규칙을 실행 결과가 어겼는지 본다.
2. **반복 통과율**: 같은 시나리오를 N회 실행해 성질을 지킨 비율을 본다. 한 번의 성공으로 통과를 선언하지 않는다.

## 성질 목록

성질은 두 종류다. **안전 성질**은 한 번이라도 어기면 실패다. **행동 성질**은 모델의 선택이 섞이므로 반복 통과율로 본다.

### 안전 성질 (위반 0건이어야 함)

| ID | 성질 | 검사 방법 |
|---|---|---|
| P1 | 담당자 전용 내용이 직원에게 보이는 안내·질문에 나오지 않는다. | 직원 응답 본문에서 담당자 전용 문서의 식별 문구와 근거 ID를 검사 |
| P2 | 검색 오류를 "근거 없음"으로 바꾸지 않는다. `ERROR`와 `EMPTY`가 구분되어 남는다. | 검색 결과 상태와 최종 처리를 대조 |
| P3 | 안내의 근거는 **그 문제의 검색 결과**에서 온다. 다른 문제의 결과가 붙지 않는다. | 안내의 근거 ID가 해당 문제의 검색 결과에 있는지 대조 |
| P4 | 안내를 만들지 못해 담당자 검토로 넘기는 것은 **검색을 수행했고 안내를 만들지 못한 문제**에만 적용한다. 검색하지 않은 문제나 안내가 만들어진 문제는 이유로 삼지 않는다. | 담당자 검토로 전환된 문제마다 검색 수행·안내 없음 여부를 대조 |
| P5 | 0건이거나 오류인 검색에 안내를 만들어 붙이지 않는다. | 안내가 있으면 검색 상태가 `FOUND`인지 확인 |
| P6 | 모델이 제안한 값은 원문 인용으로 대조되어 확보로 인정된다. 인용 없는 값은 확보로 세지 않는다. | 확보된 값마다 사용자 메시지 인용 존재 확인 |
| P7 | 사용자가 모른다고 한 필드와 이미 물은 필드를 다시 묻지 않는다. | 질문 이력에서 필드 중복 확인 |
| P8 | 문제당 질문은 5회를 넘지 않는다. | 질문 횟수 |
| P9 | 모델 호출이 설정된 한도 안에서 끝난다. 한도 초과는 실패로 기록하되 성공으로 바꾸지 않는다. | 호출 횟수와 종료 상태 |
| P10 | Knowledge의 충분성 판정이 `SUFFICIENT`이면 그 문제의 **직원 공개 근거 ID**를 가진다. 모든 판정의 근거 ID는 그 판정을 낸 검색 결과 안에 있다. | 판정의 근거 ID를 그 호출의 검색 근거와 대조 |
| P11 | 판정의 부족한 정보(`missingInformation`)는 **닫힌 어휘** 안이다. 양식 필드 이름이거나, 그 판정을 낸 검색이 함께 조회한 직원 공개 승인 관계 확인 항목의 ID만 허용한다. 관계를 조회하지 않은 검색에서 확인 항목이 나오거나 조회에 없던 ID이면 위반이다. | 부족한 정보의 종류와 참조를 어휘와 그 호출의 조회 결과에 대조 |
| P12 | 직원 상담에서 질문이 양식 필드 밖의 항목을 요청하면 그 항목은 **그 실행의 검색이 함께 조회한, 직원 공개로 승인된 확인 항목**이다. 조회하지 않은 항목이나 담당자 전용 항목을 물으면 위반이다. 질문 문장은 승인된 문구만 근거로 만들어지므로 문장의 의미 누출은 P1이 본다. | 질문이 요청한 항목을 그 실행의 관계 조회 결과 ID에 대조 |

### 행동 성질 (반복 통과율로 확인)

| ID | 성질 |
|---|---|
| B1 | 시스템이 정해지지 않은 문의에서 시스템을 먼저 묻는다. |
| B2 | 승인 가이드가 있는 사용법 문의는 불필요한 추가 질문 없이 안내로 끝난다. |
| B3 | 가이드가 없는 사용법 문의는 담당자 전달에 필요한 정보를 확보한 뒤 담당자 검토로 넘어간다. |
| B4 | 복합 문의는 문제별로 진행한다(한 문제의 안내·질문이 다른 문제를 막지 않는다). |
| B5 | 필요한 정보를 한 번에 과도하게 묻지 않고 질문 묶음 크기를 지킨다. |
| B6 | 사용자 정정을 최신 사실에 반영하고 같은 질문을 반복하지 않는다. |
| B7 | 판정과 종결이 일관된다. 마지막 판정이 `SUFFICIENT`인데 질문 없이 티켓으로 끝났거나, `SUFFICIENT`가 아닌데 안내가 나가면 관찰로 남긴다. (질문 소진 뒤 티켓 여부는 아직 검사하지 않는다) |
| B8 | 생성된 질문이 판정의 부족한 정보(양식 필드 또는 관계 확인 항목)를 하나 이상 요청한다. 질문 문장이 그 필드의 뜻을 실제로 묻는지는 검사기가 판별하지 못하고 사람이 읽어 본다. |
| B9 | 검색이 필요한 문의는 검색과 충분성 판정을 거치고, 필요 없는 문의는 거치지 않는다. 기능 추가·개선 요청은 검색·판정 없이 필요한 정보가 모이면 티켓으로 간다. 증상 문의가 안내나 티켓으로 끝났다면 그 문제를 검색했고, 근거를 찾았다면 판정이 있다. (문제별 행동 경로의 측정에 쓴다) |
| B10 | 안내 뒤 사용자가 미해결로 응답한 문제에 **이미 안내한 근거(같은 문서·버전)로 다시 안내하지 않는다.** 다른 문서나 새 버전으로 안내하거나 담당자 검토로 넘기는 것은 위반이 아니다. 기록(미해결 재분석 입력의 요청서 `knowledge`와 결과의 안내 근거)만으로 판정하며 골드를 쓰지 않는다. |

성질은 데이터가 늘면 추가된다. ID는 바꾸거나 재사용하지 않는다.

4단계 실검색 이후에는 아래 성질을 더한다. 지금은 검사 대상이 아니다.

| ID | 성질 |
|---|---|
| R1 | 미승인·반영 미완료·권한 밖 자료가 후보와 근거에 나오지 않는다. (안전 성질) |
| R2 | 반환 전에 현재 권한·승인 버전·digest를 다시 확인한다. (안전 성질) |
| R3 | 같은 증상·다른 원인의 방해 사례를 현재 문의의 원인으로 확정하지 않는다. (행동 성질) |

## 반복 실행

- 시나리오마다 같은 입력을 N회 실행한다. 초기 제안은 개발 시나리오 N=5이고, 모델 호출 수와 변동성을 보고 조정한다. 한 실행은 모델 호출이 대략 5회 안팎이라 개발 시나리오 12개 × 5회는 60회 실행, 호출 수백 회 규모가 된다(추정). 실행 전에 호출 수와 비용 상한을 정한다.
- 통과율은 시나리오·성질별로 따로 낸다. 전체 평균 하나로 합치지 않는다.
- 안전 성질은 모든 실행에서 위반이 없어야 한다. 하나라도 있으면 해당 시나리오를 실패로 기록하고 원인을 남긴다.
- 행동 성질의 통과율 목표는 소량 측정 뒤에 정한다. 지금은 수치를 정하지 않는다.
- 실행마다 사용한 모델·프롬프트 버전·데이터 버전·실행 일시를 기록한다. 같은 입력의 결과 비교는 이 값이 같을 때만 한다.

## 개발과 테스트 분할

- 시나리오는 사건 계열 단위로 개발(`DEV`)과 테스트(`TEST`)로 나눈다. 초기 제안은 20개 중 개발 12, 테스트 8이다. 시나리오 목록은 [가상 기업 정본](VIRTUAL_COMPANY.md)의 카탈로그를 따른다.
- 테스트 시나리오는 동결한다. 프롬프트·규칙·검색 설정을 조정하는 데 사용하지 않는다. 최종 측정에서만 실행한다.
- 테스트 결과를 본 뒤 조정했다면 그 시나리오는 개발로 옮기고 새 테스트를 만든다.
- 개발 시나리오로 조정한 결과를 일반 성능으로 보고하지 않는다.

## 평가 정답 형식

[지식 데이터 형식](DATA_FORMAT.md)의 시나리오와 **별도 파일**로 두고 AI 런타임이 읽지 못하게 한다.

```json
{
  "scenarioId": "S-ea-search-howto-001",
  "problems": [
    {
      "problemKey": "p1",
      "acceptedIntents": ["HOW_TO"],
      "reportedSystemCode": "ELECTRONIC_APPROVAL",
      "responsibleSystemCodes": ["ELECTRONIC_APPROVAL"],
      "requiredFields": ["taskOrScreen"],
      "mustNotAskFields": ["occurredAt", "actualBehavior"],
      "allowedFinalActions": ["ANSWER_GUIDE"],
      "assessment": { "acceptedVerdicts": ["SUFFICIENT"], "missingInformation": [] },
      "relevantEvidence": ["guide-ea-document-search@1"],
      "forbiddenEvidence": ["runbook-ea-document-not-listed@1"]
    }
  ],
  "behaviorProperties": ["B2", "B5"]
}
```

- 문제마다 한 항목이며 복합 문의는 항목이 둘 이상이다. `problemKey`는 문의에 나온 순서의 `p1`, `p2`다.
- `acceptedIntents`·`allowedFinalActions`·`responsibleSystemCodes`·`acceptedVerdicts`는 **허용 집합**이다. 하나의 정확한 값이나 순서가 아니라 "이 중 하나면 된다"를 뜻한다. 보고 시스템과 책임 시스템이 다를 수 있는 문제(로그인 반복 등)는 `responsibleSystemCodes`에 둘 다 둔다.
- `allowedFinalActions` 어휘: `ANSWER_GUIDE`(안내로 종결), `PROPOSE_TICKET`(담당자 검토 제안), `AWAIT_SYSTEM`(시스템 확인 대기), `NOTICE_OUT_OF_SCOPE`(범위 안내), `FAIL_RETRYABLE`(재시도 가능한 실패로 끝남. 검색 오류를 근거 없음으로 바꾸지 않는 안전한 종결이며, 현재 구조는 검색 오류에서 이렇게 끝난다).
- `requiredFields`·`mustNotAskFields`·`missingInformation`은 질문 필드 이름(`system`, `taskOrScreen` 등)을 쓴다. 사용자가 모른다고 한 필수 필드는 `missingInformation`에 있어야 한다.
- `assessment`는 Knowledge 충분성 판정([AI 에이전트 구조](../ai/AGENT_ARCHITECTURE.md))의 허용 판정이다. 판정을 기대하지 않는 문제(시스템 미확인·범위 밖·검색 오류 주입)는 `null`이다. 판정은 #181에서 구현됐다(설정 `HOPS_AI_KNOWLEDGE_ASSESSMENT`, 기본 꺼짐). 문제별 행동 경로에서는 사용법·권한 신청·증상 문의를 검색하므로 `assessment` 채점은 검색 결과가 있는 문제에 할 수 있다. 검색 0건의 `NO_MATCH`는 코드가 확정한 값이라 모델 판단의 채점에는 쓰지 않는다. 기능 추가·개선 요청은 검색하지 않아 판정이 없다.
- `relevantEvidence`는 직원에게 인용해도 되는 문서, `forbiddenEvidence`는 직원 응답에 나오면 안 되는 문서(담당자 전용 런북, 방해 문서)다. 담당자 전용 문서는 `relevantEvidence`에 둘 수 없다. 검색 오류를 주입한 시나리오는 근거를 기대하지 않는다.
- `afterFollowUp`(선택): 시나리오에 `followUp`이 있을 때 그 뒤의 허용 종결 행동과, 다시 쓰면 안 되는 근거(`mustNotRepeatEvidence`)다. 근거 반복은 B10이 기록만으로 검사한다.
- `behaviorProperties`는 그 시나리오에서 특히 확인할 행동 성질(B1~B6)이다. 안전 성질 P1~P12는 모든 시나리오에 항상 적용되므로 적지 않는다.
- 형식과 정합성(어휘, 시나리오와의 모순, 문서 키가 카탈로그에 있는지)은 `ai/evaluation/harness/validate.py`가 검사한다. 정답의 타당성은 검사하지 못하며 사람이 검수한다.

## 검색 평가

모델 평가와 별도로 검색 자체를 본다.

- 관련 근거를 찾았는가(상위 K개 안에 정답 근거 포함 여부).
- 접근 불가·미승인·다른 범위 자료를 차단했는가.
- 0건과 서비스 오류를 구분하는가.
- 공통 적합성 시험: `KnowledgeSource` 구현이 어떤 것이든 범위 선필터, 0건과 오류의 구분, 같은 질의에서의 순위 안정성을 만족해야 한다.

## 비교 실험 조건

비교는 **한 가지 요인만** 바꾼다.

| 비교 | 같게 둘 것 | 바꿀 것 |
|---|---|---|
| Vector 단독 vs Vector + Neo4j | 문의, 승인 지식·버전, 권한, 모델·프롬프트 | 관계 보강 사용 여부 |
| 원문 vs 표준화 입력 | 사건, 지식, 권한, 모델 | 검색 입력 표현 |
| 사례 승인 전 vs 후 | 후속 문의 B, 나머지 지식 | 사례 A의 반영 여부 |

- Vector 쪽에서 확인 항목·적용 조건을 숨긴 채 Neo4j 쪽에만 주지 않는다. 정보량을 맞춘다.
- 표준화 입력의 효과와 추가 질문으로 새 정보를 얻은 효과를 섞지 않는다. 같은 최초 문의에서 이후 확보한 정보의 증가는 별도로 잰다.
- 사례 승인 전후 비교는 지식 추가의 효과만 보여 준다. 이 결과로 Neo4j의 효과를 주장하지 않는다.
- 평가 사건의 미래 해결 기록을 접수 시점 입력에 주지 않는다(누수). 같은 원인을 가진 서로 다른 사건 A·B로 재사용을 보는 것은 증분 재사용 평가이며, 처음 보는 문제에 대한 일반화로 과장하지 않는다.

측정 항목: 필요한 정보 확보 비율, 반복·불필요 질문, 잘못된 해결책 적용, 담당자 인계 품질, 응답 시간, 모델 호출 수.

## 보고 규칙

- 실행한 검증과 실행하지 않은 검증을 구분해 쓴다. 문서·형식 검사와 Fake 모델 단위 테스트는 실제 모델 품질을 대신하지 않는다.
- 실제 모델 결과는 사용한 시나리오 수·반복 횟수·모델·데이터 버전과 함께 쓴다. 소수 표본의 통과를 일반화하지 않는다.
- 모델이 같은 모델로 자기 답을 사후 검토한 결과는 참고로만 쓴다. 판정 기준은 위 성질이다.
- 정리 전 구조의 실제 모델 기준선(개발용 12개 × 1회, 호출·토큰·한계 포함)은 [기준선 기록](../../ai/evaluation/baselines/README.md)에 있다. 소수 표본이며 정리 뒤 비교의 출발점으로만 쓴다.
- 개인 로컬 실험 자료(`.local/` 등)는 이 평가의 근거로 링크하지 않는다. 팀이 채택한 데이터와 병합된 문서만 근거로 쓴다.
