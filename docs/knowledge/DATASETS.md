# 데이터 구축 초기 계획

[PRD](../PRD.md)와 [가상 기업 명세](VIRTUAL_COMPANY.md)를 기준으로 필요한 데이터를 새로 구성한다. 다음은 구축·검수 계획이며 확정 스키마·수량·공통 데이터 선정 결과가 아니다. 원문 수집, 합성 생성, DB 적재와 실제 모델 평가는 아직 수행하지 않았다.

## 데이터 종류와 용도

| 데이터 | 핵심 내용 | 사용 위치 |
|---|---|---|
| 기업·시스템 카탈로그 | 시스템·기능·사용자·소속·현재 주담당 관계·의존 관계 | 업무 기준 데이터와 허용된 검색 문맥 |
| 매뉴얼·업무 정책·런북 | 정상 사용 절차, 기업의 접근·신청 규칙, 담당자 확인 항목과 적용 조건 | 검수한 검색 지식. 직원용과 담당자 내부 자료 구분 |
| IT 문의 상담 대화 | 자연어 최초 문의, 추가 질문, 답변·정정·미해결 반응, 표준 요청으로 이어지는 과정 | 문의 분석·질문·표준화·답변의 개발 및 평가 |
| 해결 사례 | 출처 문의·티켓·처리 기록, 확인된 조치·검증 결과·조건·한계 | 승인과 공개 조건을 충족한 재사용 지식 |
| 관계 데이터 | 시스템·기능·증상·가능 원인·확인 항목·사례 사이의 근거 있는 연결 | Neo4j 관계 탐색과 검색 보강 |
| 평가 데이터 | 시점별 모델 입력, 정답·허용 행동·관련 근거, 접근·오류 조건 | 검색·답변·표준화 및 업무 경계 평가 |

서비스의 접수·승인·공개 규칙은 PRD를 참조하고 별도 정책 JSON 사본을 먼저 만들지 않는다. 가상 기업의 문서 열람·권한 신청 규칙은 실제 상담에 필요한 업무 지식으로 작성한다. 상담 원문 전체를 자동으로 검색 인덱스에 넣거나 모든 대화를 해결 사례로 승격하지 않는다.

## IT 문의 상담 대화

단일 질문·답변뿐 아니라 여러 차례 확인하고 정정하는 대화를 핵심 데이터로 구축한다. 사용법·권한·현상·기능 추가·개선 의도를 다루고 의도와 내부 처리 유형을 별도로 검수한다. 담당자에게 보낼 정보와 사용자에게 보여줄 답변도 구분한다.

대화에는 화자·순서·원문·출처와 사건 계열 식별을 남긴다. 각 시점에서 확인된 사실·추정·미확인 항목, 필요한 질문, 표준 요청과 허용된 다음 행동을 평가 주석으로 연결한다. 실제 필드명과 JSON 형식은 소량 검토 후 정한다. 미래 답변·숨겨진 원인·최종 해결 결과를 이전 차례의 모델 입력에 넣지 않는다.

| 반드시 포함할 상황 | 확인할 행동 |
|---|---|
| 모호한 최초 문의, 사용자가 모름, 정보가 이미 있음 | 분기에 필요한 정보만 질문하고 미확인은 보존 |
| 사용자가 앞선 설명을 정정함, 안내가 해결되지 않음 | 최신 사실 반영, 같은 답변·질문 반복 방지 |
| 사용법과 실제 처리 요청, 기능 추가와 개선 | 안내·신청·조사·변경 요청을 구분 |
| 보고 시스템과 책임 시스템이 다름, 책임 근거 부족 | 맥락 보존, 근거로 제안하거나 보고 시스템 담당자에게 조사 연결 |
| 복합 문의, 문제별 진행 차이 | 독립 문제 분리, 여러 원인 후보와 구분 |
| 질문 한도, 시스템 미확인, 범위 밖 | 문제별 최대 5회 질문 묶음과 선택 대기·범위 안내. 질문 한도는 현재 규칙에서 시나리오로 도달시킬 수 없어 단위 테스트로 확인한다 |
| 권한 거부, 검색 0건, 검색 오류 | 내부 자료 비노출, 근거 부족과 검색 실패 구분 |
| 처리 후 해결·미해결·무응답 | 문의자 확인과 업무 완료 구분, 무응답 자동 종료 금지 |

전체 상담 대화와 승인된 지식은 용도가 다르다. 대화는 우선 개발·평가·선정된 프롬프트 예시에 사용하고, 운영 검색에 필요한 내용만 별도 검수된 가이드나 사례로 구성한다. 이 계획은 파인튜닝을 전제하지 않는다.

## 데이터 탐색과 기존 자료 활용

외부 자료는 대화의 현실적인 표현·질문·피드백 패턴과 기술 사실을 탐색하는 재료다. 외부 제품의 절차·권한·조직 배정을 가상 기업의 정답으로 그대로 가져오지 않는다. 사용 조건·한국어 전환 가능성·도메인 적합성·실제 대화 여부·검수 비용을 먼저 비교한다.

| 탐색 후보 | 참고할 내용 | 채택 전 확인할 점 |
|---|---|---|
| [MSDialog 공식 안내](https://ciir.cs.umass.edu/downloads/msdialog/) | Microsoft 제품 지원 포럼의 다중 차례 대화·추가 질문·피드백 | 접근 신청 필요, 내부 연구만 허용하며 데이터 재공유 금지. 팀 공유 데이터로 바로 채택하지 않음 |
| [Ubuntu Dialogue 공식 생성 저장소](https://github.com/rkadlec/ubuntu-ranking-dataset-creator) | 기술 문의 대화 구조 | 영어·Ubuntu 중심의 차이, 원자료 사용 조건 확인. 응답 순위용 무작위 오답을 실제 상담 답변으로 사용하지 않음 |
| [ABCD 공식 저장소](https://github.com/asappresearch/abcd) | 정책과 다단계 절차에 따른 상담 구성 | 온라인 쇼핑 예시를 포함한 과업 대화로, HOPS의 IT 기술 사실·업무 규칙을 제공하는 자료가 아님 |

위 후보는 공식 설명을 확인한 탐색 목록이며 데이터 확보·선정·내용 검수를 완료한 목록이 아니다. 한국어 IT 문의에 맞는 공개 상담 자료는 추가 탐색이 필요하다. 대화 제공자에게 연락하거나 자료를 다운로드하는 작업은 이번 문서 정리에 포함하지 않는다.

이미 수집한 Microsoft 지원 문서·TechQA·공개 런북·장애 보고서는 원문과 출처 정보를 보존한다. 이 중 새 기능·기술 전제에 실제로 맞는 부분만 재검토한다. TechQA 같은 질문·답변 자료만으로 추가 질문과 사용자 반응을 포함한 상담 대화를 대체하지 않는다. 쿠버네티스·OpenShift 등 가상 환경에서 쓰지 않는 기술은 수집량과 무관하게 제외한다. 기존 가이드·런북의 기술 내용도 동일한 기준으로 선별하며 부서·담당자·해결 라벨을 그대로 승계하지 않는다.

## 소량 검증과 수량 제안

처음에는 대표 기능 3개에 대한 매뉴얼과 서로 다른 상담 사건 6건 정도를 함께 검토한다. 정상 사용법과 권한·현상 문의를 구분하고, 실제로 답할 근거가 있는지 확인한 뒤 확대한다. 다음 수량은 **초기 제작 예산안**이며 최종 평가셋 규모나 운영 분포가 아니다.

| 항목 | 초기 검토안 | 수량을 정할 기준 |
|---|---|---|
| 기업·시스템·담당 관계 | 기업 1, 시스템 3, 기능 10, 시스템별 주담당 관계 3 | 기능·책임·권한 경계의 일관성 |
| 직원 가이드·기업 업무 규칙 | 기능별 가이드 약 8건, 공통 업무 규칙은 필요한 만큼 | 기능마다 실제 안내 절차와 근거가 있는가 |
| 담당자 런북 | 증상 계열별 1건씩 4건부터 | 원인 후보·확인 항목·직원 공개 범위를 구분하는가 |
| 상담 대화 | 독립 사건 계열 20개(개발 12·테스트 8)부터 | 주요 의도와 위 경계 상황을 빠짐없이 다루는가 |
| 해결 사례 | 재사용 가능한 서로 다른 처리 유형 6건(시드)부터 | 조치·검증·조건과 출처·승인 경로가 있는가 |
| 관계 | 검수 문서·사례에 필요한 연결만 | 각 연결의 의미와 근거를 추적할 수 있는가 |

표현 변형·번역을 늘려도 독립 사건 수가 늘었다고 세지 않는다. 사례를 모든 대화에 억지로 만들지 않는다. 평가 사건 수·분포·개발/테스트 분할과 점수 목표는 소량 검토 후 별도로 정하고 테스트 부분을 동결한다.

## 구축·전처리와 관리 구조

1. 사용 조건과 적용 범위를 확인한 원문을 변경 없이 보존하고 출처·버전·수집 시점·해시를 기록한다.
2. 화자·차례·절차·조건을 보존하며 형식을 정리하고 개인정보·비밀값·불필요한 마크업을 제거한다.
3. 사건 계열별 중복·유사 문서를 묶는다. 번역·가상화 시 원출처와 변경 내용을 남기고 가상 사실을 실제 기록으로 표현하지 않는다.
4. 매뉴얼·업무 규칙을 기준으로 대화와 사례의 사실·의도·정보 누락·기대 행동을 검수한다. 외부 데이터의 긍정·부정 후보 응답과 실제 해결 여부를 구분한다.
5. 사건 계열을 기준으로 개발/테스트를 분리한 뒤 예시 선정과 데이터 확대를 진행한다. 정답·미래 결과는 모델 입력·검색 자료와 분리한다.
6. 검수한 지식만 청크와 관계로 변환한다. 청크는 절차·적용 조건·공개 범위를 보존하고 문서 ID·버전·원문 위치를 연결한다.
7. 참조·권한·버전·출처·중복·해시를 검사한 후 승인·공개 조건에 맞춰 적재하고 실제 검색 결과를 확인한다.

최종 폴더·파일명은 아직 확정하지 않는다. 구축 시에는 아래 논리 구분을 기준으로 소량 데이터에 맞는 최소 구조를 정한다.

| 구분 | 보관 대상 |
|---|---|
| 비공개 원문 | 외부 원본·수집 메타데이터·개인 실험 자료. 재배포 조건에 맞춰 관리 |
| 기준 데이터 | 카탈로그, 검수한 매뉴얼·업무 규칙·런북·사례와 출처·권한·버전 |
| 상담 데이터 | 원 대화와 사건 계열, 시점별 입력·표준화 주석 |
| 평가 전용 | 숨겨진 정답·관련 근거 매핑·고정된 테스트 사건 |
| 재생성 가능한 파생물 | 청크·임베딩·관계·적재 목록과 원본 버전·해시 |

배포·공유 가능한 데이터만 프로젝트의 공통 데이터 경로에 둔다. 외부 원문이나 개인 아카이브를 실행 필수 경로로 만들지 않는다. 스키마와 생성 코드는 실제 레코드가 검토된 뒤 작성한다.

## 저장·검색과 사례 공개

검색 데이터의 신뢰 경계와 권한 우회·오염 검증은 [보안 개발 명세](../SECURITY.md)도 따른다. 업무 정본의 테이블·컬럼은 [물리 ERD](../ERD.md)를 참조하며 문서 설계와 실제 DB 적용 상태는 구분한다.

업무 데이터의 정본은 Spring이 관리한다. 문의·티켓·배정·처리·확인·승인을 Python이 직접 확정하지 않는다. pgvector에는 검수 지식의 청크·임베딩과 원문 ID·버전·접근 범위를, Neo4j에는 같은 원본을 가리키는 엔티티·관계·근거를 저장한다. 저장 경계·청크/검색 검토 기준·그래프 구조·서비스 계약의 채택값은 [결정 대장](../../specs/QUESTIONS.md#실행검색-기본값)과 에이전트 계약을 따른다. 임베딩 모델·차원·토크나이저 호환과 실제 데이터/검색 품질은 소량 검증으로 별도 확인한다.

해결 사례는 처리 기록에서 초안을 만들고 문의자 해결 확인·시스템 담당자 승인 후 같은 승인 버전의 Vector와 Neo4j 반영 성공을 확인해야 검색 공개한다. 일부 실패·결과 미확인·버전 불일치면 해당 버전은 양쪽 검색에서 비공개로 유지한다. 실패 시도는 업무 이력으로 남기며 무티켓 사용법 대화를 자동 사례로 만들지 않는다. 합성 사례의 가상 확인 설정, HOPS 시연에서 수행한 확인, 실제 운영 이력은 구분한다. 검색 결과는 현재 권한·공개 상태와 적용 조건을 검증한다.

역할별 입출력과 Curator의 초안·연결 후보 경계는 [에이전트 계약](../../contracts/agents/README.md), 승인·반영 의미는 [목표 공통 계약](../../specs/contracts/TARGET_CONTRACT.md)을 따른다. 실제 작업 담당·데이터 선정과 실행 검증은 관련 담당자가 확인한다.

## 검수와 평가

데이터 검수에서는 출처·사용 조건, 기능·권한 일관성, 사실과 추정, 합성 표시, 문서/시스템 적용 버전, 공개 범위와 참조 무결성을 확인한다. 그래프 연결이나 유사 사례만으로 현재 원인을 확정하지 않는다. 문서 검사·Mock 실행은 실제 모델 품질이나 서비스 통합 검증을 대신하지 않는다.

검색 평가는 관련 근거를 찾았는지와 접근 불가·미공개 자료를 차단했는지 확인한다. 응답 평가는 근거에 맞는 안내·미확인 보존·추가 질문·표준 요청·다음 행동을 별도로 확인한다. 검색이 정상 수행됐지만 0건인 경우와 검색 서비스 오류를 구분한다.

Vector 단독과 관계 보강, 원문과 표준화 입력을 비교할 때 같은 사건·지식 버전·권한·모델 조건을 유지한다. 기존 승인 사례는 검색할 수 있지만 평가 사건의 미래 해결 내용을 선행 지식으로 주지 않는다. 실제 연결 단계에서는 문의→담당자 처리→문의자 확인→사례 승인→양쪽 반영→다음 문의 재검색을 최소 한 건 검증한다.

다음 진행 순서는 작은 기업 명세·샘플 검토 → 출처 선정·데이터 형식과 계약 확정 → 데이터 확대·전처리 → DB 적재·검색 검증 → Knowledge·AI 서버 연결 → 품질 평가·개선이다. 대량 데이터나 물리 스키마를 먼저 만들기보다 실제 문의에 필요한 근거와 평가 조건을 소량에서 확인한다.
