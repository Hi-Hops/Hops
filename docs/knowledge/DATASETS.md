# HOPS 지식·평가 데이터 범위

기준: [PRD 1.44](../PRD.md) · 팀 합의 목표 / 수량·데이터·검수·적재 별도. 현재 v0는 기존 부서 기반 데이터이며, [v1 정책 초안](../../datasets/knowledge/v1/README.md) 5건은 AI 작성·검수 전·적재 대기다. 실제 운영 자료를 확보했다거나 공통 데이터가 모두 준비됐다는 뜻이 아니다.

## 1. 목적과 대상

가상 기업의 전자결재·공통 로그인·파일 공유에서 사용법·권한·현상 확인·기능 추가·개선 문의를 지원한다. HOPS의 실제 문의·티켓·처리·확인·사례 공개를 연결하되 대상 시스템 전체를 새로 구현하지 않는다. Mock 조회와 실제 서비스 관측은 구분한다.

| 종류 | 용도 | 접근·상태 |
|---|---|---|
| 시스템·기능·담당 관계 | 보고/책임 시스템과 주담당자 연결 | 업무 DB가 정본. 가상 ID·인물·기능 경계 검수 전. |
| 직원 가이드 | 사용법과 안전한 확인 안내 | 문서 초안 8건. 직원용 공개 범위와 출처 검토·기계 판독 데이터 생성 전. |
| 정책 | 문의·권한·배정·완료·사례 공개 규칙 | v1 5건은 검수 전 초안, `PENDING`. |
| 담당자 런북 | 확인 항목과 조건부 조치 참고 | 문서 초안 2건. 담당자용 내부 자료로 실제 적용 여부 확인·기계 판독 데이터 생성 전. |
| 해결 사례 | 확인된 조치·결과와 조건의 재사용 | 문의자 확인·담당자 승인·동일 버전 양쪽 색인 성공 후 검색 공개. |
| 관계 데이터 | 시스템·기능·증상·가능 원인·확인 항목·사례 | Neo4j 후보·스키마 검토; 연결은 인과관계 확정이 아님. |
| 평가 데이터 | 문의·응답·필수 정보·기대 행동·숨겨진 정답 | 검색 인덱스와 프롬프트 예시에서 정답·미래 해결 내용 분리. |

## 2. 초기 출발안

시스템 3, 기능 8~10, 시스템·주담당 관계 3, 직원 가이드 8, 정책 4, 승인 해결 사례 8, 담당자 런북 2, 기준 대화 시나리오 30은 출발 예시다. v1 정책 초안이 5개인 것은 범주를 나눈 작성안이며, 4개 출발안을 확정 수량으로 변경하거나 정책 5건의 검수 완료를 뜻하지 않는다. 실제 수량과 검토자·일정·관계 수량은 제작 과정에서 정한다.

## 3. 합성 데이터와 출처

초기 사례 대부분은 합성하거나 가정한다. 시연용 합성 사례에는 **가상 문의자가 해결했다고 확인한 설정**을 기록하고 해당 설정이 실제 임직원 확인이 아님을 밝힌다. HOPS 흐름에서 수행한 문의자 확인은 별도로 기록한다. 사례는 출처를 합성·데모 검증·실제 운영으로 구분하고 승인과 두 저장소의 같은 버전 반영을 마친 뒤 공개한다. 공개 자료의 사용 조건을 확인하고 기존 부서·종료 라벨을 담당자 정답·해결 성공으로 그대로 가져오지 않는다.

## 4. 데이터 전환

[가이드·런북 전환 목록](DATA_MIGRATION_REVIEW.md)에 기존 24개 자료의 분류 후보를 기록한다. 기존 데이터는 삭제하지 않는다. 기술 사실·시스템 경계·권한·출처를 확인하고 새 JSON·관련 시나리오·청크·해시를 함께 갱신해야 한다. 기존 v0 `PENDING`은 새 자료의 승인도, 기존 정책의 검색 적합성도 뜻하지 않는다. 담당자 검수·팀 공통 데이터 리뷰 및 적재 전 검증은 별도다.

## 5. 평가

평가 사건 수·분할과 최종 목표는 데이터 준비 후 정한다. 번역·표현 변형은 원 사건과 같은 분할에 둔다. 동일 질문·문서/사례 버전·권한·모델 조건에서 Vector와 관계 보강, 원문과 표준화를 비교하며 검색 및 최종 답변 품질을 구분한다. 미리 존재하는 승인 사례는 검색할 수 있지만 평가 사건의 미래 해결 내용과 정답 매핑은 검색 자료·프롬프트에 넣지 않는다. [시나리오](INCIDENT_SCENARIOS.md)와 [검수](REVIEW_CHECKLIST.md)를 따른다.

기존 데이터의 출처·검수 상태는 [v0 데이터 안내](../../datasets/knowledge/v0/README.md)와 각 원본에서 확인한다.

## 6. 종류별 데이터 작성·검수 기준

| 종류 | 작성할 내용 | 검수·전환에서 확인할 내용 |
|---|---|---|
| 시스템·기능 | 세 시스템의 이름·역할, 지원 기능과 시스템 간 의존 관계 | 보고 시스템과 책임 시스템 경계가 구분되는가. 관계만으로 현재 원인을 확정하지 않는가. |
| 주담당 관계 | 시스템별 유효 주담당자와 가상 사용자 연결 | 한 사람이 복수 시스템을 맡을 수 있고, 각 시스템의 현재 주담당자가 하나인가. 실제 사용자/운영 데이터가 아닌가. |
| 직원 가이드 | 사용 목적, 전제, 직원이 안전하게 확인할 내용과 담당자 연결 기준 | 실제 화면·제품 동작을 모르면 가정으로 표시했는가. 직원에게 내부 절차·비밀정보를 노출하지 않는가. |
| 담당자 런북 | 현상·확인할 사실·가능 원인·관측 범위·실제 조치의 참고 | 후보와 확인된 원인을 구분했는가. Mock·실제 관측 여부와 적용 조건을 명시했는가. |
| 정책 | 문의 흐름·배정·권한·완료·사례 승인·검색 공개 | 5회 질문·시스템 확인 대기·문의자 확인과 두 저장소 공개 조건에 맞는가. |
| 해결 사례 | 출처 문의/티켓/처리 기록, 실제 조치·검증, 적용 시스템 버전·조건·한계 | 문의자 확인과 담당자 승인, 동일 승인 버전의 두 저장소 성공을 구분했는가. |
| 관계 | 시스템·기능·증상·가능 원인·확인 항목·사례, 시스템 의존 | 노드/관계의 근거와 출처가 있는가. 현재 문의 원인을 자동 확정하지 않는가. |
| 평가 사건 | 최초 문의·사용자 응답·필수 정보·허용 질문·기대 행동·정답 매핑 | 정답·미래 해결 내용이 검색 지식과 프롬프트에 노출되지 않는가. |

가이드 초안 8건과 런북 초안 2건은 [가이드 목록](guides/README.md)과 [런북 목록](runbooks/README.md)에서 확인한다. 문서 초안이 작성됐다는 사실은 실제 제품의 확정 기능·사용자의 운영 경험·기계 판독 데이터·검색 적재를 뜻하지 않는다.

## 7. 기존 자료와 새 자료를 연결하는 절차

1. [전환 목록](DATA_MIGRATION_REVIEW.md)의 기존 자료를 대상 시스템·기능별로 검토하고 재사용·수정·범위 밖 후보를 판정한다. 자동 치환으로 IT 부서를 시스템 담당자로 만들지 않는다.
2. 원본의 출처·라이선스·해당 부분과 가상 정책을 분리하고 새로운 자료의 적용 조건·권한·버전을 작성한다. 정답 라벨과 실제 해결 여부를 그대로 가져오지 않는다.
3. 해당 시스템 담당 또는 데이터 담당이 내용·민감정보·실제 적용 가능성과 직원/담당자 공개 범위를 검수한다. 검수자의 개인 확인과 팀의 공통 데이터 채택 리뷰는 다르다.
4. 새 기계 판독 JSON·스키마·시나리오 참조를 작성하고 청크·manifest·해시의 생성/검증 방식을 마련한다. 현재 v1 정책 JSON의 스키마 검증이 전체 v1 데이터 생성·검증을 의미하지 않는다.
5. 검수·공통 리뷰를 마친 자료만 계획된 검색 범위에 반영한다. 해결 사례는 별도로 문의자 확인·시스템 담당자 승인과 동일 승인 버전의 양쪽 반영 성공을 확인한다.

### 7.1 기존 v0 자료의 검수 현황을 읽을 때

기존 v0에는 일반 공개 근거·PORTAL 근거, 직원 가이드·담당자 런북·정책, 용어·진단 신호와 시나리오 카탈로그가 있다. 정확한 수량·출처·검수/적재 상태는 [v0 데이터 안내](../../datasets/knowledge/v0/README.md)와 각 manifest가 원본이다. 예전 담당자 확인은 새 시스템·정책으로 바뀐 데이터에 대한 승인으로 사용하지 않는다. 진단 신호와 평가 정답 카탈로그를 그대로 검색 문서로 적재하지 않는다.

## 8. 합성 사례·관계와 관리 항목

- 합성 사례에는 문의·문제·처리 기록의 관계, 증상 또는 변경 목적, 확인 사실·원인 미확인, 실제로 수행했다고 **설정한** 조치와 검증, 적용 조건과 시스템 버전을 기록한다. 출처·가상 확인 설정을 항상 함께 표시한다.
- HOPS 시연 중 실제 흐름으로 만든 사례는 합성 초기 데이터의 설정상 확인과 구분한다. 문의자가 확인하고 담당자가 승인했더라도 실제 기업 운영 이력이 되는 것은 아니다.
- 업무 실패 시도는 티켓 이력에 보존하지만 해결 사례 지식으로 게시하지 않는다. 무티켓 사용법 대화만으로 처리 기록이 없는데 Curator가 자동 사례를 생성하지 않는다.
- 관계 데이터는 원 사례·문서와 시스템·기능·증상·가능 원인·확인 항목 사이의 의미와 출처를 보존한다. 새로운 관계 유형은 담당자가 스키마를 검토한다. 실제 노드·속성·ID와 수량은 상세 설계에서 정한다.
- 하나의 승인 사례 버전에 대해 Vector·Neo4j 결과를 각각 확인한다. 일부 반영 실패·상태 미확인 또는 버전 불일치는 양쪽 경로 모두 비공개다.

## 9. 검증·공유 산출물

- 데이터의 작성/검수 상태, 출처·사용 조건, 시스템 범위와 공개 범위, 문서/적용 버전 및 생성 방법.
- 검색 인덱스에 넣는 문서와 넣지 않는 평가 정답·숨겨진 원인·진단 신호의 구분.
- JSON·스키마 검사, 문서와 기계 판독 원본의 참조·해시, 청크·manifest 검증 결과. 이 검사는 검색 품질·실제 모델 평가나 서비스 E2E를 대신하지 않는다.
- 공통 데이터는 팀 리뷰 후 선정하며 특정 개인의 데이터셋·검색 실험을 다른 담당자에게 강제하지 않는다. 실제 개인정보·비밀값·개인 원시 로그는 공유 데이터에 포함하지 않는다.
