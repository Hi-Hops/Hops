# HOPS 문의·평가 시나리오

기준: [PRD 1.44](../PRD.md) · 아래는 팀이 채워 검토할 가상 시나리오 후보이며 실제 실행 결과나 확정 평가 데이터가 아니다. 예시에는 정답 사례 ID나 미래 해결 내용을 넣지 않는다. 정답 매핑은 검색 지식·프롬프트와 별도로 관리한다.

## 1. 작성할 시나리오

| 후보 | 최초 문의 예 | 확인할 제품 동작 |
|---|---|---|
| 사용법 | 전자결재 문서 작성 위치 문의 | 승인 직원 가이드 안내 → 문의자 확인 → 무티켓 종료 |
| 권한 | 공유 파일 열람 권한 요청 | 목적·기능 확인 → 표준 요청 → 담당 시스템 배정 |
| 현상 확인 | 결재 문서가 보이지 않음 | 기대/실제·조건 확인, 관계 기반 질문과 근거·미확인 표시 |
| 다른 책임 시스템 | 전자결재에서 로그인 반복 | 보고 시스템 보존, 대화와 근거가 충분하면 공통 로그인 담당자로 배정 |
| 근거 부족 | 결재 화면 이상이나 책임 시스템 불명확 | 원인 단정 없이 보고 시스템 담당자가 최초 조사 |
| 시스템 미확인 | 어떤 시스템인지 모르는 오류 문의 | 최대 5회 질문 묶음과 시스템 선택·확인 대기 유지 |
| 기능 추가 | 문서 일괄 다운로드 요청 | 현재 방식·문제·원하는 변경 정리, 변경 티켓과 담당자 배정 |
| 기능 개선 | 기존 결재 화면 표시 변경 요청 | 변경 전후와 미확인 수용 조건을 구분 |
| 복합 문의 | 문서 열람 실패와 기능 추가 요청 | 독립 문제와 복수 티켓, 문제별 확인 |
| 부분 실패 | 복합 문의 중 일부 생성 결과 미확인 | 성공 티켓 보존, 저장 여부 확인 전 중복 생성 금지 |
| 해결 확인 | 담당자가 기능을 구현·검증한 결과 | 구현 완료 후 문의자 확인, 미해결이면 같은 티켓 계속 |
| 사례 재사용 | 처리 후 표현이 다른 유사 문의 | 확인·승인 및 양쪽 반영을 완료한 사례와 적용 버전 표시 |
| 반영 실패 | 승인 사례의 한 검색 저장소 반영 실패 | 양쪽 검색 비공개, 기록 유지, 원인 수정 후 재실행 |
| 경계 | 범위 밖, 정보 부족, 사용자 모름, 검색 오류 | 범위·미확인·검색 결과 없음/오류를 구분 |

## 2. 평가 사건에 기록할 정보

최초 문의, 가상 사용자 응답, 필수 정보, 허용 질문, 의도, 보고 시스템, 책임 시스템, 처리 유형, 관련 지식·사례, 예상 다음 행동을 평가용으로 관리한다. 숨겨진 원인·정답 매핑·현재 사건의 미래 해결 내용은 모델 입력과 KB에 넣지 않는다. 기존 승인 사례 자체의 검색은 허용한다. 표현 변형은 원 사건과 같은 분할에 둔다.

데이터가 준비되지 않아 사건 수·분포·분할·목표·동결일·검토자는 미정이다. 실제 시나리오와 사례를 생성·검수한 후 테스트용 식별자와 기대값을 연결한다. 기존 v0 카탈로그의 부서 정답을 새 책임 시스템 정답으로 그대로 쓰지 않는다. 기존 v0 시나리오 데이터는 전환 전 자료로 남아 있다.

## 3. 시연·평가 시나리오 상세 초안

다음 예시는 제품 흐름을 검토하는 **가상 대화와 기대 행동**이다. 실제 사용자·시스템 관측·확정 데이터셋이나 측정 결과가 아니다. 평가에 채택할 때 정답 매핑·숨겨진 사실은 별도 평가 자료로 관리하며 모델에 이 문서의 기대 행동을 그대로 제공하지 않는다.

### 3.1 결재 문서 작성 방법: 무티켓 안내

- **상황:** 임직원이 “결재 문서를 어디에서 작성하나요?”라고 묻는다.
- **대화에서 확인:** 전자결재 시스템과 하려는 문서 작성 작업, 필요한 경우 현재 화면. 사용자가 알 수 없는 내부 구조는 요구하지 않는다.
- **기대 행동:** Inquiry가 사용법 의도를 정리하고 Knowledge가 공개 허용된 직원용 가이드를 찾는다. 안전한 안내를 제공한 뒤 문의자가 해결을 확인하면 티켓 없이 종료할 수 있다.
- **경계:** 관련 자료가 없거나 검색이 실패하면 둘을 구분하고 미확인 정보를 보존한다. 담당자 처리 기록이 없는 대화만으로 Curator 사례를 자동 생성하지 않는다.

### 3.2 전자결재 문서가 보이지 않음: 추가 질문과 조사

- **상황:** “전자결재에서 결재 문서가 안 보여요.”
- **대화에서 확인:** 어떤 화면과 문서를 기대했는지, 실제로 보이는 내용·시점·조회 조건 등. 사용자가 모르는 항목은 미확인으로 남긴다.
- **기대 행동:** Inquiry와 Knowledge가 허용된 관계·문서를 사용해 조회 조건이나 접근 권한 등 **가능한 확인 항목**을 제시한다. 질문은 문제당 최대 5회 묶음이며 이미 확인한 내용을 반복하지 않는다.
- **담당 연결:** 다른 책임 시스템을 뒷받침할 근거가 부족하면 전자결재 주담당자가 최초 조사한다. 담당자에게 확인 사실·미확인·근거와 적용 조건을 전달한다.
- **경계:** 그래프의 원인 후보나 유사 사례가 있다는 사실만으로 실제 원인을 확정하지 않는다. 검색 오류를 0건이나 시스템 정상으로 표시하지 않는다.

### 3.3 전자결재에서 로그인 반복: 보고·책임 시스템 구분

- **상황:** “전자결재 화면에서 로그인을 했는데 다시 로그인하라고 나와요.”
- **보고 시스템:** 문의자가 확인한 전자결재를 원 맥락으로 보존한다.
- **기대 행동:** Inquiry가 어떤 단계에서 반복되는지 묻고 Knowledge가 허용된 관계·자료를 조회할 수 있다. 대화와 근거가 공통 로그인 시스템의 처리를 충분히 뒷받침하는 가상 조건이라면 Ticket이 그 시스템을 후보로 제안한다.
- **서버 확정:** Spring이 지원 시스템·현재 주담당자·문의 버전을 검증해 공통 로그인 주담당자에게 배정한다. 보고 시스템은 전자결재로 남는다.
- **비교 경계:** 로그인 시스템과 전자결재가 연결되어 있다는 관계만 있고 현재 문제를 뒷받침할 근거가 부족하다면 전자결재 주담당자가 먼저 조사한다. 서버·Mock 조회 결과를 실제 운영 관측이라 부르지 않는다.

### 3.4 기능 요청: 구현 완료와 사용자 확인

- **상황:** “결재 문서를 하나씩 다운로드해서 불편해요. 한 번에 내려받을 수 있으면 좋겠어요.”
- **대화에서 확인:** 현재 방식, 불편한 점, 원하는 변경과 대상 기능. 구체 수용 조건이 확인되지 않았다면 AI 제안과 확정 요구사항을 구분한다.
- **기대 행동:** 변경 요청을 표준화해 책임 시스템의 주담당자에게 배정하고, 담당자가 실제 구현·검증한 경우 구현 완료를 기록한다.
- **확인:** 문의자가 해결을 확인한 뒤 최종 완료한다. 미해결 응답이면 같은 티켓에서 처리하고 무응답이면 확인 대기를 유지한다.
- **경계:** 티켓 접수는 구현 승인이나 구현 완료를 뜻하지 않는다. 기능 요청의 별도 검토·보류·반려 절차는 이번 범위에 넣지 않는다.

### 3.5 복합 문의와 일부 저장 결과 미확인

- **상황:** “문서가 안 열리고, 여러 문서를 한 번에 내려받는 기능도 있으면 좋겠어요.”
- **문제 분리:** 문서 열람 조사와 기능 추가는 완료 조건이 독립적이므로 서로 다른 문제·티켓으로 관리한다.
- **가상 장애 조건:** 한 문제는 티켓 저장이 확인되고 다른 문제는 요청 응답이 유실되어 저장 결과를 아직 확인하지 못한다.
- **기대 행동:** 성공한 티켓을 유지하고 다른 문제는 결과 미확인으로 표시한다. Spring이 같은 업무 작업의 기존 저장 결과와 현재 문의 버전을 확인한다.
- **재시도:** 이미 저장됐다면 기존 티켓을 반환한다. 조회가 불가능하면 신규 생성을 기다린다. 실제 미생성이 확인된 경우에만 동일 업무 작업의 제안을 재사용하거나 다시 만들어 재시도한다.
- **경계:** 한 문제의 여러 원인 후보는 독립 요청이 아니다. 실패한 문제를 이유로 성공 티켓을 제거하거나 전체 성공으로 표시하지 않는다.

### 3.6 사례 초안·반영 실패와 다음 문의

- **상황:** 담당자의 해결 기록이 저장되고 Curator가 사례 초안을 제안한다. 기능 요청이라면 실제 구현·검증 완료 기록도 있다.
- **확인·승인:** 문의자가 해결을 확인한 후 해당 시스템 담당자가 원문·조치·검증·적용 버전·공개 범위를 확인하고 승인한다.
- **가상 부분 실패:** 같은 승인 사례 버전의 Vector 반영은 성공했으나 Neo4j 반영이 실패하거나 상태 미확인이다.
- **기대 행동:** 어느 검색 경로에서도 해당 승인 버전을 공개하지 않는다. 업무 기록·승인과 성공한 반영은 유지한다. 원인 수정 후 실패 반영을 재실행하고 양쪽 성공을 확인한다.
- **다음 문의:** 접근 권한이 허용된 담당자가 유사 사례를 찾을 때 적용 시스템·버전·조건을 확인한다. 시스템 적용 버전을 모르면 미확인으로 표시한다.
- **출처:** 초기 합성 사례라면 가상 문의자가 확인했다는 설정을 기록한다. 시연 중 실제 HOPS 흐름에서 받은 확인과 실제 기업의 운영 이력은 각각 구분한다.

## 4. 데이터 작성과 평가 시 확인할 범위

| 항목 | 최소 기록 의미 | 아직 정하지 않은 내용 |
|---|---|---|
| 문의·응답 | 최초 문의, 문제별 사용자 응답과 확인된 사실 | 실제 사건 ID·가상 인물·응답 대본 |
| 분류 | 문의 의도·내부 처리 유형·보고/책임 시스템 | 최종 라벨 포맷·경계 사건의 검토자 |
| 질문 | 필요한 정보·허용 질문·이미 확인한 정보 | 질문 평가의 상세 채점과 자동/사람 검토 분담 |
| 근거 | 권한이 허용된 문서·사례·관계와 적용 조건 | 실제 문서/사례 ID·검색 범위·동결 버전 |
| 기대 행동 | 안내·추가 질문·담당자 연결·확인·비공개 등 | 서버·에이전트별 관찰 결과 형식 |
| 테스트 정답 | 평가자가 별도로 확인할 기대 결과와 숨겨진 정보 | 분할 수·목표·보관/접근 방식 |

같은 사건의 표현 변형은 같은 분할에 두고, 평가 사건의 정답 매핑·미래 해결 내용을 모델 검색 자료나 프롬프트 예시에 넣지 않는다. 기존에 승인된 관련 사례는 검색 대상이 될 수 있다. Vector 단독과 관계 보강, 원문과 표준화 비교는 같은 자료·권한·모델 조건으로 실시하고 검색 결과와 답변 품질을 따로 측정한다.

## 5. 검증 시나리오와 실제 완료 구분

- 예시 문의에 대한 기대 행동을 문서로 적었다고 실제 모델·검색·티켓 생성이 완료된 것은 아니다.
- Mock 시나리오는 상태·오류·권한 경계를 재현하기 위한 가상 자료이며 실제 기업의 장애 분포나 처리 시간을 나타내지 않는다.
- 실제 HOPS에서 최소 한 건은 담당자 처리 → 문의자 해결 확인 → 담당자 승인 → 동일 버전 양쪽 반영 → 다음 문의 검색까지 연결해 검증한다.
- 실제 평가 사건 수·개발/테스트 분할·점수 목표·시연 ID·검토자는 데이터 준비 후 결정한다. 시나리오 후보 목록은 확정된 평가셋이 아니다.
