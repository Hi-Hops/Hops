# 사내 포털 API 500 오류 진단 및 대응

## 적용 범위와 사용자 증상

- 서비스/컴포넌트: PORTAL / PORTAL_API
- 기본 담당: BACKEND
- 적용 환경: DEMO_PORTAL
- 제품: Spring Boot 4.1.1, Java 21, PostgreSQL 18
- 문서 상태/인덱싱: DRAFT / PENDING

## 적용 가정

- Demo Portal API가 모든 응답에 X-Request-Id를 부여하고 같은 식별자를 구조화 로그에 기록한다.
- X-Request-Id와 요청 ID를 포함한 구조화 로그는 서버가 권한을 검사한 읽기 전용 경로로만 조회한다.
- HTTP 요청 메트릭은 선택 관측값이며 없어도 구조화 로그로 기본 진단을 계속한다.
- 구체적인 MCP Tool ID는 아직 확정되지 않았으므로 모든 tool_query는 null이며 Agent가 임의 명령을 실행할 수 없다.
- 로그와 메트릭은 사용자 ID, 토큰, 요청 본문, 쿼리 문자열 등 민감값을 제거한 뒤 Agent에 제공한다.

## 범위 밖

- HikariCP 커넥션 풀 고갈 또는 DB 연결 한도 초과가 확인된 장애
- PostgreSQL lock, deadlock 또는 slow query가 주원인인 장애
- 브라우저 렌더링이나 정적 리소스만 실패하고 API 500 응답이 없는 장애
- 운영 서버에서 Agent가 설정 변경, 재시작, 배포 또는 데이터 수정을 직접 수행하는 작업

## 사용자 증상

### SYM-01

사용자 표현:
- 사내 LMS에서 강의 목록을 누르면 오류가 나요.
- 포털 화면에 서버 오류가 표시돼요.

관측 신호:
- 동일 시간대의 PORTAL API 응답 상태가 HTTP 500이다.
- 오류 응답 또는 응답 헤더에서 X-Request-Id를 확인할 수 있다.

### SYM-02

사용자 표현:
- 다른 강의는 열리는데 특정 강의만 열리지 않아요.
- 같은 메뉴에서 반복해서 오류가 발생해요.

관측 신호:
- 특정 API 경로나 비식별화된 데이터 조건에서 HTTP 500이 반복된다.
- 서로 다른 X-Request-Id의 로그에서 동일한 예외 클래스와 스택 지문이 반복된다.

## 진단 1: 요청·로그 연결

### DIA-01 · 사용자 문의와 실패 요청을 하나의 추적 단위로 연결한다.

- 조치: 사용자에게 발생 시각, 화면 또는 메뉴, 안전한 오류 문구, X-Request-Id를 확인한다. 요청 본문, 계정 정보, 토큰은 수집하지 않는다.
- 도구: 미등록 — 실행 불가
- 기대 신호:
- 발생 시각과 API 경로에 대응하는 HTTP 500 요청이 존재한다.
- X-Request-Id가 응답과 서버 로그에서 동일하게 확인된다.
- 일치 시: DIA-02로 이동해 해당 요청의 애플리케이션 예외를 확인한다.
- 불일치 시: 요청 식별 정보가 없으면 재현 가능한 메뉴와 시각을 한 번 더 확인하고, 여전히 연결할 수 없으면 근거 부족으로 이관한다.
- 근거: PE-001, PE-003

### DIA-02 · HTTP 500과 애플리케이션 예외를 같은 요청 ID로 연결한다.

- 조치: 마스킹된 구조화 로그에서 X-Request-Id로 조회하고 예외 클래스, 첫 애플리케이션 스택 위치, 스택 지문을 확인한다. 전체 스택과 원시 로그는 Agent 또는 사용자 응답에 노출하지 않는다.
- 도구: 미등록 — 실행 불가
- 기대 신호:
- HTTP 500 요청과 같은 X-Request-Id를 가진 ERROR 로그가 존재한다.
- 예외 클래스와 스택 지문이 확인된다.
- 일치 시: DIA-03으로 이동해 발생 범위와 반복성을 확인한다.
- 불일치 시: 애플리케이션 예외가 없으면 500을 만든 프록시·DB·의존 서비스 신호를 확인하고 이 런북만으로 원인을 확정하지 않는다.
- 근거: PE-002, PE-003, PE-021

### DIA-03 · 강의 목록 전체 오류인지 특정 강의 데이터 오류인지 구분한다.

- 조치: 권한이 적용된 구조화 로그에서 같은 시간 구간의 API 경로 템플릿, status=500, 예외 클래스와 비식별화된 재현 조건을 비교한다. HTTP 요청 메트릭을 사용할 수 있으면 발생 범위를 보조 확인하되, 원본 URL의 식별값이나 쿼리 문자열은 조회하지 않는다.
- 도구: 미등록 — 실행 불가
- 기대 신호:
- 여러 강의·사용자 조건에서 같은 강의 목록 경로와 예외가 반복되거나, 특정 강의 조건에서만 같은 예외가 반복된다.
- 선택 메트릭이 있으면 같은 시간대 500 발생 범위가 구조화 로그의 판단과 일치한다.
- 일치 시: DIA-04에서 DB 계층의 별도 장애 신호가 있는지 확인한다.
- 불일치 시: 메트릭만 없으면 구조화 로그로 계속한다. 로그에서도 반복 범위를 확인할 수 없으면 단발성 오류로 기록하고, 재현되지 않을 경우 확정 원인 없이 이관한다.
- 근거: PE-004A, PE-004B, PE-004C, PE-004D, PE-005, PE-007

## 진단 2: 계층 구분과 근거 충분성

### DIA-04 · 같은 500 증상을 DB 계층 장애와 구분한다.

- 조치: 같은 시간대에 커넥션 획득 timeout, DB 연결 한도, lock·deadlock, slow query 신호가 있는지 승인된 진단 근거만 확인한다. DB 원문 SQL과 바인딩 값은 보지 않는다.
- 도구: 미등록 — 실행 불가
- 기대 신호:
- DB 또는 커넥션 풀 장애를 나타내는 별도 오류 신호가 없다.
- 500 응답이 애플리케이션 예외와 직접 연결된다.
- 일치 시: BACKEND 소유의 애플리케이션 예외 후보로 판단하고 DIA-05로 이동한다.
- 불일치 시: DB 또는 HikariCP 신호가 있으면 이 런북에서 원인을 확정하지 않고 해당 런북으로 전환한 뒤 담당 부서를 재판정한다.
- 근거: PE-005, PE-021

### DIA-05 · 복구 작업 전에 근거 충분성과 담당 부서를 확정한다.

- 조치: HTTP 500, 요청 ID, 애플리케이션 예외, 반복 범위, DB 반대 신호를 함께 요약한다. 필수 신호가 하나라도 없으면 확정 원인이 아닌 원인 후보로만 기록한다.
- 도구: 미등록 — 실행 불가
- 기대 신호:
- 서로 독립적인 응답·로그·메트릭 근거가 같은 애플리케이션 오류를 지지한다.
- 담당 부서를 BACKEND로 판단할 근거와 불확실성이 함께 정리된다.
- 일치 시: 사람 담당자가 원인 코드 확인과 수정 절차를 수행하도록 티켓 초안을 만든다.
- 불일치 시: 추가 추론으로 빈칸을 채우지 않고 근거 부족 상태와 수집 실패 항목을 명시해 BACKEND에 이관한다.
- 근거: PE-001, PE-003, PE-005

## 원인 후보와 반대 신호

### CAUSE-01 · 강의 목록 API의 공통 처리 경로에서 예외가 발생해 여러 강의 또는 사용자 조건에서 목록 조회가 실패한다.

- 필요 신호 ID: SIG-001, SIG-002, SIG-003, SIG-053
- 필요 신호:
- HTTP 500과 같은 X-Request-Id의 ERROR 로그
- 애플리케이션 코드 위치를 포함한 예외 클래스와 스택 지문
- 둘 이상의 강의 또는 사용자 조건에서 같은 강의 목록 경로와 스택 지문이 반복됨
- 반대 신호 ID: SIG-004, SIG-011, SIG-015, SIG-017
- 반대 신호:
- 특정 강의 한 건에서만 같은 오류가 재현됨
- 애플리케이션 예외 없이 프록시 또는 의존 서비스가 500을 생성함
- 커넥션 풀 timeout, DB 연결 한도, lock·deadlock 신호가 주된 오류와 일치함
- 담당 부서: BACKEND
- 근거: PE-001, PE-003, PE-005

#### 레지스트리에서 결합된 신호 정의

- SIG-001 [필요] · HTTP 500 (HTTP_STATUS)
  - 매칭: 500
  - 의미: 서버 내부 처리 실패
  - 확정 제한: 단독으로 API·DB 원인을 확정하지 않음
- SIG-002 [필요] · X-Request-Id (CORRELATION_ID)
  - 매칭: X-Request-Id
  - 의미: 응답과 로그의 동일 요청 연결
  - 확정 제한: 오류 원인이 아니라 추적 식별자
- SIG-003 [필요] · 애플리케이션 예외 지문 (LOG_FIELD)
  - 매칭: exception_class+stack_fingerprint
  - 의미: 반복되는 코드 예외 경로를 구분
  - 확정 제한: 같은 지문은 같은 예외 경로의 반복을 뜻할 뿐 근본 원인을 확정하지 않으며 전체 스택 원문은 사용자에게 노출하지 않음
- SIG-053 [필요] · 여러 입력 조건의 동일 API 예외 반복 (IMPACT_SCOPE)
  - 매칭: same_stack_fingerprint_across_multiple_inputs
  - 의미: 둘 이상의 비식별화된 사용자·데이터 조건에서 같은 API 경로와 예외 지문이 반복됨
  - 확정 제한: 요청 ID로 각각의 응답과 로그를 연결하고 DB·의존 서비스 공통 장애를 별도 배제
- SIG-004 [반대] · Hikari 연결 획득 timeout (LOG_PATTERN)
  - 매칭: Connection is not available|connectionTimeout
  - 의미: 풀에서 제한시간 안에 연결을 얻지 못함
  - 확정 제한: DB 서버 한도와 풀 자체 포화를 추가 확인
- SIG-011 [반대] · 예약 연결 슬롯 오류 (LOG_PATTERN)
  - 매칭: remaining connection slots are reserved
  - 의미: 일반 연결 슬롯이 소진됨
  - 확정 제한: 연결 점유 주체는 별도 확인
- SIG-015 [반대] · Lock wait (DB_WAIT)
  - 매칭: wait_event_type=Lock
  - 의미: 잠금 해제를 기다리는 세션
  - 확정 제한: blocker·waiter 관계 확인 필요
- SIG-017 [반대] · deadlock detected (DB_ERROR)
  - 매칭: deadlock detected
  - 의미: PostgreSQL이 순환 대기를 감지하고 트랜잭션 하나를 중단함
  - 확정 제한: 재시도 안전성과 잠금 순서를 별도 확인

## Agent 사용자 안내와 처리 경계

### GUID-01 · Agent 안내

- 조건: HTTP 500과 X-Request-Id가 확인되었지만 아직 서버 측 원인이 해결되지 않은 경우
- 안내: 사용자에게 같은 동작을 한 번만 다시 시도하도록 안내하고, 다시 실패하면 새 X-Request-Id와 발생 시각을 알려 달라고 요청한다. 반복 재시도를 해결책처럼 안내하지 않는다.
- 예상 결과: 일시 오류였다면 정상 화면이 열리고, 계속 실패하면 비교 가능한 두 번째 요청 근거를 확보한다.
- 미해결 시: 기존·신규 요청 근거를 첨부하여 BACKEND로 이관한다.
- 근거: PE-001, PE-003

### GUID-02 · Agent 안내

- 조건: 특정 강의에서만 오류가 나고 다른 강의는 정상임이 확인된 경우
- 안내: 사용자에게 해당 강의에서만 서버 오류가 확인되었으며 담당 부서 점검이 필요하다고 안내한다. 내부 예외·데이터 값·스택 트레이스는 전달하지 않는다.
- 예상 결과: 사용자는 장애 범위와 이관 상태를 이해하고, 사용 가능한 다른 강의 기능은 계속 이용할 수 있다.
- 미해결 시: 특정 강의 조건과 마스킹된 요청 근거를 첨부하여 BACKEND로 이관한다.
- 근거: PE-001, PE-003, PE-005

### Agent 처리 경계

- 허용 결과: GUIDE_USER, HANDOFF
- 이관 사유: INSUFFICIENT_EVIDENCE, GUIDANCE_NOT_RESOLVED
- 금지 작업: CODE_CHANGE, CONFIG_CHANGE, DEPLOY, RESTART, DB_WRITE
- 해결 확정 근거: USER_CONFIRMATION, BACKEND_STATE

## 이관 후 IT 담당자 조치·검증

### RES-01 · 사람 수행

- 조치: Demo Portal의 격리된 개발 환경에서 민감값을 제거한 동일 입력 조건으로 오류를 재현하고, 새 X-Request-Id와 기존 예외의 스택 지문이 일치하는지 확인한다.
- 승인 필요: 아니오
- 확인: 재현 요청이 HTTP 500을 반환하고 동일한 예외 클래스와 스택 지문을 남긴다.
- 롤백: 해당 없음
- 근거: PE-001, PE-003

### RES-02 · 사람 수행

- 조치: 확정된 예외 발생 지점의 입력 검증 또는 예외 처리 코드를 수정하고 자동 테스트와 코드 리뷰를 통과시킨다. 원인이 확정되지 않았다면 임의 수정하지 않는다.
- 승인 필요: 예
- 확인: 원인 조건을 포함한 테스트가 수정 전 실패하고 수정 후 통과하며, 정상 조건의 회귀 테스트도 통과한다.
- 롤백: 배포 후 같은 예외 또는 새로운 오류가 증가하면 승인된 이전 이미지로 되돌리고 티켓을 재개한다.
- 근거: PE-001

### RES-03 · 사람 수행

- 조치: 승인된 변경을 Demo Portal에 배포한 뒤 같은 사용자 동작과 API 요청을 다시 수행하고 응답·로그·메트릭을 확인한다.
- 승인 필요: 예
- 확인: 같은 조건이 정상 응답하고 동일 예외가 재발하지 않으며 해당 URI 템플릿의 500 증가가 멈춘다.
- 롤백: 성공 기준을 충족하지 못하면 변경을 되돌리고 수집한 근거를 유지한 채 미해결로 처리한다.
- 근거: PE-003, PE-005

### 완료 판정

성공 신호:
- 동일 사용자 동작의 API 응답이 기대한 2xx 상태다.
- 같은 비식별화 데이터 조건에서 기존 예외 클래스와 스택 지문이 재발하지 않는다.
- 검증 구간에 해당 URI 템플릿의 HTTP 500 증가가 관측되지 않는다.

실패 신호:
- 동일 조건에서 HTTP 500이 계속 발생한다.
- 기존 예외가 유지되거나 새로운 예외·회귀가 발생한다.
- DB 또는 커넥션 풀 장애 신호가 새로 확인되어 원인과 담당 부서를 다시 판단해야 한다.

### 이관

- 대상: BACKEND
- 조건:
- X-Request-Id로 응답과 로그를 연결할 수 없다.
- HTTP 500은 확인되지만 애플리케이션 예외 또는 재현 조건이 없어 원인을 확정할 수 없다.
- 수정·배포 후에도 같은 오류가 지속되거나 회귀가 발생한다.
- 첨부 근거:
- 발생 시각, 서비스·API 경로 템플릿, HTTP 상태
- X-Request-Id와 마스킹된 예외 클래스·스택 지문
- 같은 시간대의 URI별 500 집계와 재현 여부
- 확인한 DB 반대 신호와 아직 수집하지 못한 정보

## 안전한 사용자 안내

사내 포털 요청 처리 중 오류를 확인하여 담당 부서에서 점검 중입니다. 요청 추적 번호는 {request_id}입니다. 해결 여부가 확인되면 안내드리겠습니다.
