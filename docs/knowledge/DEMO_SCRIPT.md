# HOPS 브라우저 시연 대본

상태: 시연 준비안 · 실제 리허설 결과와는 별도다. 이 문서는 가상 회사의 직원 문의가 상담·담당자 처리·사례 승인으로 이어지는 순서다. 실제 모델의 질문과 소요 시간은 달라질 수 있다. 결과가 다르면 성공한 것처럼 진행하지 않고 관찰 결과를 기록한다. 제품 정책은 [PRD](../PRD.md), 가상 회사와 시연 데이터는 [가상 회사 명세](VIRTUAL_COMPANY.md), 배포 준비는 [EC2 안내](../../deploy/ec2/README.md)를 따른다.

## 시연 전 준비

- 브라우저가 시연 환경의 live API에 연결되는지 확인한다. 배포 버전, 모델·프롬프트, 검색 데이터 버전과 판정 설정을 별도 실행 기록에 남긴다. 비밀번호·토큰·문의 원문 로그는 기록에 넣지 않는다.
- Spring·AI·PostgreSQL/pgvector·Neo4j가 준비됐는지 확인한다. AI `/healthz`는 생존 확인이고 `/readyz`는 실제 실행 준비 확인이다. Spring의 검색·관계 조회까지 실제로 성공하는지는 별도 확인한다([배포 점검](../../deploy/ec2/README.md#p0-검색을-배포하는-환경)).
- 시연할 전자결재 공개 가이드, 직원 공개 확인 질문과 담당자 연결이 현재 승인·공개 상태인지 확인한다. 가상 문의·처리 기록만 사용한다.
- 계정은 가상 데이터의 `requester1`(문의 A·해결 확인), `requester2`(B), `requester3`(C), `ea_owner`(전자결재 주담당자)를 사용한다. 공용 비밀번호는 환경 담당자로부터 안전하게 전달받고 이 문서나 발표 화면에 표시하지 않는다. 한 브라우저에서 전환할 때 로그아웃 후 해당 계정으로 로그인한다.
- A는 **새 문의와 새 사례**로 진행한다. 기존 승인 사례는 남겨 두며, 어떤 문의·티켓·사례가 이번 리허설에서 만들어졌는지 실행 기록에 구분한다. 데이터 초기화나 공유 DB 시드 재적재를 시연 준비의 기본 단계로 삼지 않는다.
- 예상 시간은 **20~30분 계획값**이며 측정치가 아니다. 모델 대기·계정 전환·사례 검토에 따라 달라진다. 각 단계의 실제 시간을 리허설에서 측정한다.

| 순서 | 담당자 | 준비할 가상 입력 |
|---|---|---|
| 1. 사용법 | `requester1` | 전자결재에서 지난 문서를 찾는 방법 |
| 2. 현상 A | `requester1` | 지난주 상신한 문서가 보이지 않음. 상태 `승인`, 제목 키워드 없음 |
| 3. 처리·승인 | `ea_owner` → `requester1` → `ea_owner` | 상태 `전체`로 조회한 조치와 가상의 검증 결과 |
| 4. 후속 문의 | `requester2`, `requester3`, `ea_owner` | 다른 표현 B와 다른 조건 C |

## 1. 사용법 문의

1. `requester1`로 로그인하고 **새 문의**에서 `전자결재에서 지난 문서는 어떻게 찾아요?`를 보낸다.
2. 화면에 후속 질문이 나오면 해당 질문에만 답한다. 문서 조회 방법을 알고 싶다는 목적과 전자결재 문서함이라는 맥락을 제공한다.
3. 승인된 직원용 가이드의 기간·상태·제목 키워드 조회 절차와 출처를 확인한다. 안내 뒤 해결 확인이 표시되면 **해결됨**을 선택한다.
4. 기대: 안내가 질문과 관련돼 있고 사용법 해결에 티켓을 만들지 않는다. 가이드가 없거나 검색 오류가 나면 그대로 기록하고 다음 단계의 성공으로 대체하지 않는다.

## 2. 증상 A와 티켓 생성

1. 같은 직원 계정으로 **새 문의**를 열고 `지난주 상신한 문서가 문서함에 안 보여요`를 보낸다.
2. 실제로 질문받은 내용에 맞춰 아래 가상 조건을 답한다. 질문되지 않은 사실을 한꺼번에 먼저 알려주지 않는다.
   - 시스템·화면: `전자결재 문서함의 전체 문서 목록이에요.`
   - 기대·실제 동작: `상신한 문서가 목록에 나와야 하는데 안 보여요.`
   - 상태·키워드: `상태를 '승인'으로 골랐고 제목 키워드는 넣지 않았어요.`
   - 기간: `조회 기간은 기본값 그대로예요.`
   - 기안·상신: `제가 지난주에 기안했고 임시 저장이 아니라 상신했어요.`
3. 질문 묶음과 답을 기록한다. 상태·기간 등 이미 답한 정보를 반복해서 묻거나 여러 답을 빠뜨리면 결함으로 기록한다. AI가 조건 확인 전에 원인을 확정하지 않는지 본다.
4. 티켓 접수 결과의 책임 시스템·담당자가 전자결재·`ea_owner`인지 확인하고 티켓 번호를 기록한다. 새로고침 뒤 같은 티켓과 상태가 유지되는지 확인한다. 사례 생성 전에 티켓이 여러 개라면 문제별 결과를 확인한다.
5. 화면의 진행 표시만으로 실제 Neo4j 호출을 확정하지 않는다. 환경 담당자는 같은 실행의 Spring 관계 조회 결과와 승인 질문 키를 [배포·검색 검증 절차](../../deploy/ec2/README.md#p0-검색을-배포하는-환경)로 대조한다.

## 3. 담당자 처리와 사례 승인

1. `ea_owner`로 로그인해 **담당 시스템 업무**에서 방금 기록한 A 티켓을 열고 **요청 내역**의 확인 사실·대화·미확인 내용을 검토한다.
2. **문의 처리 기록**에서 적절한 기록 유형을 선택한다. 가상 시연이므로 아래 조치와 확인 결과는 시나리오에서 실행했다고 가정한 테스트 기록이며 실제 운영 조치로 표시하지 않는다.
   - 처리 내용: `문의자에게 문서함 조회 조건의 상태를 '전체'로 바꾸고 다시 조회하도록 안내했어요.`
   - 동작 확인 결과: `상태를 '전체'로 바꿔 다시 조회하자 문서가 목록에 표시되는 것을 문의자와 확인했어요.`
   - 확인된 원인: `조회 상태를 '승인'으로 선택해 결재 진행 중인 문서가 목록에서 제외됐어요.`
3. 검증된 해결 기록을 저장하고 **기록 저장·해결 확인 요청**을 진행한다. 상태가 문의자 해결 확인 대기인지 확인한다. 모델이 만든 사례 초안은 아직 공개되지 않는다.
4. `requester1`로 다시 로그인해 해당 문의의 해결 확인 요청을 열고 시연 조건에 맞게 **해결됨**을 선택한다. 미해결을 선택한 경우에는 같은 티켓의 후속 처리로 분기하고 승인 성공으로 간주하지 않는다.
5. `ea_owner`로 돌아와 **해결 사례 검토**에서 이 티켓으로 만든 초안을 연다. 처리 내용·확인 결과·적용 조건과 한계를 읽고 담당자 내부용인지 검토한다. 실제 기록과 다른 내용은 승인 전에 바로잡는다. 적용 조건이 맞지 않으면 이 사례를 다른 문의의 원인으로 확정하지 않는다.
6. **확인한 버전 승인**을 누른 뒤 Vector와 Neo4j 각각의 승인 버전·반영 상태와 검색 공개 여부를 확인한다. `PENDING`·실패·미확인은 승인과 구분해 기록하며 검색 공개 성공으로 설명하지 않는다. 필요 시 화면의 현재 반영 상태 확인을 사용한다.

## 4. 후속 문의 B·C와 사례 접근

1. `requester2`의 **새 문의**에 `방금 올린 서류가 조회 화면에 안 보여요`를 보낸다. 전자결재, 방금 상신, 상태 `결재 중`, 키워드 없음, 본인 기안, 조회 기간 기본값이라는 가상 조건 중 실제 질문받은 것만 답한다.
2. AI가 내놓은 질문·답변에서 담당자 전용 사례 A의 원문이나 출처가 노출되지 않는지 확인하고, 만들어진 티켓 번호를 기록한다. 검색 수행 여부는 화면 표시만이 아니라 환경 담당자가 실행 기록과 검색 결과로 확인한다. 근거가 0건이면 사례가 안전하게 제외됐다고 단정할 수 없다.
3. `requester3`으로 전환해 `동료가 보내준 전자결재 문서 링크를 열면 열람 권한이 없다고 나오고 문서함에서도 안 보여요`를 보낸다. 질문에 따라 `제가 기안하거나 결재선·참조에 포함된 문서는 아니고, 동료가 상신한 문서라고 들었어요`, `조회 조건은 전체, 기간은 기본값이에요`라고 답한다.
4. C의 질문과 티켓에서 사례 A의 원인인 상태 필터가 **확정 사실**로 옮겨가지 않았는지 확인한다. 화면과 표준 요청을 사람도 읽는다. 유사한 질문 자체가 사례 A를 사용했다는 증거는 아니다.
5. `ea_owner`로 전환해 B 티켓의 **추천 해결 사례**를 확인한다. 이번에 승인한 A가 추천되면 제목·버전·적용 조건을 비교하고, 표시되지 않으면 검색 결과 없음 또는 오류를 기록한다. 별도로 **해결 사례 검토** 목록에서 A를 직접 열 수 있으며 목록 조회와 티켓 기반 자동 추천 결과는 구분한다. 추천은 티켓 제목을 이용하며 적용 가능성은 담당자가 판단한다.

## 실패 시 확인과 기록

| 관찰 | 확인할 곳과 기록할 내용 |
|---|---|
| 로그인 실패·다른 화면 | 계정 역할, 실제 응답·시간, 브라우저 live 연결. 비밀번호는 기록하지 않는다. |
| 분석 실패·질문이 반복됨 | 문의·문제·실행 ID, 질문과 답의 연결, 질문 수, 오류와 모델·프롬프트 버전. 원문·개인정보는 공유 로그에 넣지 않는다. |
| 가이드 없음·관계 질문 없음 | 검색 정상 0건과 검색 오류를 구분하고, 같은 실행의 문서 ID·버전 및 Neo4j 관계 결과를 대조한다. 확인하지 못하면 `BLOCKED`다. |
| 티켓 미생성·새로고침 불일치 | 접수 결과와 저장된 문의·티켓 상태를 먼저 확인한다. 저장 여부가 불명확하면 같은 문의를 반복 전송하지 않는다. |
| 사례 초안·승인 지연 | 해결 기록, 문의자 확인, 사례 버전과 초안 상태를 확인한다. 승인되지 않은 초안은 검색 공개가 아니다. |
| 색인 대기·실패 | 화면의 Vector·Neo4j별 상태와 승인 버전을 기록한다. 복구는 [자동 색인 배포 안내](../../deploy/ec2/README.md#승인-사례-자동-색인을-켜는-환경-244-p1)를 따른다. |
| 직원에게 내부 사례가 보임 | 시연을 멈추고 노출 경로와 범위를 보안 담당자에게 알린다. 원문·인증 정보는 공유 기록에서 제외한다. |

리허설마다 실행한 단계와 결과를 `PASS`·`FAIL`·`BLOCKED`로 구분한다. Fake/오프라인, 실제 Spring API, 실제 브라우저·모델 결과는 각각 기록하며, P0 필수 단계에 `FAIL` 또는 `BLOCKED`가 남으면 해당 실행을 시연 준비 완료로 기록하지 않는다. 2회차에는 새 가상 문의를 만들고 기존 사례를 보존하면서 같은 조건과 남은 공백을 다시 확인한다.
