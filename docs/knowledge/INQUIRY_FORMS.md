# 문의 양식

문의 유형마다 담당자가 처리하거나 안내하는 데 필요한 정보가 다르다. 이 문서는 AI 서버가 문의 유형별로 무엇을 확보하고 어떤 순서로 묻는지, 모르거나 한도에 닿으면 어떻게 하는지를 데이터 작성자와 평가자가 같은 기준으로 읽도록 정리한 **검토 기준**이다. 제품 정책은 [PRD](../PRD.md), 필드 이름은 [공통 계약](../../specs/contracts/README.md)의 `RequestDetails`를 따르며 여기서 다시 정의하지 않는다.

현재 동작의 정본은 `ai/src/hops_ai/agents/inquiry/forms.py`다. 이 문서와 코드가 다르면 코드가 현재 동작이고, 문서를 고치거나 코드 변경을 PR로 제안한다. 팀 합의는 이 문서가 PR 리뷰를 거쳐 병합된 뒤에 성립한다.

## 역할 분담

| 구분 | 담당 | 하지 않는 것 |
|---|---|---|
| 사실 추출 | 모델이 사용자 메시지에서 값을 제안한다. 값마다 원문 인용을 붙인다. | 인용이 없거나 원문과 맞지 않는 값을 확보로 세지 않는다. |
| 질문 선택 | 코드가 확보 목록과 질문 이력을 보고 정한다. | 모델이 질문 순서·한도를 바꾸지 못한다. |
| 모름 판정 | 모델이 `필드 + 메시지 ID + 인용`으로 제안하고 코드가 원문의 모름 표현인지 대조한다. | 인용이 틀렸거나 모름 뜻이 아니면 무시하고 필수 질문을 유지한다. |

확보했다는 것은 **원문에 근거가 있다**는 뜻이다. 모델이 추정해서 채운 값은 확보로 세지 않는다.

## 의도별 필수 정보

질문은 아래 순서로 한다. 시스템이 정해지지 않았다면 항상 시스템부터 묻는다. 시스템은 `RequestDetails` 필드가 아니라 문제의 보고 시스템 후보로 확인한다.

| 의도 | 필수 필드 (묻는 순서) | 비고 |
|---|---|---|
| `HOW_TO` 사용법 | 하려는 업무·화면(`taskOrScreen`), 현재 진행 방식(`currentWorkflow`) | 아래 "상태에 따라 달라지는 요구" 참조 |
| `ACCESS_REQUEST` 권한 신청 | 필요한 기능·권한(`requestedAccess`), 업무 목적(`businessPurpose`) | |
| `OBSERVED_SYMPTOM` 현상 | 하려던 업무·화면, 기대 동작(`expectedBehavior`), 실제 동작(`actualBehavior`), 발생 시점(`occurredAt`) | |
| `FEATURE_REQUEST` 기능 추가 | 현재 진행 방식, 바라는 변경(`desiredChange`) | |
| `IMPROVEMENT_REQUEST` 개선 | 현재 진행 방식, 바라는 변경 | |
| `UNKNOWN` 의도 불명 | 하려는 업무·화면 | 의도를 모르면 무엇을 하려는지부터 확인 |
| `OUT_OF_SCOPE` 범위 밖 | 없음 | 질문하지 않고 범위를 안내 |

계약에 없는 정보(사용자 역할, 발생 빈도, 영향 받는 사용자 수 등)는 지금 묻지 않는다. 필드를 늘리는 것은 공통 계약 변경이므로 팀 합의가 먼저다.

## 상태에 따라 달라지는 요구

같은 의도라도 승인된 가이드를 먼저 찾을 수 있는지에 따라 필수 정보가 달라진다. 이것이 이 양식의 "조건부 필드"다.

| 상태 | 사용법(`HOW_TO`)에 요구하는 정보 | 이유 |
|---|---|---|
| 가이드를 먼저 찾을 수 있음 (Knowledge 연결) | 시스템 + 하려는 업무·화면 | 사용법은 이 둘만 알면 검색을 시작할 수 있다. |
| 가이드를 찾지 못해 담당자에게 넘길 준비 중 | 시스템 + 하려는 업무·화면 + 원하는 결과(`expectedBehavior`) | 담당자가 요청을 이해하려면 최종 목적이 필요하다. 이때 원하는 결과 질문은 사용법에 맞는 문구를 쓴다. |

다른 의도는 이 상태 구분이 없고 위 표의 필수 필드를 그대로 쓴다.

## 모름과 한도

| 상황 | 동작 |
|---|---|
| 사용자가 어떤 필드를 모른다고 답함 | 그 필드는 **미확인**으로 두고 다시 묻지 않는다. 미확인으로 담당자에게 보존한다. |
| 이미 한 번 물은 필드 | 답을 못 얻었어도 같은 필드를 다시 묻지 않는다. |
| 한 질문에 묶는 필드 | 최대 3개. 시스템을 물어야 하면 맨 앞에 둔다. |
| 문제당 질문 횟수 | 최대 5회. 한도에 닿으면 더 묻지 않고 미확인을 보존해 담당자에게 넘긴다. |
| 시스템을 모른다고 답함 | 임의 담당자에게 배정하지 않고 시스템 확인 대기로 넘긴다. |
| 모든 필수 정보를 확보함 | 질문을 끝내고 안내 또는 티켓 제안으로 넘어간다. |

질문 결과는 네 가지 중 하나다. `ASK`(질문), `COMPLETE`(필요 정보 확보), `HANDOFF`(더 물을 수 없어 미확인과 함께 전달), `OUT_OF_SCOPE`(범위 밖).

## 복합 문의

한 문의에 독립된 문제가 여럿이면 문제별로 분리해서 위 규칙을 각각 적용한다. 질문 횟수와 확보 정보는 문제마다 따로 센다. 한 문제의 요약에 다른 문제의 내용이 섞이지 않아야 하고, 검색은 그 문제 자신의 정보로만 한다.

## 데이터 작성자가 지킬 것

- 기준 대화(시나리오)의 사용자 답변은 **질문한 필드에 해당하는 정보만** 담는다. 묻지 않은 정보를 먼저 주면 질문 선택 규칙을 시험할 수 없다.
- 사용자가 모르는 필드는 "모른다"는 표현을 원문에 둔다. 평가자가 `unknown` 보존을 확인할 근거가 된다.
- 의도 라벨과 내부 처리 유형(`KNOWLEDGE_QA`, `REVIEW_REQUIRED` 등)은 따로 검수한다. 사용법 문의가 가이드가 없어 담당자 검토로 넘어가는 경우 의도는 `HOW_TO`, 처리 유형은 `REVIEW_REQUIRED`일 수 있다.
- 표의 필드가 바뀌면 시나리오의 기대 질문 순서가 바뀐다. 이 문서의 변경은 시나리오 정답 변경과 함께 리뷰한다.
