# 데이터 설계 — PRD 전체 흐름

기준: [PRD](PRD.md) v1.42 · 2026-10-25, [API 설계](API.md), [ERD 설명](ERD_설명.md). 이 문서는 제품 전체의 논리 데이터 관계와 저장 불변식을 정리한 **팀 리뷰용 설계안**이다. ERD는 PRD v1.38 시점의 물리 컬럼 후보에 v1.41의 사번·JWT 관련 설명을 반영한 자료다. 이관 후 대화, 새 문의 동의, 부분 실패 저장까지 적용한 DDL로 간주하지 않는다. 아래의 `MVP`는 PRD 8.2, `후속`은 8.3의 필수 범위다. 상태/오류·논리 관계·버전·멱등 정책은 공통 계약의 개발 기준을 적용한다. 실제 컬럼·인덱스·마이그레이션의 구현·검증은 백엔드 담당이다.

## 1. 소유권과 공통 규칙

- PostgreSQL 업무 데이터는 Spring이 저장·확정한다. Spring은 React의 REST 변경 요청과 권한별 SSE 이벤트 전달도 담당한다. Python의 분석, 검색, 도구 결과는 제안 및 근거이며 권한·상태·부서 배정의 원본이 아니다. 모델의 임시 참조를 DB 기본키로 사용하지 않는다.
- 식별자는 서버 발급 UUID, 시각은 `timestamptz`, 이력은 추가 기록을 기본으로 제안한다. FK 삭제 연쇄로 문의·티켓·감사 이력을 지우지 않는다. 기존 물리 ERD의 `uuidv7()`와 자료형은 후보이며 실제 DB 확장·생성 방식은 마이그레이션에서 확인한다.
- 한 대화 세션은 문의 하나다. 대화 세션·JWT 인증 수명·SSE 연결 수명을 구분하며 재접속 시 기존 문의를 새로 생성하지 않는다. 문의에는 문제 여러 개, 문제에는 처리 작업·티켓 여러 개가 연결될 수 있다. 같은 장애 그룹 안에서도 사용자별 티켓과 해결/재오픈 이력을 독립 보존한다.
- 문의·문제·티켓 처리 상태·티켓 배정 상태·AI 실행 상태·복구 상태를 별도로 저장한다. 실행 성공이나 UI 이벤트만으로 티켓 생성/해결을 표시하지 않는다.
- 모든 조회는 서버에서 문의 소유자, 현재 처리 부서, 업무 관리자, 운영 관리자 권한을 구분한다. 티켓 상세가 보는 대화는 관련 문제 범위로 연결하고 다른 문제의 원문을 노출하지 않는다. 운영 로그 권한만으로 업무 변경 권한을 부여하지 않는다.

## 2. 핵심 엔터티와 관계

| 단계 | 엔터티와 관계 | 보존할 정보·검증 |
|---|---|---|
| MVP | `department`, `member`, `member_role` | JWT 자체 로그인, 사번(`employee_no` 후보·문자열·고유), 소속 부서, 복수 역할, 활성 여부. 회원 UUID와 사번·로그인 ID를 구분. 초기 IT 처리 부서는 계정 권한, 네트워크, CS, DB, backend, frontend, 인프라, 시스템의 8개. 요청자 소속과 티켓 처리 부서를 구분하고 문의 유형 6개와 부서를 일대일 매핑하지 않음. 비밀번호 해시만 저장 |
| MVP | `inquiry`, `message`, `message_revision`, `inquiry_problem` | 한 문의의 대화·최신 버전·원본과 정정 이력, 문제별 분류/추가 질문 횟수. 1~4,000자 사용자 입력, 문제당 최대 3회 질문. 문의 버전 초기 1, 추가·정정 시 원자적으로 증가, 미반영 옛 실행 결과 차단, 기존 티켓 유지 |
| MVP | 생성 작업(`ticket_work_item` 후보), `ticket`, `ticket_assignment` | 문제별 작업 ID·범위·제안·버전·재시도·오류를 티켓 생성 전부터 보존. 티켓 하나와 최초 부서 배정 이력은 함께 확정. 문제 1:N 작업, 작업당 티켓 최대 1개. 작업 ID의 성공 결과는 하나만 허용. 실패 작업과 성공 티켓 동시 존재 허용 |
| MVP | `agent_run`, 단계 기록 후보 | 실행 입력 버전, 모델/프롬프트/스키마 버전, 제안과 Spring 검증 결과, 오류·시간·추적 ID. 실행 성공과 작업별 저장 성공을 분리. 단계 근거 요약은 기록하되 내부 사고 과정·비밀값 제외 |
| 후속 | `ticket_event`, `handoff_request`, 후속 `ticket_assignment` | 담당자 가져오기/반환, AI 내용 정정 전후·주체·사유, 처리 완료·사용자 해결 확인, 재이관 제외 이력, 관리자 수동 배정. 현재 부서와 배정 이력의 종료 시각을 일치시킴 |
| 후속 | `incident_group`, `incident_group_event`, `incident_group_rejoin`, `ticket_embedding` | 동일 부서·미완료·공통 해결 근거를 검증한 그룹. 대표·구성 티켓, 일괄 완료의 티켓별 결과, 분리·재오픈 이력, 관리자 재결합 승인. 벡터 유사성은 후보 검색에만 사용 |
| 후속 | `notification`, `recovery_case`, `agent_step` | 해결 확인 알림의 실제 저장 시각, 기존 작업·배정·재이관 기술 복구의 원본/시도 이력, 단계별 공개 가능한 근거와 실패. 기술 복구와 업무 판단을 분리 |
| 후속 | `knowledge_document`, `knowledge_document_version`, `knowledge_chunk`; 서비스·의존 관계 저장 방식은 미정 | 문서 출처·접근 범위·검수·버전·데이터 분할. PRD의 가상 서비스와 의존 관계는 GraphRAG에 필요하지만 최신 ERD에서 `service`, `service_dependency` 테이블이 제외되어 저장 방식을 합의해야 함. 승인된 접근 가능 자료만 검색하고 평가 사건은 검색 지식·프롬프트 예시와 분리 |

물리명과 FK 후보는 [ERD 설명](ERD_설명.md)을 참조한다. 최신 ERD에는 첫 E2E의 생성 작업·멱등성·메시지 관련성·새 문의 동의 및 서비스 의존 관계 저장 방식이 없다. 이 불변식을 충족할 물리 모델을 구현 전에 합의해야 한다. 과거 MVP ERD에서 사용한 `departments/users/inquiries/messages/problems/ai_runs/ticket_work_items/tickets` 명명은 현재 ERD의 `department/member/inquiry/message/inquiry_problem/agent_run/ticket`과 다르므로 중복 테이블로 만들지 않는다.

## 3. 문의·대화·새 문의 분리

- 문의는 문의자, 제목·요약, 버전, 종합 상태, 숨김 표시, 해결 확인/종료 시각을 가진다. **숨김은 문의자 개인 목록 표시**이며 티켓·업무 이력은 삭제하지 않는다. 복원 가능해야 한다.
- 메시지는 최초 내용과 수정 이력·작성 주체·시각을 보존한다. 본인 사용자 메시지는 기간·횟수 제한 없이 정정한다. 종료 뒤 정정은 보완 저장만 하며 자동 재오픈하지 않는다. 분석 중 문제의 정정은 최신 버전으로 재분석하고 옛 미반영 결과를 폐기한다. 모든 문제의 분석·생성·이관 뒤의 새 입력/정정은 정보 보완으로만 저장한다. 이 단계에서는 자동 재진단·재배정·신규 티켓 생성 이벤트를 만들지 않는다.
- 티켓 상세에는 문의의 대화 원본을 복제하지 않고 관련 메시지·문제·티켓 연결과 정정 이력을 조회한다. 관련 범위의 식별·인덱스·권한 검사 방식은 구현 전 확정한다. 문의 상세 모달에는 채팅 로그를 싣지 않는다.
- 별개 문의 후보는 사용자 동의 상태와 동의 대상 버전·기존 문의·새 문의·가져간 문맥 출처를 기록한다. 동의가 없으면 새 문의를 생성하지 않는다. 같은 동의를 재전송해도 새 문의는 하나만 생성한다. 원래 문의와 티켓의 상태는 유지한다.
- 무티켓 안내는 사용자 해결 확인 전까지 해결 성과로 저장하지 않는다. 범위 밖 질문은 티켓을 만들지 않는다. 불명확한 IT 문의의 3회 질문 소진은 CS 검토 티켓으로 연결하되, 모델/통신 오류는 분류 실패로 바꾸지 않는다.

## 4. 티켓·배정·그룹 상태의 불변식

1. 제안이 통과하면 문제/작업의 소속 문의와 버전을 확인한다. 같은 처리 작업에서 티켓을 한 번만 만들고 티켓·현재 부서·최초 배정 이력을 같은 트랜잭션으로 저장한다. 여러 작업 전체는 하나의 취소 단위로 묶지 않는다.
2. `ticket`의 처리 상태와 배정 상태를 별도로 둔다. 현재 처리 부서 구성원만 티켓과 관련 대화를 조회한다. 미담당 티켓을 가져가는 경쟁 요청은 한 명만 성공하며 반환 전 재가져오기를 막는다.
3. 재이관 요청은 요청 당시 배정·제외 부서·사유·재판단 결과를 보존한다. 유효 후보가 소진되면 **배정 예외**, 기술 장애면 **복구 필요**, 정상 CS 검토는 별도로 표시한다. 운영 관리자의 재시도는 업무 관리자 수동 배정을 대신하지 않는다.
4. 담당자 처리 완료는 사용자 확인 대기로 전이한다. 처리 중 사용자의 선행 해결 신고는 담당자 작업 확인 후 반영한다. 확인 대기 24시간 후 알림을 **저장**하고 그 시각부터 48시간 무응답이면 미확인 종료한다. 알림 저장 실패 시 자동 종료를 보류한다. 미확인 종료는 해결 완료/AI 해결로 집계하지 않는다.
5. 그룹은 같은 부서·미완료·공통 조치로 함께 해결된다는 근거가 있을 때만 확정한다. 유사도만으로 그룹을 확정하지 않는다. 그룹 해결은 구성 티켓별 성공/실패를 보존한다. 미해결 재문의 시 그 티켓만 분리·재오픈한다. 재결합은 업무 관리자의 결정과 서버 재검증이 필요하다.
6. 우선순위는 긴급·높음·보통·낮음으로 두고 업무 영향·우회 가능성·서로 다른 영향 사용자 수를 함께 검증한다. 모델의 변경 제안과 수동 변경의 출처·근거·이력을 분리한다.

## 5. 실행·복구·멱등 저장

- 사용자 사번은 `member.employee_no`, JWT `sub`는 `member.id`, 부서 클레임은 `member.department_id`로 연결한 `department.id/code/name`을 원본으로 한다. 사번을 로그인 ID와 별도 관리하는 컬럼안이며 형식·길이·변경/재사용 정책은 구현 전 확정한다. 토큰의 부서명은 발급 당시 표시 정보이고 현재 부서 권한을 대체하지 않는다. 원본 계정·소속 변경 시 토큰을 무효화하고 열린 SSE를 종료하며 이후 요청을 현재 권한으로 다시 검사한다.
- Access는 메모리 15분이며 업무 테이블에 원문을 저장하지 않는다. Refresh는 HttpOnly 쿠키·최초 로그인부터 절대 7일·매 갱신 회전/이전 값 폐기다. 현재 로그인 세션 로그아웃, 역할/부서 변경·차단은 해당 사용자 기존 인증을 무효화하고 열린 SSE를 종료한다. 백엔드는 회원/세션 연결·안전한 검증값·최초/만료/폐기/교체 시각과 재사용 검출을 설계한다. 물리 저장소·키·CSRF·Origin의 실제 설정은 담당 설계/검증이 남았다. JWT 원문·서명키를 업무 JSON·로그에 남기지 않는다.
- SSE 연결·마지막 이벤트 ID는 전달 상태이며 문의·대화 원본과 별개다. Spring의 저장 데이터로 재접속 상태를 복원한다. 요청 접수·DB 커밋 후 확정 이벤트 발행·유실 복구의 경계를 정의하고, 이벤트 전달 실패가 이미 저장한 업무를 취소하지 않게 한다. replay 이력이나 outbox 등의 추가 저장 방식·보존 기간은 통합 설계에서 정한다. 과거 연결이나 target ID만으로 현재 조회 권한을 인정하지 않는다.
- 실행은 문의 버전, 입력/출력 스키마, 모델·프롬프트·설정 버전, 제안 원문과 검증/실제 적용 결과, 오류 코드·비용·소요 시간·단계별 공개 근거를 분리한다. 단일 에이전트 기준선과 최종 멀티 에이전트 비교에 필요한 실행 조건을 보존한다. 운영 로그에는 마스킹된 입출력만 기록한다.
- 생성 전 실패 작업, 배정 저장 실패, 재이관 기술 실패에는 원본 작업 식별자와 보존 데이터·자동/수동 시도 이력을 둔다. 성공한 작업은 재생성하지 않는다. 요청 접수와 복구 완료를 다른 상태로 저장한다.
- REST 업무 변경 요청 키는 행위자·메소드·경로·`Idempotency-Key`로 범위를 구분하고 요청 해시·처리 상태·저장 결과를 보존한다. HTTP 응답이 유실되어도 같은 요청은 한 번만 반영한다. 중복 수신 SSE는 `eventId`와 실행 ID·입력 버전, 메시지별 순번으로 걸러낸다. 캐시 만료 뒤에도 작업↔티켓 유일성으로 중복 생성을 막는다. 멱등 요청 결과는 최소 24시간 보존하고, 이후에도 작업↔티켓 유일성은 영구 업무 제약으로 유지한다. 정확한 재시도·복구·예산은 WIRE_CONTRACT 10절을 따른다.
- 운영 관리자는 실행·기술 복구 정보만 조회/재시도하고, 업무 관리자는 배정·정정·재결합을 확정한다. 역할은 직급이나 모델 제안으로 추론하지 않는다.

## 6. 자료·보존·집계

- 지식은 출처·사용 조건·검수 결과·버전·접근 범위와 RAG/개발/평가 분할을 기록한다. 가상 자료와 실제 운영 데이터를 구분한다. 임베딩 필드·모델·차원·임계값과 검색 설정은 후속 설계에서 결정한다.
- 업무 기록은 연결 업무가 모두 종료된 **마지막 시점부터 180일**, 운영 로그는 생성 후 **30일** 보존한다. 미해결·재오픈·복구 대기는 만료하지 않는다. 접근 가능한 지식과 감사 기록의 별도 보존/삭제 정책은 구현 전 확정한다.
- 이관 수는 배정 이력의 실제 이관만 센다. AI 해결률에는 담당자·그룹 해결과 미확인 종료를 포함하지 않는다. 무티켓 해결은 별도 집계한다. 집계 기간·기준 시점·조회 권한을 함께 저장 또는 계산하며 빈 결과와 조회 실패를 구분한다.

## 7. 담당 구현·후속 설계·미검증 항목

- **MVP:** 사번·JWT 클레임과 회원/부서/역할 원본 매핑, 부서 변경·토큰 만료/폐기와 열린 SSE 종료, 확정한 토큰 회전/폐기의 보조 저장 구현·검증. REST 멱등 키·HTTP 응답 유실·SSE eventId/replay·REST 복원, 문의·메시지·문제·작업·티켓의 물리 명명 통일, 버전과 FK, 부분 실패·중복 방지, 권한 범위, 실제 단일 에이전트 실행/평가 기록.
- **후속 기능별:** 메시지↔문제/티켓 연결, 새 문의 동의, 전체 상태 전이·알림 스케줄, 그룹 대표/재결합, 재이관 제외 이력, 우선순위 변경, 기술 복구와 자료 보존.
- **검증:** DDL·마이그레이션/제약 검사, 상태 전이·동시성·부분 실패·권한 계약 테스트, 단일/멀티 에이전트 동일 조건 비교를 각각 실제 수행 후 기록한다. 이 문서와 ERD를 검토한 사실만으로 DB 적용 또는 E2E 통과를 선언하지 않는다.

## 8. 확정 계약과 담당 경계

Knowledge Agent가 사용할 가상 기업 환경, 전체 데이터셋 범위, 장애 시나리오와 수명주기는 [Knowledge 설계](knowledge/README.md)를 참조한다. 현재 기계 판독 데이터에는 일반 공개 근거 62건과 PORTAL core 후보가 포함되어 있으며, 팀 리뷰·파생 문서 완성·임베딩·Tool 연결·Demo Portal 재현 완료를 뜻하지 않는다.

[DATA_TYPES](../specs/contracts/DATA_TYPES.md)의 enum·타입, [WIRE_CONTRACT 10절](../specs/contracts/WIRE_CONTRACT.md#10-인증재접속최신-대화분석-재시도-추가-프로필)의 시간·목록·정정·예산·관계가 개발 기준이다. DB의 문제당 티켓 1개 제약은 사용하지 않고 작업별 유일성을 적용한다. 백엔드가 실제 FK/인덱스/DDL/마이그레이션을 구현한다. 문서의 관계 수정은 DB 적용이나 ERD 그림 동기화를 의미하지 않는다.

Spring은 REST·SSE 인증과 대상 권한·열린 연결 회수·이벤트 전달을, AI는 실행 예산/유효 단계 재사용·식별자/버전 보존을 구현하고 Spring은 결과를 재검증한다. 실제 서비스·동시성·쿠키 회전·중복 방지·AI 비용/품질은 미검증이며 상세 담당/검증은 WIRE_CONTRACT 11절이다.
