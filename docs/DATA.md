# 데이터 설계 — PRD 1.44 논리 관계

상태: 팀 합의 기획을 반영한 논리 설계 · 물리 스키마·마이그레이션·구현 미확정. [PRD](PRD.md), [API](API.md), [목표 ERD와 전환 지침](ERD_설명.md)을 함께 본다. 아래 명칭은 설명용이며 컬럼·타입·코드·제약조건의 확정 DDL이 아니다.

## 1. 정본과 관계

PostgreSQL은 사용자·지원 시스템·현재 주담당자·문의·티켓·승인과 공개 상태의 업무 정본이다. Vector와 Neo4j는 승인된 지식의 검색·관계 탐색을 위한 파생 저장소이며 인물·담당자 관계의 정본이 아니다. 한 사용자는 여러 시스템을 담당할 수 있고 각 시스템에는 유효한 주담당자 한 명을 둔다. 부서는 사용자 소속 정보다.

문의 하나에 여러 독립 문제가 연결된다. 문제별로 확인 사실·미확인 정보·질문 횟수·보고 시스템·책임 시스템 후보/근거 및 처리·확인을 관리한다. 별도 완료 조건은 티켓을 분리하고 한 증상의 여러 원인 후보는 한 문제로 보존한다. 세부 작업과 티켓의 물리 관계는 계약에서 정한다.

## 2. 논리 데이터

| 영역 | 보존할 내용 |
|---|---|
| 사용자·소속·시스템 | 사용자·역할·시스템·기능·유효 주담당자 및 변경 이력 |
| 문의·메시지 | 작성자·원문·정정 이력·문의 버전·관련 문제·시스템 확인 대기 |
| 문제·표준 요청 | 의도·내부 처리 유형·보고/책임 시스템·근거·확인 사실·추정·미확인·유형별 정보 |
| 티켓·처리 | 문제 참조·책임 시스템·주담당자·배정 근거·처리/검증·수동 정정 사유·보완 정보 |
| 해결 확인 | 담당자 조치 또는 구현 완료, 문제별 문의자 해결/미해결, 확인 대기와 최종 완료 |
| 사례와 반영 | 초안·출처·원 기록·문서 버전·시스템 적용 버전·조건·공개 범위·확인·승인·저장소별 반영 결과 |
| 실행·검색 근거 | 실행과 입력 버전·허용 범위·출처·오류·공개 가능한 결과 요약 |

의도·처리 유형과 의미는 PRD 3.1에 둔다. 구체 상태 enum·필수/nullable 필드·관계 제약은 별도 합의한다.

## 3. 저장·배정·복구 불변식

- Spring은 지원 시스템과 주담당자를 검증해 저장·배정한다. 관계를 확인하지 못하면 성공으로 표시하지 않는다. 책임 시스템 근거가 부족하면 확인된 보고 시스템 담당자가 조사한다.
- 문제별 티켓 생성이 부분 실패해도 성공한 결과를 보존한다. 재시도 전에 저장 결과와 현재 문의 버전을 확인하고, 이미 생성됐으면 재사용한다. 저장 여부 미확인은 미확인으로 유지한다.
- 문의 정정 이력과 이미 저장된 티켓을 보존하고 오래된 분석 결과를 차단한다. 배정 이후 보완 메시지는 기존 티켓에 연결한다.
- 담당자 구현·검증 기록과 문의자 확인을 구분한다. 미해결은 같은 티켓에서 계속, 무응답은 확인 대기, 완료 뒤 재오픈은 범위 밖이다.
- 처리 기록 저장 직후 사례 초안이 생성될 수 있다. 문의자 확인·담당자 승인과 동일 승인 버전의 양쪽 반영 성공 후에만 공개한다. 한쪽 실패/미확인은 두 검색에서 비공개이며 승인·업무 기록은 보존한다.
- 문서 버전과 시스템 적용 버전을 구분하고 미확인은 추정하지 않는다. 합성·데모 검증·실제 운영 출처를 구분한다. 실패 시도는 업무 이력으로 남기며 검색용 해결 사례로 만들지 않는다.
- 문의·티켓·처리 기록·해결 사례는 삭제하지 않는다. 실제 운영 보존 기간은 이번 범위가 아니다.

## 4. 물리 설계·전환 과제

기존 ERD와 migration은 부서 기반 현행/기존 설계다. 시스템·주담당자·표준 요청·확인·CASE·인덱싱 정보의 테이블과 제약, 기존 데이터 이관·기존 API 호환성은 확정되지 않았다. 유일성·동시성·트랜잭션·재시도 키·권한 회수를 기능별로 검토하고 마이그레이션을 별도 작성한다. 구현이나 운영 데이터 이관을 문서 변경으로 수행하지 않는다.

## 5. 문의·대화·문제의 보존과 버전

### 5.1 입력과 문제

- 한 대화 세션은 문의 하나다. 인증 세션·SSE 연결·문의의 수명은 서로 다르며 재접속만으로 새 문의를 만들지 않는다.
- 문의 원문과 메시지·정정 전후·작성 주체·시각을 보존한다. 메시지 표시 순서와 정정 revision, 문의의 분석 입력 버전은 별개다.
- 한 문의는 독립적인 여러 문제를 가질 수 있다. 질문 횟수·시스템 확인·진행·해결 확인은 문제별로 관리한다. 같은 현상의 여러 원인 후보는 하나의 문제 안에 유지한다.
- 문의 의도와 내부 처리 유형을 별도 차원으로 저장한다. 문의자의 표현과 담당자가 확인한 장애 여부를 구분한다. `UNKNOWN` 또는 미확인 정보를 추정 사실로 바꾸지 않는다.
- 표준 요청은 원문을 대체하지 않는다. 생성 시점 문의 버전, 확인 사실·추정·미확인 항목, 대상 시스템·기능과 관련 근거를 추적한다. AI가 제안한 수용 조건은 확인 전까지 제안으로 보존한다.

### 5.2 정정과 관련 대화

정정이 저장되면 최신 입력 버전에 대한 분석이 적용돼야 한다. 이미 저장된 메시지·티켓은 보존하며 이전 버전 실행의 **미반영** 결과만 차단한다. 이미 배정된 문제에 대한 후속 메시지는 새 티켓이나 자동 재배정이 아니라 기존 티켓의 보완 정보다.

문의 원문 전체를 티켓마다 복제하는 대신 해당 문제·티켓과 관련된 메시지 범위를 식별할 수 있어야 한다. 구체 연결 엔터티·인덱스와 권한 범위는 상세 설계에서 정한다. 담당자가 다른 독립 문제의 대화나 내부 운영 로그를 자동으로 읽을 수 있다고 가정하지 않는다.

## 6. 시스템 소유권·티켓과 생성 복구

### 6.1 시스템과 현재 담당

시스템에는 기능이 연결되고 한 사람은 여러 시스템의 주담당자가 될 수 있다. 각 시스템에는 현재 유효한 주담당자 한 명을 둔다. 사용자의 부서 소속은 유지하지만 기술 부서명이 책임 시스템을 대신하지 않는다. 서버는 배정 시점에 지원 시스템과 주담당 관계를 확인한다. 변경 이력과 유효 기간, 동시에 관계가 바뀌는 경우의 제약은 물리 모델에서 정한다.

보고 시스템은 사용자가 현상을 경험한 위치다. 책임 시스템은 현재 티켓을 처리할 대상이다. 두 값이 다를 수 있으며 최초 제안 근거·미확인 항목을 보존한다. 공통 로그인 근거가 확인된 전자결재 로그인 문의는 공통 로그인 담당자에게 배정할 수 있다. 근거가 부족하면 보고 시스템 담당자가 조사한다. 시스템 간 의존 관계 하나만으로 원인을 확정하지 않는다.

### 6.2 문제·생성 작업·티켓

| 의미 | 보존해야 하는 관계·사실 | 물리 설계 전 확인할 사항 |
|---|---|---|
| 독립 문제 | 원 문의·대화 출처·질문 수·확인/미확인 정보 | 문제와 메시지/정정 간 연결 범위 |
| 티켓 생성 업무 작업 | 문제·요청 버전·제안 또는 재생성 근거·저장 확인 결과 | 작업 식별자, 동일 작업의 유일 범위, 보존·복구 방식 |
| 저장된 티켓 | 원 문의·문제, 제목·내용, 보고/책임 시스템, 확정 담당자 | 티켓과 작업의 물리 관계, 생성과 배정의 거래 경계 |
| 배정·정정 이력 | 기존/새 시스템·담당자·근거·사유·행위자·시각 | 정정 권한, 당시/현재 담당자와 접근 회수, 동시성 |
| 처리·검증 | 조치·변경·검증 결과, 담당자·시각, 기능 구현 완료 여부 | 하나의 티켓에 여러 처리 기록을 남기는 방식 |
| 해결 확인 | 대상 문제·티켓, 문의자, 해결/미해결, 응답 시각 | 요청·응답 연결, 중복 응답·오래된 응답 처리 |

동일 생성 작업의 성공 결과는 중복 생성하지 않아야 한다. 서버가 저장 여부를 확인할 수 없을 때는 미확인으로 보존하고 실패로 단정하지 않는다. 이미 저장된 티켓을 찾았다면 기존 결과를 반환한다. 실제 미생성으로 확인된 업무 작업만 현재 문의 버전을 확인해 재시도한다. 유일 제약·트랜잭션·동시 재시도의 구현 방식은 작업/티켓 모델과 함께 확정한다.

## 7. 처리 완료·사례·검색 반영

### 7.1 독립해서 보존할 사실

| 사실 | 발생 조건 | 다른 사실과의 차이 |
|---|---|---|
| 담당자 처리 기록 | 실제 조치·검증을 저장 | 문의자의 해결 확인이나 사례 승인을 뜻하지 않는다. |
| 기능 구현 완료 | 기능 요청을 실제 구현·검증하고 기록 | 문의자 최종 해결 확인 전에는 업무 최종 완료가 아니다. |
| 문의자 해결 확인 | 대상 문제의 사용자 응답을 서버가 확인 | 해당 문제의 완료 조건. 미해결은 같은 티켓에서 계속 처리한다. |
| 사례 초안 | 처리 기록을 바탕으로 Curator가 제안 | 아직 검색할 수 없고 생성 실패가 처리 기록을 취소하지 않는다. |
| 담당자 승인 | 문의자 확인 뒤 해당 시스템 담당자가 사례 버전을 확인·승인 | 두 검색 저장소에 반영됐다는 뜻은 아니다. |
| 저장소별 반영 | 같은 승인 버전의 Vector 및 Neo4j 반영을 각각 확인 | 한쪽 성공만으로 공개할 수 없다. 실패/미확인 결과도 구분한다. |
| 검색 가능 | 같은 승인 버전 양쪽 성공과 요청자의 현재 권한 검증 | 승인 상태와 사용자별 접근을 구분한다. |

문서 버전과 적용 시스템 버전은 서로 다르다. 적용 버전이 없으면 미확인으로 표현한다. 합성·데모 검증·실제 운영 출처와 가상 문의자의 설정상 확인·HOPS에서 수행한 확인을 구분한다. 사례에는 원 문의·티켓·처리 기록, 실제 조치, 검증 결과, 적용 조건·한계, 작성·승인과 공개 범위를 연결한다.

### 7.2 두 저장소 반영과 복구

Vector·Neo4j 반영 결과는 승인 버전 기준으로 각각 추적한다. 하나가 실패하거나 결과가 미확인이라면 두 경로에서 모두 검색에 공개하지 않는다. 반영 실패는 기존 처리 기록이나 승인 사실을 취소하지 않는다. 원인을 수정해 실패한 반영을 재실행하고 동일 버전의 두 성공을 확인한다. 검색 시 서버가 승인·공개 가능 상태와 요청자 권한을 검사한다. 재반영 식별자·상태 조회·중복 방지·공개 처리 원자성은 구현 계약에서 정한다.

구버전 사례는 무조건 삭제·차단하지 않는다. 담당자가 적용 시스템·버전·조건을 현 상황과 비교하고 새로운 해결을 찾으면 새 사례에 적용 버전을 기록한다. 잘못된 자료나 공개 권한을 잃은 자료의 처리 방식은 별도 검토한다.

## 8. 데이터 품질·보안·전환 검증

- **권한:** 문의 소유자, 현재 시스템 주담당자, 업무 관리자의 허용 범위를 구분한다. 검색 전 접근 범위를 제한하고 반환 전에 공개 가능 여부와 근거를 재검증한다.
- **이력:** 문의·티켓·처리 기록·사례는 이번 범위에서 삭제하지 않는다. 실제 운영 보존 기간이나 승인 취소·폐기 전파를 임의로 결정하지 않는다.
- **실행:** AI 실행·문의 입력 버전·공개 가능한 근거·시간·오류를 연결하되 비밀값과 모델 내부 사고 과정은 기록하지 않는다. 실행 성공과 업무 저장 성공을 구별한다.
- **경합:** 담당 변경과 수동 정정, 메시지 버전 충돌, 같은 작업 재시도, 사례 승인 버전 변경과 반영 완료의 경합을 검토한다. 실제 유일 제약·잠금·트랜잭션은 물리 설계 후 테스트한다.
- **전환:** 기존 부서 기반 seed·Mock·wire 필드는 새 시스템 소유권을 뜻하지 않는다. 이름을 일괄 치환하지 않고 기능 경계, 기존 ID·외래키·마이그레이션 호환성을 확인한다.
- **평가:** 합성·데모 자료와 실제 운영을 구분하고, 평가 사건의 미래 해결 내용과 정답 매핑을 검색 자료나 프롬프트에 넣지 않는다.

## 9. hops-system-1 저장 제약안

상태: 팀 리뷰용 구체 제안. 실제 DDL·테이블명·마이그레이션은 작성/적용하지 않았다. 위의 물리 설계 미확정 표시는 이 제안의 승인·구현이 남았다는 뜻이다. 타입/상태는 [신규 데이터 계약](../specs/contracts/DATA_TYPES.md#신규-계약-hops-system-1), 전이는 [TARGET](../specs/contracts/TARGET_CONTRACT.md)가 정본이다.

물리 테이블·컬럼·FK·JPA 매핑은 [기존 물리 ERD 작업 #66](https://github.com/Hi-Hops/Hops/issues/66)과 대조해 결정한다. 별도 엔티티 사전을 중복 생성하지 않는다. 아래 WorkItem/SystemAssignment 등은 논리 개념이며 동일 이름의 테이블 생성을 강제하지 않는다.

| 관계·키 | 제약 제안 | 저장 경계 |
|---|---|---|
| SystemAssignment | 시스템별 유효 PRIMARY 한 명. 유효 구간 중첩 금지 | 관계 변경 잠금·이력·권한 세대 증가·무효화 outbox를 함께 저장 |
| Inquiry → Problem | 1:N. problemId와 inquiryId 귀속 불변 | 분석 적용 시 문의 버전/활성 Run 검증·문제 ID 재사용 |
| Problem → WorkItem → Ticket | 각각 0:1. UNIQUE(problemId) 작업, UNIQUE(workItemId)와 UNIQUE(problemId) 티켓 | workItem 잠금 안에서 최신 제안·기존 성공 검사, 티켓·배정·작업 STORED를 함께 commit |
| MessageRevision | UNIQUE(messageId,revisionNo); 원 ID·sequenceNo 고정 | 메시지 revision과 inquiryVersion 비교 후 정정 이력·현재 내용 함께 저장 |
| ProblemMessage | UNIQUE(problemId,messageId,revision,startCodePoint,endCodePoint)·원문 구간 출처 | 구간은 Unicode 코드 포인트의 [start,end)이며 실제 원문·revision과 일치해야 함. 복합 메시지의 다른 문제 구간은 담당자에게 제외 |
| QuestionBundle | UNIQUE(problemId,bundleRef); 횟수 0~5 | 저장된 AI 질문과 번들·질문 수 증가를 같은 거래에서 처리 |
| CommandJournal | UNIQUE(actorId,profile,requestId); method/path/body hash 불변 | 업무 변경·결과 참조·outbox와 함께 commit. 처리 중 키 중복은 기존 작업으로 합침 |
| WorkRecord | 티켓 1:N 불변 기록; 검증 완료 종류에 verification 필수 | ticketRevision 검사·기록·확인 요청·Curator outbox를 함께 저장 |
| ResolutionRequest | 문제별 PENDING 최대 하나; sourceKind/sourceId/sourceVersion 고정 | 요청 revision 비교·한 응답·관련 문제/티켓 상태 변경 함께 저장 |
| CuratorJob | UNIQUE(workRecordId) | 중복 outbox는 기존 작업. 원 기록은 실패 시에도 유지 |
| CaseVersion/Approval | UNIQUE(caseId,caseVersion), 버전별 승인 최대 하나 | 최신 버전·원 기록 해결 확인·현재 담당 관계를 잠금 안에서 검사 |
| IndexJob | UNIQUE(caseId,caseVersion,store); attempt 단조 증가 | 중복 반영 요청은 같은 논리 작업. 외부 저장소 키도 동일 복합 키 |
| Publication | 승인 버전별 공개 gate | 같은 버전 두 성공 확인과 gate 변경을 DB 내 원자 처리 |

티켓 assignee는 배정 당시 또는 마지막 수동 정정의 저장값이다. 시스템 PRIMARY 변경으로 기존 티켓 assignee를 자동 재배정하지 않는다. 접근·처리 권한은 현재 시스템 PRIMARY가 가지며 화면은 저장된 배정과 현재 담당 관계가 다름을 표시하고 필요 시 수동 정정한다.

NOT_CREATED는 진행 중 작업이 없고 서버가 미저장/롤백을 확인한 결과다. journal 유실·조회 불가·HTTP timeout을 NOT_CREATED로 바꾸지 않는다. DB commit 후 HTTP 유실은 같은 키/작업의 기존 결과로 복구한다. journal 상세는 최소 24시간 보존하며 사용된 키 표식·원 업무 유일성은 그 이후에도 유지한다. 실제 운영 장기 보존/삭제 정책을 이번 문서에서 추가하지 않는다.

외부 AI·Vector·Neo4j와 DB 분산 트랜잭션을 구성하지 않는다. 저장 후 outbox로 실행·반영하고 중복 수신을 논리 키로 제거한다. 검색은 파생 저장소의 상태 플래그만 신뢰하지 않고 Spring 업무 DB의 승인·gate·현재 ACL을 재검증한다. 구버전 CASE의 자동 폐기·승인 취소는 추가하지 않는다.

마이그레이션은 신규 관계·유일성·불변 원 기록·이력·권한 세대를 포함해 별도 리뷰한다. 현재 부서 seed·DDL·운영 데이터를 이 문서 작업으로 삭제하거나 변경하지 않는다.

## 10. 물리 ERD 작업과의 매핑 검토

[이슈 #66](https://github.com/Hi-Hops/Hops/issues/66)은 시스템 테이블의 PRIMARY 컬럼과 문제 행의 생성 상태를 사용하는 물리안을 다룬다. 이 문서의 별도 SystemAssignment/WorkItem 저장 제안과 차이가 있으므로 두 안을 동시에 확정된 구현 지침으로 적용하지 않는다.

- 외부 workItemId는 고정 생성 작업의 논리 식별자다. 별도 테이블 없이 problemId에서 대응시켜도 동일 작업·부분 실패·결과 확인·유일성 보장을 만족하면 된다. 실제 ID 매핑을 물리안 리뷰에 기록한다.
- 유효 PRIMARY·당시 배정 이력·현재 권한 회수는 필요하지만 담당 관계를 독립 테이블 또는 시스템 컬럼/이력 중 어디에 둘지는 #66과 일치시킨다.
- 사례 문서 버전·원 처리 기록·확인 요청·동일 버전 두 반영 상태는 복원 가능해야 한다. 테이블 수·명칭은 wire DTO와 1:1일 필요가 없다.
- 이 문서 PR은 API/상태/권한/중복 방지의 검토 기준을 정리한다. 물리 ERD·Entity·Flyway 구현은 별도 연계 작업이며 현재 적용된 V1과 논리 ERD 문서는 변경하지 않는다.
