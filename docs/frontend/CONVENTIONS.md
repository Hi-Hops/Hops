# 코드 작성과 기능 완료 기준

범위: `frontend/src`. 자동 검사 규칙의 원본은 [ESLint 설정](../../frontend/eslint.config.js)·[TypeScript 설정](../../frontend/tsconfig.app.json)·[Prettier 설정](../../frontend/.prettierrc.json)이다. 기능 동작과 전송 데이터의 원본은 [스펙](../../specs/README.md)과 [공통 계약](../../specs/contracts/README.md)이다.

## 1. TypeScript·React

- strict를 유지한다. `any`, `@ts-ignore`, `@ts-nocheck`, 파일 단위 lint 비활성화는 쓰지 않는다. 불가피한 예외는 최소 범위에 이유를 명시하고 리뷰한다.
- 타입은 `type`, 타입 import는 `import type`, 정해진 값은 문자열 리터럴 유니언을 사용한다. interface는 전역 타입 보강에만 사용한다.
- 배열 인덱스·nullable 값·unknown 오류는 분기로 확인한다. non-null 단언으로 무시하지 않는다. 타입 단언은 외부 데이터 경계·라이브러리 타입 한계에서만 이유와 함께 사용한다.
- 컴포넌트는 함수와 named export로 작성하고 props는 `NameProps` 타입으로 선언한다. 파일당 공개 컴포넌트 하나를 기본으로 한다.
- 컴포넌트는 표시와 입력, 훅은 통신과 화면 로직, model은 순수 로직·상태를 맡는다. 조회는 TanStack Query를 사용하며 useEffect로 직접 구현하지 않는다.
- 목록 key는 서버 식별자를 사용한다. 조회 상태는 로딩 → 오류 → 빈 결과 → 내용 순서로 구분한다.

## 2. 통신·입력

- REST는 `shared/api/client.ts`, 실시간 연결·명령은 `shared/realtime`의 공용 구현을 거친다. 화면에서 fetch·io를 직접 호출하지 않는다. 기능별 API와 쿼리 키는 해당 기능의 api/에 둔다.
- 필드·상태·오류·ACK·권한·버전·재전송·조각 순서는 [전송 계약](../../specs/contracts/WIRE_CONTRACT.md)을 따른다. 이 문서에 같은 계약을 다시 정의하지 않는다.
- 저장 확인 전에는 성공·해결로 표시하거나 입력을 지우지 않는다. 실패·충돌·결과 미확인 상태의 입력과 요청 ID를 보존하고 계약에 따라 재조회·재전송한다.
- 입력 길이 검사는 `shared/lib/content.ts`를 사용한다. 메시지는 코드 포인트 기준으로 검사하며 원문을 자동으로 자르거나 trim해 저장하지 않는다.
- 인증과 계정 전환은 auth 기능에서 관리한다. 토큰·비밀번호를 콘솔·오류 로그·URL에 남기지 않는다. 토큰 저장·갱신은 공통 계약 10절의 확정 기준을 적용하고, 실제 키·Origin·CSRF 등 담당 설계 항목을 임의 값으로 대체하지 않는다. 현재 구현과 계약의 차이는 11절로 추적한다.
- 미정 계약을 사용하는 구현에는 관련 Q 식별자와 제안 상태를 남기고, 답변이 정해지면 문서·타입·동작·테스트를 함께 갱신한다.

## 3. 스타일·접근성

- CSS Modules와 공통 토큰을 사용한다. 인라인 style은 계산된 동적 값에만 사용한다. 새 토큰이 필요하면 공통 파일에서 관리한다.
- 화면 문구는 한국어 존댓말을 사용하고, 상태 표시명은 기능 model에 모은다. 상태는 문구와 색으로 함께 표현한다.
- 동작 요소는 button/a, 입력에는 연결된 label을 사용한다. 아이콘만 있는 버튼에는 aria-label을 제공한다.
- 모달·팝오버·탭은 Radix 기본 부품으로 포커스·키보드를 처리한다. 모달의 제목·설명·Esc 닫기·원래 위치로의 포커스 복귀를 확인한다.
- 비동기 변화는 status, 오류는 alert처럼 역할로 안내한다. 테스트에서 역할·label로 찾을 수 있도록 작성한다.
- 새 공통 UI는 실제 재사용 필요를 확인하고 [구조 문서](STRUCTURE.md#4-현재-공통-ui)에 추가한다.

## 4. 테스트

- **구현 범위의 인수 조건마다 테스트를 작성해야 기능 완료다.** describe에 기능 ID, it 이름에 `Fnnn-ACnn`을 포함해 스펙과 연결한다.
- 정상 흐름뿐 아니라 실패·빈 결과·권한 없음·충돌·ACK 유실·중복·늦은 이벤트·재접속 등 해당 기능의 예외를 검사한다.
- 순수 로직은 단위 테스트, 화면은 Testing Library와 user-event로 확인한다. getByRole/getByLabelText를 우선 사용하고 내부 상태·CSS 클래스만 검사하는 테스트는 피한다.
- Mock 데이터는 공용 JSON을 사용하며 각 테스트의 서버·인증·조회 상태를 분리한다. 자동 테스트에 개인 `.env`나 실제 인증 값을 사용하지 않는다.
- Mock 단위·컴포넌트 테스트, 실제 서버 통합 검사, 브라우저 직접 확인, 자동 E2E를 구분해서 보고한다. 하나의 통과를 다른 검사 통과로 표현하지 않는다.

## 5. 기능 완료 체크리스트

기능 작업 전 맡은 스펙에서 관찰 가능한 완료 조건과 사용할 계약을 정한다. 기존 공통 구현을 확인하고 필요한 API·로직·훅·화면 순서로 구현한다. 완료 시 아래를 확인한다.

- [ ] 구현한 인수 조건과 예외 조건의 테스트가 통과했다. 일부 범위만 구현했다면 미구현 조건을 구분했다.
- [ ] 타입·필드·권한·입력·저장 확인 동작이 해당 스펙과 계약 문서에 맞는다.
- [ ] 레이어·공개 진입점·상태 보관·공통 UI 규칙을 지켰다.
- [ ] 역할·키보드·포커스·로딩/오류/빈 결과 표시를 확인했다.
- [ ] `npm run check`, `npm run build`를 실행하고 개발 브라우저에서 변경 화면을 확인했다.
- [ ] 경로·공통 UI·환경 설정 변경은 해당 문서와 실제 설정을 함께 갱신했다.
- [ ] PR에 변경 범위·인수 조건·실행한 검사·미실행 항목·UI 증거·미정 계약을 기록했다. 문서만 바꾼 경우 앱 검사 해당 여부와 사유를 적었다.

Git·커밋·PR·승인 절차는 [Git 컨벤션](../../GIT_CONVENTION.md), 공통 작업 원칙은 [AGENTS.md](../../AGENTS.md)를 따른다. 여기서 별도 절차를 중복 정의하지 않는다.
