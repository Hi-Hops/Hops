# 코드 컨벤션

상태: 초안 · 범위: `frontend/src` · 린트로 강제되는 규칙은 [TOOLING 6절](TOOLING.md#6-eslint), 여기서는 린트가 잡지 못하는 규칙까지 정한다.

각 규칙 끝의 근거가 PRD·API면 제품 요구이고, "일관성"이면 팀 코드 스타일이다.

## 1. TypeScript

1. `strict`를 끄지 않는다. `any`, `@ts-ignore`, `@ts-nocheck`를 쓰지 않는다. 불가피하면 `@ts-expect-error -- 이유`를 쓴다. (일관성)
2. 타입 선언은 `type`으로 한다. `interface`는 전역 타입 보강(`*.d.ts`)에서만 쓴다. (일관성)
3. 타입만 가져올 때는 `import type`을 쓴다(`verbatimModuleSyntax`). (린트 강제)
4. 상태 코드처럼 값이 정해진 것은 문자열 리터럴 유니언으로 표현한다. `enum`은 쓰지 않는다. (일관성)
5. 유니언을 분기할 때 `switch`는 모든 경우를 다룬다(`switch-exhaustiveness-check`). 값별 표시명은 `Record<유니언, string>`으로 만들어 빠진 값을 컴파일러가 잡게 한다. (린트 강제)
6. 서버 응답은 [CONTRACT_TYPES](CONTRACT_TYPES.md)의 타입만 쓴다. 화면 컴포넌트 안에서 응답 모양을 새로 선언하지 않는다. (일관성)
7. 배열·객체 인덱스 접근 결과는 `undefined`일 수 있다(`noUncheckedIndexedAccess`). `!`(non-null 단언) 대신 분기한다. (일관성)
8. `catch (error)`의 `error`는 `unknown`이다. `instanceof ApiError`로 좁힌 뒤 쓴다. (일관성)
9. `as` 단언은 외부 경계(응답 파싱, 라이브러리 타입 한계)에서만, 바로 위에 이유 주석과 함께 쓴다. (일관성)

## 2. React 컴포넌트

1. 함수 컴포넌트와 이름 있는 `export function`으로 선언한다. `default export`는 쓰지 않는다(라우트 지연 로딩이 필요해질 때만 예외). (일관성)
2. props는 `<컴포넌트>Props` 타입으로 선언하고 매개변수에서 구조 분해한다. `React.FC`는 쓰지 않는다. (일관성)
3. 컴포넌트 파일 하나에 공개 컴포넌트 하나. 내부 보조 컴포넌트는 같은 파일 아래쪽에 두되 export하지 않는다. (일관성)
4. 컴포넌트는 표시와 사용자 입력만 맡는다. 데이터 조회·명령 전송·매핑은 훅(`hooks/`)과 `model/`에 둔다. (일관성)
5. 목록의 `key`는 서버 식별자(`id`)를 쓴다. 배열 인덱스를 쓰지 않는다. 같은 티켓을 두 번 보여 주지 않는 규칙(F005)의 전제다. (PRD 3.1)
6. `useEffect`는 외부 시스템과 동기화할 때만 쓴다(소켓 구독, 문서 제목). 서버 데이터 조회에 쓰지 않는다(TanStack Query 사용). (일관성)
7. 훅 규칙과 의존성 배열은 `eslint-plugin-react-hooks`를 따른다. 경고를 끄지 않는다. (린트 강제)
8. 조건부 렌더링은 상태 순서를 고정한다: **로딩 → 오류 → 빈 결과 → 내용**. 빈 결과와 실패를 같은 화면으로 보이지 않게 한다. (PRD 4.11)

## 3. REST 통신

1. 모든 요청은 `shared/api/client.ts`의 `apiRequest`로 보낸다. 컴포넌트·훅에서 `fetch`를 직접 부르지 않는다. (일관성)
2. 기능별 REST 함수는 `features/<기능>/api/<기능>Api.ts`에 두고, 쿼리 키 객체를 같은 파일에 둔다. (일관성)
3. 조회는 `useQuery`, 변경은 `useMutation`. 변경이 성공하면 관련 쿼리 키를 무효화해 다시 조회한다. 응답을 추측해 캐시를 미리 고치는(낙관적 갱신) 것은 하지 않는다. 저장 확인 전에는 성공으로 보이지 않아야 하기 때문이다. (PRD 4.11, 7.1)
4. 업무 변경 REST 요청에는 `Idempotency-Key`를 붙인다. 같은 동작의 재시도는 **같은 키**를 쓴다. 키는 사용자가 동작을 시작할 때 한 번 만들고 재시도 동안 유지한다. (API 1)
5. 상태 코드별 처리는 한 곳(공통 오류 처리)에서 한다.

| 상태 | 화면 처리 | 근거 |
|---|---|---|
| 401 | 재로그인 안내, 입력 보존(F001) | API 1 · PRD 4.2 |
| 403 | 권한 없음 화면, 내용 비노출 | PRD 4.11 |
| 404 | 찾을 수 없음 화면 | PRD 4.11 |
| 409 | "최신 내용을 다시 불러와 주세요" + 재조회, 입력 보존 | API 1 |
| 429·503 | 일시 오류 안내 + 다시 시도, 입력·저장 결과 보존 | API 1 · PRD 4.11 |
| 400 | 해당 입력 옆에 오류 표시 | API 1 |

6. 오류 문구는 `body.code`로 고른다. `body.message`를 그대로 보여 줄지는 Q-ALL-4에서 정한다. 내부 예외 문자열·스택을 화면에 보여 주지 않는다. (API 1)

## 4. 실시간(Socket.IO)

1. 소켓 연결은 앱 전체에 하나다. `shared/realtime/socket.ts`로만 만들고 Provider로 나눠 준다. 컴포넌트에서 `io()`를 직접 부르지 않는다. (일관성)
2. 명령은 `sendCommand`로 보내고 ACK를 기다린다. ACK 전에는 "전송 중", 오류 ACK는 "실패(입력 보존)", 시간 초과·끊김은 **"결과 확인 중"**이다. 실패로 표시하지 않는다. (API 2.4)
3. 명령의 `requestId`는 동일 요청을 재전송할 때 유지한다. 내용·대상 버전을 고친 새 요청에는 새 키를 쓴다. 저장 ACK와 구독 ACK는 [공통 계약](../../specs/contracts/WIRE_CONTRACT.md)대로 분리한다. (API 1, 2.4)
4. 받은 이벤트는 `eventId`로 중복을 거른다. 진행·답변 조각은 현재 문의 버전과 활성 runId로 필터링한다. 저장 메시지·정정 이력·기존 티켓은 옛 버전이라는 이유로 버리지 않는다. seq 누락은 버퍼링하고 최종 저장 메시지로 복구한다. (API 2.4)
5. `agent.progress`, `answer.delta`는 임시 표시다. 저장·성공·해결로 표시하지 않는다. `message.stored`, `state.changed`를 받으면 해당 REST 쿼리를 무효화한다. (API 2.4 · PRD 5.1)
6. 다시 연결되면 구독을 다시 요청하고, 보고 있던 화면의 REST 쿼리를 모두 무효화한다. (PRD 4.11)
7. 화면을 떠나면 그 화면이 요청한 구독을 해제한다. (API 2.4)

## 5. 입력

1. 메시지 길이는 **코드 포인트**로 센다(`[...text].length`). `text.length`(UTF-16 단위)를 쓰지 않는다. 기준은 공백 포함 1~4,000이고 공백만 있는 입력은 막는다. 함수는 `shared/lib`에 하나만 둔다. (API 1)
2. 초과·실패 시 입력을 지우지 않는다. 성공 ACK를 받은 뒤에만 입력창을 비운다. (PRD 4.3, 4.4)
3. 보내지 못한 입력(인증 만료·끊김)은 `requestId`와 함께 보관했다가 사용자 확인 후 같은 `requestId`로 다시 보낸다. (PRD 4.2)

## 6. 인증

1. 토큰을 읽는 곳은 인증 기능 한 곳이다. 다른 코드는 `registerTokenProvider`로 등록된 함수만 통해 쓴다. 보관 위치는 Q-BE-2가 정해질 때까지 메모리로 둔다. `localStorage`에 저장하지 않는다(결정 전 기본값을 확정하지 않음). (API 2.5 · PRD 8.5)
2. 화면 권한 판단은 `/api/auth/me` 결과(`CurrentUser`)로 한다. JWT를 브라우저에서 풀어 읽지 않는다. (API 2.5)
3. 토큰·비밀번호를 콘솔·오류 보고·URL에 남기지 않는다. (API 2.5 · PRD 5.4)

## 7. 스타일

1. CSS Modules + `shared/styles/tokens.css`의 CSS 변수만 쓴다. 인라인 `style`은 동적 값(진행률 너비 등)에만 쓴다. (일관성)
2. 상태 표시는 색만으로 구분하지 않고 문구를 함께 쓴다. 공통 `StatusBadge`를 쓴다. (PRD 4.11)
3. 저장 확인 전 항목은 "전송 중", "결과 확인 중"처럼 확정되지 않았다는 표시를 한다. 성공 색을 쓰지 않는다. (PRD 4.11, 7.1)
4. 화면 문구는 한국어, 존댓말 "~해요"체로 통일한다. 문구는 컴포넌트 안에 직접 쓰되, 상태 표시명처럼 여러 곳에서 쓰는 것은 `model/`의 표로 모은다. (일관성)

## 8. 접근성

ESLint 접근성 플러그인을 쓸 수 없어서(TOOLING 1절) 아래를 리뷰와 테스트로 지킨다.

1. 클릭할 수 있는 것은 `button` 또는 `a`다. `div`에 `onClick`을 달지 않는다.
2. 입력에는 보이는 `label`을 연결한다. 아이콘만 있는 버튼에는 `aria-label`을 단다.
3. 모달·팝오버·탭은 Radix 기본 부품으로 만든다(포커스 가두기·Esc·복귀 처리). 직접 구현하지 않는다.
4. 비동기로 바뀌는 상태(전송 중 → 저장됨, 연결 끊김)는 `role="status"` 영역으로 알린다.
5. 테스트는 `getByRole`, `getByLabelText`를 우선 쓴다. 역할로 찾을 수 없다면 접근성이 빠진 것이다.

## 9. 테스트

1. 스펙의 인수 조건 하나에 테스트 하나 이상. `describe`는 기능 ID와 이름, `it`은 인수 조건 ID로 시작한다.

```ts
describe('F006 내 문의 목록·상세', () => {
  it('F006-AC03 빈 목록과 조회 실패를 다른 화면으로 보여 준다', async () => {
    // ...
  });
});
```

2. 서버는 흉내 낸다. REST는 `fetch`를, 소켓은 테스트용 Socket.IO 서버 또는 가짜 소켓을 쓴다. 테스트 데이터 원본은 `specs/mocks/` 공용 JSON이며 `src/test/fixtures/`에는 읽기/변환 어댑터를 둔다(CONTRACT_TYPES 4절).
3. 사용자 동작은 `@testing-library/user-event`로 재현한다. 구현 세부(내부 상태, 클래스 이름)를 검사하지 않는다.
4. 실패·시간 초과·중복 이벤트·뒤늦은 버전·재접속처럼 스펙의 예외 인수 조건을 먼저 테스트한다. 정상 흐름만 테스트하고 끝내지 않는다.

## 10. 주석·언어·기타

1. 주석은 한국어로, **왜**를 쓴다. 코드를 그대로 읽어 주는 주석은 쓰지 않는다. (AGENTS.md "설명은 한국어")
2. 스펙·계약 근거가 있는 분기에는 근거를 짧게 단다: `// API 2.4: ACK 시간 초과는 결과 미확인`.
3. 미정 계약에 기대는 코드에는 질문 ID를 단다: `// Q-INF-5 확정 전 임시값`. 확정되면 주석과 함께 고친다.
4. `console.log`를 커밋하지 않는다(린트 강제). 사용자 데이터·토큰을 로그에 남기지 않는다.
5. 식별자·파일 이름은 영어, 화면 문구·주석·커밋 설명은 한국어. (AGENTS.md)

## 11. 금지 목록 (리뷰에서 바로 반려)

- `any`, `@ts-ignore`, 파일 단위 `eslint-disable`
- 컴포넌트·훅에서 `fetch`·`io()` 직접 호출
- 기능 내부 파일을 다른 기능·페이지에서 직접 import
- 서버 응답을 zustand·useState로 복사해 따로 관리
- 이벤트·실행 완료만으로 성공·해결 표시
- 실패 시 입력 지우기, 동일 본문·대상 버전의 재전송에 새 `requestId`·`Idempotency-Key` 사용
- 미정 계약 값을 확정값처럼 쓰기(`@contract 미정` 표기 없이 필드·코드 추가)
- 승인 없는 패키지 추가, 버전 범위(`^`, `~`) 사용
