# 체크포인트 스파이크 결과 (#189)

[에이전트 아키텍처](AGENT_ARCHITECTURE.md) 10절의 **체크포인트(같은 thread 재호출)** 가 이 저장소에 맞는지 통과 조건 5개로 확인한 기록이다. 결과에 따라 멀티턴에서 AI가 질문 이력을 이어 가는 방식(경로 A 체크포인트, 경로 B Spring 질문 이력)을 정한다. 이 문서는 AI 담당자의 검증 기록과 제안이며, 경로 선택과 계약 변경은 PR 리뷰를 거쳐 팀 기준이 된다.

## 1. 한 줄 결론

- 조건 1~4는 **조건부로 통과**했다. 체크포인트로 질문 이력을 이어 가는 것은 기술적으로 가능하다.
- 그러나 경로 A를 쓰려면 새 의존성·그래프 State 분리·쓰기 보호 래퍼·보관 삭제 작업·DB 권한 변경이 필요하고, **체크포인트가 무효화되는 경우의 복원은 어차피 Spring이 저장한 질문 이력(경로 B)이 있어야 한다**(3.2절 대조 실험). 그래서 A는 B 위에 비용을 더하는 방식이고 얻는 이점은 작다.
- **제안: 경로 B로 간다.** 단 조건 5의 문구("통과하지 못하면 경로 B")를 기계적으로 적용한 결과가 아니라 비용 대비 이득을 따진 판단이므로, 팀 리뷰에서 이의를 받을 수 있다.

## 2. 실행 환경과 방법

| 항목 | 값 |
|---|---|
| 실행일 | 2026-11-07 |
| DB | 로컬 Docker `pgvector/pgvector:0.8.7-pg18` (PostgreSQL 18.6), 데이터베이스 `hops_ai_runtime` 안의 임시 스키마 |
| 패키지 | `langgraph 1.2.16`, `langgraph-checkpoint 4.3.1`, `langgraph-checkpoint-postgres 3.2.0`, `psycopg 3.3.6`, Python 3.13 |
| 모델 | 호출하지 않음. 분석·검색·평가를 흉내 낸 가짜 노드 |
| 의존성 | **`pyproject.toml`·`uv.lock`은 바꾸지 않았다.** `uv run --with`로 임시 환경에만 설치했다 |

재현:

```bash
cd ai && uv run --with langgraph-checkpoint-postgres python -m spikes.checkpoint_spike
```

스크립트는 [ai/spikes/checkpoint_spike.py](../../ai/spikes/checkpoint_spike.py)다. `hops_ai_runtime`에 임시 스키마 `checkpoint_spike`와 임시 역할 `spike_app`을 만들고, 끝나면 지운다(실행 뒤 둘 다 남지 않은 것을 확인했다). pytest가 수집하지 않는 위치(`ai/spikes/`)라 CI에 영향이 없다.

**무엇을 실행했나.** 판단 루프를 `restore → analyze → retrieve → assess → route`로 줄인 **미니 그래프**에 Postgres 체크포인터를 붙였다. `restore`는 10절의 이어받기·무효화 규칙(요청 스냅샷 우선, `policyRevision` 불일치 시 폐기, 메시지 정정 시 해당 파생 값 폐기)을 최소로 옮긴 것이다. 메시지 본문은 그래프 State에 두지 않고 실행 설정으로만 전달해 ID·revision·digest만 남긴다. 각 조건을 **한 번씩** 실행했고 결과를 보고 코드를 고쳐 다시 맞추지 않았다.

## 3. 통과 조건별 결과

### 3.1 요약

| 조건 | 결과 | 비고 |
|---|---|---|
| 1. `ask` 뒤 저장, 같은 thread 재호출 시 노드 재실행·최신 응답 반영·질문 이력 유지 | 통과 | 3턴 실행 |
| 2. 버전 증가·정정·정책 변경 뒤에도 어긋나지 않음 | 통과 | 정책 변경 때는 Spring 이력이 필요 |
| 3. 멱등성·취소·기한이 지금과 같음 | **조건부** | 늦은 이전 실행이 최신 체크포인트를 덮어쓴다. 래퍼로 막았지만 원자적이지 않음 |
| 4. 보관·삭제·접근 권한 적용 | **조건부** | 라이브러리에 TTL이 없고 앱 계정에 DELETE 권한이 필요 |
| 5. 통과 못 하면 경로 B | 판단 필요 | 1절 참조 |

### 3.2 근거

**조건 1.** 첫 실행이 `ask`(시스템)로 끝나자 `checkpoints` 7행, `checkpoint_blobs` 21행, `checkpoint_writes` 27행이 저장됐다. 사용자 답(`inquiryVersion` 1→3)으로 같은 thread를 새 `runId`로 호출하면 `restore, analyze, retrieve, assess, route`가 다시 실행되고, 답이 분석에 반영되며, 질문 이력이 유지되어 이미 물은 `system`을 다시 묻지 않고 `taskOrScreen`을 물었다. 세 번째 실행은 답변으로 끝났고 이력 2건이 유지됐다. 실행별 키(`calls`, `usage`)는 입력으로 초기화해 매 실행 5회로 시작했다. 초기화하지 않으면 이전 실행 값이 남는다(LangGraph는 입력에 없는 키를 체크포인트 값으로 유지한다). 그래서 실행별 키 초기화를 코드가 명시해야 한다.

**조건 2.**
- 메시지 정정(revision 2, digest 변경): 정정된 메시지의 파생 값만 버리고 정정된 내용(`전자메일`)으로 다시 계산했으며 질문 이력은 유지됐다.
- `policyRevision`이 다르면 체크포인트를 버린다. 이때 **Spring이 준 질문 이력으로 복원하면** 같은 질문을 반복하지 않았고, **이력이 없으면** 같은 질문을 다시 했다(대조 실험). 즉 무효화 경로는 Spring 쪽 질문 이력에 의존한다. 이것이 경로 B의 저장이 A에서도 필요한 이유다.
- 참고: `analyze`는 매 실행 전체를 다시 계산하므로 체크포인트에서 실제로 재사용하는 값은 질문 이력뿐이다(분석·평가·검색 지문은 설계상 재계산 대상).

**조건 3.**
- 같은 `runId` 재접수: 기존 `RunLedger`가 막아(`created=False`) 그래프가 한 번만 실행됐다. 체크포인트는 이 경계와 독립이라 영향을 주지 않는다.
- 취소·기한 초과(`wait_for`): 두 경우 모두 `retrieve` 직전에 멈췄고(대기 노드 `('retrieve',)`), 새 입력으로 같은 thread를 호출하면 멈춘 지점을 이어 가지 않고 `restore`부터 다시 돌았다. 실행별 키도 새 실행 기준으로 시작했다.
- **늦은 이전 실행의 덮어쓰기:** 쓰기 보호가 없으면 느린 이전 실행이 새 실행보다 늦게 끝나면서 최신 체크포인트를 자기 상태(`inquiryVersion=1`)로 덮어썼다. 이후 재개가 낡은 상태를 읽게 된다. 라이브러리에는 compare-and-set이 없다. `aput`·`aput_writes`를 감싸는 래퍼로 "현재 실행이 아니면 쓰기 거부"를 붙이자 이전 실행이 중단되고 최신 체크포인트가 유지됐다.
- **한계:** 래퍼의 확인과 라이브러리의 쓰기는 같은 DB 거래가 아니다. 두 단계 사이의 경쟁은 이 실험이 재현하지 못했고 막는다고 말할 수 없다. 원자적 보호를 하려면 체크포인터를 직접 확장하거나 쓰기 SQL에 조건을 넣어야 한다.

**조건 4.**
- 본문 복제 없음: 메시지 본문의 표식 문자열이 세 표 어디에도 없었다(ID·digest만 저장하는 설계를 따랐을 때).
- 보관: 라이브러리에 TTL이 없다. 체크포인트 JSON의 `ts`를 기준으로 24시간 지난 thread를 앱 계정이 SQL로 지울 수 있었다(다른 thread는 유지). 지우는 작업(정기 실행)은 새로 만들어야 한다.
- 삭제: 문의 종료 시 `adelete_thread`로 세 표의 해당 thread 행이 모두 지워졌다.
- 접근: 앱 계정은 `public.ai_run_ledger` 조회, 스키마에 표 생성, 업무 DB `hops`의 `inquiry` 조회가 모두 `permission denied`였다. 표는 관리자(마이그레이터 역할)가 `setup()`으로 만든다. `setup()`이 `CREATE INDEX CONCURRENTLY`를 쓰므로 일반 거래 안에서 실행하면 안 된다.
- **현재 설정과 차이:** [03_app_privileges.sql](../../ai/db/03_app_privileges.sql)은 앱 계정에 `DELETE`를 주지 않는다. 체크포인터는 보관 삭제·`adelete_thread`에 `DELETE`가 필요하므로 새 마이그레이션과 권한 변경이 필요하다.

**참고: 실제 State.** 실제 `SupervisorState`(`AiRunRequest` 포함)는 체크포인트 직렬화기로 왕복된다. 다만 `AiRunRequest`가 허용 목록에 없는 타입이라 "미래 버전에서 차단된다"는 경고가 한 건 나왔다(허용 목록 등록 필요). 또 실제 그래프(`ai/src/hops_ai/supervisor/graph.py`)는 State 전체가 `state` 키 하나에 담겨 있어서, 그대로 체크포인트를 붙이면 입력 메시지 본문이 함께 저장될 수 있다(코드 읽기 근거이며 이 실험에서 실제 그래프로 측정하지 않았다). 본문 복제 금지 원칙을 지키려면 이어받을 값(질문 이력 등)과 실행별 값을 별도 채널로 나누는 State 개편이 필요하다.

## 4. 이 실험이 확인하지 못한 것

- 실제 그래프(`SupervisorRuntime`, 판정 모드)에 체크포인터를 붙여 실행하지 않았다. 미니 그래프로 LangGraph와 Postgres 체크포인터의 동작만 확인했다.
- 실제 모델, 실제 Spring 연동, 여러 AI 인스턴스에서의 동시 실행은 확인하지 않았다.
- 쓰기 보호 래퍼의 확인-쓰기 사이 경쟁, 저장 용량 증가, 체크포인트 정리(`aprune`)는 측정하지 않았다.
- 경로 선택의 비용 비교는 작업 항목을 나열한 판단이며 구현 시간을 측정한 것이 아니다.

## 5. 경로 A 도입 시 추가로 필요한 것

1. `langgraph-checkpoint-postgres` 의존성 추가 (팀 승인 필요. 이 스파이크에서는 추가하지 않음).
2. 그래프 State 분리(이어받는 값과 실행별 값), 직렬화 허용 목록 등록, 실행별 키 초기화 코드.
3. 쓰기 보호(원자적), `inquiryVersion`·실행 상태 확인.
4. 보관 삭제 정기 작업, 문의 종료 시 삭제 연결.
5. AI 런타임 DB 마이그레이션과 앱 계정 권한(`DELETE`) 변경.
6. 계약 S3·S4·S5 갱신(계약 변경 PR, 팀 리뷰).
7. 무효화 경로를 위한 Spring 질문 이력 저장(= 경로 B의 작업).

## 6. 제안과 다음 단계

- **제안: 경로 B.** Spring이 `questionBundles`와 물은 항목을 저장하고 다음 실행 입력으로 돌려주며, AI는 그 이력에서 `asked`를 만든다. 질문 이력은 두 경로 모두 필요한 공통분모이고, 체크포인트가 대신해 주는 것이 질문 이력 외에는 없다.
- 이 경로에서는 의존성 추가가 없으므로 의존성 승인은 필요하지 않다. 계약 S5는 바뀌지 않는다. 대신 Spring→AI 입력에 질문 이력(예: 문제별 물은 항목)을 싣는 **하위 호환 필드**를 계약 변경 PR로 올려 Spring·AI 담당자 리뷰를 받는다.
- 나중에 질문 이력 외의 AI 내부 상태를 실행 사이에 유지할 필요가 생기면 이 스파이크 결과를 근거로 경로 A를 다시 검토한다.
