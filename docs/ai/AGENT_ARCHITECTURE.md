# 에이전트 아키텍처 (목표 설계)

AI 서버의 에이전트 구조를 어떻게 바꿀지 정리한 **검토안**이다. [AI 서버 정리 계획](CLEANUP_PLAN.md)이 진단과 결정을 다룬다면, 이 문서는 정리 뒤에 만들 **목표 구조**를 정한다. 제품 정책은 [PRD](../PRD.md), 역할 경계와 State 계약은 [에이전트 계약](../../contracts/agents/README.md), 전송 형식은 [공통 계약](../../specs/contracts/README.md)이 정하며 이 문서가 대체하지 않는다. 이 문서는 PR 리뷰를 거쳐 병합된 뒤에 팀 기준이 된다. 병합 전까지는 AI 담당자의 제안이며, Spring·프론트의 계약 변경은 해당 영역 담당자의 리뷰를 받는다(11절).

진단 수치와 코드 근거는 `develop` `56068b5` 기준이다. 모델 호출 수·지연 같은 값은 **측정 전 추정**이라고 표시한다.

## 1. 목적과 범위

- **정하는 것:** 에이전트의 책임과 입출력, 그래프 구조, State 키의 소유권과 검증 경계, 관계 데이터의 역할, 접근 범위 분리, LangGraph 기능을 쓸 곳, Spring 쪽에 필요한 변경 목록.
- **정하지 않는 것:** 단일 에이전트와의 비교 실험(범위에서 제외), 프롬프트 문구, 임베딩·Neo4j의 성능 개선(2차 목표), 권한·한도 같은 하네스 강화(기능 구현 뒤).
- **PRD와 다른 점:** PRD 228행은 "Supervisor는 모델 판단으로 다음 처리를 선택한다"고 정한다. 이 문서는 그 정책을 유지하되 Supervisor를 모든 단계가 아니라 **분기점**에서만 부른다(5절). 그 밖의 차이는 12절에 모았다.

## 2. 목표 흐름

임직원의 문의가 들어오면 다음 순서로 처리한다. 한 번의 사용자 메시지가 한 번의 실행이며, 질문을 보낸 뒤에는 사용자 응답을 기다린다.

1. **Supervisor**가 문의를 받아 **Inquiry**에게 전달한다.
2. **Inquiry**가 문의를 분석(키워드, 유형, 시스템·기능 후보, 사실)하고 유형별 표준 양식을 채워 State를 갱신한다.
3. **Knowledge**가 지식 베이스와 관계 데이터에서 관련 정보를 검색하고, 검색 내용으로 정보가 **충분한지 판단**해 의견과 함께 State를 갱신한다.
4. **Supervisor**가 받아서 결정한다.
   - 충분하면 **답변**한다.
   - 불충분하면 **Inquiry**가 표준 양식의 빈 곳과 관계 데이터(무엇을 물으면 문의가 구체화되는지)를 참고해 **추가 질문**을 만든다.
5. AI가 답변 또는 질문을 보내고, 사용자가 답하면 **새 실행**이 같은 문의의 상태를 이어받아 2~4를 다시 돈다(5.1절의 재개 경로).
6. 답변으로 해결되지 않으면 **Ticket**이 티켓을 만들고 담당자를 배정한다(저장·배정의 확정은 Spring).
7. 담당자가 해결하면 **Curator**가 문의 전체 과정을 참고해 지식 표준화 양식의 **초안**을 만든다. 담당자가 수정·승인하면 지식 베이스와 관계 데이터에 저장한다(관계는 Curator가 판단한 것을 승인된 범위에서). 이렇게 쌓인 지식이 다음 문의 처리에 쓰이는 **선순환 구조**다.

## 3. 설계 원칙

1. **에이전트는 판단하고 자기 키만 쓴다.** 에이전트는 State의 일부(자기 소유 키)만 담은 패치를 반환한다. 계약 S3이 이미 "노드는 검증된 patch를 반환하고 키별로 병합한다"고 정하고 있다.
2. **검증은 에이전트 밖에서 한다.** 에이전트의 출력은 모델 출력이므로 신뢰하지 않는다. 권한·출처·digest·인용 대조·한도는 에이전트가 건너뛸 수 없는 병합 단계(reducer 또는 검증 노드)가 맡는다.
3. **모델은 언어와 판단, 코드는 구조와 한도.** 질문의 문장과 충분성 판단은 모델이 맡고, 물을 수 있는 필드·질문 횟수·공개 범위·티켓 전환 조건은 코드가 강제한다.
4. **합법한 전이는 그래프가 정한다.** 그래프의 조건부 엣지가 각 지점에서 허용되는 분기를 정하고, Supervisor의 모델은 그 안에서만 고른다.
5. **사용자에게 보이는 텍스트는 검증된 뒤에만 나간다.** 모델 토큰을 검증 전에 스트리밍하지 않는다.
6. **업무 정본은 Spring이다.** AI의 State는 한 실행(또는 AI 내부 작업 기억)이며 업무 DB를 대체하지 않는다. 입력 스냅샷이 항상 우선한다.
7. **직원 상담의 모델 입력과 응답은 서버가 확인한 사용자·목적 범위(SEC-09) 안의 자료만 쓴다.** 담당자 전용 자료를 직원 상담의 모델 입력에 쓰는 것은 기본이 아니며, 별도로 승인된 내부 판단 경계가 있을 때만 켠다(9절). 켜더라도 모델 출력이 직원에게 닿는 경로는 승인된 직원 공개 항목으로 제한한다(7.2, 8절).

## 4. 현재 구조와의 차이

`develop` 기준으로 코드와 계약을 대조한 결과다.

| 영역 | 현재 | 목표 |
|---|---|---|
| 그래프 | `decide → execute → finish` 3노드. `execute` 한 노드가 4개 역할을 처리해 그래프 위에서 보이지 않음 | 역할·단계가 노드(서브그래프)로 보임 |
| State | 그래프 State와 별개로 `analyze()` 안 `nonlocal current`에도 State를 들고 `sync_state`로 맞춤 | State 하나, 키별 소유 |
| Supervisor | 매 루프 모델 호출. 최근 1주 `ai/` fix 39개 중 7개가 "이 상태에서 이 역할을 못 고르게" 제한 | 분기점에서만 호출, 합법 전이는 엣지 |
| Knowledge | 모델 호출 없음. GUIDE 근거가 있으면 안내, 없으면 EMPTY. 원인 후보·관계 조회 미포함 | 충분성 판단(`assessment`), 원인 후보·다음 확인, 관계 조회 |
| Inquiry | 모델은 사실 추출만. 질문은 `forms.py`가 필드를 고르고 **고정 문구**(`FIELD_PROMPTS`)로 만듦. 키워드·기능 후보 없음 | 분석 확장 + 질문 생성(모델), 구조 제약은 코드 |
| 관계 데이터 | `pgvector.py`·`neo4j.py`는 자리 클래스 | `RelationSource`, 1차는 SQL 구현 |
| 접근 범위 | 직원 상담은 `allowedDocumentScopes=["EMPLOYEE"]`. AI도 직원 상담에서 비직원 근거가 State에 있으면 거부(`validate_evidence_scope`) | **기본은 현재와 같이 직원 공개 자료만**(SEC-09). 담당자 전용 자료를 평가에 쓰는 내부 판단 경계는 보안 개정·리뷰 뒤 옵션(9절) |
| Curator 입력 | 해당 문제의 **사용자 메시지**와 처리 기록 한 건(`CurationInputFactory`). 관계는 `APPLIES_TO`만 생성 | 문의 전체 과정, 관계 판단 확장(`ADDRESSES`, `USES_CHECK`는 계약에 이미 있음) |
| 멀티턴 | 질문 이력·문제 상태가 실행 사이에 이어지지 않음 | 체크포인트로 같은 thread를 다시 호출(5.1·10절). 세부는 #189에서 |

## 5. 그래프 구조

### 5.1 상담 그래프 (`INQUIRY_ANALYSIS`)

```
START → analyze ─┬─ 검색 필요 ──→ retrieve ─┬─ 1건 이상 ──→ assess ─┐
                 │                          └─ 0건·오류 ────────────┤
                 └─ 검색 불필요 ─────────────────────────────────────┴→ route ─┬─ answer ─→ END
                                                                                ├─ ask ────→ END
                                                                                ├─ ticket ─→ END
                                                                                ├─ hold ───→ END   (시스템 확인 대기)
                                                                                └─ close ──→ END   (범위 밖)
```

| 노드 | 담당 | 모델 호출 | 쓰는 키 | 검증(에이전트 밖) |
|---|---|---|---|---|
| `analyze` | Inquiry 분석 | 1회 | problems(분석·양식), analysis | 인용 대조(P6), 모름 선언 대조, 문제 분리 규칙 |
| `retrieve` | Knowledge 검색 | 0회 | evidence, searches(상태·질의 지문) | 접근 범위·digest, 0건/오류 구분(P2) |
| `assess` | Knowledge 평가 | 1회(검색 결과가 1건 이상일 때만) | assessments | 근거 ID가 검색 결과에 있는지, 닫힌 어휘(7.2절) |
| `route` | Supervisor | 1회(선택지가 둘 이상일 때만) | decisions | 합법 전이(5.3절) |
| `answer` | 답변 조립 | 0회(v1) | guide, answer | 직원 공개 근거만, 누출 검사(P1) |
| `ask` | Inquiry 질문 생성 | 1회 | questions | 필드 제약, 반복·한도(P7·P8), 누출(P1) |
| `ticket` | Ticket | 1회 | ticketProposals, ticketCreationResults | Spring 도구 결과 |
| `hold` | 시스템 확인 대기 결과 조립 | 0회 | problems(미확인 보존) | 질문·티켓을 만들지 않음, 누출 검사(P1) |
| `close` | 범위 밖 결과 조립 | 0회 | problems(범위 밖), answer(범위 안내) | 고정 범위 안내 문구, 누출 검사(P1) |

- **`hold`·`close`는 모델을 부르지 않는 결과 조립 노드다.** `WAITING_SYSTEM`·`OUT_OF_SCOPE` 같은 문제 상태의 저장과 집계는 Spring이 한다([에이전트 계약](../../contracts/agents/README.md)의 시스템 미확인·범위 밖 규칙). AI는 `hold`에서 시스템을 미확인으로 보존한 문제 제안만 돌려주고 질문·티켓은 만들지 않으며, `close`에서 범위 밖 문제 제안과 범위 안내를 돌려준다.
- **여러 문제:** 문제가 둘 이상이면 `retrieve → assess`를 문제별로 병렬 실행한다(LangGraph `Send`). `route`는 문제별 행동을 한 번에 정한다. 한 실행의 결과에 문제 A는 답변, 문제 B는 질문이 함께 들어갈 수 있다(현재 계약과 같다).
- **생략 규칙(불필요한 모델 호출을 막는다):**
  - **검색 불필요:** 의도별 정책 표의 "검색할 지식 종류"가 비어 있는 문의(기능 추가·개선 요청·범위 밖)는 `retrieve`·`assess`를 건너뛰고 `route`로 간다. 필수 정보가 확보된 기능 요청은 평가 없이 질문 또는 티켓으로 진행한다. 사용법·권한 신청·현상 문의는 검색한다.
  - **0건·오류:** `retrieve`가 0건이면 `assess`를 호출하지 않고 코드가 `NO_MATCH`로 확정한다. 검색 오류는 평가하지 않고 기존 규칙대로 안전하게 처리한다(P2).
  - **평가 불가:** 평가 모델 오류나 검증 거부는 그 문제의 `assessment`를 "없음"으로 두고 `route`로 넘긴다. 평가가 없는 문제에는 답변을 선택할 수 없고 질문·티켓·대기·범위 밖 규칙으로 진행한다. 평가 실패가 티켓 경로를 막지 않는다(예산 소진 같은 실행 한도 초과는 지금처럼 실패 처리).
  - **라우팅:** 선택지가 하나뿐이면 Supervisor 모델을 호출하지 않고 그 행동을 따른다.
- **모델 호출과 예산:** 분석 1회는 항상, 평가·라우팅·질문은 경로에 따라 0~1회씩이라 한 실행에 대체로 1~4회가 될 것으로 추정한다(측정 전). 지금은 Supervisor 판단이 역할 호출마다 1회씩 붙는다.
  - **최악의 경우는 실행당 한도 안이다.** 평가는 문제마다 한 번씩 호출하지만 한 번의 분석이 새로 만드는 문제는 현재 코드에서 최대 3개다(`MAX_PROBLEMS`). 분석 1 + 평가 3 + 라우팅 1 + 질문 1 = 6회로 `maxModelCalls`(8, 재시도 포함)를 넘지 않는다. 한도나 문제 수 상한이 바뀌면 이 계산을 다시 한다.
  - **예산 가드.** 코드는 `assess`를 부르기 전에 남은 호출 예산에서 이후 필수 호출(라우팅·질문 최대 2회)과 재시도 여유를 뺀 만큼만 평가를 호출한다. 이어받은 문제가 많아 예산이 모자라면 나머지 문제는 평가 불가로 두고(위 "평가 불가") 질문·티켓 규칙으로 진행한다. 예산 부족이 `BUDGET_EXCEEDED` 실패로 이어지지 않는다.
  - 회귀 테스트: 검색 결과가 있는 현상 문제 3개가 각각 질문을 필요로 하는 입력이 한도를 넘지 않는다. 예산을 줄여 평가를 건너뛰게 해도 모든 문제에 유효한 결과가 반환된다.
- **종료와 재개 경로:** `answer`·`ask`·`ticket` 뒤에는 현재 실행이 끝난다. 질문(`ask`)을 돌려준 실행은 `END`로 끝나고 상태가 체크포인트에 남는다. 사용자의 응답은 Spring의 **새 실행**(`runId`)으로 들어오며 같은 thread(`inquiryId`)에서 `START → analyze`부터 다시 시작한다. 입력은 최신 요청 스냅샷이고(10절 원칙) 이전 질문 이력·분석은 체크포인트에서 이어받는다. 따라서 응답 뒤에도 `analyze → retrieve → assess → route`가 필요한 만큼 다시 실행된다. `interrupt`는 같은 실행 안에서 사용자 입력을 기다릴 때 쓰는 기능인데 Spring이 메시지마다 실행을 만드는 현재 모델과 맞지 않아 기본안으로 쓰지 않는다.

### 5.2 사례 그래프 (`CASE_DRAFT`)

```
START → collect → draft → link → validate → END
```

- `collect`: 문의 전체 과정(사용자·AI 메시지, 같은 티켓의 처리 기록, 해결 확인, 사용한 근거)을 모은다.
- `draft`: 지식 표준화 양식 초안. `link`: 기존 시스템·기능·증상·원인·확인 항목에 연결할 관계 후보를 판단한다.
- 담당자의 수정·승인은 **그래프 밖(Spring)**에서 한다. 사람의 응답 대기는 몇 시간~며칠이 될 수 있고 승인된 버전의 정본은 Spring이다. 승인된 뒤의 색인은 Spring이 요청한다([에이전트 계약 I1](../../contracts/agents/README.md)).

### 5.3 합법 전이 (`route`의 선택지)

`route`는 문제마다 아래 조건을 만족하는 행동만 선택지로 받는다. 선택지는 코드가 계산하고 모델은 그중에서 고른다.

| 행동 | 조건 |
|---|---|
| 답변 | `assessment.verdict = SUFFICIENT`이고 직원 공개 근거 ID가 있음. 평가가 없는 문제(검색 생략·0건·평가 불가)에는 선택할 수 없음 |
| 질문 | 그 문제의 남은 질문 횟수 > 0 이고, 물을 수 있는 필드 또는 평가의 부족한 정보가 있음 |
| 티켓 | (a) 처리 요청 의도(권한·기능 추가·개선)이고 필수 정보 확보(검색이 불필요한 의도는 평가 없이 바로 선택 가능), 또는 (b) 보고 시스템이 정해졌고 답변을 선택할 수 없으며(평가가 `INSUFFICIENT`·`NO_MATCH`·`PARTIAL`이거나 평가 불가로 없음, 또는 `SUFFICIENT`여도 직원 공개 근거 ID가 없음) 질문을 더 할 수 없음(횟수 소진·물을 필드 없음·모름), 또는 (c) 안내 뒤 사용자가 미해결로 응답하고 다른 근거가 없음 |
| 시스템 확인 대기 | 보고 시스템이 정해지지 않았고, 사용자가 모른다고 답했거나 질문을 더 할 수 없음(횟수 소진·물을 필드 없음). 에이전트 계약은 5회 후 시스템 미확인을 `WAITING_SYSTEM`으로 보존한다고 정하므로 명시적인 모름 응답이 없어도 소진이면 대기로 끝난다 |
| 범위 밖 | 의도가 범위 밖 |

문제당 질문은 5회를 넘지 않는다. 모델의 판정은 라우팅의 입력일 뿐이며, 한도·전환 조건은 코드가 갖는다.

**모든 입력에는 합법한 행동이 하나 이상 있어야 한다.** 문제마다 다음 순서로 끝난다.
- 의도가 범위 밖이면 범위 밖.
- 시스템이 정해지지 않았으면 질문이 가능할 때 질문, 아니면 시스템 확인 대기(평가 유무와 무관).
- 시스템이 정해졌으면 답변 조건을 만족할 때 답변, 아니면 질문이 가능할 때 질문, 아니면 티켓(b).

검색 오류는 이 표 밖이며 P2 규칙에 따라 안전하게 실패 처리한다. 선택지가 비는 입력이 있으면 설계 오류이므로 회귀 테스트로 막는다. 최소한 다음 입력을 포함한다.
- 현상 문의에서 평가를 실패시키고 질문 횟수와 물을 필드를 모두 소진한 입력(시스템 확정): 티켓이 선택되고 무효한 답변은 선택되지 않는다.
- 평가 실패, 시스템 미확정, `questionCount=5`, 물을 필드 없음, 명시적 모름 응답 없음인 입력: 시스템 확인 대기가 선택되고 무효한 답변·티켓은 선택되지 않는다.

## 6. State 설계

### 6.1 키 소유와 패치

| 키 | 소유(쓰는 주체) | 병합 규칙 |
|---|---|---|
| `input` | 실행 접수 검증기 | 읽기 전용 |
| `problems`, `analysis` | Inquiry | 기존 문제 ID 유지, 신규는 `new:` 참조. 이전 확인 사실을 누락하면서 교체 불가 |
| `questions` | Inquiry(질문 생성) | 같은 키·같은 내용은 no-op, 다르면 오류 |
| `evidence`, `searches` | Knowledge(검색) | 같은 ID에 다른 내용·버전은 오류. 검색 상태는 FOUND/EMPTY/ERROR를 구분해 보존 |
| `assessments` | Knowledge(평가) | 문제당 하나, 같은 실행에서 같은 질의에는 다시 평가하지 않음 |
| `decisions` | Supervisor(`route`) | 선택지 안의 행동만 |
| `guide`, `answer` | 답변 조립(코드) | FINALIZING에서 한 번 고정 |
| `ticketProposals`, `ticketCreationResults` | Ticket | 문제당 최종 유효 제안, 생성 결과는 Spring 도구 결과만 |
| `caseProposal` | Curator | `CASE_DRAFT`에서만 |
| `phase`, `usage`, `eventSeq`, `cancellation`, `error`, `finalResult` | 실행기만 | 단일 작성자. 병렬 실행에서도 last-write-wins를 쓰지 않음 |

- 에이전트별 패치 타입을 분리한다(`InquiryPatch`, `KnowledgePatch`, `TicketPatch`, `CuratorPatch`). 타입에 자기 키만 있으므로 **소유권을 타입으로 강제**한다.
- 병합은 LangGraph의 reducer 또는 노드 뒤 `validate` 단계에서 한다. 에이전트는 이 단계를 건너뛸 수 없다. 현재 `merge_*_result`와 `validation.py`의 검증 로직을 재사용하며 규칙은 줄이지 않는다.
- `analysis`와 `assessments`, `searches`는 새 키다. 사용자에게 직접 나가지 않는 내부 키이므로 wire(AiResult)에는 필요한 요약만 싣는다.

### 6.2 State를 하나로

현재의 closure 복사본(`nonlocal current`)을 없애고 그래프 State를 단일 정본으로 삼는다. 실패 결과를 만들 때도 그래프가 마지막으로 확정한 State를 쓰고, 예산·취소 정보는 실행기가 State 키에 직접 반영한다.

## 7. 에이전트별 설계

### 7.1 Inquiry

**분석 모드(`analyze`).** 현재 `ExtractedProblem` 필드(요약, 의도, 시스템, 인용된 값, 모름 선언)에 다음을 더한다.
- `keywords`: 검색과 관계 조회에 쓸 핵심어(개수·길이 제한).
- `featureCandidates`: 요청의 시스템 기능 ID 후보. `AiRunRequest.systems`의 기능 목록 안에서만 고른다.
- 유형별 표준 양식(`forms.py`의 필드)을 채우고, 값마다 원문 인용을 붙인다. 인용 없는 값은 확보로 세지 않는다(P6).

**질문 생성 모드(`ask`).** 입력은 다음이다.
- 양식에서 물을 수 있는 필드 목록(코드가 계산: 아직 모르고, 이미 묻지 않았고, 모른다고 하지 않은 필드, 순서 포함)
- Knowledge의 `missingInformation`
- 관계 데이터의 이웃: 이 증상의 원인 후보를 가르는 확인 항목 중 **직원 공개로 승인된 것**과 그 **직원용 질문 문구**(8절). 담당자 전용 확인 항목은 이 입력에 넣지 않는다
- 질문 이력과 남은 횟수

출력은 질문 묶음(필드 3개 이하와 질문 문장)이다. 코드가 강제하는 것: 필드가 물을 수 있는 목록 안에 있음, 이미 물었거나 모른다고 한 필드 제외(P7), 한 묶음 3필드 이하, 문제당 5회 이하(P8), 질문에 담당자 전용 내용이 나오지 않음(P1), 질문 입력에 직원 공개로 승인되지 않은 확인 항목이 없음(P12). 시스템이 정해지지 않았으면 시스템을 가장 먼저 묻는다. 질문 순서·한도는 코드가 정한다는 [문의 양식](../knowledge/INQUIRY_FORMS.md)의 합의는 유지하고, **문장**만 모델이 쓴다.

### 7.2 Knowledge

**검색(`retrieve`).** 질의는 문제 자신의 정보(키워드, 확인된 값)로 만들고, 다른 문제의 단어가 섞이지 않게 한다(현재 `_build_query` 규칙 유지). 지식 베이스 검색과 관계 조회(8절)를 함께 하며, 검색 범위는 서버가 확정한 접근 문맥만 쓴다. 직원 상담의 기본 프로필에서는 직원 공개 자료와 직원 공개로 승인된 관계 항목만 읽는다(9절). 0건과 오류는 구분해 기록한다.

**평가(`assess`).** 검색 결과로 정보가 충분한지 판단한다. 출력 `assessment`(제안, 문제당 하나):

```json
{
  "problemRef": "…",
  "verdict": "SUFFICIENT | PARTIAL | INSUFFICIENT | NO_MATCH",
  "supportingEvidenceIds": ["…"],
  "missingInformation": [{ "kind": "FIELD | CHECK_ITEM", "ref": "taskOrScreen | <관계 확인 항목 ID>" }],
  "candidateCauses": [{ "text": "…", "evidenceIds": ["…"], "confirmed": false }],
  "nextChecks": [{ "checkItemId": "…" }],
  "rationale": "내부용, 사용자에게 보이지 않음"
}
```

검증(에이전트 밖):
- `supportingEvidenceIds`와 `evidenceIds`는 이번 검색의 검증된 근거에 있어야 한다.
- `SUFFICIENT`는 직원 공개(`EMPLOYEE`) 근거 ID를 가져야 한다. 없으면 거부한다(안내를 만들 수 없는 판정).
- `missingInformation`은 **닫힌 어휘**다. 양식 필드 이름이거나 관계 데이터의 확인 항목 ID만 허용하고 자유 문장을 허용하지 않는다. `CHECK_ITEM`은 **직원 공개로 승인된 확인 항목만** 허용한다(담당자 전용 확인 항목은 `nextChecks`로만 쓰고 직원 질문 입력에 넣지 않는다). 옵션 프로필(9절)에서 담당자 전용 문서를 읽은 평가가 직원에게 닿는 경로를 이렇게 닫는다.
- `candidateCauses`는 항상 `confirmed: false`이다. 과거 사례·관계 의존을 현재 원인으로 확정하지 않는다(계약 검증 규칙).
- `rationale`은 직원 응답에 쓰지 않는다.

**직원에게 가는 안내문(2단계).**
- v1: 모델은 판정과 근거 선택만 한다. 안내문은 현재처럼 승인된 근거 본문으로 코드가 조립한다. 환각 위험이 없다.
- v2: 모델이 근거 안에서 안내문을 쓰고, 코드가 인용·권한·누출을 검사한다. 평가에서 v1보다 나을 때만 켠다.

### 7.3 Supervisor (`route`)

문제별 행동을 정하는 한 번의 모델 호출이다. 입력은 문제별 분석 요약, 평가(`verdict`, 부족한 정보), 남은 질문 횟수, 이전 응답의 해결·미해결 여부다. 출력은 문제별 행동 제안이며 5.3절의 선택지 안에서만 유효하다. 실행기는 시간·호출·토큰·재시도 한도를 강제하고 에이전트끼리 직접 호출하지 못하게 한다(PRD).

### 7.4 Ticket

현재 구조를 유지한다. 모델이 제안을 만들고 Spring 도구가 생성·조회를 확정하며, 미생성이 확인된 뒤에만 제한된 재시도를 한다([Ticket 도구 계약](../../contracts/agents/TICKET_TOOLS.md)). 호출 조건만 5.3절에 맞춘다. 서브그래프로 `제안 → 생성 → 확인·재시도`를 나눌 수 있다.

### 7.5 Curator

- **입력 확장(Spring):** 해당 문제의 사용자 메시지에 더해 AI 질문·답변, 같은 티켓의 처리 기록 전부(진행·실패 시도 포함), 해결 확인 이력, 상담에 쓴 근거 ID. 권한 필터는 유지한다.
- **초안:** 지식 표준화 양식(증상, 확인된 원인, 조치, 검증, 적용 조건, 한계). 원인·조치·검증은 처리 기록의 값을 그대로 쓰고 모델이 만들지 않는다(현재 규칙 유지).
- **관계 판단(`link`):** 계약의 `APPLIES_TO`, `ADDRESSES`, `USES_CHECK`로 기존 노드에 연결할 후보를 근거와 함께 제안한다. 새 개념·관계 유형을 임의로 게시하지 않으며, 담당자 승인 전에는 검색에 공개되지 않는다.

## 8. 관계 데이터

관계 데이터는 상담 흐름에 직접 들어간다. Knowledge는 증상에서 가능한 원인과 확인 항목을 찾고, Inquiry는 어떤 확인 항목을 물어야 문의가 구체화되는지 안다.

- **인터페이스:** `RelationSource`를 둔다. `KnowledgeSource`처럼 구현을 바꿀 수 있게 한다.
  - 입력: 키워드·기능 후보·시스템(접근 범위는 서버가 정함)
  - 출력: 증상 → 가능 원인 → 확인 항목 → 직원용 질문 문구 → 승인 사례의 이웃, 각 항목의 근거(문서 ID·버전), 공개 범위, 승인 상태
- **1차 구현:** Spring이 관리하는 SQL 테이블(증상·원인·확인 항목·관계)로 구현한다. 시드는 지식 문서의 front matter와 사례에서 생성한다([데이터 형식](../knowledge/DATA_FORMAT.md)의 그래프 시드 노드: `System`, `Feature`, `Symptom`, `Cause`, `CheckItem`, `QuestionTemplate`, `Resolution`).
- **교체:** Neo4j는 같은 인터페이스 뒤로 2차에 교체한다. PRD는 Neo4j를 MVP 필수로 정했으므로 이 1차 구현이 PRD와 다른 점은 12절에 적는다.
- **직원용 질문 문구(`QuestionTemplate`)와 공개 표시:** 모든 노드와 관계는 공개 범위(`EMPLOYEE`/`SYSTEM_STAFF`)와 승인 상태를 가진다. `CheckItem`과 `QuestionTemplate`은 직원에게 질문으로 나갈 수 있는지(`employeeDisclosable`)를 별도로 가지며, 승인되고 직원 공개인 항목만 질문 입력에 들어간다. `ask`는 담당자 전용 문서 본문이 아니라 이 항목의 ID와 승인된 문구만 본다. 공개 표시가 없거나 승인되지 않은 항목은 직원 상담에서 쓰지 않는다.
- **원칙:** 연결은 후보다. 연결만으로 현재 문의의 원인을 확정하지 않는다. 근거 없는 연결은 만들지 않는다. 승인되지 않은 관계는 검색에 공개하지 않는다.

## 9. 접근 범위와 내부 판단 경계

[보안 개발 명세](../SECURITY.md)의 SEC-09는 서버가 확인한 현재 사용자·목적·시스템 범위에 맞는 결과만 검색, 관계 탐색, **모델 입력**, 응답에 쓰도록 요구한다. LLM02는 내부 런북이 모델·답변에 전달되는 것을 위험으로 본다. 현재 AI도 직원 상담에서 비직원 근거가 State에 있으면 거부한다(`supervisor/validation.py`의 `validate_evidence_scope`). 이 문서의 **기본안은 이 요구를 그대로 지킨다.**

**기본 프로필(SEC-09 준수).** 직원 상담의 검색, 평가, 질문 생성, 답변은 모두 직원 공개 자료와 직원 공개로 승인된 관계 항목만 쓴다. `accessContext`는 지금과 같고(`retrievalScopes`를 추가하지 않거나 `allowedDocumentScopes`와 같다), `validate_evidence_scope`도 바뀌지 않는다. 담당자 전용 지식(런북·사례)은 담당자가 보는 흐름(담당자 상담 `SYSTEM_WORK`, 티켓 처리 화면, Curator)에서만 쓴다. 이 프로필에서 2절의 흐름이 동작하려면 관계 데이터의 확인 항목과 질문 문구를 **직원 공개로 승인된 형태**로 둔다(8절, #191 ⑤). 평가는 직원 공개 자료로 충분성을 판단한다.

**옵션 프로필(내부 판단 경계, 기본 꺼짐).** 직원 상담에서도 담당자 전용 자료를 `assess`의 모델 입력으로 읽는 것이다. 다음을 모두 만족할 때만 켠다.
1. [보안 개발 명세](../SECURITY.md)에 서버가 확정한 별도 목적(예: 내부 판단)을 SEC-09·LLM02 요구와 함께 명시하는 개정과 보안 리뷰.
2. 서버가 확정하는 설정으로만 켜고(요청·모델이 켤 수 없음) 기본은 꺼짐. `accessContext.retrievalScopes`(가산 필드)를 서버가 확정하고, 평가·로그에서 내부 판단 사용을 구분한다.
3. 직원에게 닿는 경로는 승인된 직원 공개 확인 항목과 질문 문구뿐이다(7.2, 8절). 담당자 전용 항목의 ID·의미가 질문 생성 입력과 직원 질문에 들어가지 않는지 검사한다(P12). 식별 문구 검사(P1)만으로는 임의 확인 항목의 의미가 새는 것을 막지 못하므로, 공개 표시와 승인 상태를 코드가 강제한다.

기능 구현을 먼저 하더라도 기본 프로필로 시작하고, 옵션 프로필은 별도 결정으로 다룬다. 직원 응답의 누출 검사(P1)는 두 프로필 모두에서 유지한다.

## 10. LangGraph 기능을 쓰는 곳

설치된 `langgraph 1.2.16`에서 `Send`, `interrupt`, `Command`, `RetryPolicy`, `InMemorySaver`와 스트림 모드(`values`, `updates`, `custom`, `messages` 등)를 import로 확인했다. `langgraph-checkpoint-postgres`는 설치돼 있지 않다.

| 기능 | 쓰는 곳 | 판단 |
|---|---|---|
| 노드·조건부 엣지 | 5절 그래프. 합법 전이를 엣지로 코드화 | **적용.** 가드 함수를 줄인다 |
| 서브그래프 | Inquiry(분석 / 질문 생성), Knowledge(검색 → 평가), Ticket(제안 → 생성 → 확인), Curator(수집 → 초안 → 관계) | 역할 내부 단계마다 독립 상태·이벤트·테스트. Knowledge·Inquiry부터 |
| `Send` | 복합 문의의 문제별 `retrieve → assess` 병렬 실행 | 지연 감소 기대(측정 전). 단일 작성자 키(`usage` 등)는 병렬에서도 실행기만 쓴다 |
| 스트리밍 | 노드 경계의 진행 이벤트(SSE) | **적용.** 진행 문구는 고정 문구이며 모델 출력을 쓰지 않는다 |
| 체크포인트(thread 재호출) | `ask`로 끝난 실행의 상태를 저장하고, 다음 사용자 메시지의 새 실행이 같은 thread(`inquiryId`)에서 `START`부터 시작해 AI 내부 파생 상태를 이어받음 | **스파이크 후 확정.** 아래 |
| `interrupt` | - | 기본안으로 쓰지 않는다. 같은 실행 안에서 입력을 기다릴 때만 의미가 있고, 메시지마다 새 실행인 Spring 모델과 맞지 않는다 |
| 체크포인트(재현) | 평가 하네스에서 특정 노드 직전부터 다시 실행해 프롬프트 변경을 비교 | `InMemorySaver`로 바로 가능. 실모델 비용을 줄임 |
| `RetryPolicy` | - | 쓰지 않는다. `BudgetedLLMClient`가 예산을 아는 재시도를 이미 한다 |

**스트리밍 규칙.** 직원에게 보이는 텍스트는 검증이 끝난 뒤에 조각내어 보낸다(현재 `answerChunkSeq` 방식). 모델 토큰을 그대로 흘리는 `messages` 모드는 사용자 텍스트에 쓰지 않는다. 검증 전 문구가 노출되기 때문이다.

**체크포인트 원칙(안).**
- `thread_id = inquiryId`. 각 사용자 메시지에 대한 Spring의 한 실행이 같은 thread의 한 번의 호출이다(`START`부터 시작하고 상태는 체크포인트에서 이어받는다. `runId`, 멱등성, 기한은 그대로 실행 단위).
- **요청 스냅샷이 우선한다.** 체크포인트는 AI 내부 파생 상태(분석 결과, 평가, 질문 이력, 검색 지문)만 보관하고, 문의·메시지·문제의 업무 사실은 매번 요청에서 가져온다.
- **버전이 다르다는 이유만으로 버리지 않는다.** 새 사용자 메시지나 정정을 저장할 때마다 `inquiryVersion`이 1 오른다([WIRE 계약](../../specs/contracts/WIRE_CONTRACT.md) 6절, 12.8절). 그래서 `inquiryVersion`이 다르면 버리는 규칙은 재개마다 질문 이력을 버리게 된다. 체크포인트에는 마지막으로 반영한 `inquiryVersion`과 입력 메시지의 `(id, revision, digest)` 목록을 함께 저장하고, 재개 때 아래로 판단한다.
  - 요청의 메시지가 체크포인트의 메시지를 그대로 포함하고 새 메시지만 뒤에 붙었으면(append-only) 체크포인트를 이어받는다. 질문 이력처럼 재사용할 파생 상태는 유지하고, 분석·평가는 최신 스냅샷으로 `START → analyze`부터 다시 계산한다.
  - 이전 메시지가 정정·대체돼 `revision`이나 digest가 달라졌으면 그 메시지에서 나온 파생 값(해당 문제의 분석·평가·검색 지문)만 버리고 다시 계산한다. 질문 횟수는 정정으로 초기화되지 않으며(에이전트 계약) 횟수의 정본은 요청의 `questionCount`다.
  - `policyRevision`이 다르거나 요청의 문제 목록이 체크포인트와 맞지 않으면 체크포인트 전체를 버리고 요청에서 다시 계산한다. 이때 이미 물은 필드 목록은 Spring이 저장한 질문 이력(#189 원안)에서 복원해야 하며, 복원할 수 없으면 아래 스파이크 조건 5로 돌아간다.
- **실행별 키는 체크포인트에서 이어받지 않는다.** 이어받는 것은 `problems`, `analysis`, `assessments`, `searches`, `questions`(질문 이력)의 파생 값뿐이다. `phase`, `usage`, `eventSeq`, `cancellation`, `error`, `finalResult`와 이번 실행의 `decisions`·`guide`·`answer`·티켓 키는 새 `runId`마다 비어 있는 상태로 시작한다. 이전 실행의 사용량·이벤트 순번·취소·오류가 다음 실행에 남지 않고, 한도와 순번은 실행 단위로 유지된다([에이전트 계약](../../contracts/agents/README.md)).
- **체크포인트 쓰기를 보호한다.** 새 입력은 이전 실행을 `SUPERSEDED`로 만들고 취소를 시도하지만 취소보다 늦게 끝나는 실행이 있을 수 있다. 체크포인트는 (a) 그 실행이 취소·`SUPERSEDED` 상태가 아니고 (b) 저장된 `inquiryVersion`이 이 실행의 `inquiryVersion` 이하일 때만 쓴다(compare-and-set). 늦게 끝난 이전 실행은 최신 체크포인트를 덮어쓰지 못한다.
- 메시지 본문을 체크포인트에 복제하지 않고 ID와 digest만 둔다. 보관 기간은 RunLedger 상세 보존(최소 24시간)과 맞추고, 문의 종료 시 삭제한다. 옵션 프로필에서는 담당자 전용 근거 발췌를 담을 수 있으므로 어느 프로필이든 AI 전용 DB 계정으로만 접근한다.
- 이 설계는 계약 S5("MVP는 중간 그래프 checkpoint에서 자동 재개하지 않는다")를 바꾼다. 계약 변경 PR로 팀 리뷰를 받는다.

**스파이크 통과 조건(체크포인트 확정 전).**
1. 이 저장소의 `hops_ai_runtime` DB에서 Postgres 체크포인터로 `ask`로 끝난 실행의 상태가 저장되고, 다음 메시지로 같은 thread를 다시 호출하면 `analyze → retrieve → assess → route`가 다시 실행되어 **최신 응답을 반영한 결과**가 나오며 이전 질문 이력이 유지된다(회귀 테스트: 질문을 만든 뒤 답변으로 재호출했을 때 각 노드가 다시 실행되고 응답이 반영됨).
2. `inquiryVersion`이 올라간 사용자 응답으로 재호출해도 이전 질문 이력이 유지되어 이미 물은 필드를 다시 묻지 않는다(회귀 테스트: 질문을 저장한 뒤 버전이 증가한 응답으로 같은 thread를 재호출). 메시지 정정과 새 입력(SUPERSEDED) 뒤에는 정정된 메시지의 파생 값만 다시 계산되어 이전 체크포인트가 새 입력과 어긋나지 않는다.
3. 재개해도 실행 단위의 멱등성(같은 `runId` 재접수)과 취소·기한이 지금과 같이 동작한다. 새 `runId`로 재호출하면 실행별 키(`usage`, `eventSeq`, 취소·오류·최종 결과)가 새 실행 기준으로 시작하고, 취소보다 늦게 끝난 이전 실행이 최신 체크포인트를 덮어쓰지 않는다(회귀 테스트: 첫 실행을 지연시킨 뒤 새 입력으로 같은 문의를 재실행하고, 이전 실행이 늦게 끝나도 후속 재개가 최신 입력의 체크포인트와 질문 이력을 유지).
4. 보관 기간·삭제·접근 권한 규칙을 실제로 적용할 수 있다.
5. 통과하지 못하면 Spring이 질문 이력을 저장하는 방식(#189의 원안)으로 돌아간다.

`langgraph-checkpoint-postgres` 추가는 의존성 변경이므로 팀 승인이 필요하다.

## 12. PRD와 다른 점

| 항목 | PRD·계약 | 이 문서 | 이유 |
|---|---|---|---|
| Supervisor 호출 | 모델 판단으로 다음 처리를 선택 | 분기점에서만 모델 호출, 합법 전이는 그래프 | 정책은 유지하되 모델 호출과 막는 코드 수정을 줄임 |

| 관계 데이터 1차 | Neo4j가 MVP 필수 | `RelationSource` + SQL 구현, Neo4j는 교체 | 상담 루프에 먼저 넣기 위해. 인터페이스를 지키므로 교체 비용이 작음 |

## 13. 평가 영향

[평가 방식](../knowledge/EVALUATION.md)의 성질 ID는 바꾸거나 재사용하지 않는다. 새 구조에서 추가할 후보는 다음이다(구현할 때 확정).

| 후보 ID | 성질 | 종류 |
|---|---|---|
| P10 | `SUFFICIENT` 판정은 그 문제의 검색 결과에 있는 직원 공개 근거 ID를 가진다 | 안전 |
| P11 | `assessment`의 `missingInformation`은 닫힌 어휘 안에 있다 | 안전 |
| P12 | 직원 상담에서 직원 공개로 승인되지 않은 확인 항목의 ID·의미가 질문 생성 입력과 직원 질문에 없다 | 안전 |
| B7 | 판정과 다음 행동이 일관된다(충분 → 답변, 불충분 → 질문, 질문 소진 → 티켓) | 행동 |
| B8 | 생성된 질문이 부족한 정보를 겨냥한다 | 행동 |
| B9 | 검색이 필요 없는 의도(필수 정보를 갖춘 기능 추가·개선 요청)는 Knowledge 평가를 호출하지 않고 티켓 경로로 가며, 근거가 필요한 현상 문의는 검색·평가 경로를 쓴다 | 행동 |

평가 하네스(`ai/evaluation/`)는 공개 API(`SupervisorPipeline.run`)와 역할 매핑에 의존하므로 노드화해도 영향이 없다. 하네스의 Spring 대역은 `ask` 뒤 같은 thread를 다시 호출하는 방식에 맞춰 바꾼다. 재호출 시 각 노드가 다시 실행되는지도 검사한다.

## 15. 열린 결정과 한계

**결정이 필요한 것**
1. 관계 데이터 1차를 SQL로 구현하고 Neo4j를 2차에 교체하는 것(8절, PRD와 다름).
2. 직원 상담에서 담당자 전용 자료를 평가에 쓰는 **내부 판단 경계(옵션 프로필)**를 둘지(9절). 두려면 SECURITY.md 개정과 보안 리뷰가 필요하다. 기본안은 SEC-09를 지킨다.
3. 체크포인트를 스파이크 결과로 확정하는 것과 Postgres 체크포인터 패키지 추가(10절).
4. Knowledge v1(판정만 모델, 안내문은 코드 조립)부터 시작하는 것(7.2절).

**한계와 가정**
- 모델 호출 수·지연은 측정 전 추정이다. 병렬화의 효과도 측정하지 않았다.
- `merge.py`, `validation.py`, `finalize.py`의 전체 내용은 이 문서를 쓰는 동안 읽지 않았다. 병합 로직을 패치·reducer 방식으로 옮기는 작업량은 그 뒤에 다시 추정한다.
- 체크포인트의 Postgres 연동과 같은 thread의 재호출은 이 저장소에서 아직 실행해 보지 않았다(스파이크 대상).
- Spring 결과 처리기가 모르는 필드를 받을 때의 동작은 확인하지 않았다.
- 이 문서는 구현이 아니라 설계다. 문서 작성은 구현이나 검증 완료를 뜻하지 않는다.
