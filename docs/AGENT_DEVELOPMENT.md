# 에이전트별 개발 시작과 통합 준비

[PRD](PRD.md) → [공통 입출력 계약](../contracts/agents/README.md) → 본인의 담당 절 순서로 읽는다. 4명이 각각 전문 에이전트를 맡고 문의 분석 담당이 Supervisor를 겸임한다. 이 문서는 팀 리뷰용 작업 기준이며 구현 완료 목록은 아니다.

## 1. 목표와 범위

각 담당자가 다른 에이전트의 완성을 기다리지 않고 개발하고, 공통 실행기에 실제 구현을 연결해 검증할 수 있게 한다. 에이전트별 서버를 만들지 않고 하나의 Python 서비스 안에 모듈로 구현한다.

1주 MVP는 실제 단일 에이전트를 연결한 E2E와 기준선 평가다. 로그인·문의 저장·티켓 생성·부서 배정·조회는 실제 서비스에서 처리한다. 실제 모델로 추가 질문·정정·복합 문의를 분석하고 결과·설정·실행 이력을 보존한다. 후속 단계는 Supervisor와 4개 전문 에이전트로 개선하여 동일 조건의 수치를 비교한다. 아래 역할별 registry·계약·통합 준비는 최종 멀티 에이전트 구조를 대상으로 하며 MVP부터 4개 역할을 실행하도록 요구하지 않는다.

개발 언어 버전은 Python 3.13, Java 21이다. AI 서버는 LangGraph로 실행 흐름·상태를 관리하고 FastAPI로 Spring 연동용 HTTP API와 스트리밍 응답을 제공한다. 네 에이전트는 하나의 서버 내부 모듈로 구현하며 HTTP 처리는 공통 어댑터에서 맡는다. 선정한 프레임워크·프론트 빌드용 Node.js 버전은 9~11장을 따른다. 패키지 관리 도구·DB·Java 패치 버전은 별도로 맞춘다. 채팅·실시간 전달에는 별도 Node.js Socket.IO 서버를 두고 React와 Spring이 각각 클라이언트로 연결한다. Spring은 JWT 발급·사용자 권한·업무 저장을 담당하고 Node.js는 연결·구독·이벤트를 중계한다. Spring–Python 진행 전달은 SSE를 사용한다. Spring이 구독하고 Python FastAPI가 실행 이벤트를 제공한다. 최종 AI 결과 경로는 외부 API 계약에서 별도로 합의한다.

## 2. 먼저 함께 준비할 서비스 기반

### 서비스가 연결되는 최소 흐름

```text
로그인: React → Spring REST → JWT 발급
채팅: React → Node.js Socket.IO 서버 → Spring 검증·문의 저장
분석: Spring → Python 실행 접수 → 실제 단일 에이전트 분석 결과
진행: Python SSE → Spring → Node.js Socket.IO 서버 → React
확정: Spring 검증·복수 티켓 저장·부서 배정 → Node.js → React 갱신
조회·복구: React → Spring REST → 저장된 대화·문의·티켓·실행 상태
```

개발 중에는 Fake로 연결을 먼저 검사할 수 있으나, MVP 완료에는 실제 단일 에이전트 E2E와 평가 결과가 필요하다. React·Node.js·Spring·Python의 책임과 JWT·Socket.IO 계약안은 [API](API.md), 저장 관계 설계안은 [DATA](DATA.md)를 참조한다. 기능별 상세 계약은 구현 전에 합의한다.

- 사번·소속 부서·역할을 가진 로그인 seed와 JWT 발급·검증을 준비한다. 클레임·토큰 수명·갱신/폐기·보관/전달은 API 문서에서 합의하며 Python에는 Spring이 검증한 최소 사용자·부서·권한 문맥만 전달한다.
- Node.js 채팅 서버와 React·Spring Socket.IO 클라이언트를 연결한다. 사용자 연결과 서비스 연결을 구분하고 문의별 구독 권한을 확인한다. Node.js가 사용자나 부서를 임의 확정하지 않도록 Spring에서 검증한다.
- 문의·메시지·정정·문의 버전을 저장한다.
- runId를 발급하고 실행 요청·결과 수신·중복 수신을 처리한다.
- 생성 작업 단위로 티켓과 부서를 저장한다. 일부 실패 시 성공한 티켓을 보존한다.
- Node.js 수신, Spring 저장 ACK, AI 분석 성공, 실제 티켓 저장 성공을 구분해 표시한다. DB 커밋 뒤 확정 이벤트를 전달하고 ACK 유실 시 같은 요청 식별자로 재시도한다.
- Socket.IO로 진행·답변 조각·업무 변경을 전달하고 REST로 저장 결과를 조회한다. 양쪽 클라이언트 재접속 후 인증·구독 권한을 다시 확인하고 REST로 복구한다.

### 모두가 공유할 가상 기업 정보

부서 코드·담당 업무·분류 경계, 서비스 ID·의존 관계, 사용자·접근 범위를 공통 fixture로 만든다. 각 담당자가 다른 의미의 DB·서버·부서를 만들지 않도록 PR로 리뷰한다. 초기 8개 부서의 목록만으로는 부족하며 애매한 사례의 책임 경계도 짧게 적는다.

계약 검증용 fixture는 공통으로 사용하되 개인 검색·모델 실험의 데이터셋을 제한하지 않는다. 개인 실험은 `.local/`, 팀이 사용할 비식별 fixture와 출처는 리뷰 후 공유한다.

## 3. Python 공통 기반

첫 공통 PR에서 아래 최소 골격을 준비한다. 아직 존재하는 실행 명령이나 구현으로 간주하지 않는다.

```text
ai/
├── src/hops_ai/
│   ├── api/                  # Spring 요청·결과 어댑터
│   ├── contracts/            # 공통·역할별 Python 타입
│   ├── runtime/              # 예산·취소·추적·결과 검증
│   ├── supervisor/           # 경로와 결과 조합
│   ├── agents/               # intake·knowledge·diagnosis·ticket
│   └── services/             # 공통 LLM·검색·도구 인터페이스
└── tests/
    ├── fakes/                # 외부 연결 없는 가짜 구현
    ├── fixtures/             # 팀 공통 사례
    ├── contract/             # 각 역할 입출력 검증
    └── integration/          # Supervisor와 역할 연결 검증
```

역할 registry에서 `INTAKE`, `KNOWLEDGE`, `DIAGNOSIS`, `TICKET`을 실제 구현 또는 Fake로 선택한다. Fake/실제 교체는 설정이나 의존성 주입으로 수행하고 호출 코드를 수정하지 않게 한다.

모델 호출·재시도·출력 검증·추적은 공통 서비스를 사용한다. Python 공통 어댑터로 OpenAI API를 호출하고 에이전트별로 인증·호출 관리를 중복 구현하지 않는다. 모델·서버 자원은 실측 후 선정하고 선택 결과를 공통 설정으로 기록한다.

## 4. 담당자별 준비할 것

### 문의 분석·Supervisor 담당

**구현:** 대화 해석, 문제 분리, 추가 질문, 기존 문제 ID 유지, 사용자 해결 응답 해석. Supervisor의 조건부 호출·종료·재실행·결과 조합.

**공통 책임:** 내부 타입·JSON Schema·Fake 에이전트 registry, Spring↔Python 어댑터와 E2E 조율. 채팅·문의 화면의 입력·진행·실패 표시 연동을 책임지고 구현은 함께 분담한다.

**준비물:** 복합 문의, 추가 질문, 정정, 질문 한도 소진, 범위 밖, 모호한 해결 응답의 입력·출력 fixture. 다른 역할 없이도 Supervisor 경로를 확인할 테스트.

**완료 조건:** 판별된 문제와 추가 질문이 필요한 문제를 한 결과로 반환한다. 같은 문제의 질문 횟수를 초기화하지 않는다. 이전 문의 버전 결과를 버리고, 기존 티켓 생성을 반복하지 않는다.

### Knowledge 담당

**구현:** 접근 가능한 자료 검색, 근거 충분성 평가, 답변 초안. Hybrid·반복 검색·최소 GraphRAG 관계 조회는 같은 서비스 인터페이스 아래에서 단계적으로 추가한다.

**공통 책임:** 지식 적재 형식·문서 ID/버전·접근 범위, 서비스 관계 데이터, 공통 평가 자료 관리. 데이터 생성·검수는 전원이 분담한다.

**준비물:** 출처와 권한이 있는 작은 가상 지식 묶음, Fake 검색 서비스, 검색 성공·근거 없음·검색 장애·권한 제외 사례. 모델/검색 설정과 실험 재현 방법.

**완료 조건:** 근거 ID를 검증 가능하게 반환한다. 근거가 없으면 부족으로 반환하고 검색 장애와 구분한다. 문서 안의 지시로 도구 권한이나 공통 정책을 바꾸지 않는다. 안내만으로 해결을 확정하지 않는다.

### Diagnosis 담당

**구현:** 조건부 조회 계획, 읽기 도구 호출, 원인 후보·불확실성·처분 제안, 내부 근거 검토.

**공통 책임:** 가상 기업 Mock API, Spring 도구 권한 연동, 공용 실행 환경 준비. 자원·모델 실행은 다른 담당자가 같은 환경에서 재현할 수 있게 기록한다.

**준비물:** 계정·VPN·서비스/서버·로그/지표/DB 연결·변경 이력의 Mock 입력·출력. 정상·장애·권한 거부·시간 초과 사례와 공통 ToolResult.

**완료 조건:** 무조건 모든 도구를 호출하지 않는다. 허용 범위를 넘는 조회를 막고, 조회 실패를 정상으로 해석하지 않는다. 근거가 뒷받침하지 않는 원인은 확정하지 않으며 실제 시스템 변경을 하지 않는다.

### Ticket 담당

**구현:** 문제별 작업 분리, 티켓 초안·부서 제안·이관 이유, 기존 작업 재사용. 재이관·그룹핑은 해당 후속 계약을 만든 뒤 확장한다.

**공통 책임:** Spring 티켓·부서 배정·상태·복구와 부서/관리자 화면 연동. API 어댑터가 내부 근거를 외부 계약으로 안전하게 전달하는지 문의 분석 담당과 함께 검토한다.

**준비물:** 부서 R&R fixture, 단일/복합 문의·CS 검토·기존 생성 작업의 예시, Spring 저장을 대신할 Fake와 저장 실패 시나리오.

**완료 조건:** 필요한 복수 제안을 반환하며 모델이 ticketId나 배정 성공을 만들어내지 않는다. 유효 부서만 제안한다. 같은 작업을 재실행해도 Spring의 실제 티켓이 중복되지 않고 일부 실패 시 성공분이 유지된다.

### 전원이 함께 할 일

인증·공통 화면 기반, 데이터 생성·교차 검수, 계약 리뷰, 각 담당 영역 테스트를 분담한다. 공통 코드를 한 사람이 모두 구현해야 한다는 뜻이 아니라 변경을 조율할 책임자를 두는 방식이다. 공통 타입 수정은 다른 세 역할과 Spring 소비자 영향을 확인한다.

## 5. 통합 순서와 통과 기준

1. **공통 계약 리뷰:** 타입·필수값·enum·ID·오류를 합의하고 정상/실패 예시를 JSON Schema로 검증한다. 담당자별 해석이 갈리는 항목을 구현 기본값으로 숨기지 않는다.
2. **개발용 연결 검사:** JWT 로그인 뒤 화면→Node.js→Spring→Python과 Python→Spring→Node.js→화면 연결·저장을 필요하면 Fake로 검사한다. Node.js 수신·Spring 저장·실행 접수를 구분한다. 이 단계는 MVP 완료나 모델 품질 검증이 아니다.
3. **실제 단일 에이전트 MVP:** 실제 모델로 추가 질문·복합 문제 분석·티켓 제안을 수행하고 Spring의 저장·부서 배정·관리자 조회를 확인한다. 평가 결과와 재현 설정을 보존해 기준선을 만든다.
4. **후속 Supervisor와 역할 분리:** 문의 분석·Ticket을 실제 역할로 분리하고 조건부 실행을 검증한다. 미완성 역할의 Fake는 연결 테스트에만 사용하며 최종 평가에서는 실제 구현을 사용한다.
5. **Knowledge 연결:** 내부 역할 테스트 후, 문서 근거·무티켓 안내를 표현할 외부 계약 확장을 먼저 리뷰한다. 이후 Spring과 연결한다.
6. **Diagnosis 연결:** 읽기 도구의 서버 권한과 근거 전달을 연결한다. 상태 조회·근거 검토·시간 제한을 검증한다.
7. **통합 회귀:** 순차 호출을 먼저 검증하고 결과 의존성이 없는 검색·진단에 한해 병렬 호출을 검증한다. 정확도·속도·실패율은 동일 조건에서 별도 측정한다.

## 6. 공통 통합 사례

아래 사례는 반드시 예상 결과까지 fixture에 기록한다. 데이터셋 전체 규모나 개인 실험 범위를 고정하는 규칙은 아니다.

- 정보 부족: 해당 문제에만 추가 질문하고 서버의 횟수를 유지한다.
- 질문 한도 소진: 분류 불가 IT 문제는 CS 검토 제안, 모델 연결 실패는 기술 오류다.
- 지식 안내: 근거를 반환하며 사용자 해결 확인 전 완료를 확정하지 않는다.
- 상태 진단: 도구가 제공한 조회 시각과 근거로 원인 후보·담당 부서를 제안한다.
- 복합 문의: 하나는 티켓 제안, 다른 하나는 추가 질문인 혼합 결과를 허용한다.
- 중복·부분 저장 실패: 같은 요청/이벤트를 반복해도 성공 티켓은 늘지 않고 실패 작업만 재시도한다.
- 실행 중 정정: 새 버전 결과만 반영하고 기존 티켓은 유지한다.
- 시간 초과·권한 거부: 무한 재시도·권한 우회·가짜 정상 결과를 만들지 않는다.
- 근거 없는 출력: 존재하지 않는 문서·메시지·부서·작업 ID를 검증에서 차단한다.
- JWT·구독 권한: 사번·부서 클레임 검증, 타인 문의 구독 거부, 토큰 만료·로그아웃·부서 변경 시 전송과 구독 권한을 확인한다. 세부 정책은 API 계약과 일치해야 한다.
- 연결 종료: React 또는 Spring 재접속과 Node.js 재시작 후 저장된 답변·업무 상태를 REST로 복구한다. 저장 뒤 ACK 유실·중복 명령·이벤트 누락이 업무 중복이나 거짓 성공을 만들지 않는지 검사한다.

## 7. 각 담당자의 통합 PR 제출물

- 공통 인터페이스를 따르는 구현과 독립 실행 가능한 Fake 테스트.
- 정상·정보 부족·기술 실패 fixture와 계약 검증 결과.
- 필요한 환경변수 이름을 적은 `.env.example`. 비밀값은 포함하지 않는다.
- 사용한 모델·프롬프트·검색/도구 버전과 실제 실행·테스트 명령.
- 실패·시간 초과·취소 시 동작, 현재 제한사항.
- 입력/출력 계약 변경이 있으면 소비자·Spring·화면 영향과 변경 예시.
- 새로운 의존성의 설치 방법·사용 조건·비용. 자동 유료 전환은 금지한다.

검증 결과에는 Fake 통합, 실제 모델 테스트, 실제 Spring 저장 E2E를 구분한다. 테스트를 실행하지 않았으면 미실행으로 기록한다. 문서 작성이나 JSON 형식 검증만으로 통합 완료라고 표시하지 않는다.

## 8. 첫 작업에서 합의할 기술 선택

현재 문서로 제품 목적을 다시 결정할 필요는 없다. 다만 아래 구현 선택은 공통 기반 PR에서 결정하고 실행 방법에 기록한다.

- 공통 타입/스키마 검증 도구와 간접 의존성을 고정할 잠금 파일.
- 서비스 간 인증과 검증 가능한 accessScopeRef 전달 방식.
- JWT·Socket.IO 계약과 연결 담당: 사용자/서비스 인증, 토큰 갱신·부서 변경 시 구독 해제, 이벤트·저장 ACK·재접속, 서버/JS/Java 클라이언트 호환 버전과 Node.js 채팅 서버 런타임. 상세 정책은 API 문서를 단일 기준으로 정리한다.
- OpenAI 모델·SDK 버전·동시 호출·토큰 예산·비용 상한 설정.
- Spring 실행 요청에서 부서 R&R·서비스 카탈로그를 제공할 방법.
- 후속 무티켓 결과·문서/도구 근거의 외부 API 버전과 저장 구조.

이 선택을 기다리는 동안 각 담당자는 계약에 맞는 fixture와 Fake, 역할별 로직을 준비할 수 있다. 실제 통합 전에 공통 선택과 기계 판독 계약을 리뷰해야 한다.

Spring–Python의 최소 입출력 정보와 미정 항목은 [MVP 계약 논의](../contracts/mvp/README.md)에 정리한다. 해당 문서의 축약 예시는 설명용 제안이며 승인된 스키마나 구현 기준이 아니다.

## 9. AI 서버 개발 버전

Python 3.13을 사용하며 초기 직접 의존성을 다음 버전으로 고정한다.

- LangGraph `1.2.16`: Supervisor·역할 노드의 실행 흐름과 상태 관리.
- FastAPI `0.143.5`: HTTP 요청·응답과 스트리밍 어댑터.
- Uvicorn `0.53.0`: ASGI 실행 서버.

Python 3.13.15 환경에서 위 패키지의 설치·로딩, Fake 그래프 실행, FastAPI TestClient의 SSE 형식 응답을 확인했다. 실제 Uvicorn 네트워크 스트리밍·모델 추론·Spring 연결은 별도 통합 검증 대상이다. LangChain 상위 패키지 사용은 강제하지 않으며 langchain-core 등 LangGraph의 간접 의존성은 포함될 수 있다. 실제 프로젝트 의존성 파일과 잠금 파일은 초기 구현 시 작성한다.

출처: [LangGraph](https://pypi.org/project/langgraph/1.2.16/), [FastAPI](https://pypi.org/project/fastapi/0.143.5/), [Uvicorn](https://pypi.org/project/uvicorn/0.53.0/).

## 10. 프론트엔드 개발 버전

- Node.js `24.22.0` LTS
- React·React DOM `19.3.0`
- Vite `8.3.4`
- @vitejs/plugin-react `6.1.2`

Node.js 24.22.0에서 최소 React 화면의 의존성 설치와 Vite 프로덕션 빌드를 검증했다. npm ls에서 직접 의존성 오류가 없음을 확인했다. 실제 프로젝트의 브라우저 화면·JWT 로그인·Socket.IO 연결까지 검증한 것은 아니다. UI·라우팅 라이브러리는 선정 시 추가 호환성 검사를 수행한다.

별도 Node.js 채팅 서버와 React용 `socket.io-client`를 추가한다. 서버 런타임과 Socket.IO 서버·JavaScript/Java 클라이언트 호환 버전은 아직 선정하지 않았으며, 위 프론트 빌드 결과가 채팅 서버 검증을 대신하지 않는다. 실행·환경 설정·잠금 파일·배포 방법은 구현 시 기록한다. Spring도 클라이언트로 연결하므로 재연결·명령 라우팅·구독 권한과 전달 실패를 함께 검증한다.

팀 개발 PC와 CI는 위 버전을 맞춘다. 패키지 관리 도구 버전과 잠금 파일도 초기 구현 시 함께 고정한다. 버전 선택은 기존 PC의 전역 설치를 자동 변경하지 않는다.

출처: [Node.js 24.22.0 LTS](https://nodejs.org/en/blog/release/v24.22.0), [React 버전](https://react.dev/versions), [Vite](https://vite.dev/guide/).

## 11. 백엔드 개발 버전과 검증 범위

Java 21 + Spring Boot 4.1.1을 사용한다. Spring Framework·Security·Data JPA 등의 의존성은 Spring Boot가 관리하는 버전을 따른다. Spring 내 Swagger UI를 사용하는 경우 springdoc-openapi-starter-webmvc-ui 3.1.1을 연동 후보로 유지한다. 직접 작성한 OpenAPI YAML이 계약 원본이며 코드에서 생성한 문서가 이를 자동 대체하지 않는다.

Java 21은 Boot 4.1.1의 공식 지원 범위에 포함된다. 빌드는 Gradle Kotlin DSL과 Gradle Wrapper 9.8.1을 사용한다. IDE·JAVA_HOME·빌드 도구가 모두 Java 21을 사용하도록 맞추고, 저장소의 Wrapper로 실행한다. 현재 Spring 초기 실행 기반과 실제 업무·DB·AI 연동은 구분하며, 구성과 테스트·빌드·실행 방법은 [Spring 개발 안내](../backend/spring/hops/README.md)를 따른다. JWT 인증, DB 저장, FastAPI SSE 수신과 Node.js Socket.IO 서버를 통한 React 전달은 별도 통합 검증 대상이다. Java Socket.IO 클라이언트의 호환 버전은 별도로 선정한다.

출처: [Spring Boot 요구사항](https://docs.spring.io/spring-boot/system-requirements.html), [springdoc](https://springdoc.org/).

위 버전은 개발 기준으로 선택한 값이며 전체 서비스 무결점이나 E2E 완료를 보장하지 않는다. 공통 기준 적용은 저장소의 PR 리뷰·병합 규칙을 따른다.
