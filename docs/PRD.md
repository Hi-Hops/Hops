# HOPS 사내 IT 문의 대응 PRD

버전: 1.44 · 갱신: 2026-10-31 · 팀 합의 기획 반영안 / 문서 PR 리뷰 전

이 문서는 팀이 합의한 HOPS의 제품 목표, 사용자, 기능, 화면 흐름, 기술 구성, 데이터, 성공 기준과 개발 범위를 정의한다. 기획 합의는 구현이나 통합 검증 완료를 뜻하지 않는다. 이 개정안은 PR 리뷰와 병합을 거쳐 저장소의 공통 문서에 반영한다.

[API 설계](API.md), [데이터 설계](DATA.md), [ERD 설명](ERD_설명.md), [기능 명세와 공통 계약](../specs/README.md), [에이전트 계약](../contracts/agents/README.md), [Knowledge 자료](knowledge/README.md)의 목표 설명은 이 기획에 맞춰 작성했다. 기존 코드·Mock과 v0 데이터가 사용하는 전환 전 계약·생성 자료는 별도 표시하며, 현재 구현 설명과 새 목표를 구분한다. 이 문서는 새 제품 방향을 설명하며 기존 API·DB·화면이 이미 변경됐다는 의미가 아니다. 세부 API·상태 전이·물리 스키마·서비스 연결 계약은 해당 기능을 구현하기 전에 합의한다.

## 1. 서비스 목적

### 1.1 해결하려는 문제

기업 임직원은 IT 문제를 겪어도 그 현상이 발생한 시스템의 기술 구조나 담당자를 알기 어렵다. 사용법, 권한 신청, 이상 현상과 기능 요청이 자유로운 표현으로 접수되면 담당자는 누락된 정보를 반복 확인해야 한다. 여러 시스템을 맡은 담당자가 자신이 개발하지 않은 기능이나 과거 처리 내용을 파악하는 데도 시간이 든다.

이는 현업 자문을 바탕으로 설정한 가상 기업의 문제 가정이다. 실제 기업의 문의 분포, 시간 절감 또는 운영 성과를 이미 측정했다는 뜻은 아니다.

### 1.2 제공 가치

HOPS는 단일 기업 임직원의 비정형 IT 문의를 대화로 구체화·표준화하고, 담당자 처리가 필요하면 책임 시스템의 주담당자에게 자동 배정하는 멀티 에이전트 기반 서비스다. 담당자에게 확인된 사실과 미확인 항목, 관련 지식과 과거 해결 사례를 제공하고, 해결 후 검증된 내용을 다시 축적해 다음 문의에 활용한다.

우선순위는 다음과 같다.

1. **문의 명확화:** 필요한 추가 질문으로 처리 가능한 표준 요청을 만든다.
2. **지식 선순환:** 해결 기록을 승인된 해결 사례로 축적하고 재사용한다.
3. **업무 연결:** 대화와 근거를 바탕으로 책임 시스템과 주담당자를 연결한다.
4. **담당자 준비:** 확인 사실, 불확실성, 유사 사례와 적용 조건을 함께 전달한다.

```text
비정형 문의 → 추가 질문·지식 검색 → 표준 요청 → 책임 시스템 주담당자 배정
→ 담당자 처리·검증 → 문의자 해결 확인 → 담당자 사례 승인
→ 같은 승인 버전의 Vector·Neo4j 반영 → 검색 공개·다음 문의 재사용
```

에이전트는 담당자를 대신해 실제 시스템을 변경하거나 장애를 자동 복구하지 않는다. 장애 여부와 조치 결과는 담당자가 근거를 확인한다.

### 1.3 대상 환경과 검증 방향

대상은 하나의 가상 기업이며 임직원, 시스템 담당자와 업무 관리자가 PC 웹에서 자체 계정으로 로그인해 한국어 텍스트로 이용한다. 계열사·외부 고객사·다중 테넌트는 범위에 넣지 않는다. 사용자·시스템·문의·문서·처리 사례는 가상 데이터다.

MVP는 실제 모델을 사용하는 Supervisor와 네 전문 에이전트로 구현한다. Fake와 Mock은 개발·시연에서 연결과 조건을 확인하는 데 사용할 수 있지만 실제 모델 품질이나 서비스 통합 완료를 대신하지 않는다. 단일 에이전트 제품·기준선 및 단일/멀티 비교는 범위에서 제외한다. 측정 전 자동화율이나 실제 운영 수준을 보장하지 않는다.

## 2. 핵심 사용자

한 사람이 문의자와 담당자 역할을 함께 가질 수 있다. 부서는 사용자의 소속 정보이며 티켓 배정 기준은 시스템과 주담당자의 관계다.

| 사용자 | 주요 기능과 접근 범위 |
|---|---|
| 문의자 | 본인의 문의·대화·연결 티켓 조회, 질문 응답·정정·해결 확인 |
| 시스템 주담당자 | 담당 시스템의 업무와 허용된 관련 대화·내부 지식 조회, 처리·검증 기록, 해결 사례 초안 확인·수정·승인 |
| 업무 관리자 | 업무 관리, 책임 시스템과 담당자의 수동 정정·재배정 지원 |

시스템마다 유효한 주담당자 `PRIMARY` 한 명을 두며 한 사람이 여러 시스템을 맡을 수 있다. 티켓은 해당 주담당자에게 자동 배정하고 별도 선점·수락 절차는 두지 않는다. 정상 가상 데이터에서는 담당자 누락·중복·만료가 없다고 전제한다. 담당 관계를 확인하지 못하거나 조회에 실패하면 서버는 배정 성공으로 확정하지 않고 오류를 기록·반환한다. 별도 매핑 예외 업무 화면은 구현하지 않는다.

별도 지식 검토자 역할은 두지 않는다. 해당 시스템 담당자가 사례 검토와 승인을 겸하며 자기 승인을 허용한다. 문의 원문과 담당자 내부 자료는 전 직원에게 공개하지 않는다. 인증 및 접근 권한은 Spring이 현재 사용자와 담당 관계를 확인해 결정하며, 클라이언트나 모델이 주장하는 역할을 신뢰하지 않는다. 정확한 인증·권한·접근 회수 계약은 관련 구현 전에 정한다.

## 3. 핵심 기능

### 3.1 대화 기반 문의 분석과 복수 티켓 생성

한 대화 세션을 문의 한 건으로 관리하며 원문과 정정 이력을 보존한다. 문의자는 시스템 선택 없이 자연어로 시작할 수 있다. Inquiry는 문의 의도, 보고 시스템·기능, 확인 사실, 미확인 항목과 독립된 문제를 정리하고 필요한 질문을 한다.

문의 의도와 내부 처리 유형은 서로 다른 차원이다.

| 문의 의도 | 의미 |
|---|---|
| `HOW_TO` | 사용법 문의 |
| `ACCESS_REQUEST` | 계정·권한·접근 요청 |
| `OBSERVED_SYMPTOM` | 원인이 아직 확정되지 않은 이상 현상 |
| `FEATURE_REQUEST` | 신규 기능 추가 요청 |
| `IMPROVEMENT_REQUEST` | 기존 기능 개선 요청 |
| `UNKNOWN` | 정보가 부족해 판단하지 못함 |
| `OUT_OF_SCOPE` | 지원 범위 밖 |

| 내부 처리 유형 | 의미 |
|---|---|
| `KNOWLEDGE_QA` | 지식 안내 |
| `SERVICE_REQUEST` | 권한·설정 등 신청·작업 |
| `INVESTIGATION` | 원인·현상 조사 |
| `INCIDENT` | 담당자가 확인한 서비스 장애 대응 |
| `CHANGE_REQUEST` | 기능 추가·개선 |
| `REVIEW_REQUIRED` | 정보 부족으로 검토가 필요한 요청 |
| `OUT_OF_SCOPE` | 지원 범위 안내 |

문의자가 장애라고 표현한 것과 실제 장애 확정을 구분한다. 기본적으로 현상 확인은 조사 업무로 접수하며 담당자가 근거를 검토해 장애 여부를 확인한다. Mock 조회 결과를 실제 운영 관측으로 표현하지 않는다.

사용법은 시스템과 하려는 작업·화면, 권한 요청은 필요한 기능·권한과 업무 목적, 현상 확인은 기대·실제 동작과 발생 시점, 기능 요청은 현재 방식과 문제점·원하는 변경을 우선 파악한다. 사용자 역할, 영향 범위, 재현 조건, 승인 조건이나 수용 조건은 상황에 따라 확인한다. 상세 필수·조건부 스키마는 데이터 설계에서 정한다. 알 수 없는 정보를 강요하거나 추정으로 채우지 않는다.

추가 질문은 **문제당 최대 5회**다. 한 회는 문의자에게 보낸 한 질문 묶음이다. 이미 확인한 내용은 반복하지 않고 분기에 필요한 정보부터 묻는다. 질문 한도에 도달했더라도 시스템이 확인됐으면 누락 항목을 표시해 담당자에게 전달한다. 시스템이 끝까지 확인되지 않으면 자동 배정하지 않고 시스템 확인 대기 상태로 보존한다. 화면에서 지원 시스템 선택을 요청하되 추가 자유 질문 루프로 한도를 우회하지 않는다. 사용자가 선택하지 않고 화면을 닫아도 저장 상태를 유지한다. 지원 범위 밖이면 범위를 안내하며 관리자 검토 큐에 임의 배정하지 않는다.

표준 요청(`StandardRequest`)은 원문을 대체하지 않고 문의·문제·대화 버전에 연결해 보존한다. 문의 의도·내부 처리 유형, 보고 시스템과 책임 시스템 후보·근거, 요약·확인 사실·추정·미확인 항목, 유형별 정보, 관련 지식과 적용 조건, 티켓 제안 및 배정 결과를 포함한다. AI가 제안한 기능 수용 조건은 사용자나 담당자가 확인하기 전까지 확정 요구사항으로 취급하지 않는다.

독립된 요청과 완료 조건은 별도 문제와 티켓으로 나눈다. 예를 들어 문서 열람 실패와 일괄 다운로드 기능 추가는 같은 담당자에게 배정되더라도 각각 조사 티켓과 변경 요청 티켓으로 분리한다. 한 증상의 여러 원인 후보는 하나의 문제로 유지한다. 질문 횟수·진행·해결 확인은 문제별로 관리한다.

담당자 처리가 필요한 요청은 별도 제출 승인 없이 서버가 검증해 티켓을 생성하고, 저장·배정 결과를 문의자에게 모달로 안내한다. 접수는 기능 개발 승인이나 실제 권한 부여를 뜻하지 않는다. 일부 티켓 생성이 실패해도 성공한 티켓은 유지한다. 재시도 전 Spring은 해당 문제의 기존 저장 결과와 현재 문의 버전을 확인한다. 이미 저장됐으면 기존 결과를 반환하고, 저장 여부를 확인할 수 없으면 미확인 상태로 두어 중복 생성하지 않는다. 실제 미생성이 확인된 항목은 Ticket이 제안을 다시 만들거나 보존된 제안을 사용해 같은 업무 작업으로 재시도하며 저장은 Spring이 확정한다. 식별자·재시도 조작·권한은 구현 계약에서 정한다.

### 3.2 지식 답변과 근거 기반 분석

승인된 직원용 가이드로 답할 수 있는 사용법 문의는 안내 후 문의자의 해결 확인을 받아 티켓 없이 종료할 수 있다. 안내가 없거나 해결되지 않으면 원문·검색 결과·누락 정보를 보존해 담당자에게 전달한다. 검색 결과 없음과 검색 시스템 오류는 구분한다. 티켓 없이 해결된 대화만으로는 담당자 해결 기록이 없으므로 사례 초안을 자동 생성하지 않는다.

Knowledge는 권한 범위의 직원 가이드·정책·담당자 런북·승인된 해결 사례를 검색하고, 필요하면 Neo4j 관계를 탐색해 추가 질문·원인 후보·확인 항목을 제안한다. 관계나 유사 사례만으로 현재 원인을 확정하지 않는다. 담당자에게는 확인된 사실과 추정, 사례의 적용 시스템·버전·조건을 구분해 전달한다. 독립 Diagnosis 에이전트는 두지 않고 분석은 Knowledge의 조건부 기능으로 제공한다.

### 3.3 시스템 배정과 담당자 처리

**보고 시스템**은 문의자가 현상을 경험했다고 확인한 시스템이며, **책임 시스템**은 현재 티켓을 맡아 확인·처리할 시스템이다. 보고 시스템은 문의 맥락으로 보존한다.

```text
보고 시스템 확인 → Inquiry 멀티턴 대화·필요 시 Knowledge 검색
→ Ticket의 책임 시스템·근거 제안 → Spring의 지원 시스템·주담당자 검증
→ 티켓 저장·배정 → 문의자에게 결과 안내
```

원인을 확정해야만 접수할 수 있는 구조는 아니다. 예를 들어 전자결재에서 로그인 문제가 발생했더라도 대화와 허용된 근거가 공통 로그인 시스템을 처리 대상으로 뒷받침하면 공통 로그인 담당자에게 배정한다. 시스템 의존 관계만으로 원인을 확정하지 않는다. 다른 책임 시스템을 식별할 근거가 부족하면 확인된 보고 시스템 담당자가 최초 조사하며 미확인 사항을 보존한다.

잘못된 책임 시스템이나 담당자는 담당자 또는 업무 관리자가 근거와 사유를 남겨 수동 정정한다. 이미 배정된 티켓의 자동 재이관, 업무량·휴가 기반 배정, 담당자 선점은 구현하지 않는다. 분석 중 정정은 최신 문의 버전에 반영하고 이미 생성한 티켓을 중복 생성하지 않는다. 배정 이후 메시지는 기존 티켓의 보완 정보로 연결하며 자동 새 티켓 생성이나 재배정을 하지 않는다.

### 3.4 해결 확인과 종료

안내 제공, 도구 성공, 티켓 접수 또는 담당자 조치만으로 최종 해결을 확정하지 않는다.

| 유형 | 처리와 완료 조건 |
|---|---|
| 사용법 | 승인 가이드 안내 후 문의자가 해결을 확인하면 티켓 없이 종료 가능 |
| 서비스 요청 | 담당자의 조치·검증 후 문의자 해결 확인 |
| 조사·장애 | 담당자의 확인·조치·검증 후 문의자 해결 확인 |
| 기능 추가·개선 | 담당자가 구현·검증을 마치면 구현 완료로 기록하고 문의자 해결 확인 후 최종 완료 |

기능 요청의 검토·보류·반려 절차는 구현 범위에 넣지 않는다. 실제 구현하지 않은 요청을 구현 완료로 기록하지 않는다. 담당자 조치 또는 구현 완료 후 결과를 알리고 해결 확인을 요청한다. 문의자가 미해결이라고 답하면 같은 티켓에서 처리를 이어간다. 무응답이면 확인 대기를 유지하며 예약 재알림이나 무응답 자동 종료는 구현하지 않는다. 최종 완료 후 재오픈은 제외하고 이후 같은 현상은 새 문의로 접수한다.

### 3.5 해결 사례의 축적과 공개

해결 사례(`CASE`)는 담당자의 처리 기록을 바탕으로 확인된 조치와 결과를 재사용 가능하게 정리한 지식이다. 해결되지 않은 시도는 문의·티켓 이력으로 보존하되 실패 사례를 검색 지식으로 만들지 않는다. 모든 문의를 사례로 승격할 필요는 없으며 재사용 가능한 내용과 근거가 있어야 한다.

```text
담당자 해결 기록 저장 → Curator 자동 실행·사례 초안 생성
→ 문의자 해결 확인 → 해당 시스템 주담당자의 확인·수정·승인
→ 동일 승인 버전의 Vector 색인과 Neo4j 관계 반영
→ 양쪽 모두 성공한 경우에만 검색 공개
```

초안은 해결 기록 저장 직후 만들 수 있지만 검색에 공개하지 않는다. 기능 요청 사례는 담당자의 실제 구현·검증 완료 기록도 게시 전제다. 승인 시 원문 일치, 실제 조치·결과, 적용 조건, 공개 범위와 민감정보를 확인한다. 사례 초안 생성, 업무 완료, 담당자 승인, 검색 반영은 각각 다른 사실이다.

승인된 사례 버전마다 Vector와 Neo4j의 반영 결과를 따로 기록한다. 한쪽만 성공하거나 상태를 확인할 수 없으면 전체 반영 완료로 표시하지 않고 두 검색 경로 모두에서 공개하지 않는다. 서버가 승인·공개 가능 상태를 기준으로 검색 결과를 검증한다. 반영 실패는 기존 승인과 업무 기록을 취소하지 않는다. 담당자가 원인을 확인·수정한 후 실패한 반영을 다시 실행할 수 있어야 한다. 재반영 중복 방지와 권한·조작·구체 계약은 구현 전에 정하며 자동 재시도와 전용 복구 화면은 제외한다.

사례에는 문서 버전과 별도로 적용 시스템·버전·조건을 기록하고 검색 결과에도 표시한다. 적용 버전을 모르면 미확인으로 표시한다. 담당자가 현재 환경과 비교해 적합성을 판단하며 오래된 사례를 무조건 삭제하거나 차단하지 않는다. 새로운 해결이 필요하면 새 해결 사례와 적용 버전을 기록한다. 잘못됐거나 공개 권한을 잃은 자료의 취급은 별도 검토한다. 합성·데모 검증·실제 운영 출처를 구분한다.

### 3.6 현황·알림·추적

문의와 문제별 진행 상태, 저장된 티켓, 배정 결과, 담당자 처리와 해결 확인 상태를 보여준다. 티켓 생성이나 에이전트 실행 완료를 문제 해결이나 업무 저장 성공으로 표시하지 않는다. 담당자에게 처리에 필요한 대화·근거와 관련 지식을 권한 범위 내에서 제공한다.

화면 내 배정·처리·사례 승인 상태와 문의자의 해결 확인 요청을 우선한다. 알림을 읽은 사실은 해결 확인이 아니다. 에이전트 실행과 오류는 추적하되 모델 내부 사고 과정이나 민감한 정보를 노출하지 않는다. 별도 통계 대시보드, 동일 장애 그룹과 일괄 처리, 우선순위, 전용 운영 복구 화면은 범위에 넣지 않는다.

## 4. 화면 흐름

### 4.1 대표 흐름

문의자는 로그인 → 문의 입력 → 채팅에서 질문·안내 → 무티켓 해결 또는 문제별 티켓 접수·주담당자 배정 → 본인 문의와 진행 조회 → 처리 결과 확인으로 이동한다.

시스템 담당자는 담당 시스템 업무 목록 → 티켓 상세와 관련 대화·근거 확인 → 처리·검증 기록 → 문의자 해결 확인 요청 → Curator 사례 초안 확인·수정·승인 → 검색 반영 상태 확인으로 이동한다. 업무 관리자는 허용된 업무를 조회하고 필요한 경우 책임 시스템·담당자를 수동 정정한다. 화면 구성과 세부 경로는 기능 명세에서 설계한다.

### 4.2 로그인과 접근

자체 계정과 Spring 인증을 통해 접근한다. 문의자는 본인 문의를, 담당자는 맡은 시스템의 업무와 권한 범위의 관련 자료를, 업무 관리자는 허용된 관리 기능을 이용한다. 화면 메뉴 표시와 별개로 서버가 현재 권한을 검사한다. 인증 만료나 접근 권한이 변경되면 입력과 이미 저장된 업무를 보존하며 재인증·재조회한다. 토큰 수명·갱신·쿠키 및 권한 회수의 상세 구현은 관련 계약과 실제 구현을 대조해 확정한다.

### 4.3 메인 페이지와 문의 입력

자연어로 문의를 시작하고 필요하면 지원 시스템을 선택한다. 메시지 저장 확인 전에는 접수 성공으로 표시하지 않는다. 요청 실패나 응답 유실 시 입력을 보존하고 동일한 업무 요청의 저장 결과를 확인해 중복 생성을 방지한다. 지원 범위 밖 시스템은 범위를 안내한다.

### 4.4 채팅과 분석 예외

대화 내역과 추가 질문, 공개 가능한 진행 상태, 안내 및 문제별 결과를 표시한다. 시스템 확인이 필요하면 선택을 요청하며 선택하지 않은 문의는 확인 대기로 보존한다. 티켓 생성·배정이 확인되면 결과 모달을 표시한다. 복합 문의의 추가 질문·성공·생성 실패·저장 결과 미확인을 구분하고 성공한 티켓은 유지한다.

분석 중 문의를 정정하면 원문과 수정 이력을 보존하고 최신 버전으로 분석한다. 이전 버전의 늦은 결과는 최신 상태에 적용하지 않으며 이미 저장된 티켓은 유지한다. 배정 이후의 메시지는 기존 티켓의 보완 정보로 연결한다. 일시 장애·시간 초과·검색 결과 없음·검색 오류를 구분하고, 성공 여부를 확인할 수 없는 경우 성공이나 실패로 단정하지 않는다.

React는 변경 요청을 Spring REST로 보내고 공개 가능한 진행·업무 변경을 Spring SSE로 받는다. 진행 표시와 저장 확정은 구분하며 재접속 뒤 REST로 저장 상태를 다시 확인한다. 이벤트 수신만으로 티켓 생성이나 해결을 확정하지 않는다.

### 4.5 내 문의와 해결 확인

본인의 문의·대화와 연결된 문제·티켓의 상태를 조회하고 대화를 이어간다. 담당자가 처리 또는 기능 구현·검증을 마치면 문의자에게 결과와 해결 확인 요청을 보여준다. 문제별로 해결·미해결을 응답하며, 미해결이면 같은 티켓에서 처리를 이어간다. 응답하지 않으면 확인 대기를 유지한다. 문의자에게 담당자 전용 내부 자료나 타인의 문의 원문을 노출하지 않는다.

### 4.6 담당 시스템 업무와 티켓 상세

주담당자는 맡은 시스템의 티켓을 조회하고, 해당 티켓의 관련 대화·보완 정보·표준 요청·확인 사실·미확인 항목·검색 근거와 처리 이력을 확인한다. 원문은 문의에 보존하고 관련 범위만 권한에 따라 제공한다.

담당자는 처리·검증 내용과 실제 조치를 기록하고 문의자에게 확인을 요청한다. 기능 요청은 구현·검증을 완료한 경우 구현 완료를 기록한다. 잘못된 책임 시스템은 담당자 또는 업무 관리자가 근거와 사유를 남겨 수동 정정한다. 담당자 업무 선점과 자동 재이관은 없다.

### 4.7 업무 관리

업무 관리자는 권한 범위에서 업무 현황과 책임 시스템·담당자를 확인하고 필요한 수동 정정을 지원한다. 업무 조회 권한이 다른 사용자의 모든 대화나 담당자 내부 자료를 무제한으로 볼 권한을 뜻하지 않는다. 별도의 담당자 매핑 예외 큐나 통계 대시보드는 구현 범위에 넣지 않는다.

### 4.8 해결 사례 확인과 승인

해당 시스템 담당자는 처리 기록으로 자동 생성된 사례 초안을 확인하고 필요한 내용을 수정한다. 문의자의 해결 확인 이후 승인할 수 있으며 기능 요청은 구현·검증 완료 기록도 확인한다. 초안·승인·Vector 반영·Neo4j 반영·공개 가능 상태를 구분한다. 한쪽 반영에 실패하거나 상태를 확인하지 못하면 검색 공개 완료로 표시하지 않으며 원인을 수정한 뒤 실패한 반영을 재실행한다. 전용 복구 화면은 필요 조건이 아니다.

### 4.9 알림과 공통 예외

- 배정·처리·사례 승인 상태와 해결 확인 요청을 화면에서 확인한다. 예약 재알림은 후속이다.
- 권한 없음, 찾을 수 없음, 빈 결과와 일시 오류를 구분하고 허용되지 않은 내용을 노출하지 않는다.
- 일시 오류와 재접속 시 입력·저장 결과·성공한 티켓을 보존한다. SSE 재연결만으로 누락 이벤트 복구가 끝났다고 가정하지 않는다.
- 중복 요청, 늦은 분석 결과와 저장 결과 미확인을 다룬다. 구체적인 재시도·동시성·이벤트 계약은 구현 전에 정한다.
- 상태 문구와 표시를 통해 접수, 구현 완료, 해결 확인 대기, 최종 완료 및 검색 공개를 혼동하지 않게 한다.

## 5. 기술 스택 & 인프라

### 5.1 구성과 책임

```text
React: 문의 채팅 / 본인 문의 / 담당 시스템 업무 / 처리 기록 / 사례 확인·승인
  ↕ REST·SSE
Spring: 인증·권한 / 업무 저장 / 시스템·주담당자 조회와 배정 / 상태·승인 확정
  ↕ HTTP·진행 결과
FastAPI + LangGraph: Supervisor + Inquiry·Knowledge·Ticket·Curator
  ↕ 허용 범위의 검색·조회
Vector 저장소 + Neo4j + 읽기 전용 Mock
```

React는 웹 화면, Spring은 인증·인가·업무 저장과 REST·SSE, Python FastAPI·LangGraph는 AI 실행, PostgreSQL은 사용자·시스템 소유권·문의·티켓·승인·상태의 정본을 담당한다. Python의 AI 출력은 제안이며 업무 DB에 직접 쓰지 않는다. 서버가 저장·배정·상태·공개를 검증하고 확정한다. Spring–Python의 세부 요청·진행 전달·서비스 인증·오류 계약은 구현 전에 정한다. 프론트엔드 개발·실행 환경과 실제 서비스 구현 상태는 각 서비스 README를 따른다.

### 5.2 에이전트와 실행 제어

| 역할 | 책임과 호출 시점 |
|---|---|
| Supervisor | 대화 상태·전문 결과·서버 결과를 보고 허용된 다음 행동을 선택하고 응답을 조율 |
| Inquiry | 신규 문의·추가 응답에서 의도·사실·누락·시스템 후보 추출, 추가 질문과 복합 문의 분리 |
| Knowledge | 안내·분석 근거가 필요할 때 Vector·Neo4j 검색, 답변 근거·원인 후보·적용 조건·다음 확인 항목 제시 |
| Ticket | 담당자 처리가 필요한 문제의 제목·내용·처리 유형·책임 시스템을 제안 |
| Curator | 담당자 해결 기록 저장 직후 사례 초안·중복 후보·기존 엔티티 연결 후보 생성 |

Supervisor는 모델 판단으로 다음 처리를 선택한다. 실행 코드는 허용 경로와 시간·호출·토큰·재시도 한도를 강제하며 전문 에이전트의 무제한 상호 호출을 허용하지 않는다. 모든 문의에 모든 역할을 호출하지 않으며 역할 수와 모델 호출 수는 다르다.

사용법은 Inquiry→Knowledge 후 해결 확인, 신청·변경은 Inquiry→필요 시 Knowledge→Ticket, 현상 확인은 Inquiry와 Knowledge의 필요한 상호작용 후 Ticket 또는 근거 안내로 진행한다. Curator는 문의자 상담과 분리된 사후 실행이며 별도 서버 배포를 필수로 요구하지 않는다. Curator 실패는 저장된 처리 기록이나 업무 완료를 취소하지 않는다.

### 5.3 검색과 관계 데이터

Vector 저장소는 표현이 다른 가이드·문의·해결 사례의 의미 유사도를 검색한다. Neo4j는 시스템·기능·증상·가능 원인·확인 항목·해결 사례와 시스템 간 의존 관계를 탐색하며 MVP에 필수다. 초기 관계와 스키마는 담당자가 작성·검토하고 Curator는 새 사례를 기존 엔티티에 연결할 후보를 제안한다. 승인되지 않은 새로운 개념이나 관계 유형을 임의 게시하지 않는다.

가능한 원인과 해결 사례에서 확인된 원인을 구별한다. 그래프 관계는 인과관계나 배정 권한의 정본이 아니다. 시스템 담당자 배정의 정본은 업무 DB다. Vector 저장소·임베딩 모델과 그래프 노드·관계·속성·질의 및 검색 반영 방식은 후속 상세 설계에서 정한다.

### 5.4 모델·배포·품질 원칙

LLM은 서버에서 관리하는 OpenAI API를 사용하며 비용 최소화를 우선한다. 키·비밀번호·토큰을 브라우저·저장소·로그에 노출하지 않는다. 실제 모델·임베딩·호출/시간/비용 상한과 배포 구성은 후속 선정한다. 제한 초과나 외부 API 오류는 업무 성공으로 처리하지 않는다.

권한 없는 접근·민감정보 노출·근거 없는 성공 판정을 방지한다. 서버 저장 결과와 에이전트 제안을 구별하고 이미 저장된 결과를 보존한다. 실제 시스템의 원격 제어, 쓰기 도구·계정 변경·서버 재시작·DB 수정·자동 복구는 제외한다. MVP의 조회 도구는 고정 읽기 전용 Mock이며 필요 시 실제 데모 시스템의 읽기 도구로 확장한다.

## 6. 데이터 개요

### 6.1 가상 기업과 대상 시스템

| MVP 시스템 | 핵심 기능 | 문의 예시 | 시연 수준 |
|---|---|---|---|
| 전자결재 | 문서 작성·조회, 결재 상태, 첨부 열람 | 문서가 안 보임, 일괄 다운로드 요청 | 대표 시나리오 집중, 제한된 Mock·기존 데모 활용 |
| 공통 로그인 | 로그인·SSO, 계정·접근 권한 | 로그인 반복, 권한 요청 | 문서·합성 사례·읽기 전용 Mock |
| 파일 공유 | 업무 파일 조회·공유, 접근 권한 | 공유 파일 열람 불가 | 문서·합성 사례·읽기 전용 Mock |

시스템 ID·기능별 책임 경계·가상 인물은 데이터 설계에서 고정한다. 파일 공유와 전자결재 첨부 저장을 연결할 때 실제 시스템 목록에 정의된 의존 관계만 사용한다. HOPS의 문의 저장·티켓 생성·담당자 처리·사례 승인·검색 반영은 실제 연결 대상이지만 대상 시스템 전체 제품을 새로 만들지는 않는다. 실제 동작과 Mock을 시연에서 구분한다.

후속으로 인사·전자결재·경비 정산·구매의 업무시스템 4종과 인증·문서 저장·알림의 공통 플랫폼 3종으로 확장할 수 있다. 이는 MVP의 3개 시스템과 구별되는 후속 목표다.

### 6.2 관리할 주요 정보와 관계

- **사용자·부서·역할·시스템 소유권:** 사용자 소속, 지원 시스템·기능, 시스템별 주담당자 관계와 변경 이력.
- **문의·대화·문제·표준 요청:** 원문·정정·문의 버전, 문제별 질문·의도·내부 처리 유형, 보고 시스템과 책임 시스템 후보·근거, 확인 사실·추정·미확인 항목.
- **티켓·처리:** 문제와 연결된 티켓, 주담당자 배정, 보완 정보, 처리·검증 기록, 기능 구현 완료와 문의자 해결 확인.
- **지식·해결 사례:** 직원 가이드·정책·담당자 런북·사례 초안·승인 사례, 대상 시스템·기능·증상, 확인된 원인과 조치, 원문·티켓·처리 기록 출처, 문서 버전과 적용 시스템 버전·조건, 작성·승인·공개 범위, Vector·Neo4j 반영 상태.
- **관계·평가·실행:** 시스템 의존 관계와 증상·원인 후보·확인 항목, 가상 시나리오와 평가 분할·정답, 공개 가능한 실행 이력과 오류.

한 문의에 여러 독립 문제가 연결되고 문제별로 처리·확인을 관리한다. 처리 기록과 해결 사례, 업무 완료·승인·검색 공개 상태는 서로 구분한다. 문의·티켓·처리 기록·해결 사례는 삭제하지 않고 보존하며 실제 운영용 보존 기간은 이번 범위가 아니다.

공개 자료는 출처와 사용 조건을 확인한 후 소량의 구조 참고·변환 또는 보조 평가에 사용한다. Jira는 기능 요청·티켓 구조, 후속 질문 데이터는 질문 품질, TechQA는 근거 검색과 답변 보류의 참고 후보다. 원 데이터의 부서·담당자·종료 라벨을 HOPS의 담당자 정답이나 해결 성공으로 그대로 가져오지 않는다. 기존 장애 중심 자료는 새 시스템·문의 의도·소유권 모델에 맞춰 검토하고 기술 부서명을 시스템명으로 일괄 치환하지 않는다.

## 7. 성공 기준

### 7.1 기능 완료

기본 완료 흐름은 **문의 → 질문 → 책임 시스템 주담당자 배정 → 담당자 처리 기록 → 문의자 해결 확인 → 사례 승인과 검색 반영 → 다음 문의에서 재검색**이다. 최소 한 건은 문의자 확인·담당자 승인·동일 승인 버전의 Vector와 Neo4j 반영·새 사례 관계 연결 및 재검색까지 실제로 연결해 확인한다. 사용법 무티켓 해결과 복합 문의의 문제별 티켓 처리도 검증한다.

화면 표시, 모델 응답, Mock 호출이나 이벤트 수신만으로 업무 저장·배정·해결·공개 성공을 인정하지 않는다. 권한 없는 접근, 중복 티켓, 미확인 저장의 중복 재시도, 검색 반영 일부 실패 시 공개, 근거 없는 해결 확정은 수정·재검증 전 완료로 인정하지 않는다.

### 7.2 품질 지표

| 지표 | 측정 기준 |
|---|---|
| 문의 의도 Macro-F1 | 문의 의도 분류 성능 |
| 필수 정보 완성률 | 실제 사용자 응답·근거로 확인한 필수 정보의 비율 |
| 시스템 식별 정확도 | 보고 시스템과 책임 시스템을 올바르게 식별했는가 |
| 자동 처리 범위 | 시스템 미확정·질문 한도 처리와 배정 가능 비율 |
| CASE Hit@3 | 관련 승인 사례가 검색 상위 3개에 포함되는가 |
| 지식 선순환 성공 | 처리 기록→초안→확인·승인→검색→다음 문의 활용이 이어지는가 |
| 응답 시간 | 실행·질문 응답별로 측정하며 사용자 대기와 모델 실행을 구분 |

시스템 식별 성능과 서버의 담당자 매핑 일치율은 분리해 확인하고 AI 성과로 중복 집계하지 않는다. 기존 85%·80%는 후보값이며 데이터 분포와 분모를 확인한 뒤 최종 평가 전에 목표를 확정한다. 작은 테스트셋은 건수와 비율을 함께 보고한다.

### 7.3 평가 데이터와 비교

데이터가 아직 준비되지 않아 기준 사건 수와 개발·테스트 분할 수량은 확정하지 않았다. 30개를 개발 18개·테스트 12개로 나누는 것은 과거 출발 예시다. 번역·표현 변형은 원 사건과 같은 분할에 둔다. 질문은 정답 문장의 일치보다 필요한 정보 확보와 확인한 정보의 반복 여부로 평가한다. 테스트 분포·동결일·응답 대본·검토자는 평가 준비 시 정한다.

테스트 정답 매핑, 숨겨진 요구사항과 평가 사건의 미래 해결 내용은 검색 자료와 프롬프트 예시에 넣지 않는다. 기존 승인된 관련 사례 문서 자체는 검색 대상이 될 수 있지만 해당 평가 사건의 미래 해결 내용을 미리 제공하지 않는다.

멀티 에이전트 환경에서 **Vector 검색과 관계 보강 검색**, **원문과 표준화 자료**의 검색·정보 품질을 비교하고 각 조건의 응답 시간을 측정한다. 동일 질문·지식 내용·승인 문서와 사례 버전·공개 범위·권한·모델 조건을 유지하며 한 조건에만 정답을 추가하지 않는다. 검색 품질과 검색 근거를 사용한 최종 답변 품질을 구분하고 관계 탐색이 필요한 질문과 일반 검색 질문도 나누어 평가한다. 단일/멀티 비교는 수행하지 않는다.

### 7.4 대표 시연

| 시연 후보 | 확인할 가치 |
|---|---|
| 결재 문서 작성 방법 안내 | 근거 답변과 무티켓 해결 |
| 문서가 보이지 않음 | Neo4j 관계 기반 추가 질문·원인 후보·사례 검색 |
| 다운로드 기능 개선 | 현재 방식·문제점·원하는 변경의 표준화와 주담당자 배정 |
| 오류 확인과 기능 추가 동시 문의 | 복합 문의의 문제 분리와 복수 티켓 |
| 처리 후 다른 표현의 두 번째 문의 | 승인된 해결 사례의 Vector·Neo4j 재사용 |

최종 시연 사례 ID·순서와 예외 검증 목록은 개발 중 정한다. 완료 후 재오픈, 지식 자동 비활성화와 담당 매핑 예외 업무를 필수 시연으로 요구하지 않는다.

- 모델 기반 Supervisor와 Inquiry·Knowledge·Ticket·Curator, 실행 제한과 읽기 전용 Mock.
- Vector 의미 검색과 Neo4j 질문·관계 탐색, 새 사례의 기존 엔티티 연결.
- Curator 자동 초안, 문의자 확인 후 담당자 수정·승인, 양쪽 검색 반영 확인과 실패한 반영의 재실행.
- 지식 선순환 최소 한 건의 실제 연결, Vector/관계 보강·원문/표준화 비교 및 응답 시간 평가.

### 8.3 실행 순서

1. 대표 시스템·필수 정보·관계 스키마·에이전트 출력 계약을 정한다.
2. 가상 데이터와 Mock을 준비하고 실제 모델로 문의→배정 흐름을 연결한다.
3. 복합 문의·담당자 처리·문의자 해결 확인을 연결한다.
4. Curator·담당자 승인·Vector/Neo4j 반영과 재검색을 연결한다.
5. 관계 보강·표준화 비교 평가와 응답 시간을 측정한다.
6. 고정한 버전으로 통합 검증과 발표 시연을 수행한다.

단계는 작업 순서이며 앞 단계의 일부 화면이나 Fake 검사만으로 MVP 전체를 완료했다고 판단하지 않는다.

### 8.4 후속·제외 범위

- **후속:** 화면 내 알림을 넘어서는 예약 알림, 필요할 경우 실제 데모 시스템 읽기 도구, 업무시스템·공통 플랫폼 7종 확장.
- **현재 제외:** 계열사·외부 고객사·테넌트·계약·SLA, 선점·수락·업무량·휴가 기반 배정, 담당 매핑 누락·중복·만료의 별도 업무 흐름, 단일 에이전트 구현·비교, 별도 지식 검토자.
- **현재 제외:** 실패 사례의 검색 지식화, 완료 티켓 재오픈, 사례 자동 재검토·자동 비활성화·승인 취소·폐기 전파, 자동 색인 재시도와 전용 복구 화면.
- **현재 제외:** 동일 장애 그룹·일괄 처리, 우선순위, 별도 통계 대시보드, 교육·인수인계 전용 기능, 삭제·폐기 기능, 시스템 직접 변경·자동 복구·원격 제어.

### 8.5 구현 전에 정할 사항

제품 방향을 재논의하기 위한 목록이 아니라 구현과 연결에 필요한 세부사항이다.

- 시스템 ID·기능 책임 경계·가상 인물, 담당자 수동 정정과 권한·관련 대화 범위.
- 문의·문제·티켓·표준 요청·해결 확인·사례 승인·검색 반영의 API·스키마·상태와 전이.
- 복합 문의 부분 실패 시 저장 결과 확인, 동일 작업 식별·멱등성·동시성, 재시도 조작·권한.
- Curator 자동 실행과 사례 버전, 양쪽 반영 상태 확인·공개 제어·중복 없는 재반영 계약.
- Vector 저장소·모델·임베딩·호출/시간/비용 상한, Neo4j 노드·관계·속성·질의.
- 서비스 간 인증·오류, REST/SSE 재접속과 상태 복구, 기존 부서 기반 계약·구현의 전환과 호환성.
- 데이터 수량·검수·평가 분포·목표·동결 버전·시연 목록과 실제 일정·담당자.

개인은 데이터셋·프롬프트·검색·도구 전략을 실험하고 출처·조건·결과를 공유할 수 있다. 공통 데이터와 기본 설정은 검토 후 선정한다. 구현 상태와 검증 결과는 실제 수행한 범위만 기록한다.
