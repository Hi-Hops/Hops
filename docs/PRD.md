# 사내 IT 장애·문의 대응 PRD

버전: 1.43 · 갱신: 2026-10-27 · 개발 기준 반영 / 칸반 MVP 확장안 팀 리뷰·구현 검증 별도

이 문서는 프로젝트의 목적, 사용자, 핵심 기능, 화면 흐름, 기술 구성, 데이터 개요, 성공 기준과 개발 범위를 정의한다. 이 문서는 초기 팀 공유용 기획안이다. API와 데이터 구조의 전체 흐름 설계안은 [API 설계](API.md)와 [데이터 설계](DATA.md)를 참조한다. 세부 상태 전이와 평가 실행 조건을 포함한 구현 계약은 관련 개발을 시작하기 전에 팀이 합의한다. 이전에 작성한 상세 설계는 검토 자료이며 이 문서만으로 모두 승인된 구현 기준이 되지 않는다.

## 1. 서비스 목적

### 1.1 해결하려는 문제

IT 업무가 여러 전문 부서로 나뉜 기업에서는 문의자가 문제 원인과 담당 부서를 알기 어렵다. 담당자는 부족한 정보를 다시 확인하고 단순 안내·초기 진단을 반복한다. 잘못된 배정이나 여러 문제가 섞인 문의는 재이관과 맥락 재확인을 유발한다. 관리자는 처리 현황과 배정 오류를 함께 파악해야 한다.

이는 가상 기업 시나리오로 검증할 문제 가정이며 실제 기업 조사로 입증한 사실이나 이미 달성한 개선 성과는 아니다.

### 1.2 제공 가치

임직원이 웹 챗봇에 자연어로 문의하면 에이전트가 필요한 정보를 모으고, 해결 방법을 안내하거나 담당 부서가 처리할 수 있는 티켓으로 정리한다. 핵심 목표는 **문제를 올바른 부서에 연결하고 진단 근거와 대화 맥락을 전달하는 것**이다. 안내와 읽기 전용 진단으로 사람의 반복 업무를 줄이고 처리 이력을 추적할 수 있게 한다.

여러 문제가 섞인 문의는 필요한 복수 티켓으로 나누고, 동일 장애로 발생한 여러 문의는 사용자별 티켓을 유지하면서 함께 처리한다.

### 1.3 대상 환경과 검증 방향

실제 도입 기업은 정해져 있지 않다. 전문 IT 부서가 나뉜 가상 기업과 데이터를 구성하고 PC 웹·한국어·텍스트 기반 서비스를 구현한다. MVP는 실제 LLM을 사용하는 단일 에이전트로 서비스 연결과 업무 처리를 구현하고 평가 결과를 기준선으로 보존한다. 최종 단계는 Supervisor와 4개 전문 에이전트로 개선하고, 단일 에이전트와 최종 멀티 에이전트의 분류·배정 정확도, 응답 시간과 실패율을 같은 조건에서 비교하여 성과를 설명한다. Fake는 개발 중 연결 테스트에만 사용할 수 있으며 모델 품질 평가나 MVP 완료를 대신하지 않는다. 특정 자동화율이나 실제 기업 운영 수준을 측정 전에 보장하지 않는다.

## 2. 핵심 사용자

핵심 사용자는 개발팀의 역할이 아니라 서비스를 사용하는 기업 내 대상이다. 한 사람이 여러 역할을 가질 수 있다.

- **문의자:** IT 지원이 필요한 임직원. 문의·추가 질문 응답·내용 정정·처리 상태 조회·해결 확인을 수행한다.
- **IT 담당자:** 부서에 배정된 티켓을 가져와 처리하고 잘못 배정된 티켓의 재이관을 요청한다. 담당자도 자신의 문의를 등록할 수 있다.
- **업무 관리자:** 전체 업무 현황, 배정 예외와 생성 실패를 확인하고 수동 배정·오류 정정을 수행한다.
- **에이전트 운영 관리자:** 실행 이력과 근거 요약을 확인해 AI 처리 오류를 추적하고, 티켓 생성·재이관의 기술 실패를 복구한다. 업무 관리자와 별도 권한이며 복구 권한만으로 담당 부서나 업무 결론을 변경하지 않는다.

자체 계정으로 로그인하고 Spring이 발급한 JWT로 인증한다. JWT에는 사번과 소속 부서명을 포함하며 회원 ID·부서 ID·부서 코드·역할을 함께 전달한다. 부서명은 표시 정보이고, 접근 권한은 회원·부서 식별자와 현재 업무 상태로 검사한다. 사용자 소속 부서와 티켓 처리 부서는 구분한다. 문의자는 본인 문의를, 현재 처리 부서 구성원은 해당 부서 티켓과 관련 대화를 조회한다. 업무 관리자의 업무 조회와 운영 관리자의 로그 조회를 구분하며 직급만으로 추가 권한을 부여하지 않는다. 부서·역할 변경 시 기존 인증과 실시간 구독을 회수하고 재로그인을 요구한다. 정확한 개발 기준과 담당 구현·검증은 공통 계약 10·11절을 따른다.

## 3. 핵심 기능

이 장은 제품 전체의 핵심 동작을 설명한다. MVP·후속 필수·선택·제외 범위는 8장에서 구분한다.

### 3.1 대화 기반 문의 분석과 복수 티켓 생성

한 대화 세션을 문의 한 건으로 관리한다. 에이전트는 서비스·증상·오류·발생 시점 등을 대화로 파악한다. 문의 유형은 계정·인증, 권한, 네트워크·접속, 소프트웨어, 업무 서비스 오류, 기타의 6개다.

같은 문제의 추가 질문은 최대 3회이며, 이후에도 부서를 판별하기 어려운 IT 문의는 CS 검토 티켓으로 연결한다. 범위 밖 질문에는 안내하고 티켓을 만들지 않는다. 모델·통신 장애는 분류 실패와 구분한다.

복합 문의는 필요한 처리 단위별로 자동 분할하고 복수 티켓을 생성한다. 티켓 수에 고정 상한을 두지 않으며 판별된 문제부터 생성하고 나머지는 추가 확인할 수 있다. 에이전트가 제안한 결과를 서버가 검증해 생성·부서 배정을 확정한다. 사용자 승인이나 부서 수락은 요구하지 않는다.

문의자는 결과를 정보 카드로 확인하고 내용을 정정하거나 대화를 이어갈 수 있다. 일부 생성이 실패해도 성공한 티켓은 유지하고 실패 항목을 복구한다. 중복 요청으로 같은 업무의 티켓을 중복 생성하지 않는다.

### 3.2 지식 답변과 장애 진단

Supervisor가 다음 4개 전문 에이전트의 경로와 순서를 조율한다.

- **문의 분석:** 사용자 표현 정리, 추가 질문, 유형 분류와 문제 분할.
- **Knowledge:** 접근 가능한 정책·과거 사례·런북에서 근거 검색과 답변 구성.
- **Diagnosis:** 허용된 읽기 도구로 상태를 조회하고 원인 후보와 근거 검토.
- **Ticket:** 티켓 내용·담당 부서·재이관 후보 제안.

단순 질문은 지식 답변으로 처리하고 사용자가 해결을 확인하면 티켓 없이 문의를 완료한다. 미해결·근거 부족이면 대화 맥락을 유지해 진단으로 전환한다. 모든 에이전트를 고정 순서로 실행하지 않으며 서로의 결과가 필요 없는 검색·진단은 병렬로 수행할 수 있다.

검색은 Hybrid 검색을 기본으로 하고 근거가 부족하면 반복 검색을 사용한다. 서비스·의존 자원·담당 부서·런북의 관계가 필요한 경우 GraphRAG를 사용한다. 근거 검토는 Diagnosis 내부 단계이며 별도 Critic 에이전트를 두지 않는다.

### 3.3 부서 배정과 담당자 처리

가상 기업의 처리 부서는 계정 권한, 네트워크, CS, DB, backend, frontend, 인프라, 시스템의 8개다. 인프라는 가상화·컴퓨팅·스토리지 등 실행 기반을, 시스템은 OS·서버 공통 설정·시스템 서비스를 담당한다. 문의 유형과 부서는 일대일 관계가 아니다.

티켓 생성 시 부서를 배정하고, 해당 부서 구성원이 미담당 티켓을 가져와 개인 담당자가 된다. 이미 가져간 티켓은 반환 전까지 다른 사람이 가져갈 수 없다. 개인 담당자 자동 선정은 선택 기능이다.

담당자가 재이관을 요청하면 에이전트가 제외 이력을 반영해 부서를 다시 판단한다. 유효 후보가 소진되면 배정 예외로 업무 관리자가 처리한다. 기술 장애로 인한 복구 대기, 정상 CS 검토, 티켓 생성 자체의 실패는 서로 구분한다.

### 3.4 해결 확인과 종료

안내를 제공하거나 도구가 성공했다는 사실만으로 해결을 확정하지 않는다. 개별 티켓은 담당자 처리 완료 후 사용자 해결 확인을 받아 최종 완료한다. 처리 중 사용자가 먼저 해결을 알리면 담당자가 진행 작업을 확인한 후 완료한다.

사용자 확인 대기 진입 후 24시간 무응답이면 해결 여부 확인 알림을 보낸다. 서비스 알림함에 저장된 시점부터 48시간 추가 무응답이면 미확인 종료한다. 알림 저장이 끝내 실패하면 자동 종료를 보류한다. 미확인 종료는 해결 완료나 AI 해결 실적으로 집계하지 않는다.

종료된 티켓의 문제가 해결되지 않았다고 재문의하면 기존 티켓을 재오픈하고 이력을 보존한다. 티켓 없이 안내만 받은 문의는 대화를 재개하고 필요하면 티켓을 생성한다. 문의자는 문의를 숨기거나 복원할 수 있지만 삭제할 수 없다.

### 3.5 동일 장애 그룹과 우선순위

같은 처리 부서에 배정된 미완료 티켓 중 공통 장애 하나를 해결하면 함께 해결된다는 근거가 있는 티켓을 자동으로 그룹핑한다. 문장 유사성만으로 묶지 않으며 사용자별 티켓은 유지한다. 티켓 데이터를 임베딩 벡터로 변환하고 벡터 유사도 검색으로 기존 티켓·그룹 후보를 찾는다. 검색된 후보 중 동일 장애이며 공통 조치로 함께 해결된다는 근거가 있는 대상만 자동으로 묶는다. Spring이 부서·업무 상태·그룹 조건을 검증하고 그룹 저장을 확정한다. 근거가 부족한 티켓은 개별 상태를 유지한다. 임베딩 대상 필드·모델·유사도 임계값·그룹 대표 방식은 후속 설계에서 정한다.

그룹 담당자가 공통 장애를 해결하면 대상 티켓을 일괄 완료하며 개별 사용자의 사전 해결 확인을 기다리지 않는다. 이후 미해결을 알린 문의자의 티켓만 분리·재오픈하고 다른 티켓은 완료 상태를 유지한다. 잘못된 그룹핑은 정정할 수 있고, 분리된 티켓을 다시 결합할 때는 업무 관리자 확인이 필요하다.

우선순위는 긴급·높음·보통·낮음으로 구분하고 업무 영향·우회 가능성·서로 다른 영향 사용자 수를 함께 고려한다. 에이전트가 변경을 제안하고 서버가 검증하며 수동 조정을 지원한다. 사용자 수만으로 긴급을 확정하지 않는다.

### 3.6 현황·알림·추적

문의 전체의 종합 상태와 문제별 현황을 함께 보여준다. 티켓 생성 완료를 문제 해결 완료로 표시하지 않으며 처리 상태와 배정 상태를 구분한다.

부서 이관 수·처리 중 티켓 수·AI 해결률과 무티켓 해결 건수를 제공한다. 담당자·그룹 해결을 AI 단독 해결로 집계하지 않는다. 서비스 내부 알림과 에이전트 실행 단계·근거 요약을 제공하고 모델 내부 사고 과정은 기록하지 않는다.

에이전트 운영 관리자는 실행 이력에서 실패한 단계와 서버 검증 결과를 확인하고, 기술 복구 화면에서 보존된 작업과 재시도 이력을 확인한다. 복구는 기존 작업 식별자를 사용하며 이미 생성·배정된 업무를 중복 처리하지 않는다.

## 4. 화면 흐름

### 4.1 대표 흐름

문의자는 로그인 → 메인 문의 입력 → 채팅에서 분석·추가 질문·안내 → 무티켓 해결 또는 복수 티켓 생성·부서 배정 → 내 문의 내역·상세에서 진행과 해결 여부 확인으로 이동한다.

담당자는 부서별 티켓 현황 → 티켓 상세 또는 장애 그룹 상세 → 가져오기·처리·해결 확인 또는 재이관으로 이동한다. 업무 관리자는 관리자 대시보드 → 예외 티켓 상세·수동 배정·재검토 또는 그룹 재결합 검토를 수행한다. 에이전트 운영 관리자는 에이전트 운영 → 실행 이력·상세 → 기술 복구에서 실패 원인과 재시도 결과를 확인한다.

알림함은 권한이 있는 관련 화면으로 연결하고, 상세 통계는 역할별 조회 범위를 따른다. 아래는 최종 목표 화면이며 상세·예외 화면이 추가되어도 8장의 MVP·후속 범위를 자동으로 확대하지 않는다.

### 4.2 JWT 로그인과 인증 만료

**목표:** 자체 계정으로 로그인하고 역할에 맞는 화면에 접근한다.

로그인 성공 후 JWT를 받아 메인으로 이동하고, React는 인증된 사용자로 Node.js Socket.IO 서버에 연결한다. 계정·비밀번호 오류는 로그인 화면에서 안내한다. 토큰이 만료되면 공통 계약 10절의 refresh 정책을 적용하고, 갱신할 수 없으면 입력을 보존한 채 재로그인을 안내한다. 재인증 후 현재 권한으로 다시 연결·구독하고 저장된 문의를 이어간다. 로그아웃 시 브라우저의 인증 정보를 정리하고 관련 채팅 연결을 종료한다. Access 15분·Refresh 최초 로그인부터 절대 7일·갱신마다 회전하며 현재 로그인 세션만 로그아웃한다. 역할/부서 변경·계정 차단은 해당 사용자의 기존 인증·구독을 회수하고 재로그인을 요구한다. 키·쿠키/CSRF·환경별 설정의 실제 구현·검증은 백엔드 담당이다. 인증 만료나 소켓 연결 종료만으로 이미 접수된 서버 작업을 취소하지 않는다. 미전송 입력이 남아 있다면 사용자가 확인한 뒤 같은 요청 식별자를 사용해 재전송한다. 로그인 인증 수명과 '한 대화 세션 = 한 문의'라는 업무 단위는 별개다.

### 4.3 메인 페이지

**목표:** IT 문제나 신청 사항을 자유롭게 입력해 상담을 시작한다.

문의는 React → Node.js Socket.IO 서버 → Spring 경로로 전달하고, Spring이 문의와 첫 메시지를 저장한 결과를 채팅에 반영한다. Node.js의 수신과 Spring의 저장 완료를 구분하며 저장 확인 전에는 전송 중으로 표시한다. 전송 실패 시 내용을 보존하고 같은 요청 식별자로 재시도할 수 있게 한다. 진행 요청 상태 영역은 선택 기능이다. 시나리오 카드로 입력창에 예시 질문을 채우는 기능은 현재 제공 범위에 포함하지 않는다.

### 4.4 채팅과 분석 예외

**목표:** 대화로 문제를 구체화하고 안내·진단·티켓 생성 결과를 확인한다.

- **기본 화면:** 대화 내역, 추가 질문, 단계별 해결 가이드, 실시간 답변과 분석 진행 상태를 표시한다. 티켓 생성 결과는 정보 카드로 보여주며 승인 조작을 요구하지 않는다. 예시 질문 선택·단계/링크가 있는 구조화 가이드는 후속으로 두며 MVP는 텍스트 답변·문제 상태·저장 티켓 카드로 표시한다. PDF 매뉴얼 열람은 선택 기능이다.
- **실시간 반영:** Socket.IO로 메시지·정정 요청을 Spring에 전달하고 저장 결과·분석 진행·답변 조각·업무 변경 이벤트를 받는다. 답변 조각은 진행 표시이며 최종 답변과 티켓 상태는 Spring의 저장 결과로 확정한다. 중복 이벤트를 중복 표시하지 않고, 이전 문의 버전의 미반영 분석 결과를 최신 결과에 덮어쓰지 않는다.
- **복수 티켓·부분 실패:** 생성·배정된 티켓과 아직 추가 질문이 필요한 문제, 생성 실패 항목을 구분한다. 일부 실패가 있어도 성공한 티켓은 유지한다.
- **메시지 정정·다시 분석:** 분석 중인 문제의 내용을 정정하면 이전 내용과 수정 이력을 보존하고 최신 문의 버전으로 다시 분석한다. 이전 실행의 미반영 결과는 적용하지 않으며 이미 생성된 티켓은 유지한다.
- **이관 이후 입력:** 모든 문제의 분석·티켓 생성·이관이 완료된 뒤에도 입력창은 유지한다. 추가 메시지·정정은 기존 문의의 정보 보완으로 저장하고 관련 티켓 상세에서 담당자가 확인한다. 이를 이유로 자동 재진단·재배정·새 티켓 생성을 수행하지 않는다. 사용자 해결 확인 응답은 기존 절차로 별도 처리한다. 아직 분석 중이거나 추가 질문이 필요한 문제는 해당 문제의 분석을 계속한다.
- **새 문의 분리:** 별개 문의로 판단되면 새 문의로 시작할지 사용자에게 묻는다(HITL). 동의한 경우에만 새 대화 세션과 문의를 생성하고 필요한 관련 문맥과 출처 연결을 남긴 뒤 새 채팅으로 이동한다. 기존 문의·티켓·처리 상태는 유지하고 재시도나 중복 동의로 새 문의를 중복 생성하지 않는다. 동의하지 않거나 응답하지 않으면 새 문의를 만들지 않는다. 이는 새 문의 분리 확인이며 기존 문의 안의 티켓 자동 생성에 승인을 추가하지 않는다.
- **시간 초과·입력 초과:** 분석 시간 초과는 해결 실패나 CS 분류와 구분해 재시도를 안내한다. 4,000자 초과 입력은 전송하지 않고 원문과 수정 안내를 유지한다.
- **해결 신고:** 사용자가 해결을 알리면 관련 문제·티켓을 구분해 기존 해결 확인 절차로 연결한다. 대화나 버튼 한 번으로 처리 중인 모든 티켓을 일괄 완료하지 않는다.

### 4.5 내 문의 내역과 문의 상세

**목표:** 본인 문의의 종합 상태와 문제·티켓별 진행 상황을 확인하고 대화를 이어간다.

- **목록·숨긴 문의:** 문의 목록을 검색·필터·정렬하고 숨긴 문의를 별도로 확인·복원한다. 숨기기는 개인 목록 표시만 바꾸며 티켓과 업무 이력을 삭제하지 않는다.
- **상세 모달:** AI 요약, 연결된 여러 티켓 목록과 세부 현황을 표시하며 채팅 로그 영역은 제공하지 않는다. 대화 확인·추가 입력은 기존 채팅 화면에서 수행한다. 이 모달에서는 티켓 목록만 확인하며 담당자용 개별 티켓 상세로 이동하지 않는다. 같은 문의의 채팅을 이어갈 수 있다.
- **해결 신고:** 처리 중인 개별 티켓에 해결을 신고하면 담당자의 진행 작업 확인을 기다리는 상태를 표시한다. 담당자 확인 없이 업무를 완료하지 않는다.
- **해결 확인 응답:** 담당자의 처리 완료 후 해결 확인 요청에 응답한다. 해결됐으면 최종 완료하고, 미해결이면 해당 티켓의 처리를 이어간다. 그룹 완료 후 미해결 재문의는 해당 문의자의 티켓만 분리·재오픈한다. 무응답은 3.4의 알림·미확인 종료 정책을 따른다.

### 4.6 부서별 티켓 현황·티켓 상세·장애 그룹 상세

**목표:** 부서에 배정된 업무를 가져와 처리하고, 공통 장애와 개별 문제를 구분한다.

- **부서 현황:** 현재 부서에 배정된 티켓과 본인 담당 티켓을 확인한다. 동일 장애 그룹은 묶어서 표시하되 구성 티켓은 보존한다. 부서 통계만 조회에 실패하면 해당 영역에 재시도를 제공하고 정상 조회된 티켓 목록은 계속 사용할 수 있다.
- **보드·목록 전환(MVP):** 툴바의 `보드 | 목록`으로 읽기 전용 표시를 전환한다. 보드는 처리 대기·처리 중·사용자 확인 대기·종료의 4개 컬럼이며 종료에는 해결 완료와 미확인 종료를 함께 표시하되 각 카드에서 구분한다. 배정 상태는 처리 상태와 별도 표시한다. 카드에는 담당자·내 담당 여부, 우선순위와 설정 출처, 요청자·소속, 문의 유형, 해결 신고, 장애 그룹 정보를 포함한다. 저장된 값이 없으면 미지정·미배정·그룹 없음으로 표시하며 프론트가 추정하지 않는다. 장애 그룹은 접고 펼칠 수 있는 가로 구역으로 묶고 그룹 외 티켓도 표시한다. 이 조회 표시는 MVP에 포함하지만 그룹 생성·일괄 해결·담당자 변경·해결 신고 저장은 후속이다.
- **검색·조회(MVP):** 티켓 번호·제목의 기본 검색과 내 담당·긴급·높음·해결 신고 빠른 필터를 제공한다. 검색과 필터는 서버의 권한 범위 전체에 적용하고 받은 페이지만 거르지 않는다. 컬럼별 전체 건수와 `더 보기`를 제공하며 종료 컬럼도 두 상태를 합친 조회·건수·페이지를 지원한다. 정렬은 생성 시각 내림차순·동률 ID 내림차순이고 종료 기간은 제한하지 않는다. 일부 컬럼 조회·추가 조회 실패가 정상 컬럼이나 이미 표시한 카드를 막지 않으며 실패한 조회를 재시도할 수 있다.
- **보기 유지와 접근성(MVP):** PC 기본은 보드, 좁은 화면 기본은 목록이며 URL의 명시적인 보기 선택을 우선한다. 보기·검색·필터는 상세 모달 열기/닫기와 새로고침 후에도 유지한다. 보기 전환은 페이지를 초기화하고 목록의 처리 상태 필터는 보드에서 적용하지 않는다. 키보드로 보기 전환·카드 상세 이동·더 보기를 사용할 수 있으며 드래그로 업무 상태를 바꾸지 않는다. 상태 변경 이벤트는 REST 재조회 신호로만 사용한다. 상세 동작은 F009를 따른다.
- **티켓 상세:** 해당 티켓 관련 사용자·AI 대화를 시간순으로 조회하고 이관 이후 보완 정보·정정 이력을 확인한다. 대화 원본은 문의에 보존하고 티켓에서는 관련 범위만 참조하며 다른 문제의 대화나 내부 운영 로그는 노출하지 않는다. 현재 처리 부서 구성원도 가져오기 전에 권한 범위의 관련 대화를 확인할 수 있다. 진단 근거·처리 이력과 현재 담당을 확인하고 가져오기·처리 완료·재이관을 수행한다. 사용자 해결 신고가 있으면 담당자가 진행 작업을 확인한다. 개별 티켓의 처리 완료는 사용자 해결 확인 대기로 이어진다.
- **AI 내용 정정:** 티켓 담당자 또는 업무 관리자가 권한 범위에서 잘못된 요약·분류·진단 등 AI 작성 내용을 정정한다. 변경 전후 내용과 수정 주체·시각·사유를 보존하며 정정만으로 업무 완료나 재배정을 확정하지 않는다.
- **재이관·복구 필요:** 담당자가 재이관을 요청하면 진행 상황을 표시한다. 후보 소진에 따른 배정 예외와 기술 장애에 따른 복구 필요를 구분한다. 기술 실패를 재이관 성공으로 표시하지 않으며 운영 관리자의 복구 대상으로 연결한다.
- **장애 그룹 상세:** 대표 티켓, 공통 장애 근거, 구성 티켓·영향 사용자와 그룹 담당을 확인한다. 그룹 담당자가 공통 장애를 해결하면 구성 티켓을 일괄 완료한다. 일부 완료 반영이 실패하면 성공·실패 항목을 나누어 표시하고 전체 성공으로 표시하지 않는다.
- **그룹 이후 재오픈:** 해결되지 않았다는 재문의가 들어오면 해당 티켓만 그룹에서 분리·재오픈하고, 다른 티켓의 완료와 그룹 처리 이력은 유지한다. 분리된 티켓의 재결합은 업무 관리자 검토로 연결한다.

### 4.7 업무 관리자 대시보드와 검토 화면

**목표:** 업무상 배정 예외·오류를 판단하고 필요한 정정·수동 배정을 수행한다.

대시보드에서 미해결 티켓, 배정 예외와 생성 실패를 구분해 조회한다. 예외 티켓 상세에서는 문의·진단·이전 배정·재이관 사유를 확인하고 재검토 또는 수동 배정 결과를 기록한다. 생성 실패 항목은 티켓이 아직 없을 수 있으므로 기존 티켓 상세와 구분한다. 기술 복구는 운영 관리자 영역과 연결하며 업무 관리자의 재검토와 혼동하지 않는다.

그룹 재결합 검토 화면에서는 이전 분리 사유, 새 근거, 대상 그룹과 티켓 상태를 비교한다. 업무 관리자만 재결합 여부를 결정하며 서버가 같은 부서·미완료 상태·공통 해결 근거를 다시 검사한다. 결정 사유와 이력을 보존한다.

에이전트 운영 이력은 별도 권한으로 접근한다. 지식 문서 편집은 제공하지 않는다.

### 4.8 에이전트 운영 관리자 페이지

**목표:** AI 실행 오류와 업무 반영 실패를 추적하고, 기존 결과를 보존하면서 기술적으로 복구한다. 에이전트 운영 관리자 권한으로 접근한다.

**실행 이력 → 실행 상세**

실행 ID·문의 번호·추적 ID로 검색하고 기간·실행 상태로 조회한다. 성공·실패·재시도 필요·중단·진행 중인 실행을 구분한다. 선택한 실행에서 연결 문의와 문의 버전, 실행 시각·소요 시간, 모델·프롬프트/스키마 버전, 오류 코드, 단계별 실행 순서와 시간을 확인한다.

각 단계의 근거 요약, 도구 호출·응답 상태와 마스킹된 입출력, 실패·재시도 이력을 확인한다. 에이전트가 제안한 판단과 Spring이 검증·저장한 결과를 분리해 표시한다. 실행이 실패했어도 이미 반영된 업무가 있다면 그 사실을 표시한다. 내부 사고 과정·비밀값은 제공하지 않으며 운영 로그 보존 기간은 30일이다.

**기술 복구 목록 → 복구 상세 → 다시 시도 → 결과 확인**

티켓 생성 실패·배정 저장 실패·재이관 기술 실패를 미처리/완료로 나누어 조회한다. 복구 상세에는 원본 문의·문제·작업 또는 티켓 식별자, 관련 실행, 오류 코드, 보존된 제안, 자동·수동 재시도 이력과 결과를 표시한다.

권한 있는 운영 관리자가 실패한 작업을 다시 시도한다. 서버는 최신 문의·업무 상태와 기존 성공 여부를 검사하고 동일한 작업을 중복 저장하지 않는다. 복구 완료 후 생성된 티켓·배정 결과를 연결하고, 계속 실패하면 원인과 현재 상태를 남긴다. 재시도 요청 접수를 복구 완료로 표시하지 않는다.

기술 복구 권한만으로 부서·문의 유형·업무 결론을 수동 변경하거나 사용자 해결 확인을 대신할 수 없다. 업무 판단 수정이 필요하면 업무 관리자 검토로 연결한다. 모델·프롬프트 편집, 모델 배포, 지식 문서 편집은 이 페이지의 기능으로 추가하지 않는다.

### 4.9 서비스 알림함

**목표:** 사용자가 본인에게 필요한 업무 변화와 확인 요청을 놓치지 않도록 한다.

알림함에서 역할과 수신 권한에 맞는 알림을 확인하고 관련 문의·티켓·검토·복구 화면으로 이동한다. 문의자의 해결 확인 요청, 담당자의 배정·처리 관련 알림, 관리자의 예외·복구 관련 알림을 구분한다. 알림을 읽는 행위는 해결 확인이나 처리 완료를 뜻하지 않는다.

알림이 없는 상태와 조회 실패를 구분하고 실패 시 다시 시도할 수 있게 한다. 링크 대상의 접근 권한은 이동 시점에 다시 검사한다. 재이관 진행 알림은 기존대로 후속 기능이며 현재 진행은 문의 내역에서 확인한다.

### 4.10 상세 통계

**목표:** 처리 현황과 AI 해결 성과를 동일한 집계 기준으로 확인한다.

업무 관리자는 전체·부서별 통계를, 부서 구성원은 본인 부서 통계를 조회한다. 기간과 허용된 부서 범위를 선택해 이관 수·처리 상태별 티켓 수·AI 해결률·무티켓 해결 건수를 확인한다. 무티켓 해결은 부서 티켓 AI 해결률과 별도 지표로 표시한다.

집계 기간·기준 시점과 지표 정의를 함께 표시한다. 집계 대상 없음과 조회 실패를 0건으로 오인하게 표시하지 않는다. 통계 조회 권한만으로 다른 부서 티켓·문의 원문 접근 권한을 부여하지 않는다. 기존 제외 범위인 관리자 대시보드 차트·CSV 기능을 추가하는 의미는 아니다.

### 4.11 공통 예외와 사용성·보안 원칙

- **권한 없음:** 다른 부서 티켓 등 접근 권한이 없는 화면은 내용을 노출하지 않고 접근 가능한 목록으로 돌아가도록 안내한다.
- **찾을 수 없음:** 잘못된 주소나 존재하지 않는 대상을 안내하고 메인 또는 관련 목록으로 돌아갈 수 있게 한다.
- **일시 서버 오류:** 입력과 정상 저장된 결과를 보존하고 재시도를 제공한다. 재전송으로 중복 문의·티켓을 생성하지 않는다.
- **부분 실패:** 통계·알림 등 일부 영역의 실패가 정상 조회된 업무 영역까지 막지 않게 한다. 처리 중·빈 결과·실패·일부 성공을 구분한다.
- **재접속·상세 닫기:** React–Node.js 또는 Node.js–Spring 연결이 끊기면 구간별 오류를 표시하고 입력·저장 결과를 보존한다. 재접속 후 인증·구독 권한을 다시 확인하고 REST로 저장된 대화·문의·티켓 상태를 동기화한다. Socket.IO 재연결만으로 누락 이벤트가 모두 복구되었다고 가정하지 않는다. 상세 모달을 닫으면 기존 목록의 검색·필터·페이지를 유지한다.
- **정보 보호:** 각 화면은 역할 범위 안의 정보만 보여주며 서버가 권한을 검사한다. 상태 문구와 색상을 함께 사용하고 사용자에게 작업 성공이나 해결 여부를 오해하게 표시하지 않는다.

## 5. 기술 스택 & 인프라

### 5.1 구성과 책임

프론트엔드 개발·빌드 환경은 Node.js 24.22.0 LTS, React·React DOM 19.3.0, Vite 8.3.4, @vitejs/plugin-react 6.1.2를 사용한다.

React는 웹 화면, Node.js + Socket.IO는 별도 채팅·실시간 이벤트 서버, Java 21 기반 Spring은 JWT 발급·인증·권한·업무 처리, Python 3.13 + LangGraph + FastAPI는 AI 서버, PostgreSQL은 업무 데이터 저장을 담당한다. React와 Spring은 각각 Socket.IO 클라이언트로 Node.js 서버에 연결한다. Node.js는 연결·구독과 이벤트 중계를 담당하고 Spring이 메시지·업무 저장과 상태를 확정한다. LangGraph는 Supervisor와 4개 에이전트의 실행 순서·분기·상태를 관리하고, FastAPI는 Spring 연동용 HTTP API와 스트리밍 응답 계층을 담당한다. 에이전트는 하나의 AI 서버 내부 모듈로 구현한다. 초기 개발 버전은 Spring Boot 4.1.1, LangGraph 1.2.16, FastAPI 0.143.5, Uvicorn 0.53.0으로 고정한다. Spring 빌드는 Gradle Kotlin DSL과 저장소의 Gradle Wrapper 9.8.1을 사용한다. Socket.IO 서버·React용 클라이언트·Java용 클라이언트의 호환 버전과 채팅 서버 런타임은 통합 전에 선정한다. PostgreSQL 등 아직 선택하지 않은 버전은 별도로 정한다. 모델은 판단과 초안을 제안하고 권한·저장·상태 확정은 Spring이 검증한다. Node.js와 Python은 업무 DB에 직접 쓰지 않는다.

로그인·목록·상세 조회와 티켓 업무 변경은 React–Spring REST를 사용하고, 문의 생성·채팅 메시지·정정·새 문의 분리 동의는 React → Node.js → Spring의 Socket.IO 이벤트로 전달한다. 실시간 채팅과 관리자 대시보드 변경은 Spring → Node.js → React 경로로 전달한다. React는 이벤트로 진행 표시를 갱신하고 업무 변경 시 REST로 저장 상태를 다시 조회한다. Socket.IO는 일반 WebSocket과 다른 프로토콜이므로 양쪽 클라이언트도 Socket.IO 호환 구현을 사용한다. room 구독은 권한 확인 후 서버가 허용하며 문의 전체 대화와 티켓별 관련 대화의 조회 범위를 구분한다. 사용자 연결과 Spring 서비스 연결은 별도로 인증하고, Node.js가 전달한 사용자 문맥도 Spring이 검증한다. 토큰 검증·만료·갱신·부서 변경에 따른 구독 해제는 [API 설계](API.md)에서 상세화한다.

Spring–Python 간 에이전트 진행 상태 전달에는 SSE(Server-Sent Events)를 사용한다. Spring은 HTTP로 실행을 요청하고 Python FastAPI가 제공하는 SSE 스트림을 구독한다. Python은 에이전트 시작·검색·도구 조회·완료·실패 등 실행 이벤트를 보내고, Spring은 사용자 권한과 문의·실행 식별자를 확인해 공개 가능한 진행·근거 요약을 Node.js에 전달한다. Node.js는 허용된 React 구독자에게 Socket.IO로 중계한다. 내부 사고 과정은 전달하지 않는다. 최종 AI 결과 전달 경로, SSE 경로·이벤트 스키마·재연결·중복 처리·서비스 인증은 상세 계약에서 정한다. SSE 수신·Socket.IO ACK·에이전트 실행 완료만으로 티켓 저장·부서 배정 성공을 확정하지 않는다.

MVP는 하나의 실제 에이전트가 문의 분석·추가 질문·복합 문제 분리·티켓 제안을 수행한다. 단일 에이전트는 모델 호출 1회만 허용한다는 뜻이 아니다. 최종 단계는 Supervisor와 문의 분석·Knowledge·Diagnosis·Ticket의 4개 전문 에이전트로 확장하되 화면·업무 API·저장 책임 경계를 유지한다.

### 5.2 모델·배포·비용 제약

LLM은 OpenAI API를 사용한다. Python AI 서버가 모델을 호출하며 API 키는 서버의 환경 변수 또는 비밀 관리 기능으로 관리하고 브라우저·저장소·로그에 노출하지 않는다. 서비스는 외부 API 연결이 가능한 환경에서 실행하며 클라우드 배포도 허용한다.

비용 최소화 원칙을 유지한다. 초기 단일 에이전트는 공통 계약 10절의 60초·최대 3회 LLM 시도·자동 재시도 최대 1회·호출당 출력 최대 1,500토큰을 적용한다. 재시도는 전체 시간/횟수 안에 포함한다. 사용할 OpenAI 모델·SDK 버전·금액 상한·배포 구성은 측정 후 담당자가 선정한다. 이 초기 제한이 측정된 SLO나 후속 멀티 에이전트의 고정 예산은 아니다. 임베딩 모델과 제공자는 이번 LLM 변경으로 확정하지 않는다. 실행별 API 사용량과 비용을 기록하고 단일/멀티 에이전트 평가에서 함께 비교한다. 설정한 한도 초과나 API 실패를 업무 성공으로 처리하지 않는다.

### 5.3 가상 기업과 진단 범위

사내 업무 포털(웹·Backend API·DB), 공통 로그인/SSO, VPN, 실행 서버를 가상 서비스로 구성한다. 계정·권한, 네트워크, 서비스·서버 상태, 로그·지표·DB 연결, 최근 배포·변경 이력을 읽기 전용 Mock API로 조회한다.

정상·장애·권한 거부·시간 초과를 재현한다. 실제 계정 변경·서버 재시작·DB 수정은 이번 3주 범위에서 제외한다.

### 5.4 품질과 운영 원칙

권한 없는 접근·민감정보 노출·근거 없는 성공 판정을 방지하고 실행 시간·도구 사용을 제한한다. 실패는 명시하고 부분 성공을 보존하며 중복 저장을 막는다. 저장된 대화와 업무 이력을 통해 중단 후 처리를 이어갈 수 있어야 한다.

Spring의 저장 확정 후 상태 변경 이벤트를 발행하며 이벤트 전달 실패가 이미 저장된 업무를 취소하지 않게 한다. 이벤트 누락 시 REST 재조회로 복구하고, 재전송은 같은 요청 식별자로 중복 반영을 막는다. JWT 원문·비밀번호·서명키는 로그에 남기지 않는다. 부서명·역할 클레임은 발급 시점 정보이므로 현재 권한 검사와 부서 변경 처리를 함께 수행한다. Node.js 연결 상태·Spring 연결 실패·전송 대기량을 관측하며 서버 재시작과 토큰 만료 후 재접속을 검증한다. 전송 방식, 다중 인스턴스 라우팅·중계와 이벤트 보존 방식은 배포 전에 합의하며 별도 유료 인프라를 자동 도입하지 않는다.

## 6. 데이터 개요

엔터티 관계·저장 불변식·보존 후보는 [데이터 설계](DATA.md)를, React·Node.js·Spring·Python 간 입출력·인증·오류 계약 후보는 [API 설계](API.md)를 참조한다. 두 문서는 기능별 구현 전 리뷰할 설계안이며 이 장의 제품 정책을 변경하지 않는다.

### 6.1 관리할 주요 정보

- **사용자·부서·역할:** 자체 계정, 사번, 조직 소속과 업무 접근 권한. JWT에는 회원 ID·사번·부서 ID·코드·이름·역할을 포함하며 토큰의 원본 정보는 Spring이 관리한다. 갱신·폐기 기록의 저장 모델은 인증 정책을 정한 뒤 설계한다.
- **문의·대화·문제:** 문의 세션, 메시지, 분석 요약, 복합 문의의 개별 문제와 정정 이력.
- **티켓·배정·처리:** 진단 근거, 담당 부서·개인, 처리·배정 상태, 해결·재이관·수정 기록.
- **장애 그룹:** 대표·구성 티켓, 공통 해결 근거, 그룹 담당과 일괄 완료·분리·재오픈 이력.
- **지식·평가 데이터:** 정책·과거 사례·런북, 서비스 의존 관계, 자료 버전·권한·출처·검수·평가 분할.
- **알림·실행·감사:** 알림 전달 상태, 에이전트 실행 단계와 근거 요약, 업무 변경 주체와 이력.

### 6.2 관계와 관리 원칙

한 문의에는 여러 문제와 티켓이 연결될 수 있다. 같은 부서의 공통 장애 티켓은 그룹으로 묶되 개별 티켓과 이력은 보존한다. 문의·티켓·배정·실행의 상태를 구분하고 과거 참조를 새 처리 실적으로 중복 집계하지 않는다.

업무 기록은 연결 업무가 모두 종료된 마지막 시점부터 180일, 운영 로그는 생성 후 30일 보존한다. 미해결·재오픈·복구 대기 업무는 만료하지 않는다. 사용자에게는 삭제 대신 숨기기·복원을 제공한다.

가상 데이터는 실제 운영 기록과 구분하고 평가 사건을 검색 지식이나 프롬프트 예시에 넣지 않는다.

## 7. 성공 기준

### 7.1 기능 완료

문의 접수부터 분석·복수 티켓 생성·실제 부서 배정·조회까지 연결되어야 한다. 최종 완료에는 8장의 후속 필수 기능과 그 인수 조건 충족이 포함된다. 화면 표시만으로 저장·배정 성공을 인정하지 않는다.

### 7.2 분류·배정 품질

각 에이전트 담당자는 목적에 맞는 공개 데이터셋과 가상 데이터를 탐색·활용할 수 있다. 조사한 데이터셋은 참고 후보이며 사용 대상을 제한하지 않는다. 통합 자료와 최종 평가셋은 팀 검토를 거쳐 선정한다.

공통 평가는 최초 부서 판단과 실제 배정의 정확성, 복합 문의의 필요한 티켓·부서 전체 일치, 무티켓 해결·범위 밖·근거 부족 CS 검토의 올바른 흐름을 확인한다. 관리자 정정 전 결과로 평가하고 시간 초과·무응답을 실패에 포함한다.

개인 개발 실험과 최종 비교 데이터를 분리하며 최종 정답·실패 사례를 튜닝에 사용하지 않는다. 평가 수량·분포·수치 합격 기준은 담당자의 실험 결과와 준비 가능량을 검토해 최종 평가 전에 팀이 합의·고정한다. 결과를 본 뒤 기준을 임의로 완화하지 않는다. 이는 실제 기업 정확도를 보장하는 수치가 아니다.

### 7.3 비교와 서비스 품질

MVP 완료 시 실제 단일 에이전트의 분류·배정 정확도, 응답 시간, 실패율과 잘못된 성공 판단을 측정하고 사례별 결과·실행 이력·모델 및 실행 설정을 기준선으로 보존한다. 최종 멀티 에이전트는 동일한 평가 사례·정답·부하·실행 환경에서 비교하고, 각 지표의 전후 값과 차이를 근거로 개선 성과를 설명한다. 개선을 목표로 하되 측정 전 향상률을 보장하지 않으며, 개선되지 않거나 느려진 지표도 원인과 함께 공개한다. 공통 기능 비교와 최종 단계에 추가된 기능 검증은 구분한다.

티켓 생성 성공률, 첫 실제 답변 지연, 진단 완료 지연을 측정한다. 지연은 평균·p95(측정값의 95%가 이 값 이하인 지연)와 실패율을 함께 보고한다. MVP에서는 실제 모델 호출과 Node.js Socket.IO 중계·Spring 인증·서비스 통신·저장을 포함해 측정한다. 실제 모델·환경·부하를 고정한 MVP 실측을 바탕으로 후속 2주 시작 전에 SLO를 정한다. 최종 비교 전에는 보존한 단일 에이전트를 같은 조건에서 재실행할 수 있어야 한다.

### 7.4 안전과 대표 시연

권한 없는 조회·실행, 타인 정보 노출, 티켓 누락·중복, 근거 없는 해결 확정은 수정·재검증 전 완료로 인정하지 않는다. 모델 분류 성능과 서버 무결성은 구분하여 검증한다.

대표 시연은 무티켓 지식 해결, 계정/VPN 진단·배정, 데이터 조회 불가의 원인·부서 판별, 복합 문의의 복수 티켓, 동일 장애 그룹 해결·개별 재오픈, 재이관·관리자 예외 처리의 6개 흐름이다.

## 8. 계획 단계

### 8.1 일정과 역할

4명이 MVP 1주와 후속 2주, 총 3주를 계획한다. 시작일은 2026-10-18이며 평일 오후를 공통 작업 시간으로 둔다. 마지막 가용 2일은 통합·평가를 우선한다.

전문 에이전트별로 한 명이 책임지고 문의 분석 담당은 Supervisor도 맡는다. 화면·Node.js 채팅 서버·Spring·Mock·데이터·평가 책임을 겸임하며 JWT 인증·Socket.IO 통합·데이터 검수·테스트는 함께 분담한다. 채팅 서버와 양쪽 클라이언트 연동의 조율 담당은 구현 전에 정한다.

### 8.2 1주 MVP

JWT 자체 로그인, React·Spring 클라이언트와 Node.js Socket.IO 서버를 통한 한국어 텍스트 채팅, 문의·정정 저장, 복수 티켓 생성·부서 배정, 정보 카드와 부서/업무 관리자 읽기 전용 티켓 조회를 실제로 구현한다. 개인 세션 목록·기존 채팅 재진입·인증 갱신과 시간 초과/일시 장애 분석 재시도도 포함한다. 사번·소속 부서 클레임의 검증, 타인 문의 구독 차단, 저장 ACK 유실 후 중복 재전송, 양쪽 클라이언트 재접속과 저장 상태 복구를 검증한다. Python에는 실제 LLM을 사용하는 단일 에이전트를 연결한다. 문의 분석·추가 질문·복합 문제 분리·티켓 제안 결과를 서버가 검증하고 저장한다. MVP 완료 조건에 단일 에이전트 평가 실행과 기준선 결과 보존을 포함하며, 후속 단계의 전체 검색·진단 기능을 MVP 필수로 앞당기지 않는다.

정해진 사례로 추가 질문·복합 문의·부분 실패·정정 후 재실행을 검증한다. 단일 에이전트와 최종 멀티 에이전트는 동일한 서비스 입출력 경계에 연결할 수 있어야 한다. 최종 Supervisor는 필요한 역할만 호출하며 모든 문의에서 4개 역할을 항상 호출하지 않는다.

**완료 흐름:** Spring JWT 로그인 → React·Spring의 Node.js Socket.IO 연결 → 문의 전달·Spring 저장 → 실제 단일 에이전트 분석·추가 질문 → 서버 검증 → 복수 티켓 저장·부서 배정 → Node.js 중계로 화면 갱신·REST 관리자 조회 → 단일 에이전트 평가 결과 보존. 멀티 에이전트로 확장할 서비스 경계와 계약 테스트를 함께 준비한다.

부서 배정은 필수이며 개인 담당자 자동 선정은 필수가 아니다. 재이관·최종 처리·알림 전체를 MVP 완료 조건에 포함하지 않는다.

부서 티켓 현황의 칸반·목록 전환, 전체 카드 정보와 장애 그룹의 읽기 전용 표시, 기본 검색·빠른 필터, 컬럼별 전체 건수·더 보기, 두 종료 상태 통합 조회, 보기 복원·부분 실패·접근성을 MVP 완료 조건에 포함한다(F009-AC11~AC20). 이를 위한 조회 계약 확장도 MVP 연결 대상이다. 업무 변경 버튼·드래그 상태 변경·담당자 처리·그룹 생성/해결은 후속이며 표시 기능 추가가 이 업무들의 완료를 뜻하지 않는다. 칸반 확장안의 팀 리뷰·서버 계약 구현·프론트 구현과 통합 검증은 별도 확인한다.

### 8.3 후속 2주 필수

- MVP의 단일 에이전트를 Supervisor와 4개 전문 에이전트 구조로 개선한다. Hybrid·반복 검색·GraphRAG와 진단 근거 검토를 구현한다.
- 읽기 전용 Mock 진단과 복수 티켓 처리 고도화.
- 담당자 가져오기·개별 해결 확인·재이관·관리자 예외 처리.
- 동일 장애 그룹핑·일괄 해결·개별 재오픈·영향 기반 우선순위.
- 개인 담당자 업무 처리·업무 필터 추가 고도화, 서비스 내부 알림, 부서 통계, 무응답 미확인 종료. 부서 읽기 전용 보드·목록·상세, 내 담당 빠른 필터와 저장된 담당/그룹/우선순위/해결 신고의 표시는 MVP다.
- 독립 내 문의 상세 모달, 예시 질문, 새 문의 분리 동의, 티켓 관련 메시지, 단계/링크가 있는 구조화 가이드.
- 에이전트 운영 관리자의 실행 이력·상세와 기술 복구 화면, 체크포인트 자동 복구와 부분 실패 처리.
- 입력 인젝션 대응, 민감정보 마스킹, 출력 검증, 근거 없는 성공 방지, 도구·권한 검사, 호출·시간 제한의 가드레일.
- 필수 E2E·안전·복구 회귀와 단일/멀티 에이전트 비교 평가. 기준선과 최종 결과의 수치 차이·실패 사례·개선 원인을 정리한다.

2주차에는 에이전트·검색·진단·티켓 처리를 통합하고, 3주차에는 남은 필수 기능과 회귀·평가를 완료한다. 데이터·Mock·보안 준비는 1주차부터 병행한다. 일정 부족을 이유로 필수 범위를 임의 제외하지 않고 범위·일정을 재합의한다.

### 8.4 선택·후속·제외

- **선택:** 개인 담당자 자동 선정, 메인 진행 요청 상태 영역, PDF 매뉴얼 열람.
- **후속 제품 목표:** 권한 있는 사람의 승인 후 실제 시스템 변경, 재이관 진행 알림. 현재 재이관 진행은 문의 내역에 표시한다.
- **MVP 제외:** 이미지 업로드·해석, 사용자 출처 표시. 후속 도입은 별도 범위 결정이 필요하다.
- **현재 제외:** 관리자 지식 문서 편집, 티켓 상세 취소·회수, 디자인 예시의 자산 현황·신규 요청 버튼·관리자 차트·CSV·배정 정책 설정·자동학습 표시.

### 8.5 구현 전에 함께 정할 사항

한 번에 모든 설계를 완성하지 않고, 작업할 기능부터 필요한 계약을 합의한다.

- **확정 개발 기준:** [공통 타입](../specs/contracts/DATA_TYPES.md)과 [전송 계약 10절](../specs/contracts/WIRE_CONTRACT.md#10-인증재접속최신-대화분석-재시도-추가-프로필)의 인증·상태/오류·버전·ACK·재접속·멱등/보존·목록·정정·초기 AI 예산·MVP 범위를 적용한다. 추가 언어별 코드 생성이나 OpenAPI/JSON Schema는 연결 선행 조건이 아니다.
- **첫 E2E 착수 전 담당 설계·구현:** 실제 키/Origin·CSRF·서비스 인증, Socket.IO/Java/Node 호환 버전, DB 물리 제약/마이그레이션, 새 제어 이벤트·동시성·구독 회수·Spring 명령 처리자 라우팅을 구현하고 검증한다.
- **후속 기능별 구현 전:** 분리 동의·관련 대화·운영 복구·그룹·알림의 상세 입출력/권한/저장 계약을 정한다.
- **에이전트 통합 전:** 실제 모델/SDK·금액 상한·SSE 세부 경로/복구·데이터/도구 설정을 담당자가 선정하고 예산 강제·버전 차단·재시도를 검증한다.
- **최종 평가 전:** 사용할 자료와 검수 담당, 데이터 분할·동결 버전, 합격 기준과 동일 조건 비교 방법.

개인은 담당 영역의 데이터셋·프롬프트·검색·도구 전략을 자유롭게 실험하고 조건·결과·추천안을 공유한다. 개인 실험 설정이나 과거 설계안을 팀 공통 기준으로 자동 적용하지 않는다. 팀이 합의한 구현 계약은 해당 작업부터 공용 문서로 추가한다.
